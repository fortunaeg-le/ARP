# HANDOFF — Блок 6: Детокенизатор

## Что сделано
Реализован модуль `detokenizer.py` с единственной публичной функцией `detokenize(text, session_id, storage_dir=None)`. Функция грузит сессию через `session_store.load_session`, строит словарь `token -> original_text` из `session["entities"]` и одним проходом `re.sub` с regex `\[[A-Z_]+_\d+\]` заменяет найденные токены на исходные значения; токены, отсутствующие в сессии, остаются в тексте как есть и попадают в список unresolved (без повторов, в порядке первого появления). `SessionNotFoundError`/`SessionExpiredError` не перехватываются, пробрасываются вызывающей стороне. Все сценарии приёмки и указанное в спецификации известное ограничение (искажённые LLM токены) проверены эмпирически.

## Публичный интерфейс
dataclass'ы импортируются из `models.py`, не переопределены (сам блок 6 их напрямую не использует — работает с dict, который возвращает `session_store.load_session`).

Модуль: `detokenizer.py`

```python
def detokenize(text: str, session_id: str, storage_dir: str | None = None) -> tuple[str, list[str]]
```

Строка импорта:
```python
from detokenizer import detokenize
```

Минимальный пример вызова:
```python
from detokenizer import detokenize
# session_id — то, что вернул save_session (блок 5) на этапе encrypt
restored, unresolved = detokenize("Договор с [ORG_1], ИНН [INN_1]", session_id)
# restored -> "Договор с ООО «Ромашка», ИНН 7701234567"
# unresolved -> []
```

Исключения:
- `SessionNotFoundError` (`session_store`) — если `session_id` неверного формата, файл сессии не найден или не расшифровывается ключом. Пробрасывается из `load_session` без изменений.
- `SessionExpiredError` (`session_store`) — если `expires_at` сессии уже наступил. Пробрасывается из `load_session` без изменений.
- Других исключений `detokenize` сама не порождает — любое искажение `text` (лишние/битые токены, произвольный мусор) обрабатывается без исключений, попадает либо в замену, либо в unresolved.

## Формат данных на выходе
Пример реального вызова (проверено эмпирически):
```python
detokenize("Компания [ORG_1], ссылка [ORG_99] и снова [ORG_99].", sid)
# -> ("Компания ООО «Ромашка», ссылка [ORG_99] и снова [ORG_99].", ["[ORG_99]"])
```
`restored` — `str`. `unresolved` — `list[str]`, уникальные токены в порядке первого появления в `text` (не в порядке появления в сессии).

## Инварианты выходных данных
- `unresolved` не содержит дублей, даже если один и тот же неизвестный токен встретился в `text` несколько раз (порядок — первое появление в `text`, ключом является сам regex-проход `re.sub`, не отдельный проход по уникальным токенам).
- Токены, найденные в сессии, заменяются ровно на `original_text` соответствующей записи, без экранирования/изменений.
- Токены, не входящие в `entities` сессии, остаются в `restored` в исходном виде посимвольно (не модифицируются).
- Замена — один проход `re.sub` по исходному `text`; результат замены одного токена **не** сканируется повторно на предмет новых токенов (защита от каскадных подстрок в `original_text`).
- Функция ничего не возвращает, кроме `tuple[str, list[str]]` — исключений, кроме двух перечисленных выше (унаследованных от `load_session`), не бросает.

## Что блок ожидает на входе (предусловия)
- `session_id` — валидный по формату `^[0-9a-f-]{36}$` **или** это не проверяется блоком напрямую: если формат неверный, `load_session` кинет `SessionNotFoundError` — это и есть ожидаемое поведение, не исключение из правил.
- `session["entities"]` — список dict'ов, каждый обязательно содержит ключи `token` и `original_text` (гарантия блока 5). Блок 6 использует только эти два ключа, остальные (`entity_type`, `segment_id`) игнорирует.
- `text` — произвольная строка, без предположений о содержимом; функция не падает ни при каком содержимом `text` (см. известное ограничение ниже про искажённые токены — это не падение, а тихая невозможность распознать).

## Использованные поля конфига
Блок `entity_types.yaml` не читает. Контракт с конфигом косвенный: значение `token_prefix` в конфиге обязано соответствовать `^[A-Z][A-Z_]*$` (только заглавные латинские буквы и `_`, без цифр) — иначе токен с таким префиксом не будет находиться regex'ом `\[[A-Z_]+_\d+\]`, используемым здесь. Это ограничение уже зафиксировано спецификацией для блока 6 и проверяется на этапе block 1 (владелец конфига), самим блоком 6 не проверяется.

## Побочные эффекты импорта
`import detokenizer` подтягивает `re` (stdlib) и `session_store` (который, в свою очередь, подтягивает `cryptography.fernet` и `models`). Моделей не загружает, файлов/директорий не создаёт, диск не читает при импорте — всё ленивое, происходит только внутри вызова `detokenize` (через `load_session`). Импорт быстрый (доли секунды), можно импортировать в любой ветке CLI без задержки.

## Зависимости и окружение
Новых зависимостей нет — используется `re` (stdlib) и уже реализованный `session_store.py` (блок 5, зависит от `cryptography`).

## Известные ограничения / TODO
- Токены, искажённые LLM при переформулировке ответа (изменённый регистр `[org_1]`, пропавшие скобки `ORG_1`, вставленный пробел внутри `[ORG 1]`), не распознаются текущим regex'ом `\[[A-Z_]+_\d+\]` — они не заменяются и не попадают в `unresolved`, то есть пользователь не узнаёт об этой потере из вывода программы. Это прямо предписанное спецификацией ограничение MVP, не баг реализации. Проверено эмпирически: строка `"lower [org_1] noBrackets ORG_1 spaced [ORG 1] valid [ORG_1]"` — только последний токен `[ORG_1]` заменяется, остальные три остаются нетронутыми и не появляются в `unresolved`.

## Данные для тестов
Все примеры проверены эмпирически (`venv/Scripts/python.exe`, сессия создана через `save_session` с реальными Entity).

1. **3 валидных токена.** Сессия содержит `[ORG_1] -> "ООО «Ромашка»"`, `[INN_1] -> "7701234567"`, `[PERSON_1] -> "Иванов И.И."`. Вход: `"Договор между [ORG_1] (ИНН [INN_1]) и [PERSON_1]."` → выход: `("Договор между ООО «Ромашка» (ИНН 7701234567) и Иванов И.И..", [])` (два символа `.` в конце — один из `original_text`, один из шаблона текста, это ожидаемо, не баг). unresolved пуст. ✅ проверено.
2. **Валидный + несуществующий, с повтором несуществующего.** Вход: `"Компания [ORG_1], ссылка [ORG_99] и снова [ORG_99]."` → выход: `("Компания ООО «Ромашка», ссылка [ORG_99] и снова [ORG_99].", ["[ORG_99]"])` — несуществующий токен остаётся в тексте оба раза, но в unresolved попадает один раз. ✅ проверено.
3. **Текст без единого токена.** Вход: `"Просто текст без токенов."` → выход: тот же текст без изменений, `unresolved == []`. ✅ проверено.
4. **Просроченная сессия (граничный случай).** `expires_at` сессии вручную переставлен в прошлое → `detokenize(text, sid)` кидает `SessionExpiredError`, не перехватывая её. ✅ проверено.
5. **Искажённые LLM токены (граничный случай, известное ограничение).** Вход: `"lower [org_1] noBrackets ORG_1 spaced [ORG 1] valid [ORG_1]"` при сессии с `[ORG_1] -> "Тест"` → только последний токен заменяется на `"Тест"`, три искажённых варианта остаются в тексте нетронутыми, ни один не попадает в `unresolved`. ✅ проверено, задокументировано как ограничение MVP.
