# SHIFRATOR — инженерная спецификация

Назначение системы (1 предложение контекста, не более): локальный офлайн-инструмент на Python, который находит конфиденциальные данные в тексте договора, заменяет их обратимыми токенами перед отправкой в LLM пользователем вручную, и восстанавливает исходные значения в ответе LLM.

## Правила работы над блоком

- Ты реализуешь ровно один блок, номер указан пользователем в начале чата.
- Не выходи за границы блока: не трогай код других блоков, не добавляй форматы/языки/функциональность сверх описанного здесь.
- Не меняй зафиксированные ниже интерфейсы и форматы данных. Если видишь, что интерфейс неудобен — реализуй как есть, а несогласие вынеси в HANDOFF в раздел "Предложения", не переделывай самовольно.
- Тесты (pytest и т.п.) не пишешь. В конце блока — только раздел "Данные для тестов" с конкретными примерами вход/выход.
- Язык реализации: Python 3.11 (зафиксировано для воспроизводимости окружения; фактически стек работает и на 3.12 — см. ниже). Уточнение по факту (проверено эмпирически): `inspect.getargspec` удалён в Python 3.11, поэтому «голый» pymorphy2 0.9.1 (`pymorphy2.MorphAnalyzer()`) падает уже на 3.11, а не «на 3.12+»; работоспособность natasha на 3.11 и 3.12 обеспечивает хотфикс `pymorphy2_311_hotfix()`, который `yargy==0.16.0` применяет при своём импорте. Следствие для кода блока 3: не инстанцировать `pymorphy2.MorphAnalyzer` напрямую — использовать только `natasha.MorphVocab` (импорт natasha гарантированно подтягивает yargy и хотфикс). Если проверочный импорт блока 3 всё же падает — «даунгрейд до 3.11» не является средством решения; выносить проблему в HANDOFF как и предписано.
- Если для блока указан внешний пакет — используй именно его, не заменяй альтернативой без явного запроса.
- В конце блока обязателен файл `HANDOFF_<N>.md` строго по шаблону в конце этого документа.
- Если задача блока не влезает в разумный по объёму ответ — не сокращай и не упрощай реализацию ради краткости; отвечай настолько подробно, насколько требует полнота блока.

## Единый внутренний формат документа

Все три dataclass'а (`TextSegment`, `SourceDocument`, `Entity`) определяются один раз в отдельном модуле `models.py`, который создаёт **блок 1** (включая `Entity`, хотя сам блок 1 его не использует — это нужно, чтобы у всех последующих блоков была одна точка правды). Блоки 2-6 обязаны импортировать их из `models.py` (`from models import Entity, TextSegment, SourceDocument`) и **не имеют права** определять свои копии этих классов в своих файлах. В HANDOFF каждого блока 2-6 в разделе "Публичный интерфейс" явно указывать: "dataclass'ы импортируются из models.py, не переопределены".

**Реестр модулей и публичных функций (зафиксирован для всех блоков, менять нельзя без общего решения):**

| Блок | Модуль | Публичная функция |
|---|---|---|
| 1 | `extractor.py` (+ `models.py`, + `entity_types.yaml`) | `def extract(path: str) -> SourceDocument` |
| 2 | `regex_detector.py` | `def detect_regex(doc: SourceDocument, config_path: str) -> list[Entity]` |
| 3 | `ner_detector.py` | `def detect_ner(doc: SourceDocument, config_path: str) -> list[Entity]` |
| 4 | `tokenizer.py` | `def tokenize(doc: SourceDocument, entities: list[Entity], config_path: str) -> tuple[str, list[Entity]]`, плюс `def build_plain_text(doc: SourceDocument) -> str` |
| 5 | `session_store.py` | `save_session` / `load_session` / `purge_expired` (сигнатуры — см. раздел блока 5) |
| 6 | `detokenizer.py` | `def detokenize(text: str, session_id: str, storage_dir: str \| None = None) -> tuple[str, list[str]]` |
| 7 | `shifrator.py` | CLI (`argparse`), без собственных публичных функций сверх точки входа |

Каждый блок реализует ровно эту сигнатуру в этом модуле — без переименований и без изменения порядка аргументов, даже если кажется, что другое имя удобнее (несогласие — в HANDOFF, раздел "Предложения", как и для остальных интерфейсов).

Все форматы файлов на входе (.docx, .txt) приводятся к структуре ниже. Дальнейшие блоки (2-7) работают только с ней и ничего не знают про исходный формат файла.

```python
@dataclass
class TextSegment:
    id: str                 # уникальный id, напр. "p12" (параграф 12), "t0_r1_c2" (таблица 0, строка 1, ячейка 2), "l5" (строка 5 txt)
    text: str
    source_type: str        # "docx_paragraph" | "docx_table_cell" | "txt_line"
    metadata: dict           # для параграфа: {"paragraph_index": 12, "style": "Heading1"}
                              # для ячейки таблицы (обязательно все три ключа): {"table_index": 0, "row_index": 1, "col_index": 2}

@dataclass
class SourceDocument:
    segments: list[TextSegment]
    source_format: str       # "docx" | "txt"  ("pdf" зарезервировано для фазы 2, блок 1 его не выдаёт)
    source_path: str
```

Сегменты в `SourceDocument.segments` должны идти строго в порядке следования элементов в теле документа (параграфы и таблицы вперемешку, как в исходном файле), не отдельными группами "сначала все параграфы, потом все таблицы". Блок 4 группирует ячейки по `metadata["table_index"]`/`row_index`/`col_index`, не парсит строку `id`.

## Формат Entity (используется блоками 2, 3, 4)

```python
@dataclass
class Entity:
    id: str                  # uuid4
    segment_id: str          # ссылка на TextSegment.id
    start: int                # смещение символа начала внутри segment.text
    end: int                  # смещение символа конца (не включительно)
    original_text: str
    entity_type: str          # ключ из entity_types.yaml, напр. "PERSON", "INN", "ORG"
    detector: str              # "regex" | "ner"
    confidence: float          # 0.0-1.0; для regex всегда 1.0. Natasha не предоставляет confidence для NER-спанов — для всех entity из блока 3 записывать 1.0. Поле оставлено в формате на будущее (другие NER-бэкенды).
    token: str | None = None   # заполняется в блоке 4, до этого None; дефолт обязателен — блоки 2 и 3 создают Entity без этого поля
```

## Конфиг сущностей — entity_types.yaml

Читается динамически, добавление новой категории не требует правки кода детекторов.

```yaml
entity_types:
  PERSON:
    method: ner
    ner_label: PER
    token_prefix: PERSON
  ORG:
    method: ner
    ner_label: ORG
    token_prefix: ORG
  ADDRESS:
    method: ner
    ner_extractor: addr        # НЕ ner_label/LOC — см. требования Блока 3: используется natasha.AddrExtractor, а не NER-тэггер
    token_prefix: ADDRESS
  INN:
    method: regex
    pattern: '\b\d{10}(\d{2})?\b'
    validate: inn_checksum
    token_prefix: INN
  OGRN:
    method: regex
    pattern: '\b\d{13}(\d{2})?\b'
    validate: ogrn_checksum
    token_prefix: OGRN
  KPP:
    method: regex
    pattern: '\b\d{9}\b'
    token_prefix: KPP
  BANK_ACCOUNT:
    method: regex
    pattern: '\b\d{20}\b'
    token_prefix: ACCOUNT
  BIK:
    method: regex
    pattern: '\b04\d{7}\b'
    token_prefix: BIK
  PASSPORT:
    method: regex
    pattern: '(?i)(?:паспорт|серия)[^\n\d]{0,20}(\d{2}\s?\d{2})\s?(\d{6})\b'
    token_prefix: PASSPORT
    # без контекстного якоря ("паспорт"/"серия") этот паттерн матчил бы любое 10-значное число —
    # у паспортных данных нет контрольной суммы, поэтому единственная защита от ложных срабатываний — якорь по контексту
  PHONE:
    method: regex
    pattern: '(?<!\d)(\+7|8)[\s\-]?\(?\d{3}\)?[\s\-]?\d{3}[\s\-]?\d{2}[\s\-]?\d{2}(?!\d)'
    token_prefix: PHONE
  EMAIL:
    method: regex
    pattern: '[\w\.-]+@[\w\.-]+\.\w+'
    token_prefix: EMAIL
  SUM:
    method: regex
    pattern: '\d[\d\u00A0 ]*[.,]?\d*\s?(руб(лей|ля|\.)?|₽|USD|\$|долл(аров|\.)?)(?![а-яА-ЯёЁ])'
    token_prefix: SUM
    # пробельный класс внутри числа — только пробел/неразрывный пробел (\u00A0), не \s, чтобы не захватывать переводы строк
    # правая граница (?![а-яА-ЯёЁ]) — чтобы не съедать часть следующего слова, напр. "5 рубашек" не должно матчиться как "5 руб" + "ашек"
  DATE:
    method: regex
    pattern: '\d{1,2}[.\/]\d{1,2}[.\/]\d{2,4}'
    token_prefix: DATE
    enabled: false
```

## Формат токенов

`[TYPE_N]`, инвариантная форма, без склонения. Пример: `[ORG_1]`, `[PERSON_2]`, `[INN_1]`. Нумерация сквозная по `token_prefix` (не по `entity_type`), начиная с 1.

## Формат файла сессии (хранилище токен-маппинга)

Хранится зашифрованным на диске (`cryptography.fernet`), не в памяти.

```json
{
  "session_id": "b2f1e6b0-0000-0000-0000-000000000000",
  "created_at": "2026-07-09T14:03:00+03:00",
  "expires_at": "2026-07-10T14:03:00+03:00",
  "entities": [
    {"token": "[ORG_1]", "entity_type": "ORG", "original_text": "ООО «Ромашка»", "segment_id": "p3"},
    {"token": "[INN_1]", "entity_type": "INN", "original_text": "7701234567", "segment_id": "p3"}
  ]
}
```

```

SourceDocument → Блок2(regex) ┐
SourceDocument → Блок3(ner)   ┴→ list[Entity] → Блок4(tokenize) → анонимизированный текст + list[Entity] с token

[пользователь: LLM]

## Блок 1 — Экстрактор документов

**Вход:** путь к файлу `.docx` или `.txt`.
**Выход:** `SourceDocument`.
**Требования:**
- Создать файл `models.py` с dataclass'ами `TextSegment`, `SourceDocument`, `Entity` (все три, даже если сам блок 1 использует только первые два) — это общий модуль для всех последующих блоков, см. правило в разделе "Единый внутренний формат документа".
- Создать файл `entity_types.yaml` в корне проекта — **посимвольная копия YAML-конфига из раздела "Конфиг сущностей" этой спецификации, без единого изменения** (не добавлять ключи, не менять паттерны, не менять `token_prefix`). Это единственный источник конфига для всего проекта: блоки 2, 3, 4 только **читают** этот файл и не создают собственных копий; если файла нет — падают с `FileNotFoundError`, а не генерируют его сами (иначе три изолированных чата гарантированно создадут три немного разных версии одного конфига, и расхождение — например, разное имя `token_prefix` — сломает токены молча, без ошибки). Полный текст `entity_types.yaml` обязан быть приложен в HANDOFF_1 целиком.
- `.docx` через `python-docx`. **Важно:** обход только `document.paragraphs` + `document.tables` по отдельности НЕ ДОПУСКАЕТСЯ — это два независимых списка, и все таблицы окажутся в конце итогового списка сегментов, а не на своём месте в документе. Вместо этого обходить `document.element.body` по порядку, для каждого дочернего элемента определять тип по тегу (`CT_P` → параграф, `CT_Tbl` → таблица) и оборачивать в `Paragraph(child, document)` / `Table(child, document)` из `python-docx`, сохраняя порядок как в исходном файле.
- Параграфы: `id` вида `p{index}` (сквозной индекс параграфа), `metadata = {"paragraph_index": index, "style": <имя стиля>}`. `paragraph_index` — сквозной порядковый номер параграфа среди параграфов тела документа (счётчик, инкрементируемый только на `CT_P`, начиная с 0); индексы таблиц ведутся отдельным счётчиком по `CT_Tbl` (используется в `table_index` ячеек ниже). В `metadata["style"]` записывается `paragraph.style.name` **как есть, без нормализации** (для встроенного заголовка в англоязычном Word это `"Heading 1"` — с пробелом, а в документах русской локали может быть `"Заголовок 1"`; точное значение `"Heading1"` без пробела не гарантировано и не требуется). Если `paragraph.style` равен `None` — записывать `None`.
- Ячейки таблиц: `id` вида `t{table_idx}_r{row_idx}_c{col_idx}`, `source_type = "docx_table_cell"`, `metadata` обязательно содержит все три ключа `{"table_index": table_idx, "row_index": row_idx, "col_index": col_idx}` (блок 4 группирует ячейки именно по этим полям metadata, не по строке id). Текст ячейки — `cell.text` целиком (абзацы внутри ячейки, если их несколько, склеены `"\n"`), одна ячейка = один сегмент. **Объединённые ячейки:** при вертикальном/горизонтальном merge несколько координат сетки указывают на один и тот же `_tc`-элемент. Отслеживать уже обработанные `_tc` через множество самих элементов, с удержанием ссылок: `seen_tcs = set()`; для каждой ячейки `tc = cell._tc`; если `tc in seen_tcs` — добавить сегмент с пустым `text` (сохраняет координатную сетку), иначе `seen_tcs.add(tc)` и обычный сегмент. Хранить именно объекты: это удерживает lxml-прокси живыми, а lxml гарантирует, что для живого прокси повторное обращение к тому же элементу возвращает тот же объект — сравнение по идентичности корректно. Запрещено хранить только числа `id(cell._tc)` без удержания ссылок: прокси уничтожаются сразу после выхода из выражения, их адреса переиспользуются, и сравнение по `id()` даёт и ложные дубликаты (текст обычных, не объединённых ячеек молча теряется из сегментов), и пропуск настоящих (текст merged-ячейки дублируется) — проверено эмпирически.
- `.txt`: определять кодировку в порядке **BOM UTF-16 → `utf-8-sig` → `cp1251`**. Сначала читать файл в байтах и проверять BOM UTF-16: если он начинается с `\xff\xfe` (LE) или `\xfe\xff` (BE) — декодировать через кодек `utf-16` (так блокнот Windows сохраняет файл в режиме «Юникод»; без этой проверки `utf-8-sig` падает, происходит молчаливый откат на `cp1251`, и UTF-16-байты превращаются в моджибейк — ПДн не детектируются и утекают искажёнными). Иначе декодировать как `utf-8-sig`; при `UnicodeDecodeError` повторить попытку с `cp1251` (частая кодировка русских .txt из Windows). Перед разбиением нормализовать переводы строк: `text = raw.replace("\r\n", "\n").replace("\r", "\n")`, затем `lines = text.split("\n")`; если файл заканчивается на `\n`, финальный пустой элемент отбрасывается (`if lines and lines[-1] == "": lines.pop()`). Сам символ `\n` в `TextSegment.text` не сохраняется. `id` вида `l{index}`, `source_type = "txt_line"`, `metadata` обязательно содержит оба ключа: `{"line_index": index, "encoding": <кодировка>}`, где `<кодировка>` — фактически применённая: `"utf-16"`, `"utf-8-sig"` или `"cp1251"` — использованную кодировку также упоминать в HANDOFF.
- Параграфы получают `source_type = "docx_paragraph"` явно (значение задаётся кодом, а не подразумевается).
- Пустые параграфы/строки — включать в список сегментов (с пустым `text`), не пропускать (иначе собьётся нумерация/восстановление).
- `extract` кидает `FileNotFoundError` (стандартный), если файла нет по указанному пути, и `ValueError(f"Неподдерживаемый формат: {ext}. Поддерживаются: .docx, .txt")`, если расширение файла (в нижнем регистре) не входит в `{".docx", ".txt"}`. Выбор обработчика (`.docx`/`.txt`) определяется только по расширению; корректность самого содержимого при этом не предполагается — битый `.docx` отлавливается уже при разборе (см. следующий пункт).
- **Битый/не-настоящий `.docx`.** Файл с расширением `.docx`, который не является корректным zip-контейнером Office (переименованный `.txt`, обрезанный/недокачанный файл, пустой файл на 0 байт), заставляет `python-docx` кинуть `PackageNotFoundError` (а битый zip — `zipfile.BadZipFile`). `extract` обязан перехватывать эти исключения при открытии `Document(path)` и оборачивать их в `ValueError(f"Файл не является корректным .docx (повреждён или неверный формат): {path}")` — чтобы блок 7 (CLI), уже ловящий `ValueError`, показал аккуратное `Ошибка: …`, а не сырой трейсбек внутренностей python-docx.
- **Область охвата MVP — только тело документа** (`document.element.body`). Колонтитулы (`section.header`/`footer`), сноски, комментарии, текстовые поля/надписи (`w:txbxContent`) и **вложенные таблицы внутри ячеек** (`cell.text` в python-docx молча игнорирует вложенную таблицу) в MVP не извлекаются; требование "не терять ни одного символа" относится именно к телу документа, а не ко всем возможным частям .docx. Это ограничение обязательно фиксируется в разделе "Известные ограничения" HANDOFF_1. Если в теле документа обнаружена вложенная таблица (`len(cell.tables) > 0`), блок печатает предупреждение в stderr с координатами ячейки (в договорах в колонтитулах часто лежат реквизиты — важно, чтобы пользователь знал, что они не обработаны, а не считал, что весь текст уже проверен).
- Не терять ни одного символа исходного текста (в пределах области охвата, см. выше).
**Зависимости:** `python-docx`.
**Приёмка:** на .docx с параграфами + таблицей 2x2 + заголовком — список сегментов покрывает весь текст тела документа, id уникальны, `metadata["style"]` для заголовка непусто и совпадает с именем стиля, которое показывает Word (точное значение `"Heading1"` без пробела не требуется), порядок сегментов в списке совпадает с порядком элементов в исходном документе (таблица стоит между окружающими её параграфами, а не в конце списка).

## Блок 2 — Regex-детектор структурных сущностей

**Вход:** `SourceDocument`, `entity_types.yaml` (записи с `method: regex`).
**Выход:** `list[Entity]`.
**Требования:**
- Публичная функция блока принимает `config_path: str` явным аргументом (путь к `entity_types.yaml`) — путь не хардкодить внутри модуля.
- Для каждого сегмента прогонять все regex-паттерны из конфига, где `enabled` не `false`.
- Каждый созданный `Entity` — с `detector = "regex"`, `confidence = 1.0`.
- Для `INN`: реализовать `inn_checksum(value: str) -> bool` по алгоритму ФНС (для 10-значного и 12-значного ИНН отдельные весовые коэффициенты — стандартный публичный алгоритм контрольного числа ИНН РФ). Найденное совпадение паттерна включать в результат только если чек-сумма верна.
- Для `OGRN`: аналогично реализовать `ogrn_checksum` (для ОГРН — 13 знаков, для ОГРНИП — 15 знаков) по стандартному алгоритму остатка от деления.
- Конфиг — единственный источник паттернов, не хардкодить паттерны в коде детектора отдельно от YAML. Поле `validate` резолвится через словарь-реестр в коде: `VALIDATORS = {"inn_checksum": inn_checksum, "ogrn_checksum": ogrn_checksum}`. Если в конфиге указано значение `validate`, не входящее в этот реестр — печатать предупреждение в stderr и пропускать весь этот тип целиком (не создавать по нему ни одного Entity), не игнорировать проверку молча. Уточнение к заявленной расширяемости конфига: добавление нового типа **без** `validate` действительно не требует правки кода; добавление типа **с** новой чек-суммой требует добавить функцию валидатора и зарегистрировать её в `VALIDATORS` — это правка кода, и это нормально.
- `start`/`end` в `Entity` — точные символьные смещения внутри `segment.text` (не внутри всего документа).
- **Границы Entity — это границы всего совпадения, а не отдельной capture-группы:** `start = m.start()`, `end = m.end()`, `original_text = m.group(0)`. В функцию-валидатор из `VALIDATORS` тоже передаётся `m.group(0)`. Capture-группы в паттернах (`INN`, `OGRN`, `SUM`, `PASSPORT`) — вспомогательные для структуры самого регулярного выражения и **не определяют** границы Entity; использовать `m.span(1)`/`m.group(1)` как границы **запрещено**. Особенно важно для `PASSPORT`: групп там две, с разрывом между ними — взяв только первую группу, номер паспорта останется в открытом тексте. Следствие: для `PASSPORT` слово-якорь входит в токен целиком (например, "паспорт серия 45 12 345678" → один `[PASSPORT_1]`) — это ожидаемое поведение, не повод менять паттерн.
**Зависимости:** `PyYAML`, стандартная библиотека `re`.
**Приёмка:** тестовый набор строк с валидными и специально испорченными (неверная чек-сумма) ИНН/ОГРН — валидные находит, испорченные — не находит. На строках со случайными 10-значными числами, не являющимися ИНН по контексту (например, номер телефона без кода страны) — не даёт ложных срабатываний, если чек-сумма не сходится. `PASSPORT` и `KPP` не имеют контрольной суммы, поэтому для них другой критерий: случайное 10-значное число **без** слова-якоря ("паспорт"/"серия") рядом не должно порождать `PASSPORT`-entity — это проверяется отдельно и обязательно. А вот случайное 9-значное число, ошибочно распознанное как `KPP` вне реального контекста КПП (например номер договора) — это **известное ограничение MVP** (у КПП принципиально нет контрольной суммы для проверки), не блокирует приёмку, фиксируется в HANDOFF_2.

## Блок 3 — NER-детектор

**Вход:** `SourceDocument`, `entity_types.yaml` (записи с `method: ner`).
**Выход:** `list[Entity]`.
**Требования:**
- **Перед началом реализации** выполнить и привести в HANDOFF вывод команды: `python -c "from natasha import Segmenter, MorphVocab, NewsEmbedding, NewsNERTagger, AddrExtractor, Doc; print('ok')"`. Зафиксированные версии пакетов: `natasha==1.6.0`, `pymorphy2==0.9.1`, `yargy==0.16.0` (плюс `razdel`, `navec`, `slovnet` — идут как зависимости natasha). Если импорт падает на текущем интерпретаторе — **не писать обходных хаков и не подменять пакет молча**: остановиться и вынести проблему в HANDOFF в раздел "Отклонения от спецификации" с предложением решения (например, `pymorphy3` с патчем импорта). Это единственное разрешённое исключение из общего запрета "не заменяй пакет альтернативой" — но именно вынести решение в HANDOFF, не принимать его самостоятельно.
- **Перед написанием логики склейки адресов** — выполнить в реальном окружении небольшой скрипт, который прогоняет `AddrExtractor(MorphVocab())` на 2-3 тестовых строках с реальными русскими адресами, и посмотреть на фактическую структуру возвращаемых объектов (поля `Match`, есть ли оффсеты у частей факта или только у всего match). Не полагаться на память о структуре API — она не была верифицирована предыдущими ревью и de facto менялась между раундами спецификации. Реализовать склейку по тому, что показал реальный вывод, а не по тексту ниже, если они разойдутся — расхождение зафиксировать в HANDOFF.
- Публичная функция блока принимает `config_path: str` явным аргументом (путь к `entity_types.yaml`) — путь не хардкодить внутри модуля.
- Каждый созданный `Entity` — с `detector = "ner"`, `confidence = 1.0` (Natasha не предоставляет score для NER-спанов и matches AddrExtractor).
- Для `PERSON`/`ORG` (записи конфига с `ner_label`): стандартный NER-пайплайн Natasha — `Segmenter`, `NewsEmbedding`, `NewsNERTagger`, `Doc`. Последовательность обязательна: `doc.segment(segmenter)` → `doc.tag_ner(ner_tagger)`. Маппинг меток Natasha (`PER`/`ORG`) на ключи конфига через поле `ner_label`.
- Для `ADDRESS` (запись конфига с `ner_extractor: addr`) — **НЕ использовать NER-тэггер с меткой `LOC`**. `LOC` у Natasha — это географические названия ("Москва", "Тверская область"), а не почтовые адреса; в строке вида "г. Москва, ул. Ленина, д. 5, оф. 12" как `LOC` найдётся в лучшем случае "Москва", а улица/дом/офис останутся в открытом тексте — прямая утечка данных. Вместо этого использовать `natasha.AddrExtractor(MorphVocab())`.
- Фактическая структура вывода `AddrExtractor` (проверена эмпирически на natasha 1.6.0): `AddrExtractor(morph_vocab)(segment.text)` возвращает по одному `Match` на каждую часть адреса, а не на адрес целиком: для «г. Москва, ул. Ленина, д. 5, оф. 12» — четыре отдельных `Match` («г. Москва», «ул. Ленина», «д. 5», «оф. 12»), каждый со своими `.start`/`.stop`; `.fact` каждого — одиночный `AddrPart(value, type)`, поля `.parts` у него нет. Сокращения-маркеры («г.», «ул.», «д.») входят внутрь соответствующего Match, а разрыв между соседними Match состоит из чистой пунктуации (как правило `", "`). Правило склейки: соседние Match склеиваются в один Entity, если разрыв между `match_i.stop` и `match_{i+1}.start` не длиннее 6 символов и целиком состоит из символов множества пробел/неразрывный пробел/запятая/точка (`[ ,.\u00A0]`) — букв в разрыве быть не должно: разрыв с буквами (« и » в «Москва и Тверь», « в » в «из Москвы в Санкт-Петербург») склейку запрещает. Итоговый Entity цепочки: `start` первого Match, `end` последнего, `original_text = segment.text[start:end]`. Перед реализацией всё равно выполнить проверочный прогон из пункта выше и, если фактический вывод на твоём окружении разойдётся с описанным здесь, зафиксировать расхождение в HANDOFF_3. Известное поведение (не баг): `AddrExtractor` матчит и одиночные упоминания городов без маркера, в том числе в косвенных падежах («из Москвы» → Match «Москвы» с `type=None`) — такие одиночные упоминания становятся самостоятельными `ADDRESS`-entity; это избыточная токенизация, восстанавливается посимвольно точно и приёмку не блокирует.
- Границы `start`/`end` — по границам слов/токенов, найденных Natasha (для NER) или после склейки matches (для адресов), не обрезать середину слова.
- Инициализация моделей (`Segmenter`, `NewsEmbedding`, `NewsNERTagger`, `MorphVocab`, `AddrExtractor`) — один раз при старте модуля, не на каждый вызов функции (иначе неприемлемая скорость).
- Для сегментов, где Natasha/AddrExtractor не уверены (нет явной разметки), ничего не придумывать — просто не создавать Entity.
- Natasha прогоняется **на каждом сегменте отдельно** (`Doc(segment.text)` для NER; `AddrExtractor` — тоже на `segment.text`), не на склеенном документе целиком — иначе `start`/`end` окажутся смещениями внутри всего документа, а не внутри `segment.text`, как того требует формат Entity.
- Если AddrExtractor не покрыл часть адреса в конкретном сегменте (например, индекс или "оф. 12" не вошли в span даже после склейки) — это не баг блока, а известное ограничение MVP; зафиксировать в HANDOFF явно.
- После NER для `PERSON` выполнять расширение спана в обе стороны — независимо друг от друга: **вправо**, если сразу за концом span (допускается один пробел/неразрывный пробел) следуют инициалы вида "И.И." (`^\s?[А-ЯЁ]\.\s?[А-ЯЁ]\.`), включить их; **влево**, если сразу перед началом span (тот же допуск на пробел) находятся инициалы вида "И.И." (`[А-ЯЁ]\.\s?[А-ЯЁ]\.\s?$`), включить их тоже — в договорах подписной блок часто оформлен как "И.И. Иванов" (инициалы слева), а не только "Иванов И.И.", и без левого расширения эти инициалы остаются в открытом тексте. Другие расширения границ не выполнять.
- **После любого изменения границ спана — обязательный пересчёт `original_text`.** Если `start`/`end` были изменены относительно того, что вернула Natasha (расширение `PERSON` инициалами влево/вправо; склейка соседних Match'ей в один `ADDRESS`), поле `original_text` обязано быть пересчитано как `segment.text[start:end]`. Запрещено оставлять в `original_text` текст, пришедший напрямую от Natasha (`span.text`, текст отдельного `Match` до склейки) — он относится к неизменённым границам и разойдётся с реальным `start`/`end`. Без этого пересчёта нарушение не даёт исключения нигде по пайплайну: блок 4 подставит токен по корректным `start`/`end`, но в файл сессии уйдёт усечённый `original_text` — и детокенизация молча восстановит "Иванов" вместо "Иванов И.И.". Дополнительно `original_text` — ключ переиспользования токена в блоке 4 (см. блок 4), поэтому усечённые значения могут схлопнуть в один токен спаны разной длины из разных мест текста. Инвариант, который блок 3 обязан выдерживать для каждого выдаваемого Entity: `entity.original_text == segment.text[entity.start:entity.end]` — рекомендуется проверять его в коде явно перед возвратом списка.
**Зависимости:** `natasha`.
**Приёмка:** абзац с 2-3 ФИО (в формате "Иванов И.И."), названием организации и полным адресом (город, улица, дом) — все три категории найдены как единые span'ы, границы совпадают с полными словами включая инициалы (не "Иван" вместо "Иванов", не "Иванов" без "И.И."). Для адреса: приёмка пройдена, если после склейки matches получился один Entity, охватывающий город+улицу+дом единым текстом; потеря хвоста (например, "оф. 12" или индекс) приёмку не блокирует и фиксируется в HANDOFF как известное ограничение.

## Блок 4 — Токенизатор

**Вход:** `SourceDocument`, объединённый `list[Entity]` из блоков 2 и 3.
**Выход:** анонимизированный текст (`str`, вся SourceDocument собранная в один текст с подставленными токенами) + финальный `list[Entity]` с заполненным полем `token`. Дополнительно блок экспортирует функцию `build_plain_text(doc: SourceDocument) -> str` — та же сборка текста, что описана ниже, но **без подстановки токенов** (обычный исходный текст); она нужна как независимый эталон для сквозной приёмки блока 7 (сравнение восстановленного текста с этим эталоном, а не с результатом самого детокенизатора).
**Требования:**
- **Состав выходного `list[Entity]`.** В выходной список попадают **только** entity, пережившие разрешение пересечений и реально подставленные в текст токеном; у каждого из них поле `token` заполнено непустой строкой. Entity, удалённые при разрешении пересечений (проигравшие), в выходной список **не включаются** — они не возвращаются с `token = None`. Блок 5 опирается на инвариант `all(e.token for e in result)`, поэтому это правило обязательно.
- **Разрешение пересечений (полный алгоритм, применяется внутри каждого сегмента отдельно).** Два entity считаются пересекающимися, если их интервалы `[start, end)` имеют непустое пересечение (включая полное совпадение и вложенность одного в другой — это гарантированно случается: например 9-значное число, начинающееся с "04", матчится и как `KPP`, и как `BIK`; 10-значный ИНН без пробелов может совпасть с паттерном `PASSPORT`).

  **Правило сравнения любой пары entity (кто из двух "сильнее"), применяется как сквозной tie-break:**
  1. `regex` побеждает над `ner`.
  2. Среди двух `regex` — побеждает более длинный span (`end - start`).
  3. При равной длине среди `regex` — побеждает тип, идущий раньше в списке приоритетов: `BANK_ACCOUNT > OGRN > INN > BIK > KPP > PASSPORT > PHONE > SUM > EMAIL > DATE`. Типы, отсутствующие в этом списке (добавленные пользователем в `entity_types.yaml` позже, вне MVP-набора), имеют приоритет ниже всех перечисленных; между собой такие типы упорядочиваются по алфавиту `entity_type`.
  4. Среди двух `ner` — побеждает более длинный span, при равенстве длины — больший `confidence` (на практике confidence всегда 1.0 в MVP). Если длина и `confidence` равны, но интервалы не идентичны (например PERSON `[0,10)` vs ORG `[3,13)`) — применять фиксированный приоритет типа `ADDRESS > ORG > PERSON`; при равном типе — меньший `start`.
  5. Если ничего из 1-4 не разрешило пару (интервалы идентичны по всем параметрам) — сравнивать кортежи `(entity_type, original_text)` лексикографически, побеждает меньший. `id` (uuid4) в сравнении не участвует нигде — иначе результат разрешения пересечений был бы невоспроизводим между запусками на одних и тех же входных данных.

  **Процедура разрешения для сегмента (обрабатывает цепочки пересечений из более чем двух entity, а не только изолированные пары):**
  ```
  пока среди ещё не зафиксированных entity сегмента есть хотя бы одна пересекающаяся пара:
      выбрать глобально сильнейший entity среди ВСЕХ ещё не зафиксированных
          (сравнивая по правилу выше со всеми остальными ещё не зафиксированными)
      зафиксировать его как "оставшийся" (победитель)
      удалить все entity, которые пересекаются именно с этим победителем
          (НЕ удалять entity, не пересекающиеся с победителем напрямую,
           даже если они пересекались с уже удалённым проигравшим — это важно:
           иначе маленький regex-спан, пересекающий сразу двух соседних ner-сущностей,
           безвозвратно удалит обе, хотя они не пересекались друг с другом)
  ```
  После выполнения процедуры в сегменте не должно остаться двух entity с пересекающимися интервалами, и ни один entity не должен быть удалён без прямого пересечения с зафиксированным победителем. **Важно про итоговое множество:** результат сегмента — это **все** entity, которые не были удалены на шаге "удалить всех, кто пересекается с победителем", то есть и зафиксированные победители, и entity, которые ни с кем не пересекались вообще и потому в цикл разрешения не попали (обычный случай для большинства сущностей в чистом тексте — например одиночный ИНН или email без конфликтов). Entity, не участвовавший ни в одном пересечении, проходит дальше без изменений и обязан получить токен наравне со всеми. Инвариант: `len(результат) == len(вход) - len(удалённых)`, где `удалённые` — только те entity, что имели непустое пересечение с каким-либо зафиксированным победителем. **Известное ограничение MVP:** если короткий regex-спан лишь частично пересекается с длинным NER-спаном (например `PERSON`/`ADDRESS`), весь NER-entity удаляется целиком (правило 1), и его часть, не покрытая победившим regex-спаном, остаётся в открытом тексте. Усечение проигравшего спана вместо полного удаления — фаза 2, не MVP; фиксировать это в HANDOFF_4.
- **Идентичность сущности (правило "тот же токен").** Токен переиспользуется только при **точном посимвольном** совпадении `entity_type` и `original_text`. Никакая нормализация (регистр, кавычки, пробелы, падежи) при сравнении не применяется: "ООО «Ромашка»" и "ООО РОМАШКА" — это два разных токена. Это осознанное ограничение MVP (нужно, чтобы гарантировать: у каждого токена ровно один вариант `original_text`, и детокенизация восстанавливает текст посимвольно точно — при нормализации разные варианты написания схлопнулись бы в один токен, а восстановленный текст перестал бы совпадать с оригиналом в части мест). Схлопывание вариантов написания одной сущности — фаза 2, не MVP.
- **Формат токена и источник TYPE.** Токен имеет вид `[TYPE_N]`, где `TYPE` — это значение поля `token_prefix` из `entity_types.yaml` для данного `entity_type`, **а не сам `entity_type`** (пример: для `entity_type = "BANK_ACCOUNT"` в конфиге указан `token_prefix: ACCOUNT`, поэтому итоговый токен — `[ACCOUNT_1]`, не `[BANK_ACCOUNT_1]`). Нумерация `N` сквозная по `token_prefix`, начиная с 1. "Порядок появления" = сортировка по паре `(индекс сегмента в SourceDocument.segments, start)`.
- Подстановка токена в текст сегмента — с учётом того, что несколько entity могут быть в одном сегменте; подставлять от конца сегмента к началу (по убыванию `start`), чтобы не сбить смещения предыдущих. К моменту подстановки в сегменте уже не должно быть пересекающихся entity (см. разрешение пересечений выше) — иначе подстановка их испортит.
- Итоговый `list[Entity]` на выходе блока (тот, что возвращается с заполненным `token`) отсортирован по паре `(индекс сегмента в SourceDocument.segments, start)` — тем же ключом, что используется для нумерации токенов. Блок 5 имеет право опираться на этот порядок при выборе "первого по порядку вхождения" (см. блок 5).
- Сборка финального текста документа выполняется **одним проходом по `SourceDocument.segments` в их исходном порядке**. Последовательные сегменты с `source_type == "docx_table_cell"` и одинаковым `metadata["table_index"]` образуют один "блок-таблицу"; блок-таблица целиком занимает в выходном тексте то место, где встретился её первый сегмент (то есть таблицы не переносятся в конец — они остаются на своей позиции среди параграфов). Внутри блока-таблицы: строки — по возрастанию `metadata["row_index"]`, ячейки внутри строки — по возрастанию `metadata["col_index"]` (сортировка по значениям metadata, не по позиции сегмента в списке); **перед склейкой** внутренние переводы строк в тексте каждой ячейки заменяются на пробел (`cell_text.replace("\n", " ")`) — ячейка может содержать несколько абзацев (см. блок 1), и без этой замены такая ячейка разорвала бы строку таблицы пополам; если ячейка попала под токенизацию, эта замена выполняется **после** подстановки токенов в неё. Эта же замена обязательна и в `build_plain_text` — иначе эталон для сквозной приёмки блока 7 разойдётся с результатом `tokenize` на документах с многострочными ячейками. Сама замена влияет только на сборку итогового текста; `TextSegment.text` и оффсеты `Entity.start`/`Entity.end` не меняются. Ячейки строки склеиваются через `" | "`, строки таблицы — через `"\n"`. Сегменты `docx_paragraph` и `txt_line` выводятся по одному на строку. Между любыми двумя соседними верхнеуровневыми единицами (параграф, строка таблицы, строка txt) — ровно один `"\n"`, без завершающего `"\n"` в конце документа. Пустые сегменты (пустой параграф, пустая строка txt, повторное вхождение merged-ячейки) выводятся как пустая строка/пустая ячейка и не пропускаются.
- **Предусловия (не проверяются блоком; нарушение = тихая порча текста, не исключение):** для каждого входного Entity — `segment_id` присутствует среди `doc.segments`; `0 <= start < end <= len(segment.text)`; `original_text == segment.text[start:end]`; `token is None`.
**Зависимости:** нет новых.
**Приёмка:** документ с 2 упоминаниями одной организации в абсолютно одинаковом написании и одним ИНН — организация получает один и тот же токен оба раза (`[ORG_1]`), ИНН — `[INN_1]`, финальный текст не содержит оригинальных значений. Отдельно: строка с 9-значным числом, начинающимся на "04" (потенциальный KPP/BIK конфликт) — после разрешения пересечений в тексте остаётся ровно один токен на этом месте, не два наложенных друг на друга. Отдельно: сегмент с тремя пересекающимися entity (цепочка A-B-C, где A∩B и B∩C, но A∩C = ∅) — после разрешения в тексте не должно остаться токенов для entity, не пересекавшихся напрямую с итоговым победителем.

## Блок 5 — Хранилище сессии

**Вход:** `list[Entity]` с токенами (блок 4), `session_id: str | None` (если `None` — сгенерировать `uuid4`).
**Выход:** функции:
```python
def save_session(entities: list[Entity], session_id: str | None = None, ttl_hours: int = 24, storage_dir: str | None = None) -> str: ...  # возвращает session_id
def load_session(session_id: str, storage_dir: str | None = None) -> dict: ...  # формат см. выше
def purge_expired(storage_dir: str | None = None, exclude_session_id: str | None = None) -> int: ...  # возвращает число удалённых файлов
def delete_session(session_id: str, storage_dir: str | None = None) -> bool: ...  # ручное удаление одной сессии
```
**Требования:**
- Директория хранилища по умолчанию (при `storage_dir=None` в любой из трёх функций): `~/.shifrator/sessions` — создаётся автоматически при первом сохранении, если не существует. Это соглашение обязательно для всех трёх функций, чтобы блок 7 (encrypt/decrypt) гарантированно работал с одной и той же директорией без явной передачи пути.
- Шифрование через `cryptography.fernet.Fernet`. Ключ — генерируется при первом запуске, хранится в файле `{storage_dir}/key.bin` (не в коде, не в переменных окружения для MVP). `key.bin` не защищён паролем — это осознанное ограничение MVP (защита от случайного прочтения файла постороннним ПО, не от локального злоумышленника с доступом к диску); пароль/OS keyring — фаза 2. При создании `key.bin` и файлов `*.enc` выставлять права доступа `0o600` (на POSIX-системах; на Windows это не действует, там ограничений на MVP не накладывается).
- **Атомарное создание `key.bin`** (`_load_or_create_key`). Создание ключа обязано быть атомарным, иначе два одновременных `save_session` на свежую директорию оба увидят отсутствие `key.bin`, каждый сгенерирует свой ключ, второй перезапишет первый — и сессия, зашифрованная перезаписанным ключом, становится нерасшифровываемой навсегда (TOCTOU-гонка, тихая потеря токен-маппинга). Механизм: сгенерированный ключ пишется целиком во временный файл в той же директории и публикуется под финальным именем `key.bin` через `os.link` — эксклюзивную операцию, которая кидает `FileExistsError`, если цель уже существует. Победитель гонки публикует свой ключ, проигравшие ловят `FileExistsError` и читают уже полностью записанный ключ победителя (а не свой). Так закрыты сразу два окна: перезапись ключа (успешная публикация возможна лишь однажды) и чтение недописанного файла (`key.bin` появляется под финальным именем сразу целиком). **Гарантия по платформам:** на POSIX `os.link` атомарен и по спецификации падает на существующей цели; на Windows/NTFS он ложится на `CreateHardLinkW` с той же семантикой отказа, поэтому гарантия держится. На файловых системах без жёстких ссылок или если временный файл оказался на другом томе гарантия **слабее** — предусмотрен неатомарный запасной путь через `os.open(..., O_CREAT|O_EXCL)` (перезапись по-прежнему невозможна, но остаётся узкое окно чтения недописанного файла у проигравшего). В процессе создания в директории хранилища может кратковременно появиться временный файл вида `key.bin.*.tmp`, который затем удаляется; код, перечисляющий содержимое директории, должен это учитывать.
- Файл сессии — `{storage_dir}/{session_id}.enc`. `session_id`, приходящий в `load_session` извне (например, из аргументов CLI в блоке 7), перед формированием пути к файлу валидировать регулярным выражением `^[0-9a-f-]{36}$` (формат uuid4); при несовпадении — сразу `SessionNotFoundError`, к файловой системе не обращаться (защита от path traversal через "чужой" session_id).
- `load_session` — при отсутствии файла или истёкшем `expires_at` кидает явное исключение (`SessionNotFoundError`, `SessionExpiredError`) — не `None` молча. Оба класса — `SessionNotFoundError(Exception)` и `SessionExpiredError(Exception)` — определяются **в `session_store.py`** (том же модуле, что и `save_session`/`load_session`/`purge_expired`); отдельного модуля исключений не создавать. Другие блоки импортируют их как `from session_store import SessionNotFoundError, SessionExpiredError`.
- **Повреждён файл или ключ в `load_session`.** Формулировка «повреждён файл или ключ» покрывает два случая: (1) `.enc` не расшифровывается (`cryptography.fernet.InvalidToken` из-за битого содержимого файла) и (2) сам `key.bin` невалиден по содержимому (обрезан, затёрт, синхронизирован наполовину) — тогда конструктор `Fernet(key)` кидает `ValueError` ещё до `decrypt`. Оба случая обязаны перехватываться и превращаться в `SessionNotFoundError` (а не в необёрнутый `ValueError`/крах): для невалидного ключа — с сообщением `Сессия не расшифровывается (повреждён ключ): <id>`, для битого `.enc` — `Сессия не расшифровывается (повреждён файл или ключ): <id>`.
- Если `entities` (вход `save_session`) пуст — сессия всё равно создаётся, с `"entities": []` в файле. Если `session_id` передан в `save_session` явно (не `None`) — валидировать тем же регулярным выражением `^[0-9a-f-]{36}$`; при несовпадении — `ValueError`. Если файл сессии с таким id уже существует — он перезаписывается.
- `created_at`/`expires_at` — timezone-aware ISO 8601 (пример формата — как в JSON выше, с `+03:00`): `created_at = datetime.now().astimezone()` (локальная таймзона с offset), `expires_at = created_at + timedelta(hours=ttl_hours)`, сериализация обеих через `.isoformat()`. Сравнение для проверки TTL при загрузке выполнять только в UTC: `datetime.now(timezone.utc)` против `datetime.fromisoformat(expires_at)`; naive datetime (без таймзоны) нигде не использовать — иначе сравнение упадёт или даст неверный TTL.
- В поле `entities` файла сессии писать по одной записи на токен (дедупликация по `token`); каждая запись содержит поля `token`, `entity_type`, `original_text`, `segment_id` — ровно как в примере формата файла сессии выше. На входе может быть несколько Entity с одним и тем же токеном (несколько упоминаний одной сущности в документе), в файле сессии это должна быть одна запись на токен. По правилу переиспользования токена все такие Entity имеют одинаковые `entity_type` и `original_text`; при дедупликации сохранять `segment_id` **первого** по порядку вхождения в исходном `list[Entity]` (поле не используется при детокенизации, но выбор должен быть детерминированным, а не произвольным).
- `purge_expired` перебирает **только файлы с расширением `.enc`** в `storage_dir`; `key.bin` и любые прочие файлы (включая нераспознанные) игнорируются и никогда не удаляются — это критично, потому что случайное удаление `key.bin` делает все ранее сохранённые сессии невосстановимыми. Если файл `.enc` не расшифровывается (`cryptography.fernet.InvalidToken`) или содержит невалидный JSON / не содержит поля `expires_at` — файл **пропускается, не удаляется**, в stderr печатается предупреждение с именем файла. Возвращаемое число — количество фактически удалённых просроченных файлов.
- **Повреждён `key.bin` в `purge_expired`.** Если сам `key.bin` невалиден по содержимому, `Fernet(key)` кидает `ValueError` ещё до перебора файлов. `purge_expired` обязан перехватить это, напечатать предупреждение в stderr и вернуть `0` без падения (без валидного ключа ни одну сессию не расшифровать, значит удалять по TTL нечего) — иначе CLI `decrypt`, вызывающий `purge_expired` в начале, рухнул бы с трейсбеком на нормальном вводе.
- **`exclude_session_id` и очистка в `decrypt`.** Параметр `exclude_session_id` (по умолчанию `None` — прежнее поведение, вычищаются все просроченные) при заданном значении заставляет `purge_expired` **не трогать** файл `{exclude_session_id}.enc` в этом проходе (даже если он просрочен), вычищая все ОСТАЛЬНЫЕ просроченные сессии. Это нужно блоку 7: `decrypt` зовёт `purge_expired(exclude_session_id=session_id)` в начале команды, чтобы чужой просроченный мусор не копился на диске бесконечно, но файл именно запрошенной сессии оставался на месте — тогда последующий `load_session` отличит «истекла» (`SessionExpiredError`) от «не найдена» (`SessionNotFoundError`) по значению `expires_at`, а не по наличию файла. Механизм не создаёт новой межпроцессной гонки: удаление истёкшего файла другим параллельным процессом было возможно и раньше, `exclude_session_id` лишь не даёт вызову удалить файл из-под собственного последующего `load_session`.
- **`delete_session(session_id, storage_dir=None) -> bool`** — ручное удаление одной сессии по запросу пользователя (используется подкомандой CLI `delete`, блок 7). Валидирует `session_id` тем же regex `^[0-9a-f-]{36}$`, что и `load_session`; при несовпадении к файловой системе **не обращается** и возвращает `False` (защита от path traversal). Если файл `{storage_dir}/{session_id}.enc` существует — удаляет его и возвращает `True`; если файла нет — возвращает `False`. В обоих штатных случаях исключений не кидает. `key.bin` не трогает никогда.
**Зависимости:** `cryptography`.
**Приёмка:** `save_session` → `load_session` в новом процессе (перезапуск интерпретатора), без явной передачи `storage_dir` — данные идентичны исходным, файл найден по дефолтному пути. Ручное изменение `expires_at` на прошедшую дату → `load_session` кидает `SessionExpiredError`. Документ с 2 упоминаниями одной организации → в файле сессии одна запись для `[ORG_1]`, не две. `purge_expired`, запущенный в директории с `key.bin` и просроченными `.enc`-файлами, удаляет только просроченные `.enc`, `key.bin` остаётся нетронутым. `delete_session` на существующей сессии возвращает `True` и удаляет `.enc`; на отсутствующей или невалидном по формату id — `False`, `key.bin` не тронут.

## Блок 6 — Детокенизатор

**Вход:** `text: str` (ответ LLM, произвольный текст), `session_id: str`.
**Выход:** `tuple[str, list[str]]` — восстановленный текст + список токенов, которые встретились в тексте, но не найдены в сессии (unresolved).
**Требования:**
- Загружает сессию через `load_session` (блок 5, модуль `session_store.py`). `detokenize` **не перехватывает** `SessionNotFoundError`/`SessionExpiredError` — они пробрасываются наверх вызывающему коду (блоку 7). Требование "не падать ни при каких искажениях" (см. ниже) относится **только** к содержимому аргумента `text`, а не к отсутствию или истечению самой сессии — иначе блок 7 не сможет отличить "сессия истекла" от "пустого ответа LLM".
- `load_session` возвращает dict ровно того вида, что описан в разделе "Формат файла сессии" выше; блок 6 использует из него только `session["entities"]` — список dict'ов с ключами `token` и `original_text`.
- Ищет regex `\[[A-Z_]+_\d+\]` в тексте, для каждого совпадения — если есть в `entities` сессии, заменяет на `original_text`; если нет — оставляет как есть и добавляет в список unresolved. Замена выполняется **одним проходом** через `re.sub(pattern, repl_func, text)` — повторный проход по уже заменённому тексту не выполняется (иначе, если `original_text` одной сущности случайно содержит подстроку, похожую на другой токен, возможны каскадные замены).
- Контракт с конфигом: `token_prefix` в `entity_types.yaml` обязан соответствовать `^[A-Z][A-Z_]*$` (только заглавные латинские буквы и подчёркивание, без цифр) — иначе он не будет находиться этим regex'ом. Это ограничение при расширении конфига пользователем.
- Список unresolved — уникальные токены (без повторов, даже если один и тот же неизвестный токен встретился в тексте несколько раз), в порядке первого появления в тексте.
- Не падает ни при каких искажениях текста ответа LLM (это внешний, не контролируемый вход). **Известное ограничение:** токены, которые LLM исказила при переформулировке (изменённый регистр `[org_1]`, пропавшие скобки `ORG_1`, вставленный пробел `[ORG 1]`), не распознаются этим regex'ом и не попадают ни в замену, ни в unresolved — пользователь не узнает об этой потере из вывода программы. Фиксировать в HANDOFF_6 явно.
**Зависимости:** нет новых.
**Приёмка:** текст с 3 валидными токенами → все заменены, unresolved пуст. Текст с одним валидным и одним несуществующим токеном (`[ORG_99]`) → валидный заменён, `[ORG_99]` остался в тексте и попал в unresolved.

## Блок 7 — CLI

**Вход:** аргументы командной строки.
**Выход:** консольный интерфейс:
```
python shifrator.py encrypt <путь_к_файлу.docx|.txt>
    → сохраняет анонимизированный текст в файл {storage_dir}/{session_id}.txt
      (тот же storage_dir, что использует save_session блока 5; кодировка utf-8)
    → печатает в stdout ТОЛЬКО session_id (одна строка, без лишнего текста)
python shifrator.py decrypt <session_id>
    → читает текст ответа LLM из stdin
    → печатает восстановленный текст в stdout
    → если есть unresolved токены — печатает предупреждение в stderr
python shifrator.py delete <session_id>
    → удаляет сессию (файл {storage_dir}/{session_id}.enc) без подтверждения
    → печатает в stdout "Сессия <id> удалена" при успехе либо
      "Сессия <id> не найдена", если файла не было (или id невалиден по формату)
    → код возврата 0 в обоих случаях
```
**Требования:**
- Только склейка блоков 1-6 через их публичные функции, без новой бизнес-логики.
- В начале `main()` выполнять `sys.stdout.reconfigure(encoding="utf-8")` и `sys.stderr.reconfigure(encoding="utf-8")` — иначе на Windows консоль по умолчанию использует cp1251/cp866, и вывод кириллицы упадёт с `UnicodeEncodeError` на первом же символе.
- `encrypt` вызывает блоки в таком порядке: `extract` (блок 1) → `detect_regex` + `detect_ner` (блоки 2 и 3, результаты объединяются в один список: сначала entity от regex, затем от ner — порядок влияет только на читаемость промежуточных данных, не на логику) → `tokenize` (блок 4) → `save_session(entities, session_id=None, ttl_hours=24)` (блок 5). Один и тот же путь к конфигу (флаг `--config <путь>`, по умолчанию `entity_types.yaml` рядом с `shifrator.py`) передаётся во **все три** функции, где он нужен: `detect_regex`, `detect_ner` **и `tokenize`** (последней он нужен, чтобы взять `token_prefix` для формирования токенов).
- `decrypt` **в начале команды** (до чтения stdin и загрузки сессии) вызывает `purge_expired(exclude_session_id=session_id)` — чтобы просроченные сессии с расшифрованными данными не копились на диске бесконечно; очистка выполняется ВСЕГДА, независимо от того, какую сессию просит пользователь и найдётся ли она. Передача `exclude_session_id=session_id` оставляет файл именно запрошенной сессии нетронутым в этом проходе (см. блок 5), поэтому последующий `load_session` корректно кидает `SessionExpiredError` на честно истёкшей запрошенной сессии — ветка `except SessionExpiredError` в `decrypt` достижима и не является мёртвым кодом (пользователь видит «сессия истекла», а не «не найдена»). Все ОСТАЛЬНЫЕ просроченные сессии при этом вычищаются за тот же вызов. Ошибки внутри `purge_expired` не должны прерывать `decrypt` — логируются в stderr, выполнение продолжается.
- Подкоманда `delete <session_id>` вызывает `delete_session(session_id)` (блок 5, дефолтная директория) и печатает в stdout `Сессия <id> удалена` при возврате `True` или `Сессия <id> не найдена` при `False`; код возврата 0 в обоих случаях, подтверждение не запрашивается.
- Путь к `entity_types.yaml` по умолчанию — файл рядом с `shifrator.py` (той же директории); функции блоков 2 и 3 принимают `config_path: str` явным аргументом, CLI подставляет дефолтный путь, если пользователь его не указал отдельным флагом.
- `decrypt` читает stdin до EOF (Ctrl+D в Linux/macOS, Ctrl+Z затем Enter в Windows); перед чтением обязательно печатать в stderr короткую подсказку об этом, иначе пользователь не поймёт, почему терминал "завис" в ожидании ввода.
- Понятные сообщения об ошибках (файл не найден, неподдерживаемый формат, сессия не найдена/истекла). В частности, битый/переименованный/пустой `.docx` приходит из блока 1 как `ValueError` (см. блок 1) и печатается как `Ошибка: Файл не является корректным .docx (повреждён или неверный формат): <path>` с кодом возврата 1 — сырой трейсбек `PackageNotFoundError` наружу выводиться не должен.
- Перед стартом этого блока в чат должны быть загружены **все шесть** HANDOFF-файлов блоков 1-6 без исключения — блок 7 не содержит своих собственных публичных функций сверх CLI и полностью зависит от сигнатур, зафиксированных в HANDOFF предыдущих блоков.
**Зависимости:** нет новых (стандартный `argparse`).
**Приёмка:** полный ручной прогон: реальный .docx → encrypt → анонимизированный текст сохранён в файл `{storage_dir}/{session_id}.txt` (session_id взят из stdout encrypt) → decrypt с содержимым этого файла, поданным как "ответ LLM" без изменений → восстановленный текст идентичен результату вызова `build_plain_text(doc)` (эталонная функция блока 4 — та же сборка текста, но без подстановки токенов, включая её разделители `"\n"` и `" | "`), а не бинарному содержимому исходного .docx-файла — сравнение с обеих сторон идёт по плоскому тексту, не по файлу. Сквозной тест сравнивает `build_plain_text(doc)` именно с содержимым файла `{storage_dir}/{session_id}.txt`, а не со stdout encrypt (stdout теперь содержит только session_id). Эталон берётся именно из `build_plain_text`, а не из повторного вызова детокенизатора над самим собой — иначе тест проверял бы блок 6 сам через себя и не заметил бы, если оба места ошиблись одинаково.

```markdown

## Что сделано
3-5 предложений, без пересказа кода целиком.

## Публичный интерфейс
Точные сигнатуры функций/классов/dataclass'ов для следующих блоков (имена модулей и функций — по реестру в разделе "Единый внутренний формат документа", не переименовывать). Для каждой публичной функции — сигнатура, **строка импорта** (`from <module> import <name>`), **минимальный работающий пример вызова** (3-5 строк: импорт → вызов → что в результате, чтобы следующий блок мог скопировать без чтения исходников) и **список исключений**, которые она может выбросить (тип исключения + модуль, в котором класс исключения определён, + когда возникает).

Конкретный пример реального JSON/объекта (не абстрактное описание).

Для каждого `source_type`/структуры на выходе — исчерпывающий список ключей `metadata` (имя → тип → пример значения) и явное указание, какие ключи гарантированно присутствуют, а какие опциональны. Какие инварианты входных данных блок считает выполненными и не проверяет сам. Если предусловие нарушено — что произойдёт (исключение или тихая порча данных, и какая именно).

Сколько это занимает по времени/памяти, и можно ли импортировать модуль лениво (актуально для блока 7 — например, ветке `decrypt` NER не нужен вовсе).
