## 0. Границы компонента — прочесть до начала работы

**Что делаем.** Берём принесённый пользователем файл `.docx`/`.xlsx`/`.pptx` **как есть**,
находим в нём токены, заменяем на оригинальные значения из сессии, сохраняем файл с той же
структурой и тем же оформлением, что были в принесённом файле.

**Что НЕ делаем (частая ошибка понимания задачи — прочитать дважды):**
- Мы **не** восстанавливаем исходный договор и **не** используем его структуру. Структура
  исходного документа, поданного на `encrypt`, в этом компоненте не участвует **вообще**.
  Единственное, что берётся из сессии — плоский маппинг `токен → original_text`.
- Мы **не** переносим форматирование из исходного документа в новый. Форматирование берётся
  **только** из того файла, который сейчас лежит на входе `decrypt`.
- Мы **не** трогаем `encrypt`: он по-прежнему принимает только `.docx`/`.txt` (расширение
  `encrypt` на xlsx/pptx — отдельная задача, вне этого документа).
- Мы **не** делаем PDF (отложено осознанно, вне этого документа).

**Ключевое требование по стилю.** Значение, вставленное вместо токена, обязано унаследовать
оформление того текстового прогона (run), в котором **начинался токен**: шрифт, кегль, цвет,
жирность/курсив, а для ячейки Excel — стиль ячейки. Практически это достигается тем, что мы
**меняем только текстовое содержимое узлов и никогда не трогаем узлы/атрибуты оформления**
(`<w:rPr>`, `<a:rPr>`, атрибут `s` у `<c>`). Это инвариант всего компонента.

## Отношение к блоку 6 (`detokenizer.py`) — почему не переиспользуем

Блок 6 принимает **плоскую строку** и возвращает плоскую строку. Наивная идея «вытащить весь
текст из docx, прогнать через `detokenize`, засунуть обратно» **не работает**: обратного пути
из плоской строки в размеченный XML не существует — вставить строку обратно можно только
уничтожив разметку. Поэтому компонент 2 работает **по узлам XML на месте**, не собирая
документ в строку. Это принципиально другой алгоритм, а не обёртка над блоком 6.

`detokenizer.py` остаётся как есть и продолжает обслуживать «текстовый» decrypt (копипаст
ответа LLM). Два пути сосуществуют:

```
ответ LLM как текст  → detokenizer.detokenize(text, session_id)          → текст   (блок 6, как было)
ответ LLM как файл   → file_detokenizer.detokenize_file(path, session_id) → файл    (блок 12, новое)
```

## Дублирование регулярного выражения токена — сознательное

Блок 6 ищет токены паттерном `\[[A-Z_]+_\d+\]`. Блок 8 определяет **свою** константу с
**посимвольно тем же** паттерном (импортировать из `detokenizer.py` нельзя: его импорт — часть
чужого блока, а связывать их жёстко ради одной строки хуже, чем продублировать). В HANDOFF_8
обязательно зафиксировать: «TOKEN_RE совпадает с паттерном блока 6 посимвольно; при изменении
формата токенов правятся оба места».

## Общая архитектура компонента

Все три формата — это ZIP-контейнеры с XML внутри (OOXML). Различаются они только тем, **в
каких частях архива лежит текст и как называются узлы**. Поэтому архитектура — «одно ядро +
три тонких адаптера»:

```
                       ┌──────────────────────────────────────┐
файл .docx/.xlsx/.pptx │  Блок 12: file_detokenizer.py        │
       + session_id ──►│  фасад: формат → адаптер,            │
                       │  session_store.load_session →        │
                       │  resolve(token) -> original_text     │
                       └───────┬──────────────────────────────┘
                               │ resolve
              ┌────────────────┼────────────────┐
              ▼                ▼                ▼
      Блок 9            Блок 10           Блок 11
   docx_rewriter.py  pptx_rewriter.py  xlsx_rewriter.py
   (какие части ZIP, какие узлы = текст, что = один run-группа)
              └────────────────┼────────────────┘
                               ▼
                    ┌──────────────────────────┐
                    │ Блок 8: ooxml_core.py    │
                    │ • чтение/пересборка ZIP  │
                    │ • парс/сериализация XML  │
                    │ • TextUnit / RunGroup    │
                    │ • замена токенов, сшивка │
                    │   разорванных run'ов     │
                    └──────────────────────────┘
```

**Реестр модулей и публичных функций компонента 2 (зафиксирован, менять нельзя):**

| Блок | Модуль | Публичный интерфейс |
|---|---|---|
| 8 | `ooxml_core.py` | `TextUnit`, `RunGroup`, `TOKEN_RE`, `replace_tokens_in_group`, `read_zip_parts`, `rewrite_zip`, `parse_xml`, `serialize_xml`, `OoxmlError` |
| 9 | `docx_rewriter.py` | `def rewrite(src_path: str, dst_path: str, resolve: Resolver) -> list[str]` |
| 10 | `pptx_rewriter.py` | `def rewrite(src_path: str, dst_path: str, resolve: Resolver) -> list[str]` |
| 11 | `xlsx_rewriter.py` | `def rewrite(src_path: str, dst_path: str, resolve: Resolver) -> list[str]` |
| 12 | `file_detokenizer.py` (+ правка `shifrator.py`) | `def detokenize_file(src_path: str, session_id: str, dst_path: str \| None = None, storage_dir: str \| None = None) -> tuple[str, list[str]]` |

Три адаптера (9, 10, 11) имеют **абсолютно одинаковую сигнатуру** — это не совпадение, а
контракт: блок 12 выбирает адаптер по расширению и вызывает их полиморфно, ничего не зная про
формат.

```python
# Тип, общий для блоков 8-12 (определяется в ooxml_core.py, импортируется остальными)
Resolver = Callable[[str], str | None]
# принимает токен целиком, включая скобки: "[ORG_1]"
# возвращает original_text, либо None если токен неизвестен сессии
```

**Порядок работы и параллельность:**

```
Блок 8 (ядро)  ← блокирующий, делается первым, в одиночку
      ├── Блок 9  (docx)  ┐
      ├── Блок 10 (pptx)  ├─ можно делать параллельно, в трёх независимых чатах:
      └── Блок 11 (xlsx)  ┘  файлы не пересекаются, общая зависимость — только HANDOFF_8
Блок 12 (фасад + CLI) ← последним, после всех трёх; требует HANDOFF_8..11 в чате
```

## Инварианты, обязательные для всех блоков компонента

1. **Исходный файл не модифицируется никогда.** Все блоки читают `src_path` и пишут в
   `dst_path`. Совпадение `src_path` и `dst_path` — ошибка (см. блок 12).
2. **Оформление не трогаем.** Изменяется только текстовое содержимое текстовых узлов
   (`<w:t>`, `<a:t>`, `<t>`). Узлы и атрибуты оформления (`<w:rPr>`, `<a:rPr>`, `<w:pPr>`,
   `<a:pPr>`, атрибут `s` у `<c>`, `xl/styles.xml`) **не читаются и не изменяются** — они
   переживают операцию просто потому, что мы их не касаемся.
3. **Части архива, которые мы не меняли, переносятся в новый архив байт-в-байт** — с теми же
   именами, тем же методом сжатия и той же датой (см. `rewrite_zip`, блок 8). Мы не
   «пересобираем документ», мы точечно подменяем несколько XML-частей.
4. **Неизвестный токен остаётся в тексте как есть** и попадает в список unresolved (то же
   поведение, что в блоке 6). Молча удалять или подставлять пустую строку — запрещено.
5. **Никаких сетевых обращений, никаких LLM, никаких новых тяжёлых зависимостей.** Компонент
   должен оставаться быстрым и лёгким — это его смысл существования (см. раздел «Бюджет
   ресурсов»).

## Бюджет ресурсов (нефункциональное требование, проверяется на приёмке блока 12)

Компонент существует ради того, чтобы не поднимать локальную LLM. Если он станет тяжёлым, он
потеряет смысл. Поэтому:
- Детокенизация файла **не импортирует `natasha`** и не грузит NER-модели ни при каких
  условиях (импорт `ner_detector` из блоков 8–12 **запрещён**; это сотни МБ памяти и секунды
  на импорт — см. «Побочные эффекты импорта» в HANDOFF_3).
- Целевое время обработки файла на 200 страниц / 10 тыс. ячеек — **менее 3 секунд**, память —
  порядка размера файла, не больше десятков МБ.
- Разрешённые внешние зависимости компонента: `lxml` (парсинг XML) и стандартные `zipfile`,
  `re`, `os`, `shutil`, `tempfile`. `python-docx` / `openpyxl` / `python-pptx`
  **использовать запрещено** во всех блоках 8–11: эти библиотеки пересобирают документ по
  своей модели и **теряют** часть неизвестной им разметки (а именно её сохранность — вся суть
  задачи). Работаем с XML напрямую. (`python-docx` остаётся зависимостью блока 1 — там он на
  чтение, это нормально и не отменяется.)

## Блок 8 — Ядро OOXML (`ooxml_core.py`)

**Назначение:** всё, что одинаково для трёх форматов. Ничего не знает ни про Word, ни про
Excel, ни про PowerPoint — оперирует абстракцией «группа текстовых кусочков, идущих подряд».

**Публичный интерфейс (зафиксирован):**

```python
Resolver = Callable[[str], str | None]

TOKEN_RE = re.compile(r"\[[A-Z_]+_\d+\]")   # посимвольно как в блоке 6

class OoxmlError(Exception): ...             # битый/недопустимый контейнер

@dataclass
class TextUnit:
    node: object          # lxml-элемент текстового узла (<w:t>/<a:t>/<t>), либо None
    text: str             # текущий текст (для разделителя — фиксированное значение)
    writable: bool        # True — в узел можно писать; False — псевдо-разделитель

@dataclass
class RunGroup:
    units: list[TextUnit]  # строго в порядке следования текста в документе

def replace_tokens_in_group(group: RunGroup, resolve: Resolver) -> list[str]: ...
    # заменяет токены во всех units группы, включая разорванные между units;
    # возвращает список НЕразрешённых токенов в порядке появления (с возможными повторами)

def read_zip_parts(src_path: str) -> dict[str, bytes]: ...   # имя части → байты
def rewrite_zip(src_path: str, dst_path: str, modified: dict[str, bytes]) -> None: ...
def parse_xml(data: bytes): ...       # -> lxml ElementTree
def serialize_xml(tree) -> bytes: ...
```

**Требования:**

- **`replace_tokens_in_group` — центральный алгоритм компонента.** Работает так:
  1. Склеить тексты всех `units` группы в одну строку `joined`, запомнив для каждого символа,
     какому unit и какому смещению внутри него он соответствует (карта оффсетов).
  2. Найти все совпадения `TOKEN_RE` в `joined`. **Именно эта склейка решает проблему
     разорванного токена:** редактор или сама LLM свободно разбивают `[PERSON_2]` на несколько
     run'ов (`[PERSON` + `_2]`) из-за проверки орфографии, правок, копипаста — в отдельно взятом
     `<w:t>` такой токен не найдётся никогда, и без склейки он молча остался бы неразрешённым
     (это тот же класс проблемы, что B3 из `BREAKING_REPORT.md`, но на границе run'ов, а не
     сегментов).
  3. Для каждого совпадения вызвать `resolve(token)`. Если вернулся `None` — токен в текст **не
     трогать**, добавить в возвращаемый список unresolved, перейти к следующему.
  4. Если значение получено — применить замену. **Правило распределения по узлам (важно для
     стиля):** всё значение целиком записывается в **тот unit, в котором токен начинался** —
     потому что оформление берётся из его run'а. Символы токена, попавшие в последующие units,
     из них удаляются (эти units могут остаться с пустым текстом — это нормально и допустимо,
     удалять сами узлы/run'ы **запрещено**: их удаление меняет структуру документа и может
     задеть нумерацию/закладки/ревизии).
  5. Совпадения применять **от конца группы к началу** (по убыванию позиции в `joined`), чтобы
     не сбивать оффсеты ещё не применённых совпадений.
  6. Записать получившиеся тексты в узлы `units` (только `writable=True`).
- **Псевдо-разделители (`writable=False`).** Если внутри группы между текстовыми узлами стоят
  нетекстовые элементы, физически разрывающие текст (`<w:br/>`, `<w:tab/>`, `<a:br/>` и т.п.),
  адаптер обязан вставить в `units` псевдо-unit с `writable=False` и `text="\n"`. Ядро
  учитывает его текст при склейке, но никогда в него не пишет. Смысл: `\n` не входит в
  `TOKEN_RE`, поэтому токен физически не может «склеиться через разрыв строки» — это защита от
  ложного склеивания двух разных фрагментов в псевдо-токен.
- **Значение с переводом строки.** Если `original_text` содержит `\n` или `\r` (возможно:
  текст многоабзацной ячейки таблицы в исходном договоре), перед вставкой в XML они заменяются
  на пробел. Обоснование: в OOXML `\n` внутри текстового узла не является переносом строки и
  ведёт себя непредсказуемо; та же нормализация уже применяется в `build_plain_text` блока 4,
  так что поведение согласовано. Зафиксировать как известное ограничение в HANDOFF_8.
- **Экранирование.** Значение вставляется как текст lxml-узла — экранирование `&`, `<`, `>`
  выполняет сам lxml. Руками экранировать **запрещено** (двойное экранирование даст `&amp;lt;`
  в документе).
- **`xml:space="preserve"`.** После записи текста: если итоговый текст узла начинается или
  заканчивается пробельным символом — выставить у узла атрибут
  `{http://www.w3.org/XML/1998/namespace}space = "preserve"`. Без этого Word/Excel обрежут
  ведущие/хвостовые пробелы, и «ООО «Ромашка» » склеится с соседним словом. Если атрибут уже
  стоял — не снимать его ни при каких условиях.
- **`parse_xml` / `serialize_xml`.** Парсер lxml настроить так, чтобы он **не менял** документ
  сверх наших правок: не удалял пробельные узлы (`remove_blank_text=False`), не трогал
  комментарии и PI. При сериализации обязательно выводить XML-декларацию с
  `encoding="UTF-8"` и `standalone=True` — Office требует `<?xml version="1.0"
  encoding="UTF-8" standalone="yes"?>`, и без `standalone` некоторые версии Excel считают файл
  повреждённым. Пространства имён не переобъявлять и не переименовывать префиксы (lxml
  сохраняет их сам, если ничего не пересоздавать).
- **`read_zip_parts`.** Открывает архив, возвращает `{имя_части: байты}`. Если файл не ZIP или
  битый (`zipfile.BadZipFile`) — кидает `OoxmlError(f"Файл не является корректным OOXML-контейнером (повреждён или неверный формат): {src_path}")`.
- **Защита от zip-бомбы (DoS).** До чтения содержимого просуммировать `file_size` всех записей
  архива по его оглавлению. Если суммарный **распакованный** размер превышает **200 МБ**, либо
  число записей превышает **5000** — кидать `OoxmlError` с внятным сообщением, не распаковывая.
  (Тот же класс защиты, что B1 в `BREAKING_REPORT.md`: вход не контролируется нами, файл
  принесён из внешней LLM/агента.) Мы никогда не распаковываем архив на диск — только в
  память, поэтому zip-slip (имена записей вида `../../`) неприменим; отдельной защиты от него
  не требуется, но факт зафиксировать в HANDOFF_8.
- **`rewrite_zip`.** Создаёт новый архив по `dst_path`: перебирает записи исходного архива **в
  исходном порядке**, для каждой — если её имя есть в `modified`, пишет новые байты, иначе
  копирует старые. Для каждой записи сохранять исходные `compress_type` и `date_time` из
  `ZipInfo`. Записи, отсутствующие в `modified`, не перекодировать и не пересжимать иначе, чем
  исходным методом. Новые записи не добавлять, существующие не удалять. Писать во временный
  файл в директории назначения и публиковать через `os.replace` — чтобы прерывание не оставило
  недописанный файл под финальным именем.
- Модуль не выполняет никаких действий при импорте (никаких моделей, директорий, чтения
  файлов) — импорт обязан быть мгновенным.

**Зависимости:** `lxml`, стандартные `zipfile`, `re`, `os`, `tempfile`.

**Приёмка:**
- Группа из трёх units с текстами `"Договор с "`, `"[ORG"`, `"_1] на сумму"` и
  `resolve("[ORG_1]") -> "ООО «Ромашка»"` → тексты units становятся `"Договор с "`,
  `"ООО «Ромашка»"`, `" на сумму"`; unresolved пуст. (Токен, разорванный между run'ами, найден
  и собран — ключевой сценарий блока.)
- Та же группа, но `resolve` возвращает `None` → тексты units **не изменились ни в одном
  символе**, unresolved == `["[ORG_1]"]`.
- Группа `["[PHONE", псевдо-разделитель "\n", "_1]"]` → замена **не** происходит (токен разорван
  реальным переносом строки, это не один токен), unresolved пуст, тексты не изменились.
- `rewrite_zip` без единой модифицированной части (`modified={}`) → выходной файл открывается
  Word/Excel/PowerPoint без предупреждений, набор и порядок записей архива совпадает с исходным.

## Блок 9 — Адаптер Word (`docx_rewriter.py`)

**Вход:** путь к `.docx` (сгенерированному кем угодно), `resolve`.
**Выход:** новый `.docx` по `dst_path` + список unresolved-токенов.

```python
def rewrite(src_path: str, dst_path: str, resolve: Resolver) -> list[str]: ...
```

**Требования:**
- Импортирует всё из `ooxml_core` (блок 8), **не переопределяет** `TextUnit`/`RunGroup`/
  `TOKEN_RE` и не пишет свою логику замены — вся замена делается вызовом
  `replace_tokens_in_group`. Задача блока — **только** «какие части архива открыть, какие узлы
  считать текстом, как разбить их на группы».
- **Обрабатываемые части архива** (по маске имени): `word/document.xml`,
  `word/header*.xml`, `word/footer*.xml`, `word/footnotes.xml`, `word/endnotes.xml`.
  Колонтитулы обязательны: в договорах в них часто лежат реквизиты (в блоке 1 они осознанно
  не извлекались, но здесь мы работаем с чужим файлом и обязаны раскрыть токен везде, где он
  стоит). Части, отсутствующие в архиве, просто пропускаются.
- **Группа = абзац** (`<w:p>`). Токен не может пересекать границу абзаца, и склеивать соседние
  абзацы **запрещено** (иначе конец одного и начало другого сложатся в ложный токен).
- **Текстовые units внутри абзаца** — все `<w:t>` в порядке следования по документу, включая
  те, что лежат внутри `<w:hyperlink>`, `<w:smartTag>`, `<w:ins>` (вставка в режиме
  рецензирования) и прочих обёрток. Обход — по порядку в дереве абзаца, а не только по прямым
  детям `<w:p>`.
- **Псевдо-разделители:** `<w:br/>` и `<w:tab/>`, встреченные между текстовыми узлами абзаца,
  добавляются в группу как `TextUnit(node=None, text="\n", writable=False)`.
- **Удалённый текст рецензирования** (`<w:del>` / `<w:delText>`) — **не трогать**: этот текст
  уже помечен как удалённый, замена в нём бессмысленна и опасна. В группу не включать.
- Текст в таблицах отдельной обработки не требует: `<w:p>` внутри `<w:tc>` — обычный абзац и
  попадает в общий обход. Стиль ячейки при этом не затрагивается.
- Части архива, не попавшие в маску (стили, темы, изображения, `[Content_Types].xml`) —
  переносятся в новый файл нетронутыми через `rewrite_zip`.
- unresolved возвращается **в порядке первого появления в документе**, с возможными повторами
  (дедупликацию делает блок 12).

**Зависимости:** `ooxml_core` (блок 8), `lxml`. `python-docx` — **запрещён**.

**Приёмка:** `.docx`, где `[PERSON_1]` стоит внутри предложения, написанного красным цветом,
кеглем 26, полужирным; после `rewrite` в этом месте стоит «Иванов Иван Иванович» **тем же
красным, тем же 26-м, тем же полужирным**, а остальной текст абзаца не изменил оформления.
Отдельно: токен, разбитый Word'ом на два `<w:r>` (частый случай после ручной правки текста в
Word) — раскрывается корректно, одним значением. Отдельно: токен в колонтитуле — раскрывается.
Отдельно: файл с таблицей, картинкой и нумерованным списком — после `rewrite` открывается без
предупреждений «файл повреждён», таблица/картинка/нумерация на месте.

## Блок 11 — Адаптер Excel (`xlsx_rewriter.py`)

**Вход:** путь к `.xlsx`, `resolve`. **Выход:** новый `.xlsx` + unresolved.

```python
def rewrite(src_path: str, dst_path: str, resolve: Resolver) -> list[str]: ...
```

Самый неочевидный из трёх адаптеров — **прочитать требования целиком до начала кода.**

**Требования:**
- Всё общее — из `ooxml_core`, как в блоках 9–10.
- **Где в xlsx лежит текст (главное отличие от docx/pptx).** Строковое значение ячейки, как
  правило, **не хранится в самой ячейке**. В `xl/worksheets/sheet*.xml` ячейка выглядит как
  `<c r="B2" t="s" s="3"><v>17</v></c>`, где `t="s"` означает «строка», а `17` — это **индекс в
  общей таблице строк** `xl/sharedStrings.xml`. Сам текст лежит там, в `<si>`-записи под этим
  индексом. Поэтому:
  - **Основная обрабатываемая часть — `xl/sharedStrings.xml`**, и именно в ней происходит
    подавляющее большинство замен.
  - **Группа = одна запись `<si>`.** Внутри `<si>` возможны два вида содержимого: простой
    (`<si><t>текст</t></si>`) и rich text (`<si><r><rPr>…</rPr><t>кусок</t></r><r>…</r></si>` —
    несколько прогонов с разным оформлением внутри одной ячейки). Текстовые units — все `<t>`
    внутри данной `<si>`, в порядке следования; для rich text это в точности та же схема, что
    в docx, и токен, разорванный между `<r>`, собирается тем же ядром.
- **Дополнительно обрабатывать inline-строки:** `<is>` внутри `<c t="inlineStr">` в
  `xl/worksheets/sheet*.xml` (некоторые генераторы пишут именно так, минуя sharedStrings).
  Группа — одна `<is>`, units — `<t>` внутри неё.
- **Что НЕ трогать в xlsx (запрещено явно):**
  - `<f>` — формулы. Токен внутри формулы не заменяется; если токен встретился в тексте
    формулы, он **не** идёт даже в unresolved (мы туда не смотрим). Зафиксировать как известное
    ограничение.
  - `<v>` внутри ячейки — это либо число, либо индекс sharedStrings. **Никогда не писать туда
    текст** и не менять `t`-атрибут ячейки.
  - Атрибут `s` у `<c>` (индекс стиля ячейки), `xl/styles.xml`, ширины колонок, условное
    форматирование, диаграммы. Именно потому, что мы их не касаемся, стиль ячейки (шрифт,
    цвет, заливка, формат числа) сохраняется автоматически.
- **Сохранение типа ячейки.** После замены токен-строка остаётся строкой, даже если её значение
  выглядит как число (например `[INN_1]` → `7701234567`). **Конвертировать ячейку в числовую
  запрещено** — ИНН, счёт, телефон и не должны быть числами (Excel съест ведущие нули и
  переведёт длинные номера в экспоненциальную запись, испортив данные). Мы просто не меняем ни
  `t`, ни `s`. Зафиксировать это в HANDOFF как **осознанное решение**, а не как недоработку.
- **Общие строки — один `<si>` может использоваться многими ячейками.** Это ожидаемо и
  корректно: одинаковый токен → одинаковое значение во всех ячейках, где он стоял. Специально
  «расшаривать»/дублировать `<si>` не нужно.
- **Атрибуты `count` / `uniqueCount`** у корневого `<sst>` в sharedStrings — **не пересчитывать
  и не изменять**: число записей мы не меняем, только их содержимое.
- unresolved — в порядке появления: сначала по `sharedStrings.xml` (в порядке `<si>`), затем по
  листам.

**Зависимости:** `ooxml_core`, `lxml`. `openpyxl` — **запрещён** (пересобирает книгу и теряет
часть разметки — диаграммы, сводные таблицы, условное форматирование).

**Приёмка:** `.xlsx`, где в ячейке B2 со стилем «жёлтая заливка, полужирный, 14 кегль» стоит
`[ORG_1]`, а в C2 — `[INN_1]`; после `rewrite` значения раскрыты, **заливка/шрифт/кегль ячеек
не изменились**, ИНН остался текстом и не превратился в `7,7E+09`. Отдельно: тот же токен в
двух разных ячейках — раскрыт в обеих. Отдельно: книга с формулой и диаграммой — после
`rewrite` открывается без предупреждений, формула и диаграмма на месте. Отдельно: ячейка с rich
text, где токен разорван между двумя `<r>` — раскрывается корректно.

## Блок 12 — Фасад и CLI (`file_detokenizer.py` + аддитивная правка `shifrator.py`)

**Вход:** путь к файлу, `session_id`. **Выход:** путь к созданному файлу + unresolved.

```python
def detokenize_file(
    src_path: str,
    session_id: str,
    dst_path: str | None = None,
    storage_dir: str | None = None,
) -> tuple[str, list[str]]: ...
```

**Требования:**
- **Перед стартом блока в чат должны быть загружены HANDOFF_8, HANDOFF_9, HANDOFF_10,
  HANDOFF_11** — блок не содержит своей логики разбора форматов и целиком зависит от их
  сигнатур.
- Определение формата — **по расширению** `src_path` в нижнем регистре:
  `.docx` → `docx_rewriter.rewrite`, `.pptx` → `pptx_rewriter.rewrite`, `.xlsx` →
  `xlsx_rewriter.rewrite`. Иное расширение →
  `ValueError(f"Неподдерживаемый формат: {ext}. Поддерживаются: .docx, .xlsx, .pptx")`.

  не пытаться его обработать и не притворяться, что получилось).
- **Построение `resolve`.** Через `session_store.load_session(session_id, storage_dir)` (блок 5,
  импортируется как есть, **не модифицируется**). Из полученного dict взять `session["entities"]`
  и построить словарь `{token: original_text}`. `resolve = lambda tok: mapping.get(tok)`.

  наверх (тот же контракт, что у блока 6: отличать «сессия истекла» от «в файле нет токенов»
  должен вызывающий).
- **Куда пишем.** Если `dst_path` не задан — сформировать его рядом с исходным файлом, добавив
  суффикс `_restored` перед расширением (`отчёт.docx` → `отчёт_restored.docx`). Если
  `dst_path` совпадает с `src_path` (после `os.path.realpath`) — `ValueError`, перезаписывать
  вход запрещено. Если файл `dst_path` уже существует — `FileExistsError` (молча затирать чужой
  файл нельзя).
- **Дедупликация unresolved.** Адаптеры возвращают токены с повторами; фасад возвращает
  **уникальные, в порядке первого появления** — ровно тот же контракт, что у блока 6.
- Отсутствующий `src_path` → стандартный `FileNotFoundError`. Битый/не-OOXML файл приходит из
  ядра как `OoxmlError` (блок 8) и **пробрасывается наверх как есть** — CLI переводит его в
  понятное сообщение.
- Модуль **не импортирует** `ner_detector`, `extractor`, `tokenizer` — детокенизация файла не
  нуждается ни в NER, ни в детекторах. Импорт `file_detokenizer` обязан быть мгновенным.

**Аддитивная правка `shifrator.py` — точные границы (единственное разрешённое изменение
существующего кода во всём компоненте):**
- Добавить **одну новую подкоманду**, не меняя ни одной существующей:
```
python shifrator.py decrypt-file <session_id> <путь_к_файлу.docx|.xlsx|.pptx> [--out <путь>]
    → создаёт файл с раскрытыми токенами
    → печатает в stdout путь к созданному файлу (одна строка)
    → если есть unresolved токены — печатает предупреждение со списком в stderr
```

- `decrypt-file` **не** вызывает `purge_expired` (в отличие от `decrypt`) — чтобы не менять

- Импорт `file_detokenizer` в `shifrator.py` делать **лениво, внутри ветки подкоманды**, а не на
  верхнем уровне модуля — как и остальные тяжёлые импорты (это соглашение уже действует в блоке

**Зависимости:** `ooxml_core`, три адаптера, `session_store` (существующий, не менять).

**Приёмка (сквозная, ручная — главная приёмка всего компонента):**

   правок тестов**. Это формальное подтверждение, что компонент 2 ничего не сломал в блоках 1–7.

## Сводка того, что осознанно НЕ делается в этом компоненте

Фиксируется здесь, чтобы ни один блок не «дорисовал» это по своей инициативе:

- **PDF** — отложен (нет способа заменить текст на месте без потери верстки; решение по подходу
  не принято).
- **`encrypt` для `.xlsx`/`.pptx`** — вне компонента; вход шифровки остаётся `.docx`/`.txt`.
- **Искажённые LLM токены** (`[org_1]`, `ORG_1`, `[ORG 1]`) — не распознаются, как и в блоке 6
  (то же известное ограничение, тот же regex).
- **Мастера и макеты pptx, формулы xlsx, удалённый текст рецензирования docx** — не
  обрабатываются (см. соответствующие блоки).
- **Веб-интерфейс** (Компонент 1) — отдельный документ; блоки 8–12 обязаны быть пригодны для
  вызова из веб-слоя, но сами про него ничего не знают и никаких HTTP-зависимостей не тянут.

## Шаблон HANDOFF_<N>.md

Используется **тот же шаблон**, что в `SHIFRATOR_SPEC_AI.md` (раздел «Шаблон HANDOFF_<N>.md»),
без изменений. Дополнительно к нему, в разделе «Известные ограничения / TODO» каждый блок 8–11
обязан явно ответить на вопрос: **«какие элементы оформления/разметки этого формата мой блок
гарантированно не портит, и какие он в принципе не видит»** — это то, чем будет пользоваться
блок 12 при формулировке ограничений для пользователя.
