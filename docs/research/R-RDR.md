## 2. Дерево правил на живом остатке (часть 1)

Взят **самый крупный класс** — «не найдено вовсе», внутри него самая крупная
причина, вёрстка. На срезе (33 док., 1 283 эталонных сущности) это
137 «не найдено» + 47 «чужой тип» = **184 сущности без маски своего типа**;
внутри «не найдено» вёрстка даёт 73 случая (перенос строки 49, разрыв
ячейки 24) — на них дерево и строилось.

**Устройство слоя.** Слой работает ПОВЕРХ конвейера и трогает только те куски
текста, где конвейер маски своего типа не поставил. Генератор кандидатов —
метка-якорь договора («код подразделения», «Тел.:», «БИК», «ИНН», «р/с»,
«E-mail», «Дата рождения», «Контакт», «Ответственное лицо», …) и окно 46
символов после неё; перевод строки внутри окна кандидата не разрывает — в этом
вся суть класса. Дерево: корневое правило на якорь + исключения под ним.

### Четыре числа

| | |
|---|---|
| **закрыто случаев** | **63** из 184 непокрытых на срезе (34.2 %), все — целиком, ни одного частично |
| **правил понадобилось** | **17** (13 корневых + 4 исключения) |
| **зафиксирована ли регрессия** | **ДА, одна** — и это главный результат части 1 (ниже) |
| **трудоёмкость на правило** | ≈ 2 мин на корневое правило, ≈ 2.5 мин на исключение (13 правил ≈ 25 мин, 4 исключения ≈ 10 мин, замер отдельно) |

Новых спанов слой ставит 64: PASSPORT 27, PER 9, INN 9, PHONE 8, BIK 5,
ACCOUNT 2, KPP 2, BIRTHDATE 1, INN_PER 1.

### Регрессия проверена ПРОГОНОМ, а не рассуждением

Прогон по всем 33 документам среза, четыре независимые линии
(`experiments/research/rdr/run_rdr.py`):

| линия | до исключений | после исключений |
|---|---:|---:|
| маска на типизированном негативе | 0 | 0 |
| маска мимо любого эталона (порча прозы) | 0 | 0 |
| маска ЧУЖОГО типа на эталоне | 0 | **1** |
| сдвиг уже верной сущности | 0 | 0 |
| закрыто случаев | 64 | 63 |

Единственная регрессия: `loan_0006__m2718_homoglyph`, фрагмент `9О64\t108О98` —
эталон `INN_PER`, слой поставил `INN`.

**Что это значит для метода.** Обещание «регрессия невозможна по построению»
выполняется ТОЛЬКО пока новое правило — лист под тем правилом, которое
ошиблось. Три исключения из четырёх (E2 ОГРНИП-15, E3 точка в дате, E4
кириллица в домене) — настоящие листья, и они не стоили ни одной регрессии.
Четвёртое (E1 «буква считается омоглифом цифры только рядом с цифрой») я
поставил не листом, а правкой общего числового сканера — и оно немедленно
сломало ранее верный случай и отняло 4 закрытых PASSPORT, вернув 3 других типа.
Итог правки: закрытых 64 → 63, регрессий 0 → 1. **Свойство метода держится не
на методе, а на дисциплине «правило кладётся листом и никогда — в общий код».**
Формально это значит: реализация обязана механически запрещать правку общих
предикатов и обязана перепроверять опорные случаи ветки — иначе гарантия
превращается в лозунг.

Оговорка о полноте: 34 % — это доля на срезе и по классу с метками-якорями.
Класс «значение без якоря вообще» (например ФИО в подписи в отдельной строке)
дерево не берёт: у него нет генератора кандидатов. Молча это не потеряно —
сказано здесь.

## 3. Интерфейс для юриста — прикидка (часть 2)

Смысл метода в том, что правило добавляет предметный человек. Экран — часть
уже существующего интерфейса (`app/`, `127.0.0.1`), отдельного приложения не
нужно.

**Точка входа — экран проверки, который уже есть.** Юрист видит зашифрованный
текст с подсветкой масок. Он замечает пропуск: «здесь номер паспорта остался
открытым». Выделяет мышью это место и нажимает «научить».

**Что видит.** Всплывает карточка из трёх частей:
1. **Случай** — строка документа с выделенным значением и ~40 символами слева и
   справа. Это и есть опорный случай, он сохранится вместе с правилом.
2. **Что программа думает сейчас** — «здесь ничего» или «здесь ИНН». То есть
   ветка дерева, под которую ляжет новое правило, названа словами.
3. **Вопрос** — «Что это на самом деле?» Список типов из набора юриста
   (не свободный ввод: тип обязан существовать).

**Что вводит.** Ровно две вещи, обе выбором, не текстом:
- **тип** — из списка;
- **по какой примете узнавать** — программа сама предлагает 3–5 готовых примет,
  вычисленных из выделения: «сразу после слов "код подразделения"», «в той же
  ячейке, что слово "Счёт"», «шесть цифр подряд, перенос строки внутри
  не мешает», «после двоеточия до конца строки». Юрист отмечает одну или две.
  Свободного регулярного выражения нет и не будет: правило, которое человек не
  может прочесть вслух, нельзя проверить.

**Как проверяется — ДО сохранения.** Кнопка «Проверить» гоняет правило по
опорным случаям своей ветки и по загруженному документу и показывает три
цифры, всегда в этом порядке:

```
Закроет нового:      7 мест
Сломает уже верного: 0 мест     ← если не ноль, кнопка «Сохранить» закрыта
Тронет лишнего:      2 места    ← с показом самих мест, списком
```

Строка «сломает уже верного» — прямое следствие §2: без неё гарантия метода
существует только на бумаге. Ноль в ней — условие сохранения, а не пожелание.
«Тронет лишнего» блокировкой не является, но требует нажать «вижу».

**Что показывается перед сохранением.** Правило одной фразой человеческим
языком — «Шесть цифр сразу после слов "код подразделения" — это номер
паспорта», под ней опорный случай и список мест, которые изменятся, с
«было → стало» построчно. Кнопки: «Сохранить», «Изменить примету», «Отмена».

**После сохранения.** Правило уходит в файл правил юриста (отдельный от
`entity_types.yaml`, чтобы обновление программы его не затирало), в списке
правил у каждого — автор, дата, опорный случай и кнопка «выключить» (не
«удалить»: выключенное правило остаётся видимым, как и всё в этом проекте).

**Чего в интерфейсе нет намеренно:** свободного регекса, правки чужих правил,
удаления правил, изменения порядка ветвей вручную.

## 4. Вердикт по морфологии (часть 3): НЕТ, в приоритет не поднимать

Ответ числом. Измерено на ЧИСТОМ тексте (метки приёма нет, значит вёрстка,
регистр и омоглифы исключены; падеж определён по первому склоняемому слову,
сомнение всегда трактовалось в пользу именительного, то есть вклад морфологии
скорее завышен, чем занижен):

| тип | падеж | N | ошибок | доля |
|---|---|---:|---:|---:|
| PER | именительный | 1 210 | 271 | **22.4 %** |
| PER | косвенный | 225 | 19 | **8.4 %** |
| ORG | именительный | 178 | 8 | 4.5 % |
| ORG | косвенный | 2 | 0 | 0 % |
| ADDRESS | именительный | 455 | 0 | 0 % |
| ADDRESS | косвенный | 34 | 0 | 0 % |

Избыток ошибок у косвенных над именительным: PER **−31**, ORG −0, ADDRESS +0.
**Итого 0 сущностей из 3 505 остатка — 0.0 %.**

У косвенных падежей ошибок не больше, а **втрое меньше**, чем у именительных.
Механизм понятен и уже описан этапом B: косвенный падеж стоит при управляющем
слове («в лице», «Уведомления направляются <кому>»), то есть при якоре, а
именительный часто стоит голым в подписи или в ячейке — там ломается не
морфология, а поиск якоря. Крупнейшие поимённые случаи именительного —
«Беляев Олег Олегович», «Петрова Ольга Ивановна», «Петров Консалтинг» — это
класс «нет якоря», ровно тот, что берёт дерево правил из §2.

Отдельная техническая находка, важная для решения: **прямой `pymorphy2` 0.9.1
на Python 3.11 этого venv не поднимается вовсе** — `MorphAnalyzer()` падает на
`inspect.getargspec` (удалён в 3.11). Тот же словарь доступен через уже
установленную `natasha.MorphVocab` (она отдаёт `OpencorporaTag`), и мерил я им.
То есть даже «лёгкий вариант поверх pymorphy2» — не бесплатная надстройка:
он либо тянет починку зависимости, либо ходит через natasha.

**Вердикт:** контекстное разрешение морфологической неоднозначности не даёт
измеримого выигрыша (0 из 3 505). Приоритет — вёрстка (1 367, 39 %) и класс
«значение без якоря» внутри «не найдено» (940, 26.8 %).
