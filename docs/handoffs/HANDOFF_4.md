## Что сделано
Реализован `tokenizer.py` с публичными функциями `tokenize(doc, entities, config_path)` и
`build_plain_text(doc)`. `tokenize` разрешает пересечения Entity внутри каждого сегмента по
полному алгоритму ТЗ (regex > ner; далее длина, приоритет типа, confidence, лексикографический
tie-break без участия `id`), присваивает переиспользуемые токены `[TYPE_N]` (TYPE = `token_prefix`
из конфига, сквозная нумерация по префиксу, порядок появления = `(индекс сегмента, start)`) и
собирает анонимизированный текст одним проходом по `segments` с сохранением позиции таблиц.
`build_plain_text` — та же сборка без подстановки токенов (эталон для блока 7). dataclass'ы
импортируются из `models.py`, не переопределены.

**B3-fix (сущности на границе сегментов).** Перед разрешением пересечений `tokenize` делает
дополнительный проход `_detect_boundary_entities`: по каждой паре соседних непустых сегментов
строит граничное окно `хвост(≤60) + разделитель + голова(≤60)` и повторно гоняет по нему **те же**
публичные `detect_regex`/`detect_ner`, оставляя только сущности, реально пересекающие точку стыка,
и деля их на пару `Entity_A`/`Entity_B` в исходных сегментах. Пара связывается внутренним реестром
`boundary_partner` (id↔id) и получает **общий токен**, если обе половины пережили разрешение
пересечений. Публичная сигнатура `tokenize()` и `models.Entity` не менялись.

## Публичный интерфейс
```python
from tokenizer import tokenize, build_plain_text

# tokenize: SourceDocument + объединённый list[Entity] (блоки 2+3) + путь к конфигу
def tokenize(doc: SourceDocument, entities: list[Entity], config_path: str) -> tuple[str, list[Entity]]: ...
def build_plain_text(doc: SourceDocument) -> str: ...
```

Минимальный пример:
```python
from extractor import extract
from regex_detector import detect_regex
from ner_detector import detect_ner
from tokenizer import tokenize, build_plain_text

doc = extract("contract.docx")
entities = detect_regex(doc, "entity_types.yaml") + detect_ner(doc, "entity_types.yaml")
anon_text, final_entities = tokenize(doc, entities, "entity_types.yaml")
# anon_text -> str с [ORG_1]/[INN_1]/...; final_entities -> list[Entity] с непустым .token
plain = build_plain_text(doc)   # тот же текст без токенов, для сверки в блоке 7
```

Исключения:
- `FileNotFoundError` (стандартный) — если `config_path` не существует (кидает `open`).
- `KeyError` — если во входном Entity `entity_type` отсутствует в `entity_types.yaml`
  (нет `token_prefix`); это нарушение предусловия (детекторы читают тот же конфиг).
- `build_plain_text` исключений при корректном `SourceDocument` не кидает.

## Формат данных на выходе
`tokenize` возвращает кортеж из двух элементов.

1) Анонимизированный текст (`str`), пример:
```
Договор с [ORG_1], ИНН [INN_1].
Сторона [ORG_1] подтверждает.
```

2) `list[Entity]` — только пережившие разрешение пересечений, каждый с заполненным `token`:
```python
[
  Entity(id="…", segment_id="p0", start=11, end=24, original_text="ООО «Ромашка»",
         entity_type="ORG", detector="ner", confidence=1.0, token="[ORG_1]"),
  Entity(id="…", segment_id="p0", start=30, end=40, original_text="7707083893",
         entity_type="INN", detector="regex", confidence=1.0, token="[INN_1]"),
  Entity(id="…", segment_id="p1", start=8,  end=21, original_text="ООО «Ромашка»",
         entity_type="ORG", detector="ner", confidence=1.0, token="[ORG_1]"),
]
```

## Инварианты выходных данных
- `all(e.token for e in result)` — у **каждого** возвращённого Entity `token` — непустая строка
  вида `[TYPE_N]`. Проигравшие при разрешении пересечений в список **не** попадают (не с `token=None`).
- Список **отсортирован** по ключу `(индекс сегмента в doc.segments, start)` — тем же, что для
  нумерации токенов. Блок 5 может опираться на этот порядок для выбора «первого по вхождению».
- Токен переиспользуется тогда и только тогда, когда совпадают `entity_type` **и** `original_text`
  посимвольно (без нормализации). Один токен ⇒ ровно один вариант `original_text`.
- Нумерация `N` сквозная по `token_prefix` (не по `entity_type`), с 1.
- Внутри любого сегмента у результата нет двух Entity с пересекающимися интервалами `[start, end)`.
- В анонимизированном тексте: верхнеуровневые единицы разделены ровно одним `"\n"`, без хвостового
  `"\n"`; ячейки строки таблицы — через `" | "`, строки таблицы — через `"\n"`; таблица стоит на
  месте своего первого сегмента. Внутренние `"\n"` текста ячейки заменены на пробел.

## Что блок ожидает на входе (предусловия)
Не проверяются; нарушение ⇒ тихая порча текста (не исключение), кроме отмеченного:
- для каждого Entity `segment_id` присутствует среди `doc.segments` — иначе Entity молча
  выпадает из обработки и из результата (его сегмент не итерируется);
- `0 <= start < end <= len(segment.text)` и `original_text == segment.text[start:end]`;
- `token is None` на входе (перезаписывается);
- `entity_type` каждого Entity присутствует в `entity_types.yaml` c `token_prefix` — **иначе
  `KeyError`** (единственное нарушение, дающее исключение);
- сегменты таблицы (`docx_table_cell`) идут подряд и содержат ключи `table_index`, `row_index`,
  `col_index` в `metadata` (гарантирует блок 1).

## Использованные поля конфига
Читает `entity_types.yaml` и берёт только `token_prefix` для каждого `entity_type` (для
формирования токена). Все прочие поля (`method`, `pattern`, `ner_label`, `ner_extractor`,
`validate`, `enabled`) игнорируются — фильтрация типов и `enabled` уже выполнена детекторами.
Если у типа нет `token_prefix`, он в карту префиксов не попадает и обращение к нему даст `KeyError`
(см. предусловия). Блок файлом `entity_types.yaml` не владеет и его не создаёт.

## Побочные эффекты импорта
`import tokenizer` по-прежнему не загружает моделей, не создаёт директорий и не читает файлов —
только `import yaml`/`import uuid` и `from models import …`. Мгновенно, память незначительна.
**Важно (B3-fix):** `detect_regex`/`detect_ner` импортируются **лениво, внутри
`_detect_boundary_entities`**, поэтому `import tokenizer` natasha не тянет (юнит-тесты блока 4,
работающие с рукотворными Entity, natasha не грузят). Но при **вызове** `tokenize` на документе с
≥2 непустыми соседними сегментами natasha будет загружена (через `ner_detector`) — в реальном
пайплайне она к этому моменту уже загружена детектором блока 3.

## Известные ограничения / TODO
- Частичное пересечение короткого regex-спана с длинным NER-спаном (`PERSON`/`ADDRESS`) приводит к
  **полному** удалению проигравшего NER-entity (правило 1), и непокрытая победившим regex-спаном
  часть остаётся в открытом тексте. Усечение проигравшего спана вместо удаления — фаза 2, не MVP.
- Схлопывание вариантов написания одной сущности (регистр, кавычки, падежи) не выполняется —
  токен переиспользуется только при точном посимвольном совпадении `original_text` (осознанное
  ограничение MVP; см. блок 4 ТЗ).
- Нарушение предусловия `original_text == segment.text[start:end]` не проверяется и приведёт к
  тихой порче анонимизированного текста (токен подставится по `start/end`, но в блок 5 уйдёт
  рассогласованный `original_text`).
- **B3, разделитель граничного окна ≠ разделитель `build_plain_text`.** `" | "` между ячейками
  строки таблицы — **только** для читаемости итогового текста (в `build_plain_text`/сборке). При
  построении граничного окна детекции `" | "` **не** используется: он рвёт паттерны. Соседние
  ячейки одной строки одной таблицы склеиваются в окне **без разделителя** (`""`), прочие границы —
  `"\n"`. Не «выравнивать» это с `build_plain_text` — иначе ИНН/телефон между ячейками снова
  перестанут детектиться.
- **B3, «резкий» случай общего токена.** Половины разорванной сущности получают один токен, только
  если обе пережили разрешение пересечений. Если одна половина сама по себе — валидная сущность в
  своём сегменте (напр. `ООО`) и вытесняет граничную половину при разрешении, половины могут
  получить **разные** токены. Утечки при этом нет (обе части покрыты токенами); это осознанное
  ограничение, не дефект.
- **Производительность B3.** Доп. проход добавляет **один вызов `detect_ner` (natasha) на каждую
  пару соседних непустых сегментов**. На документах в сотни сегментов это заметно (NER доминирует);
  regex-часть дёшева. Пары с пустым сегментом пропускаются. Безопасный кандидат на оптимизацию (не
  внедрён, чтобы не жертвовать корректностью): пропускать `detect_ner` для окон без заглавных
  кириллических букв. Границу соседних ячеек одной строки таблицы пропускать **нельзя** — именно там
  реконструируются порванные реквизиты.

## Данные для тестов
1. **Переиспользование токена (приёмка).** Сегменты `p0="Договор с ООО «Ромашка», ИНН 7707083893."`,
   `p1="Сторона ООО «Ромашка» подтверждает."`; Entity: ORG(p0,11..24,"ООО «Ромашка»",ner),
   INN(p0,29..39,"7707083893",regex), ORG(p1,8..21,"ООО «Ромашка»",ner).
   Ожидается: обе ORG → `[ORG_1]`, ИНН → `[INN_1]`; в тексте нет оригиналов; `len(result)==3`,
   `all(e.token)`.
2. **KPP/BIK конфликт (граничный).** Один сегмент с `044525225` (9 знаков, начинается на «04»);
   Entity KPP(9..18) и BIK(9..18), обе regex, равная длина. Ожидается: в результате **один**
   Entity — `BIK` (BIK раньше KPP в списке приоритетов), в тексте ровно один токен `[BIK_1]`.
3. **Цепочка A-B-C, A∩B, B∩C, A∩C=∅ (граничный).** В одном сегменте: A=PERSON(0..6,ner),
   B=INN(4..12,regex), C=ORG(10..16,ner). Победитель — B (regex сильнее обоих ner), пересекается
   с A и с C → обе удаляются. Результат: только `INN`; в тексте один токен. (Если бы победителем
   был C, не пересекающийся с A, — A обязан выжить: проверено отдельным кейсом ADDRESS/ORG/PERSON.)
4. **Сборка таблицы (build_plain_text).** Параграф «Заголовок»; таблица 2×2 (r0: «A1»,«B1\nB2»;
   r1: «C1»,«D1»); параграф «Хвост». Ожидается ровно:
   `"Заголовок\nA1 | B1 B2\nC1 | D1\nХвост"` (внутренний `\n` ячейки заменён пробелом, таблица на
   своём месте, без хвостового `\n`).
5. **Сущности на границе сегментов (B3).** Полные тесты — в `tests/test_boundary_entities.py`
   (через полный `tokenize`). Ключевые кейсы: телефон `+7 (495)` / `123-45-67` в двух соседних
   `txt_line` → обе половины → **один** `[PHONE_1]` (не `_1`/`_2`); ИНН `770708` / `3893` в двух
   соседних ячейках строки таблицы → обе ячейки → `[INN_1]` (окно склеивает ячейки **без**
   разделителя); организация `ООО` / `Ромашка` в двух `docx_paragraph` → `Ромашка` больше не
   утекает; телефон целиком внутри одного сегмента → ровно один токен, окно дубликат не создаёт;
   обычный текст на стыке → ни одной ложной сущности. Репродукции B3 из BREAKING_REPORT
   (`tests/test_breaking_leaks.py::TestEntitySplitAcrossSegmentBoundary`) после фикса переведены из
   `xfail(strict)` в обычные проходящие тесты, а pin по организации перевёрнут (`"Ромашка" not in`).
