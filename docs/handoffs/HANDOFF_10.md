# HANDOFF — Блок 10: Адаптер PowerPoint (`pptx_rewriter.py`)

## Что сделано
Реализован адаптер `.pptx` для Компонента 2 — единственная публичная функция
`rewrite(src_path, dst_path, resolve)`. Модуль сам не ищет и не заменяет токены:
он определяет, какие части архива открыть (`ppt/slides/slide*.xml`,
`ppt/notesSlides/notesSlide*.xml`), строит по одной `RunGroup` на каждый `<a:p>`
(units — все `<a:t>` абзаца в порядке следования, `<a:br>` — псевдо-разделитель),
и вызывает `ooxml_core.replace_tokens_in_group` для каждой группы. Обход `root.iter(a:p)`
естественным образом покрывает `<a:txBody>` любой фигуры, включая фигуры внутри таблиц
(`<a:tbl>`) и внутри групп фигур — это то же дерево, отдельной логики для них не
потребовалось. Мастера и макеты (`slideMasters`, `slideLayouts`) в маску не входят и не
обрабатываются. Вся замена, включая токены, разорванные между `<a:r>`, и стиль
вставленного значения — целиком в ядре (блок 8). Проверено эмпирически на синтетическом
`.pptx`, собранном вручную через `zipfile` (`python-pptx` не установлен в окружении и не
является зависимостью блока): заголовок с нетривиальным оформлением (`sz="4400"`,
`b="1"`, `<a:solidFill><a:srgbClr val="FF0000"/>`), токен в теле, токен, разорванный между
двумя `<a:r>` внутри ячейки таблицы, токен в заметках докладчика, неизвестный токен,
`<a:br>` как псевдо-разделитель.

## Публичный интерфейс
```python
from pptx_rewriter import rewrite

def rewrite(src_path: str, dst_path: str, resolve: Resolver) -> list[str]: ...
```
`Resolver` — тот же тип, что в блоке 8 (`Callable[[str], str | None]`), отдельно не
переопределяется, импортируется из `ooxml_core`.

Минимальный пример вызова:
```python
from pptx_rewriter import rewrite

mapping = {"[ORG_1]": "ООО «Ромашка»", "[INN_1]": "7701234567"}
unresolved = rewrite("ответ.pptx", "ответ_restored.pptx", lambda tok: mapping.get(tok))
# ответ_restored.pptx создан на диске; unresolved -> [] (если все токены известны)
```

Исключения:
- `OoxmlError` (`ooxml_core`) — если `src_path` не ZIP/повреждён/zip-бомба. Пробрасывается
  из `read_zip_parts` без изменений.
- `FileNotFoundError` — если `src_path` не существует. Пробрасывается из `read_zip_parts`
  без изменений (стандартное исключение Python, не оборачивается).
- `lxml.etree.XMLSyntaxError` — если одна из целевых частей архива не well-formed XML
  (не ожидается для настоящих OOXML-файлов, но не перехватывается и не маскируется).
- Исключения из переданного `resolve`, если он их бросает, — не перехватываются, часть
  документа может остаться частично обработанной (тот же контракт, что у
  `replace_tokens_in_group` в блоке 8).

## Формат данных на выходе
`rewrite(...)` возвращает `list[str]`, например `["[ORG_99]"]` или `[]`. Побочный эффект —
файл `dst_path` создан на диске (тот же набор записей архива, что в `src_path`, тот же
порядок, `compress_type`/`date_time` сохранены для не тронутых блоком 10 частей).

## Инварианты выходных данных
- unresolved — **в порядке первого появления в документе**, с возможными повторами
  (дедупликацию делает блок 12). Порядок обхода частей: сначала `ppt/slides/slide*.xml`
  по возрастанию числового номера в имени (`slide2.xml` перед `slide10.xml` — сравнение
  числом, а не строкой), затем `ppt/notesSlides/notesSlide*.xml` по тому же правилу.
  Внутри части — порядок `<a:p>` в дереве (document order), внутри абзаца — порядок
  `<a:t>`/`<a:br>` в поддереве абзаца.
- Части архива, не входящие в маску (`ppt/slideMasters/*`, `ppt/slideLayouts/*`,
  `ppt/theme/*`, `[Content_Types].xml`, `docProps/*` и т.п.) — байт-в-байт идентичны
  исходным (проверено: `ppt/theme/theme1.xml` и `ppt/slideMasters/slideMaster1.xml`
  совпадают побайтово до и после `rewrite`).
- Части, входящие в маску, но отсутствующие в конкретном архиве (нет заметок докладчика) —
  просто пропускаются, не создаются с нуля.
- Оформление (`<a:rPr>`, `<a:solidFill>`, любые атрибуты кроме текста `<a:t>` и, при
  необходимости, `xml:space`) не читается и не изменяется — гарантия ядра (блок 8),
  адаптер сам оформление не трогает вовсе.
- Токен не может «перепрыгнуть» границу абзаца: `RunGroup` строится на уровне `<a:p>`,
  соседние абзацы никогда не склеиваются в одну группу.

## Что блок ожидает на входе (предусловия)
- `src_path` — путь к файлу, который **является** OOXML-контейнером (проверяет и об этом
  сигнализирует `OoxmlError` ядро, блок 10 сам не проверяет расширение — этим занимается
  блок 12).
- Внутри целевых частей архива структура — валидный PresentationML/DrawingML: `<a:t>`
  содержит текст в `.text` (может быть `None`, тогда трактуется как `""`), `<a:p>` не
  вложены друг в друга. Если структура нарушена нестандартным генератором — поведение не
  определено (не тестировалось за пределами того, что производит PowerPoint/python-pptx).
- `resolve` — чистая функция без побочных эффектов, вызывается многократно и в порядке
  появления токенов слева направо, отдельно для каждой группы.

## Использованные поля конфига

## Побочные эффекты импорта
`import pptx_rewriter` не загружает моделей, не создаёт директорий, не читает файлов.
Время импорта — `~0.10 c` (целиком за счёт `from ooxml_core import ... from lxml import
etree`, собственных тяжёлых импортов у блока 10 нет). Проверено: после импорта `natasha`,
`ner_detector` и `python-pptx` (`pptx`) **не** в `sys.modules`.

## Зависимости и окружение
- Python: `Python 3.11.9` (`venv/Scripts/python.exe --version`).
- Внешние зависимости: только то, что тянет `ooxml_core` (`lxml 6.1.1`) — блок 10 сам
  новых зависимостей не добавляет. Стандартная библиотека: `fnmatch`, `re`.
- **Запрещённые библиотеки не используются:** `python-pptx` в окружении не установлен и
  нигде не импортируется; тестовый `.pptx` для проверки собран вручную через `zipfile` —
  это разовый внешний скрипт (`scratch_test_block10.py`), не часть модуля и не его
  зависимость.

## Соглашения о путях и файлах времени выполнения
Блок не владеет постоянными путями. Пишет ровно один файл — `dst_path`, через
`ooxml_core.rewrite_zip` (временный файл создаётся и публикуется этой функцией, см.
HANDOFF_8). Никаких других файлов и директорий не создаёт.

## Отклонения от спецификации
Отклонений нет. Уточнение реализации: числовой (не строковый) порядок сортировки имён
`slide*.xml`/`notesSlide*.xml` — спецификация требует «слайд за слайдом, по порядку
частей», что при строковой сортировке ломается на презентациях от 10 слайдов
(`slide10.xml` встал бы перед `slide2.xml`); реализовано сравнение по извлечённому из
имени числу, чтобы гарантировать документный порядок независимо от числа слайдов
(релевантно для целевого объёма «200 страниц» из бюджета ресурсов базовой спеки).

## Известные ограничения / TODO
**Ответ на обязательный вопрос компонента — что мой блок гарантированно не портит и
чего он в принципе не видит:**
- **Гарантированно не портит:** любые узлы/атрибуты оформления во всех обработанных
  частях (`<a:rPr>`, `<a:pPr>`, `<a:solidFill>`, шрифты, размеры, цвета); части архива вне
  маски (`slideMasters`, `slideLayouts`, `theme`, изображения, `docProps`, `customXml`,
  `[Content_Types].xml`) — байт-в-байт; структуру таблиц (`<a:tbl>`) и групп фигур — узлы
  не удаляются и не перемещаются, меняется только `.text` у `<a:t>`.
- **В принципе не видит:** текст в мастерах и макетах слайдов (осознанно вне маски —
  там шаблонные плейсхолдеры, а не пользовательский текст); искажённые LLM токены
  (`[org_1]`, `ORG_1`, `[ORG 1]`) — не распознаёт, это `TOKEN_RE` ядра (то же ограничение,
  что у блока 6); текст внутри встроенных OLE-объектов и диаграмм (`ppt/charts/*`,
  `ppt/embeddings/*`) — вне описанных частей архива, не анализируется.
- **Осознанное ограничение:** мастера и макеты (`slideMasters`, `slideLayouts`) не
  обрабатываются согласно спецификации блока 10 — если пользовательский токен по ошибке
  окажется там (нетипичный случай), он не будет раскрыт.

## Данные для тестов
Реально проверенные сценарии (`venv/Scripts/python.exe`, синтетический `.pptx`, собранный
вручную для проверки через `scratch_test_block10.py`, т.к. `python-pptx` в окружении нет):

1. **Форматированный заголовок.** `[ORG_1]` внутри `<a:r>` с `sz="4400"`, `b="1"`,
   `<a:solidFill><a:srgbClr val="FF0000"/></a:solidFill>`. После `rewrite` с
   `resolve("[ORG_1]") -> "ООО «Ромашка»"` — текст стал «ООО «Ромашка»», `sz`/`b`/цвет не
   изменились.
2. **Токен в теле.** `"INN: [INN_1]"` → после `rewrite`
   (`resolve("[INN_1]") -> "7701234567"`) — `"INN: 7701234567"`.
3. **Токен, разорванный на два `<a:r>` внутри ячейки таблицы (граничный).** Ячейка
   `<a:tbl>/<a:tr>/<a:tc>`: runs `"[PHONE"`, `"_1] cell"` → после `rewrite`
   (`resolve("[PHONE_1]") -> "+7 495 123-45-67"`) — первый run стал
   `"+7 495 123-45-67"`, второй — `" cell"` (с `xml:space="preserve"` из-за ведущего
   пробела); значение целиком в run'е, где токен начинался.
4. **`<a:br>` как псевдо-разделитель (граничный).** Абзац: run `"Line1"` + `<a:br/>` +
   run `"Line2"` — не участвуют в склейке токена, оба run'а не изменились (в тексте
   токенов не было; проверено, что `<a:br>` корректно строит псевдо-unit и не ломает
   обход).
5. **Токен в заметках к слайду.** `"Заметка: [ORG_1]"` в `ppt/notesSlides/notesSlide1.xml`
   → после `rewrite` — `"Заметка: ООО «Ромашка»"`.
6. **Неизвестный токен (граничный).** `"Unknown: [ORG_99] here"`, `resolve` не знает
   `[ORG_99]` → текст не изменился ни в одном символе, `unresolved == ["[ORG_99]"]`.
7. **Мастер/макет не тронуты (граничный).** `ppt/slideMasters/slideMaster1.xml` и
   `ppt/theme/theme1.xml` — байт-в-байт идентичны до и после `rewrite` (не входят в маску).
8. **Числовой порядок частей (граничный).** `_part_sort_key` на списке
   `["ppt/slides/slide10.xml", "ppt/slides/slide2.xml", "ppt/slides/slide1.xml",
   "ppt/notesSlides/notesSlide2.xml", "ppt/notesSlides/notesSlide10.xml"]` даёт порядок
   `slide1 → slide2 → slide10 → notesSlide2 → notesSlide10` (слайды по номеру, затем
   заметки по номеру).
9. **Округлостность архива.** `zipfile.testzip()` выходного файла -> `None`;
   `namelist()` входа и выхода совпадают.
