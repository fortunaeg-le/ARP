# HANDOFF — Блок 2: Regex-детектор структурных сущностей

## Что сделано
Создан `regex_detector.py` с публичной функцией `detect_regex(doc, config_path)`. Функция читает `entity_types.yaml` по переданному пути, берёт записи с `method: regex` (кроме `enabled: false`), прогоняет каждый паттерн по тексту каждого сегмента и возвращает список `Entity` с точными смещениями внутри `segment.text`. Реализованы валидаторы `inn_checksum` (10 и 12 знаков, весовые коэффициенты ФНС) и `ogrn_checksum` (13 знаков — mod 11, 15 знаков ОГРНИП — mod 13), зарегистрированные в реестре `VALIDATORS`; совпадение включается в результат только при сошедшейся чек-сумме. Незнакомое значение `validate`, отсутствующий или некомпилируемый `pattern` — предупреждение в stderr и пропуск всего типа целиком, без тихого игнорирования.

## Публичный интерфейс

dataclass'ы импортируются из models.py, не переопределены.

```python
def detect_regex(doc: SourceDocument, config_path: str) -> list[Entity]
```
Импорт: `from regex_detector import detect_regex`

Пример:
```python
from extractor import extract
from regex_detector import detect_regex
doc = extract("contract.docx")
entities = detect_regex(doc, "entity_types.yaml")
# entities: list[Entity], у всех detector="regex", confidence=1.0, token=None
```

Исключения:
- `FileNotFoundError` (встроенное) — конфига нет по пути `config_path` (пробрасывается из `open()`, файл не генерируется на месте).
- `yaml.YAMLError` (модуль `yaml`, пакет PyYAML) — конфиг не является валидным YAML.
- `KeyError` (встроенное) — в конфиге нет верхнеуровневого ключа `entity_types`.

Дополнительно модуль экспортирует (используются только внутри блока, но доступны для тестов): `inn_checksum(value: str) -> bool`, `ogrn_checksum(value: str) -> bool`, реестр `VALIDATORS: dict[str, Callable[[str], bool]]`.

## Формат данных на выходе

Реальный вывод на сегменте `l0` с текстом `"ИНН 7707083893, КПП 773601001"`:
```python
[
    Entity(id="3f2b8c1e-9a44-4d7b-b1c0-5e8f2a6d9c11", segment_id="l0", start=4, end=14,
           original_text="7707083893", entity_type="INN", detector="regex",
           confidence=1.0, token=None),
    Entity(id="a81d4e02-6c3f-4b9a-8d25-1f7e0b3c4a90", segment_id="l0", start=20, end=29,
           original_text="773601001", entity_type="KPP", detector="regex",
           confidence=1.0, token=None),
]
```
(`id` — свежий uuid4 при каждом запуске, остальные поля детерминированы.)

## Инварианты выходных данных

- У каждого Entity: `detector == "regex"`, `confidence == 1.0`, `token is None`.
- `entity.original_text == segment.text[entity.start:entity.end]` — смещения символьные, внутри текста сегмента (не документа); `0 <= start < end <= len(segment.text)`.
- Границы — границы всего совпадения (`m.start()`/`m.end()`/`m.group(0)`), не capture-группы. Следствие: у `PASSPORT` слово-якорь входит в `original_text` (например `"паспорт серия 45 12 345678"` — один Entity).
- `entity_type` — всегда ключ из `entity_types.yaml` с `method: regex` (в текущем конфиге: INN, OGRN, KPP, BANK_ACCOUNT, BIK, PASSPORT, PHONE, EMAIL, SUM; DATE выключен).
- `id` — uuid4, уникален в списке, но невоспроизводим между запусками — в сравнениях/сортировках не использовать.
- **Ключ сортировки списка:** (порядок сегмента в `doc.segments`, порядок типа в YAML-конфиге, `start` по возрастанию внутри типа). То есть entities одного сегмента идут подряд, но по `start` внутри сегмента список НЕ отсортирован (например, KPP-совпадение может идти раньше BANK_ACCOUNT-совпадения с меньшим `start`). Блоку 4 сортировать самому по своему ключу `(индекс сегмента, start)`.
- **Пересечения возможны и ожидаемы**: 9-значное число, начинающееся с "04", даёт и `KPP`, и `BIK` Entity на одном интервале (проверено на "044525225"). Разрешение пересечений — зона ответственности блока 4, блок 2 их не фильтрует.
- Для сущностей с `validate` (INN, OGRN) в списке только значения с сошедшейся чек-суммой.

## Что блок ожидает на входе (предусловия)

- `doc.segments` — список `TextSegment` с полями `id: str` и `text: str`; `text` не `None` (при `None` — `TypeError` из `finditer`). Пустой `text` допустим (совпадений просто нет).
- `metadata`/`source_type` сегментов не читаются — блоку безразличен исходный формат документа.
- Конфиг по `config_path` — YAML со схемой из спецификации. Значение `entity_types` — dict; записи, не являющиеся dict, молча пропускаются. Глубокой валидации схемы нет: паттерн проверяется только на компилируемость.
- Функция чистая по отношению к `doc`: ничего в нём не изменяет.

## Использованные поля конфига

Читает `entity_types.yaml` (путь — только через аргумент, не хардкод):
- `method` — используется как фильтр: обрабатываются только записи со значением строго `"regex"`; всё остальное (в т.ч. `ner`, незнакомые значения) молча пропускается — это зона блока 3.
- `enabled` — если строго `false`, тип пропускается молча; отсутствие поля = включён.
- `pattern` — компилируется через `re.compile` как есть (инлайн-флаги вида `(?i)` работают). Отсутствует/пустой/не компилируется → предупреждение в stderr, тип пропущен целиком.
- `validate` — имя резолвится через `VALIDATORS = {"inn_checksum": ..., "ogrn_checksum": ...}`. Незнакомое имя → предупреждение в stderr, тип пропущен целиком (ни одного Entity по нему). Валидатору передаётся `m.group(0)`.
- Игнорируются: `token_prefix` (зона блока 4), `ner_label`, `ner_extractor` (зона блока 3), любые незнакомые ключи.

Расширяемость: новый тип с `method: regex` без `validate` работает без правки кода; новый тип с новой чек-суммой требует дописать функцию и зарегистрировать её в `VALIDATORS` (это нормально по спецификации).

## Побочные эффекты импорта

`import regex_detector` — только импорт `re`, `sys`, `uuid`, `yaml`, `models`. Никаких моделей, файлов, директорий; конфиг читается при каждом вызове `detect_regex`, не при импорте. Импорт мгновенный, модуль полностью ленив.

## Известные ограничения / TODO

- `KPP` не имеет контрольной суммы: любое 9-значное число вне контекста КПП (например, номер договора) даст ложный `KPP`-Entity. Зафиксировано спецификацией как известное ограничение MVP, не блокирует приёмку.
- Аналогично `BANK_ACCOUNT` (20 цифр), `PASSPORT` (защищён только контекстным якорем), `SUM`, `PHONE`, `EMAIL` — валидация только структурная, по паттерну.
- Пересечения совпадений разных типов (KPP/BIK на одном 9-значном числе с "04"; PASSPORT поверх 10 цифр) не разрешаются в этом блоке — передаются блоку 4 как есть.
- Конфиг перечитывается на каждый вызов функции (кэширования нет — осознанно, ради простоты и соответствия сигнатуре).

## Данные для тестов

**Пример 1 — валидные и испорченные чек-суммы.**
Вход: сегменты со строками `"ИНН 7707083893, КПП 773601001"`, `"ИНН 7707083894"`, `"ОГРН 1027700132195, ОГРНИП 304500116000157"`, `"ОГРН 1027700132196"`.
Выход: `INN("7707083893", [4:14])` и `KPP("773601001", [20:29])` из первой строки; из второй — ничего (чек-сумма не сходится); `OGRN("1027700132195")` и `OGRN("304500116000157")` из третьей; из четвёртой — ничего. 12-значный ИНН `500100732259` — валиден, `500100732258` — нет.

**Пример 2 — паспорт: якорь обязателен (граничный случай).**
Вход: `"паспорт серия 45 12 345678 выдан ОВД"` и `"случайное число 4512345678 без якоря"`.
Выход: из первой строки один Entity `PASSPORT`, `original_text="паспорт серия 45 12 345678"`, `[0:26]` — якорь внутри спана (границы по `m.group(0)`); из второй — ни одного Entity (нет якоря для PASSPORT, чек-сумма INN не сходится).

**Пример 3 — пересечение KPP/BIK (граничный случай для блока 4).**
Вход: `"р/с 40702810400000012345 в банке, БИК 044525225"`.
Выход: три Entity — `KPP("044525225", [38:47])`, `BANK_ACCOUNT("40702810400000012345", [4:24])`, `BIK("044525225", [38:47])`. KPP и BIK лежат на одном интервале — блок 2 отдаёт оба, разрешает блок 4.

**Пример 4 — SUM и правая граница.**
Вход: `"Цена договора: 1 500 000,00 руб. без НДС; аванс 500 000 ₽"` и `"куплено 5 рубашек"`.
Выход: `SUM("1 500 000,00 руб.")` и `SUM("500 000 ₽")` (неразрывный пробел внутри числа захватывается); `"5 рубашек"` — ничего.

**Пример 5 — выключенный тип и дефектный конфиг.**
Вход: `"дата 12.07.2026"` → ничего (`DATE` имеет `enabled: false`). Конфиг с записью `validate: snils_checksum` (нет в `VALIDATORS`) → предупреждение в stderr `"неизвестный validate 'snils_checksum' у типа SNILS — тип пропущен целиком"`, по типу SNILS ни одного Entity, остальные типы работают. `detect_regex(doc, "нет_такого.yaml")` → `FileNotFoundError`.
