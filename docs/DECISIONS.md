# DECISIONS — отвергнутые решения и почему

Защита от переоткрытия. Каждый раз, когда хочется «а давайте сделаем X» — проверь, не отвергли
ли X уже и почему. Первоисточники — отчёты в `docs/reports/` (историчны, могут содержать
устаревшие статусы; здесь — только сам вывод «решения»).

---

## Разрешение пересечений: обрезать проигравшего, НЕ выбрасывать целиком

**Отвергнуто:** выбрасывать проигравшую при пересечении сущность целиком (было так до фикса
W2-D1).
**Почему:** если проигравший нёс ПДн вне зоны пересечения (адрес слева от regex-ИНН), выброс
целиком отправлял хвост в открытый текст — утечка. Принято: обрезка до непересекающейся части
(`tokenizer.py:_trim_to_free`). См. [ARCHITECTURE.md](ARCHITECTURE.md), инвариант разрешения
пересечений; отчёт `docs/reports/WAVE2_VERIFICATION.md`.

## B3-пары: раздельные токены половинам, НЕ общий токен через реестр

**Отвергнуто:** связывать обе половины разорванной границей сущности отдельным реестром пар и
давать им ОДИН общий токен (pre-P1).
**Почему:** вызывало порчу данных при восстановлении B3-пар. Принято: Вариант А — каждая
половина независима, получает свой токен по `(entity_type, original_text)`; восстановление
посимвольно точно, ложное срабатывание B3 становится терпимо-шумным, а не разрушительным.
Первоисточник — `docs/reports/WAVE1_VERIFICATION.md`; память `shifrator-audit-2026-07-12`.

## Составные «ORG+ФИО»: направление ребра appos, НЕ список ролевых слов

**Отвергнуто:** сливать по appos пару «PER рядом с ORG» в ЛЮБУЮ сторону; отдельно —
фильтровать по списку ролевых слов (свидетель/директор).
**Почему:** склейка в любую сторону ложно объединяла РАЗНЫЕ стороны («Свидетель Иванов И.И.
ООО «Ромашка»» → одна ORG, ФИО исчезало) — дефект W2-D3. Список слов хрупок. Принято:
синтаксический критерий — зависимый токен в PER-спане, голова в ORG-спане
(`syntax_compound._appos_links`). См. [ARCHITECTURE.md](ARCHITECTURE.md), составные сущности.

## Типизация «роль + ФИО» (директор/глава + ФИО) — НЕ сливать в ORG

**Отвергнуто:** считать «директор Иванов» организацией.
**Почему:** человек здесь представитель, а не сторона-организация. Осознанная типизация: в ORG
сливается только «ИП/юрлицо + ФИО». Первоисточник — `docs/reports/DETECTION_REBUILD.md` (этап B),
спека компонента — архив `docs/archive/SHIFRATOR_SPEC_AI.md`, блок 4.

## Детекция адреса: yargy в парсере окрестности, НЕ сканером по всему документу

**Отвергнуто:** гонять yargy-парсер адреса по каждому сегменту как самостоятельный сканер.
**Почему:** yargy был доминантой времени детекции (разведка: ~256 c из 277 c батча — yargy) при
низкой полноте спана. Принято: место подтверждают дешёвые LOC-спаны Natasha + маркеры, а yargy
добирает полный спан ТОЛЬКО в окне сегментов с хитом. Ускорение основного прохода ~2.83×.
Первоисточники — `docs/reports/RECON_REPORT.md`, `docs/reports/DETECTION_REBUILD.md` (этап A).

## Разделитель граничного окна B3: `""` для соседних ячеек, НЕ `" | "`

**Отвергнуто:** использовать `" | "` (разделитель читаемой сборки) и внутри окна детекции B3.
**Почему:** `" | "` физически разрывает паттерны — ИНН/телефон, порванные границей ячеек, не
матчатся. Принято: соседние ячейки одной строки склеиваются `""`. См. [ARCHITECTURE.md](ARCHITECTURE.md),
инвариант B3; память `b3-boundary-window-separator`.

## Осознанно отложено

- **B4 (омоглифы в цифрах реквизитов)** — кириллические буквы в номере ломают `\d`, номер
  утекает. Отложен, `xfail(strict)` (`tests/test_breaking_leaks.py`). Не «фича», а известный
  незакрытый дефект-утечка низкого приоритета.
- **`encrypt` для `.xlsx/.pptx`** — не реализован (только `.docx/.txt`); `decrypt-file`
  поддерживает все три. Область MVP.
- **PDF-извлечение, компонент 1 (веб)** — не начаты.
