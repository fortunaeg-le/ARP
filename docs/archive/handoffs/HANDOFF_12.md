## Что сделано
Реализован финальный блок Компонента 2 — фасад `detokenize_file`, связывающий три
адаптера (блоки 9–11) с хранилищем сессий (блок 5). Фасад выбирает адаптер по
расширению файла, строит `resolve` из маппинга `token -> original_text` загруженной
сессии, вызывает `rewrite(src, dst, resolve)` полиморфно и дедуплицирует список
unresolved (уникальные, в порядке первого появления — контракт блока 6). В
`shifrator.py` **аддитивно** добавлена одна подкоманда `decrypt-file`; ни одна
существующая ветка (`encrypt`/`decrypt`/`delete`) не изменена. Собственной логики
разбора форматов и своей замены токенов блок не содержит — вся она в блоках 8–11.
Импорт модуля мгновенный (≈0.14 c, без NER/детекторов/tokenizer).

## Публичный интерфейс
```python
from file_detokenizer import detokenize_file

def detokenize_file(
    src_path: str,
    session_id: str,
    dst_path: str | None = None,
    storage_dir: str | None = None,
) -> tuple[str, list[str]]: ...
```
Минимальный пример вызова:
```python
from file_detokenizer import detokenize_file
dst, unresolved = detokenize_file("ответ.docx", "a276c5dc-…-a843e006")
# dst == "ответ_restored.docx" (создан на диске); unresolved -> [] или ["[ORG_99]", …]
```
Исключения (тип + модуль определения + когда):
- `ValueError` (builtins) — расширение `src_path` не из `.docx/.xlsx/.pptx` (в т.ч.
  `.pdf`); **или** `dst_path` совпадает с `src_path` по `os.path.realpath`.
- `FileNotFoundError` (builtins) — `src_path` не существует (пробрасывается из
  адаптера/ядра, не оборачивается).
- `FileExistsError` (builtins) — `dst_path` уже существует (молча затирать нельзя).
- `OoxmlError` (`ooxml_core`, блок 8) — файл не корректный OOXML-контейнер / повреждён
  / zip-бомба. Пробрасывается наверх как есть.
- `SessionNotFoundError` / `SessionExpiredError` (`session_store`, блок 5) — сессия не
  найдена / истекла. **Не перехватываются** — пробрасываются (контракт блока 6:
  отличать «сессия недоступна» от «в файле нет токенов» должен вызывающий).
- `lxml.etree.XMLSyntaxError` (`lxml.etree`) — если целевая часть архива не well-formed
  (не ожидается для настоящих файлов; из адаптера, не маскируется).

### CLI (аддитивная подкоманда)
```
python shifrator.py decrypt-file <session_id> <файл.docx|.xlsx|.pptx> [--out <путь>]
```
- stdout — одна строка: путь к созданному файлу.
- stderr — при наличии unresolved: `Предупреждение: не удалось восстановить токены: …`.
- код возврата: `0` успех; `1` ошибка (файл не найден / битый / формат / сессия / dst
  уже существует).

## Формат данных на выходе
`detokenize_file(...)` → кортеж, например:
```python
("C:\\...\\ответ_restored.docx", ["[ORG_99]"])
# или при полном раскрытии:
("C:\\...\\отчёт_restored.xlsx", [])
```
Побочный эффект — файл `dst_path` создан на диске (тот же набор/порядок записей архива,
что в `src_path`; оформление принесённого файла сохранено).

## Инварианты выходных данных
- Первый элемент кортежа — путь к созданному файлу (равен `dst_path`, если он задан;
  иначе `src` с суффиксом `_restored` перед расширением: `отчёт.docx` →
  `отчёт_restored.docx`).
- Второй элемент — `unresolved`: **уникальные токены в порядке первого появления в
  документе** (дедуплицированы фасадом; порядок появления задаётся адаптером блоков
  9–11 и здесь только сохраняется). Пустой список = все токены раскрыты.
- Исходный файл `src_path` не модифицируется никогда.
- Оформление принесённого файла сохранено полностью — гарантия ядра и адаптеров (блоки
  8–11); фасад оформления не касается вообще.

## Что блок ожидает на входе (предусловия)
- `session["entities"]` — список dict'ов с ключами `token` и `original_text` (формат
  блока 5); при коллизии токенов в маппинг попадает **последнее** значение (сессия
  блока 5 уже дедуплицирована по token при сохранении, коллизий не ожидается).
- Адаптеры блоков 9–11 присутствуют и импортируются (ленивый импорт внутри
  `_load_adapter`); их сигнатура — ровно `rewrite(src, dst, resolve) -> list[str]`.
- Проверки формата и коллизии путей делаются **до** обращения к диску адаптером;
  проверку «src существует» и «src — корректный OOXML» выполняет уже адаптер/ядро.

## Использованные поля конфига
`entity_types.yaml` не читается. Блок 12 к конфигу не обращается вообще.

## Побочные эффекты импорта
`import file_detokenizer` тянет только `from session_store import load_session` (лёгкий)
и стандартный `os`. Адаптеры и `ooxml_core` импортируются **лениво**, внутри
`detokenize_file`/`_load_adapter`, и только для нужного формата. Импорт `shifrator.py`
не изменился: `file_detokenizer` импортируется лениво внутри ветки `decrypt-file`, как и
прочие тяжёлые импорты. Проверено: время импорта `file_detokenizer` ≈ 0.14 c; после
импорта `natasha` и `ner_detector` **не** в `sys.modules`.

## Соглашения о путях и файлах времени выполнения
Блок не владеет постоянными путями. Пишет ровно один файл — `dst_path` (через адаптер →
`ooxml_core.rewrite_zip`, публикация атомарна через `os.replace`). Сессии читаются из
хранилища блока 5 (`~/.shifrator/sessions` по умолчанию, либо `storage_dir`). Других
файлов/директорий не создаёт.

## Отклонения от спецификации
Отклонений нет. Уточнения реализации (в рамках спеки):
- В CLI `decrypt-file` `FileExistsError` (dst уже существует) переведён в код возврата 1
  с сообщением в stderr — это подпадает под требование «1 при ошибке»; спецификация
  явно перечисляет «файл не найден / битый / формат / сессия», существование dst — тот
  же класс пользовательской ошибки.
- `purge_expired` в `decrypt-file` **не вызывается** (в отличие от `decrypt`) — по
  прямому требованию спеки блока 12.

## Предложения по изменению интерфейсов
Нет. Зафиксированный интерфейс реализуем как есть. (Опционально к рассмотрению вне
этого блока: стоит ли `decrypt-file` тоже звать `purge_expired` для единообразной
очистки — спека оставила это на усмотрение и попросила вынести предложением, а не
реализацией. Реализовано **без** очистки.)

## Известные ограничения / TODO
- Формат определяется **только по расширению** (нижний регистр); файл с неверным
  расширением, но валидным содержимым другого формата, не переопознаётся — попадёт в
  «неподдерживаемый формат» либо в `OoxmlError` соответствующего адаптера.
- `.pdf` осознанно не поддержан — та же ветка `ValueError`, что и любой другой
  неподдерживаемый формат (PDF отложен во всём компоненте).
- Искажённые LLM-токены (`[org_1]`, `ORG_1`, `[ORG 1]`) не распознаются — то же
  ограничение `TOKEN_RE`, что во всех блоках (см. [[b3-boundary-window-separator]] по
  смежной теме границ). Наследуется от ядра, фасад ничего к распознаванию не добавляет.

## Данные для тестов
Реально прогнанные сценарии (`venv/Scripts/python.exe`, реальные `.docx` через
`python-docx` и реальная сессия через `save_session`):
1. **Токен, разорванный между runs, `.docx`.** Параграф `"Договор с "`+`"[ORG"`(bold)+
   `"_1] на сумму"`, сессия знает `[ORG_1] -> "ООО «Ромашка»"` → в
   `..._restored.docx` абзац содержит «ООО «Ромашка»», `unresolved == []`, оформление
   сохранено.
2. **CLI + unresolved.** `decrypt-file <sid> cli.docx` на файле
   `"Директор [PERSON_1] и неизвестный [ORG_99]."` (сессия знает только `[PERSON_1]`) →
   rc `0`; stdout — путь к `cli_restored.docx`; stderr — `…не удалось восстановить
   токены: [ORG_99]`; в файле `[PERSON_1]` раскрыт, `[ORG_99]` остался как есть.
3. **Повторный вызов на существующий dst (граничный).** Второй `detokenize_file` при
   уже созданном `..._restored.docx` → `FileExistsError`, файл не перезаписан.
4. **dst == src (граничный).** `detokenize_file(tmp, sid, dst_path=tmp)` → `ValueError`
   (перезапись входа запрещена).
5. **Неподдерживаемый формат.** `detokenize_file("x.pdf", sid)` → `ValueError:
   Неподдерживаемый формат: .pdf. Поддерживаются: .docx, .xlsx, .pptx`.
6. **Сессия не найдена.** `detokenize_file(tmp, "0000…0000")` → `SessionNotFoundError`
   проброшен наверх (не перехвачен); CLI переводит его в rc `1` + stderr.
