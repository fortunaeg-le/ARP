## Что сделано
Реализован модуль `ner_detector.py` с публичной функцией `detect_ner(doc, config_path) -> list[Entity]`. PERSON/ORG находятся стандартным NER-пайплайном Natasha (`Segmenter` → `NewsEmbedding` → `NewsNERTagger`, `Doc.segment` → `Doc.tag_ner`), почтовые адреса — через `natasha.AddrExtractor(MorphVocab())` с последующей склейкой соседних `Match`'ей в единый span. Спан PERSON независимо расширяется инициалами вида «И.И.» влево и вправо, после любого изменения границ `original_text` пересчитывается срезом сегмента. Модели инициализируются один раз при импорте модуля; Natasha прогоняется на каждом сегменте отдельно, `start`/`end` — смещения внутри `segment.text`. Оба обязательных проверочных прогона (импорт natasha и реальная структура вывода AddrExtractor) выполнены — их вывод приведён ниже, расхождений со спецификацией не обнаружено.

## Публичный интерфейс
dataclass'ы импортируются из `models.py`, не переопределены (`from models import Entity, SourceDocument`).

Сигнатура:
```python
def detect_ner(doc: SourceDocument, config_path: str) -> list[Entity]: ...
```
Строка импорта:
```python
from ner_detector import detect_ner
```
Минимальный работающий пример:
```python
from extractor import extract
from ner_detector import detect_ner
doc = extract("dogovor.docx")
entities = detect_ner(doc, "entity_types.yaml")
# entities: list[Entity] с detector="ner", confidence=1.0, token=None
```
Исключения:
- `FileNotFoundError` (stdlib) — если `config_path` не существует (возникает в `open()` при чтении конфига).
- `KeyError` (stdlib) — если YAML не содержит верхнего ключа `entity_types`.
- `AssertionError` (stdlib) — если нарушен внутренний инвариант `original_text == segment.text[start:end]` (не должно происходить при корректных моделях; это самопроверка блока перед возвратом).
- Исключения `natasha`/`yargy` при загрузке моделей — только на этапе `import ner_detector` (см. «Побочные эффекты импорта»), не внутри `detect_ner`.

Функция ничего не пишет на диск и не мутирует вход `doc`.

## Формат данных на выходе
`list[Entity]`. Пример реального вывода (абзац `"Договор подписал Иванов И.И. от лица ООО «Ромашка»."`, segment_id `p0`):
```python
Entity(id="3f2a...-uuid4", segment_id="p0", start=17, end=28,
       original_text="Иванов И.И.", entity_type="PERSON",
       detector="ner", confidence=1.0, token=None)
Entity(id="9b1c...-uuid4", segment_id="p0", start=37, end=50,
       original_text="ООО «Ромашка»", entity_type="ORG",
       detector="ner", confidence=1.0, token=None)
```
Пример склеенного адреса (сегмент `"Адрес: г. Москва, ул. Ленина, д. 5, оф. 12."`):
```python
Entity(segment_id="p2", start=7, end=42,
       original_text="г. Москва, ул. Ленина, д. 5, оф. 12",
       entity_type="ADDRESS", detector="ner", confidence=1.0, token=None)
```

## Инварианты выходных данных
- Каждый Entity: `detector == "ner"`, `confidence == 1.0`, `token is None`, `id` — свежий uuid4-string.
- Инвариант границ: для **каждого** Entity `entity.original_text == doc.segments[<с этим segment_id>].text[entity.start:entity.end]` (проверяется `assert`'ом перед возвратом).
- `0 <= start < end <= len(segment.text)`; `start`/`end` — смещения внутри `segment.text`, не внутри всего документа.
- `entity_type` — только ключи конфига с `method: ner` (в MVP-наборе: `PERSON`, `ORG`, `ADDRESS`).
- **Порядок списка:** entity идут в порядке обхода сегментов (в порядке `doc.segments`), внутри одного сегмента — сначала все PERSON/ORG (в порядке `doc.spans` Natasha), затем все ADDRESS (в порядке склеенных цепочек по возрастанию start). **Строгой сортировки по `(segment, start)` блок не гарантирует** — блок 4 всё равно сам сортирует по `(индекс сегмента, start)`, поэтому опираться на порядок из блока 3 не следует.
- Один и тот же участок текста может породить несколько пересекающихся Entity разных типов (например NER-имя и «город» AddrExtractor'а на одном слове) — это ожидаемо, разрешение пересечений выполняет блок 4.

## Что блок ожидает на входе (предусловия)
- `doc` — валидный `SourceDocument` из блока 1; `segment.text` — строка (может быть пустой; пустые сегменты пропускаются, Entity по ним не создаётся).
- `config_path` указывает на существующий `entity_types.yaml` с ключом `entity_types`. Отсутствие файла → `FileNotFoundError` (не тихая порча). Отсутствие ключа `entity_types` → `KeyError`.
- Блок не проверяет уникальность `segment.id`; для самопроверки инварианта берётся первый сегмент с совпавшим `id`.

## Использованные поля конфига
Читаются записи с `method: ner`. Используемые поля:
- `method` — фильтр (обрабатываются только `ner`).
- `ner_label` — метка Natasha (`PER`/`ORG`), маппится на ключ `entity_type`. Строится словарь `{ner_label: entity_type}`; NER-span с меткой, которой нет в этом словаре (например `LOC`), **игнорируется**.
- `ner_extractor` — если значение `addr`, для этого `entity_type` запускается `AddrExtractor` (метка `LOC` NER-тэггера для адресов **не используется** — см. требования блока 3).
- `enabled` — если явно `false`, запись пропускается (для согласованности с блоком 2; в MVP-наборе ни одна ner-запись не отключена).
Игнорируются: `token_prefix` (нужен блоку 4, не блоку 3), `pattern`/`validate` (относятся к regex-записям), любые прочие ключи.
Поведение при незнакомом значении: запись `method: ner` без `ner_label` и без `ner_extractor: addr` пропускается с предупреждением в stderr (Entity не создаются). Блок **не** владеет файлом `entity_types.yaml` — только читает его (владелец — блок 1).

## Побочные эффекты импорта
Уже при `import ner_detector` (до вызова `detect_ner`) создаются модели Natasha на уровне модуля: `Segmenter()`, `MorphVocab()`, `NewsEmbedding()`, `NewsNERTagger(emb)`, `AddrExtractor(morph_vocab)`. Это загружает эмбеддинги navec и веса slovnet в память — порядка сотен МБ RSS. Замеренное время импорта на тест-машине — **~1.0 с** (модели уже в дисковом кеше пакетов navec/slovnet; первый импорт после установки может быть дольше). Диск/файлы модуль при импорте не создаёт, сеть не требуется (модели идут в составе пакетов). **Для блока 7:** ветке `decrypt` NER не нужен вовсе, поэтому `import ner_detector` в ней стоит делать лениво (внутри ветки `encrypt`), чтобы не платить секунду и сотни МБ на каждом `decrypt`.

Обязательный проверочный прогон `AddrExtractor` (реальный вывод на natasha 1.6.0, Python 3.11.9):
```
STRING: 'г. Москва, ул. Ленина, д. 5, оф. 12'
num matches: 4
  start=0  stop=9  text='г. Москва'  fact=AddrPart(value='Москва', type='город')
  start=11 stop=21 text='ул. Ленина' fact=AddrPart(value='Ленина', type='улица')
  start=23 stop=27 text='д. 5'       fact=AddrPart(value='5', type='дом')
  start=29 stop=35 text='оф. 12'     fact=AddrPart(value='12', type='офис')
STRING: 'адрес: 630090, г. Новосибирск, проспект Академика Лаврентьева, д. 1'
num matches: 4  (индекс, город, проспект, дом — каждый отдельным Match)
STRING: 'поставка из Москвы в Санкт-Петербург'
num matches: 2  (Москвы type=None, Санкт-Петербург type=None; разрыв ' в ' содержит букву → склейка запрещена)
```
Подтверждено: по одному `Match` на часть адреса, у каждого свои `.start`/`.stop`, `.fact` — одиночный `AddrPart(value, type)`, поля `.parts` нет (`hasattr(fact,'parts') == False`), сокращения-маркеры входят внутрь Match, разрыв между соседними Match — чистая пунктуация. Полностью совпадает с описанием в SHIFRATOR_SPEC_AI.md — расхождений нет.

## Соглашения о путях и файлах времени выполнения
- Вход: `entity_types.yaml` — путь передаётся аргументом `config_path` (не хардкодится). Файл читается, не пишется.
- Модуль ничего не пишет на диск и не создаёт директорий.
- Веса моделей Natasha читаются из установленных пакетов (`navec`, `slovnet`) — отдельных путей проекта не требует.

## Отклонения от спецификации
Отклонений нет. Реальный вывод `AddrExtractor` и NER-тэггера полностью совпал с описанным в спецификации, правило склейки (`разрыв ≤ 6 символов, целиком из [ ,. ]`) реализовано дословно. Расширение PERSON инициалами реализовано ровно двумя паттернами из ТЗ (`^\s?[А-ЯЁ]\.\s?[А-ЯЁ]\.` вправо и `[А-ЯЁ]\.\s?[А-ЯЁ]\.\s?$` влево), применёнными к срезам `text[end:]` / `text[:start]`, чтобы якоря `^`/`$` работали на границе среза.

## Предложения по изменению интерфейсов
Нет. Интерфейс `detect_ner(doc, config_path) -> list[Entity]` удобен и реализован как есть.

## Известные ограничения / TODO
- **Избыточная токенизация AddrExtractor'ом.** `AddrExtractor` матчит одиночные упоминания городов без маркера, в т.ч. в косвенных падежах («из Москвы» → Match «Москвы» с `type=None`), а также иногда распознаёт фамилии/слова как «город» (в тестах «Иванов», «П.П. Петров» породили лишний `ADDRESS`-entity, пересекающийся с PERSON). Это известное поведение natasha, а не баг блока: такие entity восстанавливаются посимвольно точно, а пересечения с PERSON/ORG разрешает блок 4 (правила 4–5). Приёмку не блокирует.
- **Возможная потеря хвоста адреса.** Если `AddrExtractor` не покрыл часть адреса (индекс/офис не вошли в Match даже после склейки) — эта часть не попадает в span. В проверенных примерах «оф. 12» и индекс «630090» вошли в склейку, но гарантии на произвольных адресах нет — фиксируется как ограничение MVP.
- **Разрыв склейки > 6 символов или с буквой** намеренно оставляет части адреса разными entity (или отдельными городами) — это по спецификации, а не дефект.
- Другие метки Natasha (`LOC`, и т.п.) в MVP не используются: адреса берутся только из `AddrExtractor`, `LOC` игнорируется.

## Данные для тестов
Вход — `SourceDocument` из абзацев (`source_type="docx_paragraph"`), `config_path="entity_types.yaml"`.

1. **PERSON + ORG (инициалы справа), граничный — расширение спана вправо.**
   Сегмент `p0`: `"Договор подписал Иванов И.И. от лица ООО «Ромашка»."`
   Ожидаемо:
   - `PERSON [17,28) "Иванов И.И."` (span расширен инициалами вправо; без расширения было бы «Иванов»).
   - `ORG [37,50) "ООО «Ромашка»"`.

2. **PERSON (инициалы слева), граничный — расширение спана влево.**
   Сегмент `p1`: `"Со стороны заказчика — П.П. Петров, директор ЗАО «Вектор»."`
   Ожидаемо: `PERSON [23,34) "П.П. Петров"` (span расширен инициалами влево), `ORG "ЗАО «Вектор»"`.

3. **ADDRESS — склейка четырёх Match в один span (город+улица+дом+офис).**
   Сегмент `p2`: `"Адрес: г. Москва, ул. Ленина, д. 5, оф. 12."`
   Ожидаемо: один `ADDRESS [7,42) "г. Москва, ул. Ленина, д. 5, оф. 12"` (четыре Match склеены — разрывы «, » проходят условие склейки).

4. **Граничный — склейка НЕ выполняется (разрыв с буквой).**
   Сегмент `"поставка из Москвы в Санкт-Петербург"`.
   Ожидаемо: два раздельных `ADDRESS` — `"Москвы"` и `"Санкт-Петербург"` (разрыв « в » содержит букву → склейка запрещена).

5. **Пустой сегмент.**
   Сегмент с `text=""` → ни одного Entity (сегмент пропускается).

Все примеры реально прогнаны — инвариант `original_text == segment.text[start:end]` выполнен для всех выданных Entity.
