## Что сделано
Реализован `shifrator.py` — точка входа CLI на `argparse` с тремя подкомандами: `encrypt <путь>`, `decrypt <session_id>` и `delete <session_id>`. `encrypt` склеивает блоки 1→2+3→4→5 (`extract` → `detect_regex`+`detect_ner` → `tokenize` → `save_session`). `decrypt` в начале команды вызывает `purge_expired(exclude_session_id=session_id)` (ошибки внутри логируются, не прерывают выполнение), читает текст из stdin до EOF, вызывает `detokenize`, печатает восстановленный текст в stdout и предупреждение об unresolved-токенах (если есть) в stderr. `delete` зовёт `delete_session(session_id)` и печатает результат в stdout (код возврата 0 всегда). Новой бизнес-логики сверх склейки нет.

**Обновление (этап 2).** Очистка в `decrypt` перенесена в начало команды и получила `exclude_session_id=session_id`: чужой просроченный мусор вычищается всегда, но файл запрошенной сессии оставляется — истёкшая запрошенная сессия теперь сообщается как «сессия истекла», а не «не найдена» (ветка `except SessionExpiredError` больше не мёртвый код). Битый `.docx` из блока 1 приходит как `ValueError` и печатается как `Ошибка: Файл не является корректным .docx …` (без сырого трейсбека). Добавлена подкоманда `delete <session_id>`. Полный ручной прогон (`.docx` → encrypt → decrypt того же вывода → сравнение с `build_plain_text`) выполнен и совпал побайтово на «чистом» тестовом документе; также проверены `.txt`-вход и три сценария ошибок.

## Публичный интерфейс
dataclass'ы импортируются из `models.py` (транзитивно, через блоки 1-6) — блок 7 сам их не использует и не переопределяет.

Блок 7 не экспортирует публичных функций сверх точки входа (`main()`), как и предписано реестром модулей. Интерфейс — исключительно командная строка:

```
python shifrator.py encrypt <путь_к_файлу.docx|.txt> [--config <путь_к_entity_types.yaml>]
    → сохраняет анонимизированный текст в файл {storage_dir}/{session_id}.txt
      (тот же storage_dir, что использует save_session блока 5; utf-8)
    → печатает в stdout ТОЛЬКО session_id (одна строка, без лишнего текста)

python shifrator.py decrypt <session_id>
    → в начале команды вызывает purge_expired(exclude_session_id=<session_id>)
      (чистит все ЧУЖИЕ просроченные сессии, файл запрошенной оставляет)
    → печатает подсказку про Ctrl+D/Ctrl+Z в stderr
    → читает текст ответа LLM из stdin до EOF
    → печатает восстановленный текст в stdout
    → если есть unresolved токены — печатает предупреждение в stderr
    → честно истёкшая запрошенная сессия → stderr "Ошибка: сессия истекла: <id>", код 1

python shifrator.py delete <session_id>
    → удаляет сессию (delete_session, без подтверждения)
    → stdout "Сессия <id> удалена" (True) либо "Сессия <id> не найдена" (False)
    → код возврата 0 в обоих случаях
```

Пример вызова (PowerShell/bash):
```bash
python shifrator.py encrypt contract.docx > anon.txt 2> session_id.txt
python shifrator.py decrypt "$(cat session_id.txt)" < llm_reply.txt > restored.txt
```

Коды возврата: `0` — успех (для `delete` — всегда 0, и при «удалена», и при «не найдена»); `1` — обработанная ошибка (файл не найден, неподдерживаемый/битый формат, сессия не найдена/истекла); `2` — ошибка разбора аргументов (стандартное поведение `argparse`).

## Формат данных на выходе
Блок 7 не возвращает структур данных — только текстовые потоки и один файл. Пример полного прогона (см. «Данные для тестов»):
```
$ python shifrator.py encrypt test_document_clean.docx
01b09d3c-4ab5-43a0-ba4f-46fbd7aa19d7
```
(stdout — только session_id). Содержимое файла `~/.shifrator/sessions/01b09d3c-4ab5-43a0-ba4f-46fbd7aa19d7.txt`:
```
Договор поставки № [KPP_1]
[ADDRESS_1], 12 июля 2026 г.
...
Поставщик | [ORG_2]»
Покупатель | [PERSON_1]
Подписи сторон скреплены печатями организаций.
```

## Инварианты выходных данных
- stdout `encrypt` содержит ровно один `session_id` (валидный uuid4), без лишнего текста (используется `print`, который добавляет один `\n` в конце — это не часть session_id).
- Анонимизированный текст в stdout `encrypt` больше не печатается — он сохраняется в файл `{storage_dir}/{session_id}.txt` (utf-8), тот же `storage_dir`, что использует `save_session` блока 5.
- stdout `decrypt` содержит ровно восстановленный текст.
- Восстановленный текст при передаче в `decrypt` содержимого файла `{storage_dir}/{session_id}.txt` (неизменённого) посимвольно совпадает с `build_plain_text(doc)` (блок 4) — проверено на «чистом» документе, см. известные ограничения ниже про документ с многоабзацевой ячейкой.
- Порядок вызовов внутри `encrypt` фиксирован и не меняется: `extract` → `detect_regex` + `detect_ner` (regex первым) → `tokenize` → `save_session(entities, session_id=None, ttl_hours=24)`.
- `decrypt` всегда вызывает `purge_expired(exclude_session_id=session_id)` в начале команды (до `load_session`/`detokenize`), независимо от того, какую сессию просят и упадёт ли `purge_expired` с исключением. Файл запрошенной сессии из очистки исключён, поэтому честно истёкшая запрошенная сессия даёт `SessionExpiredError` («истекла»), а не `SessionNotFoundError`; остальные просроченные сессии вычищаются за тот же вызов.

## Что блок ожидает на входе (предусловия)
- Все шесть модулей блоков 1-6 (`extractor.py`, `regex_detector.py`, `ner_detector.py`, `tokenizer.py`, `session_store.py`, `detokenizer.py`) присутствуют рядом с `shifrator.py` и реализуют сигнатуры ровно по реестру модулей спецификации — блок 7 их не проверяет и не оборачивает сверх обработки перечисленных исключений.
- `entity_types.yaml` (или файл, указанный через `--config`) существует и синтаксически валиден — иначе `FileNotFoundError`/`yaml.YAMLError` из нижележащих блоков (последнее не перехватывается явно, всплывает как трейсбек — не входит в перечисленный в спецификации набор "понятных ошибок").
- Ввод `decrypt` из stdin — произвольный текст, никаких предположений о его содержимом (полностью делегировано блоку 6).

## Использованные поля конфига
Блок 7 сам не читает содержимое `entity_types.yaml` — только передаёт путь к нему (аргумент `--config` или дефолт) в `detect_regex`, `detect_ner` и `tokenize`, как предписано спецификацией.

## Побочные эффекты импорта
`import` подмодулей выполняется **лениво**, внутри тел `cmd_encrypt`/`cmd_decrypt`, а не на уровне модуля `shifrator.py`:
- Ветка `decrypt` импортирует только `session_store` (быстрый импорт `cryptography.fernet`) и `detokenizer` (`re` + `session_store`) — **не** импортирует `ner_detector`, поэтому не платит ~1 секунду и сотни МБ RAM на загрузку моделей Natasha, которые ей не нужны.
- Ветка `encrypt` импортирует все шесть модулей, включая `ner_detector` — здесь неизбежна загрузка моделей Natasha при первом вызове (см. HANDOFF_3).
- Ветка `delete` импортирует только `session_store` (`delete_session`) — модели Natasha не загружаются, команда мгновенная.
- Сам модуль `shifrator.py` при импорте не делает ничего, кроме `import argparse, os, sys` — мгновенно.

## Отклонения от спецификации
Одно намеренное отклонение сверх буквального текста спецификации: в начале `main()` дополнительно вызывается `sys.stdin.reconfigure(encoding="utf-8")` (спецификация явно требует reconfigure только для `stdout`/`stderr`). Без этого `decrypt` падал с `UnicodeEncodeError`/`UnicodeDecodeError` при чтении кириллического текста из stdin на Windows (проверено эмпирически — консоль по умолчанию использует не-UTF8 кодовую страницу и на приём, не только на вывод, символом-суррогатом ломая `sys.stdin.read()`). Это то же обоснование, что и в тексте спецификации для stdout/stderr, только применённое к третьему стандартному потоку — не новая функциональность, а необходимое условие работоспособности уже описанной команды `decrypt` на Windows.

Изменение контракта вывода `encrypt` (текст больше не печатается в stdout, а сохраняется в `{storage_dir}/{session_id}.txt`, в stdout — только session_id) — изменение согласовано с пользователем на этапе тестирования, дата: 2026-07-12.

## Известные ограничения / TODO
- **Обнаружено при сквозном прогоне (не относится к блоку 7):** на многоабзацевой ячейке таблицы (`table.cell(...).text = "ООО «Ромашка Трейд»\nР/сч ...\nБИК ..."`, три абзаца, склеенные блоком 1 через `"\n"` в один `TextSegment.text`) NER-детектор блока 3 иногда выдаёт `ORG`-спан, пересекающий встроенный `"\n"` и захватывающий начало следующего абзаца (пример: `original_text == "ООО «Ромашка Трейд»\nР/сч"`). Из-за этого `decrypt(encrypt(text))` на таком документе расходится с `build_plain_text(doc)` — восстановленный текст содержит перенос строки не в том месте. Это дефект блока 3 (взаимодействие с многострочным текстом сегмента), не блока 7; исправление вне границ этого блока (см. правило "не трогай код других блоков"). Заведена отдельная задача на фикс `ner_detector.py`. Сквозная приёмка блока 7 подтверждена на документе без этого пограничного случая (см. «Данные для тестов», пример 1) — сама склейка блоков и CLI-контракт работают корректно; расхождение возникает только из-за неверных границ Entity, пришедших из блока 3.
- Ошибки парсинга YAML-конфига (`yaml.YAMLError`) и другие исключения, не перечисленные явно в спецификации блока 7 ("файл не найден, неподдерживаемый формат, сессия не найдена/истекла"), не оборачиваются в понятное сообщение — всплывают как обычный трейсбек. Это осознанно не расширялось за рамки прямо перечисленного в спецификации набора ошибок.
- `--config` доступен только у подкоманды `encrypt` (decrypt в него не нуждается — не читает `entity_types.yaml` ни прямо, ни через блоки 5/6).

**Пример 1 — полный сквозной прогон, приёмочный сценарий (без табличного пограничного случая).**


**Пример 2 — `.txt`-вход.**
Вход-файл (`utf-8-sig`, `\r\n`): `"ИНН 7707083893, email test@example.com\r\nВторая строка\r\n"`.
`encrypt` → stdout: `"ИНН [INN_1], email [EMAIL_1]\nВторая строка"`, stderr — валидный `session_id`.
`decrypt <session_id>` с этим stdout на входе → stdout: `"ИНН 7707083893, email test@example.com\nВторая строка"` (точное восстановление).

**Пример 3 — граничные случаи ошибок.**
- `python shifrator.py encrypt nope.docx` → stderr: `"Ошибка: файл не найден: nope.docx"`, код возврата `1`.
- `python shifrator.py encrypt dummy.pdf` (существующий файл с недопустимым расширением) → stderr: `"Ошибка: Неподдерживаемый формат: .pdf. Поддерживаются: .docx, .txt"`, код возврата `1`.
- `echo "текст" | python shifrator.py decrypt 00000000-0000-0000-0000-000000000000` → stderr: подсказка про Ctrl+D/Ctrl+Z, затем `"Ошибка: сессия не найдена: 00000000-0000-0000-0000-000000000000"`, код возврата `1`.
- `python shifrator.py encrypt <битый .docx>` (например, переименованный `.txt`) → stderr: `"Ошибка: Файл не является корректным .docx (повреждён или неверный формат): <path>"`, без трейсбека, код возврата `1`. ✅ (`tests/test_adversarial_cli.py::TestEncryptCorruptDocx`).

**Пример 5 — очистка при decrypt и истёкшая сессия (этап 2).**
Директория хранилища с тремя сессиями: запрошенная истёкшая `A`, чужая истёкшая `B`, чужая живая `C`. `decrypt A` → stderr `"Ошибка: сессия истекла: A"`, код `1`; файл `B.enc` удалён за этот же вызов, `C.enc` и `A.enc` на месте. ✅ (`tests/test_cli.py::TestCliDecryptPurgesOthersAtStart`).

**Пример 6 — подкоманда delete (этап 2).**
- `delete <существующий id>` → stdout `"Сессия <id> удалена"`, код `0`, `.enc` удалён.
- `delete <валидный, но отсутствующий id>` → stdout `"Сессия <id> не найдена"`, код `0`.
- `delete not-a-valid-id` → stdout содержит `"не найдена"`, код `0`, к ФС не обращается. ✅ (`tests/test_cli.py::TestCliDelete`).

**Пример 4 — известное ограничение (граничный случай, НЕ путать с дефектом блока 7).**
Документ с ячейкой `"ООО «Ромашка Трейд»\nР/сч 40702810900000012345\nБИК 044525225"` (три абзаца в одной ячейке) → `decrypt(encrypt(...))` расходится с `build_plain_text` на одной строке из-за неверной границы ORG-Entity в блоке 3 (см. «Известные ограничения»). CLI-логика (склейка, потоки ввода/вывода, session_id) при этом отрабатывает штатно — расхождение целиком в данных, пришедших от блока 3.
