Место в плане: перед T4/T3 (`docs/ENTITY_SPEC.md` §8.3). Все будущие структурные

## ШАГ 0. Карта арбитража как он есть

### 0а. Все места, где решается победитель пересечения

Арбитраж живёт в **трёх независимых местах**, разного назначения и разной
области действия. До этого этапа ни один документ не собирал их в одну карту.

| # | место | файл:строка | что решает |
|---|---|---|---|
| 1 | `tokenizer._winner` | [`src/tokenizer.py:71-131`](../src/tokenizer.py) | победитель между ДВУМЯ УЖЕ НАЙДЕННЫМИ пересекающимися `Entity` — вызывается из `_resolve_overlaps` для каждой пересекающейся пары |
| 2 | `ner_detector._address_barriers` | [`src/ner_detector.py:607-621`](../src/ner_detector.py) | какая территория ВООБЩЕ НЕДОСТУПНА адресу — регекс-реквизиты и структурные ORG/PER считаются РАНЬШЕ (`pipeline.run_detection`, шаги 1-2) и передаются барьером в шаг 3 (`detect_ner`, только ADDRESS). Проигравший здесь НЕ попадает в `_winner` вообще — конкурировать ему не с кем, спан адреса на этом месте просто не строится |
| 3 | `AnchorEngine._type_rank` | [`src/anchor_registry.py:1242-1243`](../src/anchor_registry.py) | арбитраж ТИПА ключа реестра при коллизии ORG/PER на одной лемме (внутри `AnchorEngine.run`, PASS 1b, до эмиссии `Entity`) — `{"ORG": 0, "PERSON": 1}`, при равной уверенности побеждает ORG |

Правило внутри места 1 (`_winner`) — полный порядок:

```
rule 1: a.detector != b.detector -> побеждает "regex"                (БЕЗУСЛОВНО)
  если оба regex:
    rule 2: длиннее спан -> побеждает
    rule 3: равная длина -> _REGEX_PRIORITY (раньше в списке = сильнее)
  если оба ner:
    [ЭТАП T-ARB, новое] ADDRESS против ОДНОСЛОВНОГО PERSON -> ADDRESS       (см. §1в)
    rule 4: длиннее спан -> побеждает
    затем больший confidence (МЁРТВАЯ ветка — confidence везде 1.0, см.
      ARCHITECTURE_AUDIT.md §2.1)
    rule 4б: равная длина, разные интервалы -> _NER_PRIORITY
    равный тип, разные интервалы -> меньший start
rule 5: тотальный tie-break — (entity_type, original_text) лексикографически
```

Порядок применения (место 4-е по счёту, отдельное от трёх выше — это НЕ
арбитраж пересечения, а порядок, который РЕШАЕТ, дойдёт ли вообще дело до
арбитража): [`src/pipeline.py:26-62`](../src/pipeline.py) —
`regex → detect_structural (ORG+PER, один реестр) → detect_ner (ТОЛЬКО адрес,
барьером — уже готовые regex/ORG/PER) → suppress_conflicts → merge_compound`.
Именно этот порядок и есть корень дефекта B-ADDR-HOMONYM (§0г).

### 0б. Каждый из 15 типов — где стоит, что происходит на пересечении

Три класса соседей по механизму получения кандидата: **шаблонные** (regex,
`detector="regex"`), **якорные** (`anchor_registry`, structure-first ORG/PER —
несут `detector="ner"`, НЕ `"regex"`!), **нейросетевые** (Natasha
LOC/`yargy.AddrExtractor` — тоже `detector="ner"`, для ADDRESS смешаны с
якорной валидацией `_addr_span_strong`). Ключевой факт: **якорные и
нейросетевые типы сегодня — ОДИН И ТОТ ЖЕ класс в `_winner`** (оба
`detector="ner"`), хотя по механизму получения кандидата они разные. Это не
дефект (документировано `ARCHITECTURE_AUDIT.md` §3.2 как заранее известное
ограничение будущего GLiNER-яруса), но должно быть явным при чтении карты.

| тип | механизм | список приоритета | позиция |
|---|---|---|---|
| PERSON | якорный (anchor_registry) | `_NER_PRIORITY` | 3 (слабее ADDRESS/ORG) |
| ORG | якорный (anchor_registry) | `_NER_PRIORITY` | 2 |
| ADDRESS | нейросетевой+якорная валидация | `_NER_PRIORITY` | 1 (сильнее всех ner) |
| INN | шаблонный | `_REGEX_PRIORITY` | 3 |
| INN_PERSON | шаблонный | `_REGEX_PRIORITY` | 4 |
| OGRN | шаблонный | `_REGEX_PRIORITY` | 2 |
| KPP | шаблонный | `_REGEX_PRIORITY` | 7 |
| BANK_ACCOUNT | шаблонный | `_REGEX_PRIORITY` | 1 (сильнее всех regex) |
| BIK | шаблонный | `_REGEX_PRIORITY` | 5 |
| PASSPORT | шаблонный | `_REGEX_PRIORITY` | 8 |
| PHONE | шаблонный | `_REGEX_PRIORITY` | 9 |
| EMAIL | шаблонный | `_REGEX_PRIORITY` | 11 |
| SNILS | шаблонный | `_REGEX_PRIORITY` | 6 |
| BIRTHDATE | шаблонный | `_REGEX_PRIORITY` | 12 |
| SUM | шаблонный | `_REGEX_PRIORITY` | 10 |
| *(DATE, не в корпусе, `enabled: false`)* | шаблонный | `_REGEX_PRIORITY` | 13 |

На пересечении **шаблонный × якорный/нейросетевой** — `detector` различается,
решает rule 1: шаблонный побеждает БЕЗУСЛОВНО, независимо от длины спана и
силы якоря (единственное известное последствие этого — Stage-E-A: анкорный
INN/SNILS «защищают» от PHONE только потому, что стоят раньше в списке, не
потому что якорь сильнее; сегодня это не дефект — направление ошибки
безопасное, обе стороны маскируются). На пересечении **якорный × якорный**
(ORG↔PER на одной лемме) решает место 2 (`_type_rank`) РАНЬШЕ, чем сущности
вообще эмитятся — `_winner` эту пару никогда не видит. На пересечении
**якорный(PER) × нейросетевой(ADDRESS)** решает место 2 (`_address_barriers`,
порядок конвейера) — это и есть дефект B-ADDR-HOMONYM.

### 0в. Типы вне списков приоритетов — поимённо

**Сегодня, на боевом `entity_types.yaml`, таких типов НОЛЬ.** Все 15 типов
корпуса плюс отключённый `DATE` (итого 16 типов с `token_prefix`) — каждый в
своём списке (`_REGEX_PRIORITY` — 13, `_NER_PRIORITY` — 3). Список для
шаблонных типов расширялся при каждом появлении нового типа (T2-INN:
`T2_INN_REPORT.md:86` — «добавить `INN_PERSON`» прямым текстом в чек-листе
этапа); список для якорных/нейросетевых **не расширялся НИ РАЗУ** с момента
появления ORG/PERSON (этапы A/B) — потому что новых типов этого класса с тех
пор не было.

Что делает код с типом СЕГОДНЯ, если его забыть вписать (проверено юнит-тестом
`tests/test_arbitration_contract.py::TestIntersectionClasses::
test_regex_vs_regex_unlisted_type_loses_to_any_listed_type`, а до этапа T-ARB
— НИЧЕМ не охранялось): `_regex_rank`/`_ner_rank` возвращают `(1, entity_type)`
для типа вне списка против `(0, index)` для перечисленных — забытый тип
слабее ВСЕХ перечисленных даже при пересечении с более коротким спаном чужого
типа. Поражение не падает никаким тестом — оно тихое и обнаруживается только
на живом пересечении в корпусе (или не обнаруживается вовсе, если пересечений
с этим типом в тестовых данных не случилось). Это и есть «молчаливый
проигрыш», который ШАГ 1/2 закрывают контрактом и стражем.

### 0г. Дефект «сила якоря против порядка конвейера» — разбор и минимальный пример

**Находка: B-ADDR-HOMONYM** (`docs/FINDINGS.md`, введена
`docs/archive/reports/HANDOFF_STAGE_C_ADDRESS.md` §4, тяжесть НЕЗНАЧИТЕЛЬНО —
«малый реальный риск», формулировка задания). Дословно источник: *«улица-
однофамилец, ошибочно помеченная PER под мутацией… ВЫИГРЫВАЕТ у адреса —
якорный адрес конфликт НЕ разрешает. Разрешение требует либо правки PER-guard
(вне границ этапа C — "PER не трогать"), либо **арбитража PER↔ADDRESS** (риск
потери реального PER)»*. Именно вторую, отклонённую тогда альтернативу этот
этап и реализует — узко, на этом одном классе.

**Механизм (до правки).** `pipeline.run_detection` считает структурный PER
(`detect_structural`) РАНЬШЕ адреса (`detect_ner`, шаг 3). В `detect_ner`
`per_norm`-спаны передаются в `_address_barriers` как **безусловный** барьер
(4-й параметр `org_spans`, вместе с ORG) — в отличие от `ner_spans` (сырые
Natasha-теги), которые проверяются `_addr_transparent` и могут уступить
адресу. Структурный PER такой проверки не проходит НИКОГДА: адрес в принципе
не пытается строиться на территории ЛЮБОГО PER, независимо от того, насколько
слабо этот PER заякорен. Побеждает не более сильный якорь, а то, что PER
физически посчитан РАНЬШЕ в конвейере.

**Минимальный пример (воспроизведён на HEAD `2f61b89`, ДО правки этапа
T-ARB — живой, не архивный; тот же класс, что `labor_0006__m2718_linebreak`
в измерении этапа C, `experiments/stage_c/measure_stagec.txt:43`):**

```
3.1. Место исполнения обязательств: Тверь, Полев\nая 21.
```

(перенос строки внутри слова «Полевая» — та же мутация `linebreak`, что ломает
корпусный документ; здесь дан как самостоятельный минимальный текст).

`run_detection` до правки даёт единственную сущность:

```
PERSON 'Полев\nая' (43, 51)
```

Никакого ADDRESS-кандидата НЕ существует вовсе — `_address_barriers` вычеркнул
эту территорию до попытки построения адреса, `_winner` эту пару никогда не
видит. Итог `tokenize()`:

```
3.1. Место исполнения обязательств: Тверь, [PERSON_1] 21.
```

Улица замаскирована НЕВЕРНЫМ типом, а **номер дома «21» остаётся открытым
текстом** — это не только неверная типизация (тема masking C), это утечка
ПДн (адрес субъекта частично в открытом виде), тот же класс тяжести, что и
остальные утечки корпуса.

**Кто выигрывает сейчас и почему это неверно.** Выигрывает PERSON — единственно
потому, что он единственный кандидат: ADDRESS не был допущен к конкуренции
порядком конвейера. Если бы адрес получил шанс быть построенным на этом месте,
его якорь (Titlecase-топоним «Полевая» + номер дома «21», house-pattern
`_addr_span_strong`) СИЛЬНЕЕ, чем у PERSON: голая однословная «Полев\nая» не
несёт своей формы ФИО (само-якорь ФИО — ВСЕГДА многословный, «фамилия+имя/
отчество» или «фамилия+инициалы», см. `PerAnchorDetector` докстринг) — она
попала в реестр либо по внешнему маркеру, либо падежным вхождением уже
зарегистрированной в документе фамилии. Ни то ни другое не может быть
СИЛЬНЕЕ подтверждённого `_addr_span_strong` якоря — но заранее конкурировать
им было негде.

## ШАГ 1. Контракт арбитража

### Полный порядок приоритетов (обоих механизмов) — см. таблицу §0б

Порядок НЕ менялся — все 15 типов уже были на месте (§0в). Изменение — только
явное закрепление контрактом (ШАГ 2) и один новый узкий пункт правила (ниже).

### Правило для типа, которого нет в списке — теперь ошибка сборки

`src/tokenizer.py`: `assert_priority_contract(config_path)` — тип
`entity_types.yaml` с `token_prefix` без места в списке приоритетов своего
механизма (`method: regex` → `_REGEX_PRIORITY`; `method: ner`/
`anchor_registry` → `_NER_PRIORITY`) роняет `ArbitrationContractError` с ИМЕНЕМ
типа. Зовётся из `resolve_for_masking` — ДО первого пересечения, то есть до
того, как забытый тип успел бы молча кому-то проиграть. Тип без
`token_prefix` (не маскируется) контрактом не проверяется — арбитраж его не
касается.

### Решение по силе якоря — реализовано на классе B-ADDR-HOMONYM, узко

Два взаимно необходимых изменения (одно без другого не работает):

**1) `src/ner_detector.py` — территория, не арбитраж кандидатов.**
`_recover_address_over_weak_per` (новая функция, вызвана в ОБОИХ адресных
проходах `detect_ner` — основном и E′-расплетённом): если в барьерах есть
структурный PER-спан БЕЗ внутреннего пробела/точки («однословный» —
`_per_span_is_weak`, тот же признак, что уже использует
`PerAnchorDetector.guard` для «многословный спан — форма ФИО»), пробуется
собрать адрес БЕЗ этого одного барьера — **тем же, ничем не ослабленным**
`_addr_span_strong`/`_finalize_address_spans`, что и везде. Если результат сам
подтверждается (якорь адреса независимо силён), он добавляется как ВТОРОЙ,
КОНКУРИРУЮЩИЙ кандидат — не заменяет PER, а даёт `_winner` увидеть обоих.
Многословный PER (само-якорь ФИО) в эту функцию не попадает НИКОГДА —
барьером остаётся всегда, как раньше. Пустой список слабых PER-спанов даёт
пустой результат за одну проверку — нулевая цена, когда класс не применим
(подавляющее большинство сегментов корпуса).

**2) `src/tokenizer.py` — кто из двух кандидатов побеждает.** Новое правило в
`_winner`, ветка «оба ner», **перед** правилом длины: `ADDRESS` против
ОДНОСЛОВНОГО `PERSON` (`" " not in original_text and "." not in original_text`)
— побеждает `ADDRESS`, БЕЗУСЛОВНО, даже если PERSON длиннее. Единственное
место в контракте, где сила якоря решает раньше длины — ровно то, что
предписано заданием: *«если якорь одного типа сильнее… он выигрывает у более
длинного спана без якоря»*. Обоснование безопасности правила: ADDRESS
СУЩЕСТВУЕТ ТОЛЬКО если уже прошёл `_addr_span_strong` — существование
кандидата само есть доказательство силы его якоря, других ADDRESS не бывает.
Многословный/с точкой инициала PERSON (само-якорь ФИО) под правило не
подпадает — решает как раньше (длина → `_NER_PRIORITY`).

**Почему это не меняет поведение нигде, кроме класса находки.** До правки (1)
пара «ADDRESS vs однословный PERSON» физически не могла возникнуть НИ В ОДНОМ
из известных путей: основной проход и E′-проход держали структурный PER
безусловным барьером (правка (1) выше), а B3-граничный путь
(`tokenizer._detect_boundary_entities`) держит его контролируемым через
`_addr_transparent`, которая требует ЦИФРУ внутри спана — голая фамилия без
номера дома её никогда не проходила и НЕ ТРОГАЛАСЬ этим этапом (граница
правки, согласованная с владельцем: только `ner_detector.py`/
`anchor_registry.py`, где PER стоял безусловным барьером). Значит правило (2)
в `tokenizer.py` до этой сессии было МЁРТВОЙ веткой — применять её было не к
чему; теперь оно решает исключительно те пары, которые породила правка (1), и
только их.

## ШАГ 2. Охрана контракта

`tests/test_arbitration_contract.py`, 22 теста, три группы:

1. **`TestContractCompleteness`** — `assert_priority_contract` на боевом
   конфиге не падает (сегодня контракт держится); синтетический тип без места
   в `_REGEX_PRIORITY`/`_NER_PRIORITY` (оба механизма отдельно) роняет с его
   именем в сообщении; тип без `token_prefix` не проверяется; **красное
   состояние приёмки** — монки-патч убирает реальный тип (`PERSON`/`EMAIL`) из
   списка, `assert_priority_contract` падает и называет именно его; страж
   реально висит на боевом пути — `resolve_for_masking` с урезанным списком
   тоже падает (не только собственный юнит-тест функции).
2. **`TestIntersectionClasses`** / **`TestAnchorStrengthOverridesLength`** —
   победитель по каждому классу: regex безусловно бьёт ner даже при меньшем
   спане; regex-regex по длине и по приоритету при равной длине; тип вне
   списка проигрывает даже более короткому перечисленному (документирует
   default из §0в); ner-ner по длине и по приоритету (ORG>PERSON) при равной
   длине; **новое правило** — ADDRESS бьёт более длинный однословный PERSON;
   ADDRESS бьёт и более КОРОТКИЙ однословный PERSON (правило безусловное, не
   «пока не длиннее»); многословный ФИО и ФИО с инициалом (точка) — контроль,
   что правило их НЕ касается (длина решает как раньше, реальные ФИО
   защищены); ORG против однословного PERSON — контроль, что расширение не
   уползло за пределы названного класса (ТОЛЬКО ADDRESS↔PERSON).
3. **`TestBAddrHomonymIntegration`** — сквозной пайплайн на минимальном
   примере §0г: «Полев\nая» больше не даёт `[PERSON_N]` и не оставляет «21»
   открытым текстом; отдельный тест на нулевую цену при отсутствии слабых
   PER-спанов.
