## 2. Топ-3 ускорения по соотношению выигрыш/риск

### 1. Убрать дублирование точек входа «полный прогон» (самый дешёвый и самый безопасный)

**Находка.** В проекте существует **три независимых** способа прогнать полный
324-документный корпус через Natasha:
1. `pytest -m slow -q` → `test_corpus_no_crash.py` (проверяет только «0 крешей»);
2. `tests/corpus/gate.py` (проверяет креши **+** leak_v2 **+** FP **+**
   masking_correctness — строгий надмножество проверки №1);
3. `tests/corpus/run_measurement.py` напрямую (для отчётного `results_stageN.json`
   этапа, использует тот же `run_all()`).

Условие 1 гейта (`gate.py`, docstring строки 9–11) — это буквально то же самое,
что проверяет `test_corpus_no_crash.py`, посчитанное на том же корпусе. Если в
рамках одной сессии перед коммитом гоняются и `pytest -m slow`, и `gate.py` — это
два полных прохода Natasha ради одной и той же проверки «0 крешей» плюс то, что
даёт только гейт.

**Экономия.** Один полный прогон снят на сессию, где сейчас гоняются оба — это
**~8–20 минут за сессию**, судя по времени прогона из HANDOFF (§1.1/1.5, README.md).

**Риск.** Минимальный: gate.py уже строго дороже по проверкам, чем
`test_corpus_no_crash.py`. Правило простое и не требует правки кода — только
явно зафиксировать в `docs/STATE.md`/шаблоне промпта: **«если в сессии всё равно
будет запущен `gate.py`, отдельный `pytest -m slow` перед этим не нужен — условие
1 гейта его покрывает»**. `run_measurement.py` напрямую — гонять только если
код между последним `gate.py` и текущим моментом НЕ менялся и нужен именно
именованный `results_stageN.json` для отчёта; иначе достаточно
`results_gate_current.json`, который `gate.py` и так пишет.

### 2. Скрипт-однострочник для подвыборки (снижает риск «слепой» итерации без замены полного прогона)

**Находка.** Правило «итерируйся на 30-50 док., полный только в конце» есть в
задании, но **в харнессе нет вообще никакой поддержки** — ни флага, ни параметра
у `run_measurement.py`/`gate.py`. Судя по HANDOFF-ам, сессии реально итерировались
на **ручных точечных проверках одного документа** (прямой вызов `tokenize()`
на конкретном файле), а не на репрезентативной подвыборке. Это НЕ то же самое:
`HANDOFF_STAGE_4.md` §3.1 прямо документирует случай, где такая точечная
проверка пропустила регрессию (гомоглиф-мутация якорного слова, редкий класс,
не встретившийся в ручной выборке), которую поймал только полный прогон.

**Что предложить.** Скрипт-обёртка вида
`tests/corpus/run_measurement.py --sample N[=40] [--seed S]`, читающий
`gold.json`, детерминированно (по `doc_id`, не `random`) отбирающий N документов
из разных `source`/`contract_type`, и прогоняющий тот же `process_doc()` только
по ним. Не заменяет `gate.py` перед коммитом — обязательный финальный прогон
остаётся полным. Даёт быстрый (доли минуты вместо 8-20) сигнал «не сломал ли я
явно» между правками внутри одной итерации.

**Экономия.** Трудно оценить в минутах напрямую (зависит от числа итераций внутри
сессии — не задокументировано явно), но качественно: устраняет ложную дилемму
«или дорого-и-полно, или дёшево-и-слепо-на-одном-документе», которая сейчас
толкает сессии либо к повторным полным прогонам, либо к ручным проверкам, не
ловящим редкие классы регрессий.

**Риск.** Низкий, если скрипт **явно** не заменяет финальный `gate.py`-прогон
(тот же принцип, что уже задокументирован для `run_measurement.py` — «полный
прогон обязателен перед фиксацией baseline», HANDOFF_STAGE_4 §3.1). Нужно
прописать в докстринге скрипта прямым текстом: «результат подвыборки НЕ
основание для коммита/пересборки baseline».

### 3. Кеш сырых спанов детекции для метрик-only сессий (оцениваю, не реализую — отдельная сессия)

**Находка.** `run_measurement.py::process_doc()` НЕ разделяет (а) прогон
конвейера (`extract → detect_regex → detect_ner → merge_compound_entities →
tokenize → save_session → detokenize`) и (б) подсчёт метрик (`leak_pieces`,
`leak_v2`, `mc_check_a/bc`) — они переплетены в одной функции. Из-за этого
сессия, меняющая **только** `tests/corpus/measure_lib.py` (метрику, не
детектор), всё равно гоняет полный Natasha-конвейер заново на всех 324
документах, хотя выход конвейера (`anon_text`, `kept`, `det_located`,
`plain`/`restored`) от такой правки не меняется вообще.

Дважды подтверждено: `HANDOFF_METRIC_ADDRESS.md` и `HANDOFF_METRIC_NUMERIC.md` —
обе сессии прямым текстом пишут «`src/` не тронут» и обе гоняли полный конвейер,
чтобы получить новые цифры метрики поверх НЕИЗМЕНИВШЕГОСЯ вывода детекции.

**Оценка реализуемости.** Корпус заморожен (`MANIFEST.sha256`), Natasha
детерминирована на нём (доказано этапом 3 аудита — 0 недетерминизма из 10315
прогонов). Значит вывод конвейера — чистая функция от (документ, код
`src/`). Кешируемо: сохранить на диск per-doc `{doc_id, anon_text, kept
(сериализуемо), det_located, plain, restored, refused_zones}` под ключом —
хэш содержимого `src/*.py` + `entity_types.yaml` (не хэш корпуса — он и так
неизменен по MANIFEST). При запуске `run_measurement.py`/`gate.py`: если ключ
совпал с последним кешем — детекцию не гонять, только пересчитать метрики
(`leak_pieces`/`leak_v2`/`mc_check_*`) поверх кеша; иначе — полный прогон и
обновление кеша.

**Кто выигрывает.** Только сессии, которые НЕ трогают `src/`/`entity_types.yaml`:
чинки метрики (`measure_lib.py`), правки харнесса-отчётности, работа над
доками/аудитами, требующая пересчёта цифр без изменения детекции. Сессии,
меняющие детекторы (этапы 3, 4, нормализация) выигрыша не получают — им кеш
инвалидируется каждый раз.

**Оценка экономии.** Полный прогон (Natasha — доминирующая доля времени) — это
почти весь бюджет ~8-20 мин; пересчёт одних метрик поверх готового
`anon_text`/`kept` — операция на порядки быстрее (чистый Python по уже
посчитанным строкам, без NER). Для сессий вида METRIC_ADDRESS/METRIC_NUMERIC
это может сэкономить почти весь прогон.

**Почему НЕ делать прямо сейчас.** Это структурная правка харнесса
(`run_measurement.py::process_doc` придётся разделить на «прогон конвейера» и
«скоринг»), а харнесс — это тот самый прибор, чьей неприкосновенности
подчинена вся модель доверия к цифрам проекта (`measure_lib.py` «заморожен» на
нескольких этапах подряд, HANDOFF_STAGE_4 §3.2). Трогать его стоит **отдельной,
узкоспециализированной сессией**, с тем же уровнем строгости приёмки, что и
любая правка измерительного прибора (см. `COVERAGE_AUDIT.md`, враждебный аудит
харнесса) — не походя внутри этапа детекции.

## 3. Явный список «НЕ трогать — это фундамент»

Ничего из перечисленного не предлагается сокращать ни в этом отчёте, ни как
следствие топ-3 выше:

- Полный прогон корпуса (`gate.py`) **перед коммитом, трогающим `src/`** —
  финальная подпись цифр, обязателен как есть.
- Зеркальные тесты метрик (`tests/test_future_contracts.py` и др., ловящие
  фальшивые/красивые цифры) — не сокращать, не «озеленять» вручную.
- Проверка `MANIFEST.sha256` до и после прогона — провенанс корпуса.
- Сравнение с `results_baseline.json` — точка отсчёта регресс-гейта, пересобирать
  только осознанно и с явной причиной в коммите (как это уже происходит).
- Поэнтитийный разбор (13 типов сущностей раздельно в `gate.py::compare`) — ловит
  регрессы, спрятанные усреднением по типам.
- Двойная приёмка recall + `masking_correctness` (A/B жёстко, допуск 0) — асимметрия
  «пропуск виден человеку, кривая маскировка — нет» обоснована в `docs/STATE.md` §6.
- Кеш из топ-3 (§2.3) — **валиден только пока не тронут `src/`/`entity_types.yaml`**;
  любая правка детектора обязана инвалидировать кеш и гонять полный Natasha-прогон
  заново. Кеш ускоряет метрики-only сессии, не заменяет проверку детекции.

## 4. Рекомендации: отдельная сессия vs правка шаблона промптов

**Отдельной сессией (структурная правка харнесса, требует своей приёмки):**
- Кеш сырых спанов детекции (§2.3, топ-3) — разделение `process_doc()` на
  прогон+скоринг, кеш-ключ по хэшу `src/`+`entity_types.yaml`, инвалидация при
  правке детектора. Приёмка — та же строгость, что у любой правки измерительного
  прибора (сверка старого/нового вывода метрик побайтово на неизменном кеше).
- Скрипт подвыборки (§2.2, топ-2) — новый CLI-флаг/скрипт, детерминированный отбор
  N документов по `source`/`contract_type`, докстринг с явным «не для baseline».

**Просто поправить в шаблоне промптов этапов (без правки кода):**
- Явно указать: «если в этой сессии будет запущен `tests/corpus/gate.py`, отдельный
  `pytest -m slow` не нужен — условие 1 гейта строго покрывает креш-проверку»
  (§2.1, топ-1).
- Явно указать: «`gate.py` не гонять параллельно с `pytest` в этом же терминале/
  сессии — CPU-голодание даёт ложный `TimeoutExpired` в `test_g_regression`»
  (уже частично задокументировано в HANDOFF_STAGE_0D §1.5, но стоит вынести в сам
  шаблон промпта этапа, а не только в архивный HANDOFF, который «читать не по
  умолчанию»).
- Явно указать: «`run_measurement.py` напрямую (для именованного
  `results_stageN.json`) гонять только если код с последнего `gate.py`-прогона не
  менялся — иначе используйте `results_gate_current.json`, который `gate.py` и так
  пишет».
