# Этап T2-INN — разделение ИНН на два типа

Ветка `main`, 2026-07-29. Коммиты этапа перечислены в §9.

**Одной строкой.** ИНН перестал быть одним типом: `INN` — это ИНН организации
(10 цифр, не персональные данные), `INN_PERSON` — ИНН человека (12 цифр,
персональные данные, токен `[INN_PER_N]`). Набор «только персональные данные»
теперь маскирует второй и не трогает первый; до этапа он не трогал оба, и ИНН
предпринимателя по умолчанию оставался в тексте открытым.

---

## 1. ШАГ 0 — установленные факты (до правок)

### 1а. Как был устроен шаблон и где различалась длина

Один тип, один паттерн на обе длины —
[`entity_types.yaml:50-55`](../entity_types.yaml) на коммите `7e4e2fa`:

```yaml
INN:
  method: regex
  pattern: '\b\d(?:[ ]?\d){9}(?:(?:[ ]?\d){2})?\b'   # 10 цифр + необязательные ещё 2
  validate: inn_checksum
  anchor: '(?i)инн'
  token_prefix: INN
```

Длина различалась ровно в трёх местах, ВСЕ — внутренние, наружу (в
`Entity.entity_type`) она не выходила:

| место | что делает | файл:строка (на `7e4e2fa`) |
|---|---|---|
| КС | `inn_checksum` ветвится по `len(digits)`: 10 → один весовой набор, 12 → два | `src/regex_detector.py:23-39` |
| якорь ORG | реквизит юрлица = `kind == "INN" and dc == 10` | `src/anchor_registry.py:794` |
| якорь PER | реквизит физлица = `kind == "INN" and dc == 12` | `src/anchor_registry.py:1046` |

Признак якоря PER (**то самое место около 1046 из задания**) устроен так:
`_requisites_src_by_seg` (`src/anchor_registry.py:1162-1172`) отбирает из
regex-сущностей типы `INN/OGRN/SNILS` и считает у каждой `digit_count` по
ИСХОДНОМУ тексту; `PerAnchorDetector.detect` берёт из них `SNILS` и `INN` с
12 цифрами как ВНЕШНИЙ МАРКЕР, позволяющий заякорить ГОЛУЮ фамилию рядом
(«Морозов, ИНН 500100732259» → `PERSON`).

**Разделение этот механизм ломает молча, если не поправить два места**:
12-значный ИНН приезжает под новым именем, и (1) `_requisites_src_by_seg` его
отфильтровывает, (2) условие `kind == "INN"` в `PerAnchorDetector` не совпадает.
Ни одна метрика ИНН этого бы не показала — упала бы только полнота по людям.
Оба места исправлены, поведение сохранено побайтно (проверка длины `dc == 12`
оставлена намеренно: `dc` считается по исходному тексту, где омоглиф на месте
цифры даёт `dc < 12`, и такие значения якорем PER не были — снимать проверку
значило бы тихо изменить полноту по людям). Пришпилено тестами
`test_t2_inn_split.py::test_inn_of_a_person_still_anchors_a_bare_surname` и
`::test_inn_of_a_company_does_not_anchor_a_bare_surname`.

### 1б. Контрольная сумма — ОТВЕТ НА ПРЯМОЙ ВОПРОС

**Реализованы ОБА алгоритма, и оба проверяются.** У 10-значного ИНН одно
контрольное число (веса `2,4,10,3,5,9,4,6,8`, `mod 11 mod 10`), у 12-значного —
ДВА (веса `7,2,4,10,…` для 11-го знака и `3,7,2,4,10,…` для 12-го); обе ветки
лежат в одной функции `inn_checksum` (`src/regex_detector.py:23-39`) и обе
покрыты тестами на эталонных номерах ФНС
(`tests/test_regex_detector.py:20-36`: валидный/невалидный на каждую длину).

**Находки «реализован только один» НЕТ.** Что действительно стоит назвать: до
этапа функция была ОДНА на два алгоритма и выбирала ветку сама по длине входа —
то есть тип не мог ошибиться алгоритмом, потому что типа не было. После
разделения такая ошибка становится возможной, поэтому заведены
`inn10_checksum`/`inn12_checksum` — прибитые к длине входы в ту же функцию
(`src/regex_detector.py`), и конфиг зовёт их. Если завтра паттерн ослабят,
12-значное значение не сможет проехать по 10-значному алгоритму.

Роль КС не менялась: инвариант этапа 4 («под якорем «ИНН» КС — сигнал, не
шлагбаум; без якоря — фильтр») сохранён для ОБОИХ типов и пришпилен
параметризованными тестами `test_broken_checksum_under_the_anchor_is_still_masked`
и `test_broken_checksum_without_the_anchor_is_not_taken`.

### 1г. Какие линии гейта покрывают новый тип, а какие нет

Гейт — `tests/corpus/gate.py`, четыре линии + условия.

| линия / условие | как перечисляет типы | покрывает `INN_PER`? |
|---|---|---|
| (б) leak_v2 по типам и агрегату | цикл по `ML.ALL_ENTITY_TYPES` (`gate.py:153`) | **да**, автоматически после записи в список |
| (в) masking A (round-trip) по типам | цикл по `ML.ALL_ENTITY_TYPES` (`gate.py:237`) | **да** |
| (г) masking B (границы) по типам | там же | **да** |
| (3) FP на негативах | агрегат по всем типам | **да** |
| (1) креши, (4) MANIFEST | типов не знают | **да** |
| **(а) precision** | цикл по `ML.NER_SPINE_TYPES` = `ORG/PER/ADDRESS` (`gate.py:280`) | **НЕТ** |
| (5) известный долг | только `ADDRESS` | нет (и не должен) |

**Сказано прямо, как требует задание:** линия точности (а) новый тип НЕ
охраняет — она по построению держит только NER-хребет (ORG/PER/ADDRESS), а
regex-реквизиты в неё не входили и до этого этапа (`INN`, `OGRN`, `SNILS` — все
вне линии «а»). Precision `INN_PER` СЧИТАЕТСЯ и ПЕЧАТАЕТСЯ (таблица
`print_precision` идёт по `ALL_ENTITY_TYPES`), но красным не роняет. Косвенная
охрана точности у него есть — условие (3), общий счёт FP на негативах с
допуском `gate_config.FP_TOLERANCE`: массовое ложное срабатывание нового типа
уронит гейт по этому счёту. Расширять `NER_SPINE_TYPES` на regex-типы —
отдельное решение (это изменило бы охрану ВСЕХ реквизитов, не только ИНН), и
этап его не принимает; зафиксировано как открытый пункт §8.

## 2. Имя нового типа и вид токена

* тип в конфиге — **`INN_PERSON`**, тип в замере/эталоне — **`INN_PER`**,
  токен — **`[INN_PER_N]`**.
* **Обоснование одной строкой:** имя `INN` оставлено за организацией по решению
  владельца, поэтому новый тип назван по владельцу значения (`PERSON` — уже
  существующее в конфиге слово для человека), а короткий код `INN_PER` следует
  той же традиции сокращений замера, что `PERSON→PER` и `BANK_ACCOUNT→ACCOUNT`.

Вид токена проверен на совместимость: `_TOKEN_RE = \[[A-Z_]+_\d+\]`
(`src/detokenizer.py:34`, посимвольно тот же в `src/ooxml_core.py:43`) допускает
подчёркивания внутри префикса, нумерация в `tokenizer` идёт по префиксу, поэтому
`[INN_1]` и `[INN_PER_1]` — независимые ряды, а не пересекающиеся.

## 3. ШАГ 2 — переразметка эталона

Скрипт — [`experiments/stage_t2_inn/retype_gold.py`](../experiments/stage_t2_inn/retype_gold.py),
дамп — [`dump_before_after.txt`](../experiments/stage_t2_inn/dump_before_after.txt),
**зерно выборки 20260729**.

**Классификатор.** Наивный `len(re.sub(r"\D",""))` НЕ ГОДИТСЯ: корпус
адверсариальный, внутри значения живут пробелы-разряды, дефисы, перенос строки,

вместо «6»). По `\d` распределение длин ИНН выглядело как 4…12 цифр, и
настоящие 12-значные значения попали бы в 10-значную половину. Классификатор

единственной неразобранной скрипт не пишет ничего и падает).

**Что изменено:** 675 записей, у каждой — РОВНО поле `type` (`INN` → `INN_PER`).

**Проверки до записи** (все зелёные): число документов и записей не изменилось;

других отличий, кроме `type`; записи не типа `INN` не тронуты; ни одна запись с

**Независимая сверка с `git show HEAD:tests/corpus/gold.json`** (не кодом

## 4. Цифры: как изменились две половины ИНН

Полный прогон корпуса (324 документа, 737 с, 0 крешей) —
`tests/corpus/results_t2inn.json`, он же принят новым `results_baseline.json`.

### 4.1. Сравнение «яблоки с яблоками»

Сравнивать половину с прежним ОБЩИМ числом нельзя: прежние 82.6% полноты по
типу `INN` — это среднее по двум разным по трудности популяциям. Поэтому старый
прогон разбит по ФАКТИЧЕСКОЙ длине значения тем же классификатором, что и
эталон, и сравнивается половина с половиной:

| | было (10 цифр) | стало `INN` | было (12 цифр) | стало `INN_PER` |
|---|---:|---:|---:|---:|
| сущностей | 369 | 369 | 675 | 675 |
| детектировано | 269 (72.9%) | **269 (72.9%)** | 593 (87.9%) | **578 (85.6%)** |
| утечка leak_v2 ≥6 | 58 (15.7%) | **58 (15.7%)** | 90 (13.3%) | **90 (13.3%)** |
| утечка leak_v2 ≥8 | 55 | **55** | 83 | **83** |

**ИНН организации не сдвинулся НИ НА ЕДИНИЦУ** — ни полнота, ни утечка
(приёмка, пункт 2). **Утечка ИНН человека тоже не сдвинулась**; изменилась
только его полнота, −15 сущностей, и причина названа в §5 (T2-A).

### 4.2. Точность и корректность маскирования

| | было (один тип `INN`) | стало `INN` | стало `INN_PER` |
|---|---:|---:|---:|
| precision (tp / fp на негативах) | 100.00% (889 / 0) | **99.29%** (280 / 2) | **100.00%** (593 / 0) |
| masking A (round-trip) | 100.00% | 100.00% | 100.00% |
| masking B (границы) | 89.93% | 86.71% | 91.57% |
| masking C (тип маски) | 99.44% | 93.02% | 100.00% |

Агрегат по всему корпусу: **A 100.00% → 100.00%** (инвариант round-trip цел),
**B 86.95% → 86.95%** (побайтно), C 95.37% → 95.23% (мягкий уровень,
предупреждение гейта), FP на негативах **15 → 16**, креши 0 → 0, утечка по
КАЖДОМУ из 13 прочих типов — байт-в-байт.

Разбиение B/C по половинам — не регресс, а другой знаменатель: поимённая сверка
всех 10 992 масок (`experiments/stage_t2_inn/compare_split.py`) показала, что
признаки `a_ok`/`b_ok` не изменились НИ У ОДНОЙ маски; изменился только `c_ok`
у 16 масок (T2-A) и состав корзин.

### 4.3. Доказательство, что разделение — бухгалтерия, а не смена поведения

`compare_split.py` склеивает две половины обратно в одну корзину и сверяет
прогоны поимённо по документам. Итог: маски, сущности эталона и ложные
срабатывания совпали ВЕЗДЕ, кроме 16 масок, разобранных в §5. Самое короткое
подтверждение — из красного прогона гейта против СТАРОГО baseline:

```
+ INN[leak_v2>=6]: 148 -> 58 (-90)        (это ушла 12-значная половина)
- (б) INN_PER[leak_v2>=6]: 0 -> 90 (+90)  (и ровно она же пришла сюда)
```

58 + 90 = 148 — прежнее число утечек ИНН, не изменившееся ни на единицу.

## 5. Что изменилось в поведении: две находки

### T2-A. Разорванный ИНН физлица получает тип организации (16 масок, 14 док.)

Двенадцатизначный ИНН, разорванный переносом строки (`9375532509` + перенос +
`15`) или границей ячейки, детектируется ТОЛЬКО 10-значным префиксом — механизм
сборки разорванных значений (`src/multispan.py`, этап E′) на ИНН не
распространён, это пред-существующий класс `SplitEntities`. До этапа префикс
получал тип `INN` и совпадал с типом эталона — промах засчитывался как
попадание. Теперь тип эталона `INN_PER`, и та же маска честно считается
промахом (`found=False`) и ошибкой типа (`c_ok=False`).

* 16 масок в 14 документах, ВСЕ — адверсариальные мутации (13 `linebreak`,
  1 `digit_spaces`); на чистых документах корпуса класс не встречается ни разу;
* обратного случая (маска `INN_PER` поверх эталонного `INN`) — 0;
* **значение при этом маскируется как прежде**: утечка `INN_PER` не выросла
  (90 → 90), masking A/B не изменились.

**Практическое следствие, которое надо знать владельцу.** В наборе «только
персональные данные» тип `INN` (организации) ВЫКЛЮЧЕН, поэтому такой
10-значный обрывок ИНН человека в узком наборе останется в тексте открытым.
Это не регресс относительно прежнего поведения (до этапа узкий набор не
маскировал ИНН вообще) и не новая утечка в «Максимуме», но это ЩЕЛЬ в новом
обещании набора. Закрывается распространением мультиспана на ИНН — работа
класса `SplitEntities`, вне границ этого этапа.

### T2-B. Два ложных ИНН на КБК (+2 FP), минус один ложный ORG (−1 FP)

Раздельные паттерны генерируют кандидатов чуть иначе, чем один: прежний
паттерн на «цифровом супе» (КБК из 20 цифр, разбитый пробелами) давал ОДИН
кандидат в 12 цифр, который отбраковывался 12-значной КС; теперь рядом
появляется и 10-значный кандидат, у которого 10-значная КС может СЛУЧАЙНО
сойтись. Это тот же класс, что известная находка `Stage4-C` (КС ОГРНИП
случайно сходится на подстроке КБК), и он проявился дважды —
`cession_0008__m1337_digit_spaces` и `sale_0013__m1337_digit_spaces`, оба
раза на УЖЕ ОБЪЯВЛЕННОМ негативе-КБК, то есть это over-masking мусора, а не
утечка.

Одновременно ушёл один ложный ORG (`services_0008__m2718_combo`, маски «О» и
«Об» на негативе «код ОКВЭД»): 12-значный ИНН, у которого омоглифы съели две
цифры, раньше проходил как «реквизит ЮРЛИЦА» (`dc == 10`) и якорил ORG; теперь
он по ТИПУ — ИНН физлица, и якорем организации быть не может. Precision ORG
вырос 99.78% → 100.00%.

Итог по FP: **15 → 16** (+2 ИНН, −1 ORG). Допуск `FP_TOLERANCE = 0`, поэтому
против старого baseline гейт по этому условию краснел; +1 принят сознательно
вместе с пересборкой baseline — направление ошибки безопасное (лишняя маска на
не-ПДн), а точность нового типа продолжает охраняться условием (3).
