# HANDOFF — Этап D: метрика PRECISION + гейт (капстоун precision-хребта)

Ветка `stage-c-address`. Замораживает precision, достигнутый A/A′/B/C, чтобы будущая
recall-работа (Entity.spans, R) не могла тихо его уронить. **Детекция НЕ тронута — 0
правок в `src/`**: этап D строит ИЗМЕРИТЕЛЬ (`measure_lib.precision_by_type`) и ГЕЙТ
(`experiments/stage_d/gate_d.py`). Результаты — в `experiments/stage_d/`, корпус заморожен.

## 1. Метрика precision (единая FP-дефиниция разбора C §9.1)

`measure_lib.precision_by_type(results)` — чистая функция над записями
`run_measurement.process_doc`:
- **FP** = kept-МАСКА (после разрешения пересечений в tokenize, НЕ сырой спан),
  пересекающая ОБЪЯВЛЕННЫЙ негатив (`gold['negatives']`);
- **TP** = kept-маска, легшая на gold-сущность СВОЕГО типа (`scored & c_ok`);
- **precision_T = TP_T / (TP_T + FP_neg_T)**; уровень — kept-маска, набор — весь корпус.
- FP по типам == `aggregate_results['fp_on_neg']` (та же ось; итого 650 на C — сверено
  тестом `test_fp_neg_matches_aggregate_definition`).

**Диагностика (НЕ в precision, НЕ в гейт), считается отдельными счётчиками:**
- `cross` — маска на gold ДРУГОГО типа (ошибка ТИПА, домен `masking_correctness C`);
- `nothing` — маска на НЕАННОТИРОВАННОЙ прозе (over-mask, on-nothing) — неоднозначный
  набор, В ГЕЙТ НЕ БЕРЁТСЯ (иначе over-маскирование прозы гейту невидимо), но ВИДЕН в отчёте.

## 3. Приёмка 2 — ЗЕРКАЛА метрики (`tests/test_precision_metric.py`, 10 тестов)

Метрика ДОКАЗАННО различает чистую детекцию и мусор (иначе — фикция):

## 4. Приёмка 3 — гейт, baseline D (`experiments/stage_d/gate_d.py`)

Гейт КРАСНЕЕТ, если ЛЮБОЕ:
- **(2a)** precision любого NER-типа (ORG/PER/ADDRESS) < baseline − допуск (**0.5пп**);
- **(2b)** FP всего (единая ось) > baseline (**650**) + допуск (**5**);
- **(2c)** утечка-долг (ADDRESS `found=False & leak_v2`) > baseline (**116**) + допуск (**3**).
- + крешы → красный (историческая линия).

**Прогон на текущем HEAD → baseline D зафиксирован** (`baseline_d.json`), гейт **ЗЕЛЁНЫЙ**
(`gate_d_report.txt`): precision ORG 99.77 / PER 99.96 / ADDRESS 99.92; FP 650;
утечка-долг 116; over-mask 328 (диагностика); cross 510 (диагностика).

### Почему утечка-долг = 116, а не 61 (ЧЕСТНО, не подогнано)

`known_leaks_stage_c.json` = **61** — долг, ПРИЧИНённый этапом C (критерий «found на HEAD
b-per через over-capture И missed на C»). Само-содержащийся гейтовый критерий (без опоры
на HEAD) «ADDRESS found=False & leak» даёт **116**: те же 61 + **55 пред-существующих**
(HEAD b-per их ТОЖЕ не детектировал и ТОЖЕ тёк — не вина этапа C). Гейт замораживает
честные **116**; `known_leaks` (61) двигает ДИАГНОСТИКУ состава (какие утечки
документированы как долг C, какие пред-существующие/новые). Число 116 показано как есть —
подгонять под «красивое 61» значило бы спрятать 55 реальных пред-существующих утечек.

### Диагностика состава (компенсатор мягкого порога 2c)

При каждом прогоне множество утекающих сущностей сравнивается с baseline-множеством (116)
и помечается по `known_leaks`: если счёт в пределах порога, НО состав сменился (ушла И
пришла) → **ПРЕДУПРЕЖДЕНИЕ** «leak-set changed at same count: −[ушли] +[пришли] (не в
known_leaks: N)». Гейт не краснеет, но подмена «116 на другой 116» ВИДНА, не тонет.

## 8. Разбор старой «precision 90%» (задача 3, FINDINGS D-PRECISION-90)

В проекте до D НЕ было честной precision. За неё принимался **`masking_correctness C =
90.81%`** (STATE §2). Это ФИКЦИЯ: `mc_check_bc` ставит `scored=False` любой маске, НЕ
легшей на gold, → B/C считаются ТОЛЬКО по маскам-на-gold и СТРУКТУРНО СЛЕПЫ к
over-маскированию. На HEAD b-per masking C «не видел» 634 ADDRESS-маски на негативах +
2610 на прозе и показывал ~90% «качества». (Второе историческое число — сырой precision
**46.3%** COVERAGE_MEASUREMENT §Precision — наоборот ЗАНИЖЕН: SUM-негативы + банки-cross +
проза в одном мешке.) Обе помечены неверными в FINDINGS D-PRECISION-90 со ссылкой на
честную дефиницию (`precision_by_type`): ADDRESS 66.86(HEAD)→99.92%(C), ORG 99.77, PER 99.96.
