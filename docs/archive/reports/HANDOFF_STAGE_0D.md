### 1.2. Порог `leak_v2` ≥6 / ≥8 — как считался, чтобы не разойтись с уже опубликованными цифрами

`leak_v2_numeric(strict=8, soft=6)` **адаптирует** строгий порог вниз для коротких числовых
ядер (`thr_strict = min(8, core_len)`) — иначе короткое ядро (например 6-значный код
подразделения паспорта), выжившее ЦЕЛИКОМ, никогда бы не набрало буквальных 8 цифр и
несправедливо не считалось бы «строгой» утечкой. `measure_lib._leak_v2_hits()` (новая функция,
этап 0d) воспроизводит именно эту адаптацию по уже сохранённым `window_len`/`core_len` из
JSON, а не по литеральному `window_len >= 8`. Разница ощутима: литеральный расчёт дал бы
39.8% для агрегата ≥8 (BIK-excl) вместо верных **43.0%**, задокументированных в
`HANDOFF_STAGE_0B_FIX.md`. Пересчёт `aggregate_results()` по `results_baseline.json`
воспроизвёл официальные 48.0% / 43.0% и 1968 FP-на-негативах бит-в-бит — числа гейта и
числа прошлых отчётов согласованы.

### 3.1. EOL-конверсия — реальная, не гипотетическая опасность

Перед коммитом `sha256sum -c MANIFEST.sha256 --quiet` → `exit 0` (замораживали неиспорченное).
После первого коммита (`7bbb0b5`, ещё без `.gitattributes`) опасность CRLF-порчи проверена
эмпирически, не на словах: `git worktree add --detach /tmp/wt_before HEAD` (чистый checkout
в отдельный каталог, не трогая рабочее дерево) → `sha256sum -c` в нём дал **656/656 расхождений**,
включая порчу **самого `MANIFEST.sha256`** (перенос строки внутри файла тоже конвертировался
в CRLF, `sha256sum` не смог даже разобрать строки — `'GENERATION_NOTES.md'$'\r': No such file
or directory`). Причина: `core.autocrlf=true` у пользователя конвертирует LF→CRLF при checkout
любого файла, который git счёл текстовым, независимо от того, есть ли в нём уже CRLF — это
не поведение «на всякий случай», оно сработало на 100% файлов корпуса.

Добавлен `tests/corpus/.gitattributes` (`* -text`, действует на весь каталог рекурсивно) —
отключает у git текстовую эвристику для corpus целиком, не только для `.docx` (которые git и
так распознаёт бинарными по NUL-байту), но и для `.txt`/`.json`/`.py`/`MANIFEST.sha256`,
которые git иначе считает текстовыми и конвертирует. Повторный тест тем же способом
(`git worktree add --detach /tmp/wt_after HEAD` после коммита `.gitattributes`) →
**656/656 OK**. Оба worktree удалены (`git worktree remove --force`), рабочее дерево основного
репозитория не трогалось ни на одном из шагов проверки.

### 3.2. Предложение (НЕ реализовано) — защита от будущих незаметных правок

Заморозка теперь доказуема через git: любая правка `tests/corpus/{docs,gold.json,MANIFEST.sha256,
_model,corpus_lib.py,generate.py,mutate.py,validate.py}` начиная с `c48abd1` — видимый диф в
истории, а не тихое расхождение с чужим представлением о «замороженном». Для защиты от
случайной/незамеченной правки в будущих PR предлагаю (решение и реализация — за пользователем):

- CI-проверка на PR: `git diff --stat <base>...<PR-head> -- tests/corpus/docs tests/corpus/gold.json tests/corpus/MANIFEST.sha256 tests/corpus/_model` должен быть пуст, если PR НЕ помечен лейблом (например) `corpus-change`. Непустой диф без лейбла — красный статус, а не молчаливый мердж.
- Тот же PR, но С лейблом `corpus-change`, дополнительно должен требовать: `MANIFEST.sha256` пересобран (`sha256sum` в списке файлов PR совпадает с новым содержимым — простая проверка, что автор не забыл обновить манифест вместе с содержимым) и обновлён `results_baseline.json` регресс-гейта (иначе 0d увидит фантомный регресс/улучшение от смены эталона, как уже было на переходе 0c→0b-fix).
- Отдельно от CI: `tests/corpus/validate.py` (сверка каждого спана `gold.json` с файлом на диске) стоит гонять в `slow`-наборе pytest, если это ещё не так — он ловит рассогласование эталона с текстом независимо от git-истории.
