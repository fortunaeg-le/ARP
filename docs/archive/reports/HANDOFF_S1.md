# HANDOFF — Этап S1: гигиена данных и жизненный цикл разметки

Ветка `u1-desktop-packaging` (незакоммичено — по постановке этой сессии). Три
независимые правки в слое хранения (`src/storage.py`, минимально
`src/session_store.py` — только новые поля payload), `app/core.py`,
`app/server.py`, `app/index.html`. **Детекция НЕ тронута — 0 правок в `src/`
за пределами `storage.py`/`session_store.py`.**

## 0. Зачем

Архитектурный аудит (`docs/archive/reports/ARCHITECTURE_AUDIT.md`, §3.6/§5.10) нашёл три
самостоятельные, но связанные дыры в слое хранения:

1. Разметка (U3) — единственный источник будущего эталонного корпуса —
   удалялась вместе с сессией и её 24-часовым TTL, то есть исчезала раньше,
   чем накапливалась.
2. `{sid}.doc.json` сериализовал служебные кеши детекции как побочный эффект —
   лишние копии ПДн на диске без необходимости.
3. Запись маски не несла провенанс (`detector`) — GLiNER-ярус, анализ
   ручной/автоматической разметки, замер «какой механизм сработал» были
   архитектурно невозможны.

## 1. Задача 1 — разметка переживает сессию

### Решение

Разметка вынесена в **отдельное хранилище**, `default_markup_dir()` —
`~/.shifrator/markup/` (сосед `~/.shifrator/sessions/`, не внутри неё). Два
независимых жизненных цикла:

| | сессия восстановления | разметка (U3) |
|---|---|---|
| назначение | обратная подстановка ПДн | эталонный корпус для будущего анализатора |
| срок | 24 ч (TTL, без изменений) | **30 дней** (новая политика, см. ниже) |
| хранилище | `~/.shifrator/sessions/` | `~/.shifrator/markup/` |
| удаление сессии | стирает `.enc/.txt/.meta/.doc` | **НЕ трогает разметку** (по умолчанию) |
| `purge_expired` (сессии) | чистит просроченные `.enc` + сиротские sidecar | **не видит `markup/` вообще** |

### Политика срока — обоснование

**30 дней, а не бессрочно и не 24 часа.** Разметка нужна для накопления
эталонного корпуса — это процесс, растянутый на недели пилотного использования
(разметка = побочный продукт КАЖДОЙ проверки документа, не отдельное усилие),
поэтому 24-часовой TTL сессии для неё бессмыслен — корпус не успеет
накопиться. Но разметка по-прежнему содержит фрагмент РЕАЛЬНОГО текста
документа (поле `value`) — то есть ПДн открытым текстом, поэтому «хранить
вечно молча» — запрещённый инвариантом «срок не бесконечен» вариант. 30 дней —
достаточно, чтобы пережить перерывы между рабочими сессиями пользователя, и
достаточно коротко, чтобы не превращаться в тихое бессрочное хранилище.
Реализовано как `purge_expired_markup(ttl_days=30)` — **отдельная функция**,
не вызывается автоматически внутри `purge_expired()` сессий (тот её вообще не
видит); библиотечная, вызывается явно (аналогично тому, как CLI сам вызывает
`purge_expired` сессий перед `decrypt`).

### Управление разметкой (видимость + явное удаление)

- Экран проверки (`app/index.html`, панель «Ваши правки») теперь показывает
  **явное предупреждение**: разметка хранится отдельно и дольше сессии
  (N дней, не 24 часа), содержит фрагменты текста документа; динамическая
  сводка (`GET /api/markup/summary` → `storage.markup_summary()`) — сколько
  записей, по скольким сессиям, дата самой старой.
- Кнопка «Удалить всю накопленную разметку (все сессии)» →
  `POST /api/markup/delete-all` → `storage.delete_all_markup()`.
- Диалог удаления ОДНОЙ сессии теперь задаёт **второй явный вопрос**: удалить
  ли и накопленную разметку этой сессии — `delete_session(sid,
  delete_markup=True)` → `storage.delete_session_markup(sid)`. По умолчанию
  (без флага) разметка сохраняется.

### Миграция

`storage.migrate_legacy_markup()` — переносит `{sid}.markup.json`, сохранённые
ДО этого этапа (лежали в директории сессий), в новое хранилище; сливает по
`id`, если файл почему-то уже есть в обоих местах; идемпотентна. Вызывается
**один раз при старте UI** (`app/server.py::main` → `_migrate_legacy_markup_once`),
до старта HTTP-сервера; сбой переноса не блокирует запуск (только
предупреждение в stderr — та же осторожность, что у `save_session_meta`).
Проверено тестом `test_migrate_legacy_markup_moves_and_merges`
(`tests/test_storage_s1.py`): файл в старом месте → миграция → читается из
нового, старый файл удалён, повторный вызов — no-op.

### Приёмка (задача 1)

1. Разметка переживает удаление сессии и `purge_expired` с истёкшим TTL —
   `test_markup_survives_session_deletion`,
   `test_markup_survives_purge_expired_of_session`. Проверено и живым сервером
   (см. §4).
2. Отдельное удаление разметки (одна сессия / все) —
   `test_delete_session_markup_standalone_action`, `test_delete_all_markup`,
   и живым HTTP (см. §4).
3. Миграция — `test_migrate_legacy_markup_moves_and_merges`.

## 2. Задача 2 — `{sid}.doc.json` не раздувает лишние копии ПДн

### Что убрано и почему это безопасно

`segment.metadata` после `run_detection` содержит служебные кеши производных
видов текста, которые кладут туда детекторы **для собственного использования
во время детекции**:

| ключ | кто пишет | что это |
|---|---|---|
| `detection_text` | `extractor.py` | регистро-нормализованная копия текста сегмента |
| `_norm_cache` | `normalizer.py` (`detection_view`) | ещё одна нормализованная копия + карта индексов |
| `_anchor_search_cache` | `anchor_registry.py` (`anchor_search_view`) | копия текста для ORG/PER-якорей |
| `_per_search_cache` | `anchor_registry.py` (`per_search_view`) | копия текста для PER-якорей |

Все четыре — **производные полные копии текста сегмента** (кроме `_norm_cache`,
где ещё и карта индексов той же длины). Ни один из них не читается НИГДЕ после
завершения `run_detection`/`tokenize`: экран проверки и пересборка
(`app/core.py::_render_state/_validate_missed/_add_missed`,
`tokenizer._assemble/_render_segment`) работают только с `s.text`,
`s.source_type` и структурными ключами `metadata` (`paragraph_index`, `style`,
`table_index`/`row_index`/`col_index`) — проверено `grep`'ом по `app/` и
`tokenizer.py` (ноль совпадений на все четыре ключа). `load_doc_segments`
используется ТОЛЬКО для рендера текущего состояния и добавления РУЧНЫХ масок —
детекция здесь заново не запускается, значит эти кеши физически не нужны на
этом пути.

`storage._strip_detection_caches()` фильтрует эти четыре ключа из `metadata`
ПЕРЕД сериализацией в `save_doc_segments`; `load_doc_segments` не менялся
(просто читает то, что записано).

### Числа (реальный конвейер, не синтетика)

Замерено на `tests/fixtures/synthetic_many_styles.docx` (284 стиля — фикстура
E2-CORPUS-POVERTY) и `tests/corpus/docs/agency_0002.docx`, реальным
`extract`→`run_detection`→`tokenize`, наивная сериализация (все поля
`metadata` как раньше) против новой:

| документ | наивный размер | новый размер | во сколько раз меньше |
|---|---:|---:|---:|
| `synthetic_many_styles.docx` | 884 028 байт | 131 392 байт | **6.7×** |
| `agency_0002.docx` (корпус) | 63 963 байт | 8 211 байт | **7.8×** |

(Аудит на другом сегменте нашёл до 17.8× на уровне ОДНОГО сегмента — разброс
ожидаем: доля JSON-накладных расходов/структурных полей зависит от длины
сегмента и числа сегментов документа; порядок величины подтверждён.)

**Копий ПДн в файле: было 4 (`s.text` + 3 полные копии в кешах,
`detection_text` — 4-я при аномальном регистре), стало 1 (`s.text`)** —
единственная, необходимая для восстановления/рендера экрана проверки.

### Round-trip не пострадал

- `test_doc_segments_roundtrip_survives_cache_strip` (`tests/test_storage_s1.py`)
  — `load_doc_segments` после strip отдаёт сегмент, чьего `.text` достаточно

## 3. Задача 3 — провенанс маски

### Схема

`models.Entity` уже имел поля `detector` (`"regex"`/`"ner"`, обязательное) и
`group_key` (`"PER:5"`/`"ORG:12"`/`None`, этап E) — детекторы их и так
проставляли, но `session_store.save_session` их **не сериализовал** (главная
находка аудита §3.2 п.3). Правка — чисто в слое сериализации:

- запись сессии (на токен) получила два новых поля: `detector` и `group_key`
  — значения ПЕРВОГО вхождения (та же v1-конвенция, что у `original_text`/
  `segment_id`);
- КАЖДОЕ вхождение в `occurrences[]` тоже несёт `detector`/`group_key` СВОЕГО
  вхождения (не только записи в целом) — так провенанс не теряется, если
  внутри одного токена смешаны автоматические и вручную поправленные
  вхождения (например, «поправить границу» у одного конкретного вхождения).

`detector` пишется ВЕРБАТИМ, без переинтерпретации — это то же значение, что
детекторы (`regex_detector`/`multispan`/`anchor_registry`/`ner_detector`/
`syntax_compound`) и так проставляют в `Entity.detector` (см. `grep detector=`
в `src/`). "PER:5"/"ORG:12" из `group_key` — это и есть "какое правило" из
постановки: конкретная запись реестра кореференции, к которой отнесено
вхождение.

**Почему не введены новые категории вида "structural"/"multispan".** Сейчас
`Entity.detector` содержит только `"regex"`/`"ner"`/`"manual"` — это НЕ
описание механизма буквально, а сигнал арбитража пересечений
(`tokenizer._winner`: `regex` побеждает при равной уверенности). Структурный
ORG/PER-якорь (`anchor_registry`) и настоящий Natasha/yargy-NER (ADDRESS) ОБА
сейчас помечены `"ner"` — это заложено в `tokenizer.py` и трогать эту
семантику значило бы менять логику разрешения пересечений, что прямо запрещено
границами этой сессии («логику правил... не касаться»). Точная детализация
механизма (structural vs statistical NER) потребовала бы правки самих
детекторов (`anchor_registry.py`/`ner_detector.py`/`multispan.py` — эмиссия
`Entity`), что вне периметра `storage.py`/`session_store.py`. Решение —
поднять то, что реально есть (`detector`+`group_key`), а не изобретать новую
таксономию поверх чужого слоя. Если нужнее детальный провенанс — отдельная,
согласованная с детекцией сессия (см. STOP-примечание ниже).

### Ручные маски U3 отличимы от автоматических

`app/core.py::_add_missed` — вручную добавленное вхождение получает
`detector="manual"`, `group_key=None` явно.

**Найден и исправлен побочный дефект** в `apply_pending_markup`: код
перезаписывал **ВСЕ** сущности сессии (включая давно стоявшие автоматические)
значением `detector="manual"` при КАЖДОЙ пересборке — то есть после первой же
ручной правки автоматические маски теряли провенанс безвозвратно. Исправлено:
пересборка теперь читает `occ.get("detector")`/`occ.get("group_key")` каждого
конкретного вхождения и переносит их как есть — «manual» остаётся только у
вхождений, реально добавленных через разметку.

### Обратная совместимость

Сессии, сохранённые до этого этапа, не содержат `detector`/`group_key` в JSON
вообще (поля отсутствуют, не `null`). `_entities_from_session` (`app/core.py`)
и все точки чтения используют `.get(...)` — отсутствие поля не роняет загрузку.
Проверено `test_old_session_without_provenance_still_loads`: вручную собранная
legacy-сессия (формат `v2` без provenance-полей) читается `storage.load_session`
без исключений.

### Приёмка (задача 3)

  `test_session_persists_manual_detector`,
  `test_old_session_without_provenance_still_loads` (`tests/test_storage_s1.py`).

## 4. Живая проверка (не моки)

Через реальный `app/server.py` на изолированном временном профиле
(`USERPROFILE`/`HOME` подменены, не трогали настоящий `~/.shifrator`):

1. `encrypt` (txt) → `session_id`.
2. `mark-missed` → `GET /api/markup/summary` возвращает `{sessions:1,
   entries:1, ttl_days:30, oldest_created_at:<реальная дата>}`.
3. Кнопка «Удалить всю разметку» (через `POST /api/markup/delete-all` из
   браузера, реальный DOM/JS, не прямой вызов) → summary `{sessions:0,
   entries:0}`; `GET /api/sessions` показывает сессию НЕТРОНУТОЙ.
4. Новая сессия + разметка → `session-delete` с `delete_markup:false` →
   сессия исчезает из `/api/sessions`, разметка остаётся в summary.
5. Новая сессия + разметка → `session-delete` с `delete_markup:true` →
   сессия исчезает, разметка ИМЕННО ЭТОЙ сессии не добавляется к общему
   счётчику (проверено сравнением summary до/после).
6. Панель «Ваши правки» в браузере (реальный DOM, `read_page`) — предупреждение
   и кнопка рендерятся; после `loadMarkupSummary()` текст заполняется живыми
   значениями с сервера (`ttl_days`, число записей, дата).
