## ШАГ 0. Что именно протекало

### 0а. Как устроен сторож

`assert_structural(report)` (`app/report.py`) обходит готовый отчёт целиком
(`_walk`) и требует, чтобы КАЖДАЯ строка — и ключ, и значение — прошла
`_string_ok`. Веток было пять:

1. ключ входит в `_SCHEMA_KEYS` (только для ключей);
2. строка входит в `_ALLOWED_VALUES` (коды словарей: типы, детекторы,
   контейнеры, регистровые формы, наборы типов);
3. значение дословно совпадает с одним из текстов-констант модуля (`_FIXED_PROSE`);
4. строка совпадает с `_ISO_RE` (дата);
5. **строка совпадает с `_BUILD_RE` = `^[A-Za-z0-9][A-Za-z0-9._-]{0,63}$`.**

Ветка 5 заведена ради ОДНОЙ вещи — слага версии сборки: это единственная строка
отчёта, которую нельзя перечислить заранее. По замыслу она должна была работать
в трёх местах схемы, где слаг и живёт: значение `tool_build`, значение
`findings[].build`, ключи словаря `by_build` (он «слаг → счётчики»). Фактически
она применялась к КАЖДОМУ ключу и КАЖДОМУ значению отчёта, потому что
`_string_ok` не знала, где в схеме находится проверяемая строка.

### 0б. Что реально проходило — прогоном

`report.assert_structural(...)`, семь случаев из задания:

| случай | где | ДО починки | ПОСЛЕ починки |
|---|---|---|---|
| новое поле с латинским именем (`totally_new_field`) | ключ | **НЕ отсекалось** | отсекается |
| адрес эл. почты (`ivanov@example.com`) | значение | отсекался | отсекается |
| имя файла (`dogovor.docx`) | значение | **НЕ отсекалось** | отсекается |
| название организации латиницей (`Gazprom-Neft`) | значение | **НЕ отсекалось** | отсекается |
| доменное имя (`sberbank.ru`) | значение | **НЕ отсекалось** | отсекается |
| фамилия транслитом (`Ivanov`) | значение | **НЕ отсекалось** | отсекается |
| фамилия кириллицей (`Иванов`) | значение | отсекалась | отсекается |

**Уточнение к формулировке находки T1-A.** В задании (и в исходном тексте
находки) сказано, что через дыру проходят адреса электронной почты. Прогон это
не подтвердил: символа `@` нет в классе `_BUILD_RE`, поэтому e-mail целиком
отсекался и до починки. Протекали имя файла, домен, название организации
латиницей, фамилия транслитом и любое новое поле с латинским именем — то есть
дыра реальна и класс «латиница проходит» верен, но конкретно e-mail в него не
входил. Заметим: **домен из адреса** (`yandex.ru`) и **локальная часть**
по отдельности форму слага имеют и проходили.

### 0в. Попадает ли это в отчёт НА САМОМ ДЕЛЕ

Факт, а не рассуждение: живой сервер (`app/server.py`), реальный конвейер,
документ корпуса `tests/corpus/docs/agency_0001.txt`, в котором есть два адреса
электронной почты (`novikova@…`, `zaycev@…`). Сценарий: шифрация → отклонение
автоматической маски e-mail на экране проверки (в записи разметки при этом
`value` = сам адрес, проверено) → сборка отчёта по HTTP `/api/report`.

Единственная находка отчёта — по этому самому адресу:

```
document 1 | kind false_mask | entity_type EMAIL | detector regex
container text_line 47 | length_chars 18 | tokens 1
has_digits нет | has_latin да | has_cyrillic нет | has_punct да
has_initials нет | case_shape lower | build u1b-rebuild-20260725
```

Полный состав строк отчёта — только схемные ключи, коды закрытых словарей
(`EMAIL`, `regex`, `text_line`, `lower`, `personal`, `session`, `false_mask`, …),
ISO-даты, проза-константы модуля и ОДНА свободная строка: слаг сборки
`u1b-rebuild-20260725` (в `tool_build`, в `findings[].build` и ключом `by_build`).
Фрагментов документа — ноль.

**Вывод.** По существующему пути в отчёт не приходит ничего, кроме кодов: первые
два рубежа (белый список `_FINDING_FIELDS` и нормализация `_norm_*`) держат.
Дыра в стороже была ЛАТЕНТНОЙ — она снимала защиту от будущего промаха, а не
выносила текст сегодня. Это и есть причина чинить: сторож существует ровно на
случай, когда первые два рубежа однажды пропустят.

## ШАГ 1. Починка

`_string_ok` получила параметр `path` — путь обхода, который `_walk` и так вёл
для сообщений об ошибке. Ветка слага сборки разрешена теперь не по виду строки,
а по МЕСТУ (`_build_slug_allowed`):

* значение `report.tool_build`;
* значение `report.findings[N].build`;
* КЛЮЧ словаря `report.by_build`.

Везде остальном свободная латиница отвергается наравне с кириллицей. Заодно
ветка ISO-даты ограничена значениями (ключом дата не бывает).

Белые списки полей НЕ расширялись. Ничего законного проходить не перестало:
отчёт по документу корпуса из шага 0в, собранный до и после починки, побайтно
идентичен (кроме `generated_at`/`period`), и проходит починенного сторожа.

## ШАГ 2. Маркерный тест

`tests/test_u4_report.py::test_guard_rejects_marker_everywhere` — 7 видов
маркера × 4 места внесения = 28 случаев:

* виды: маркер целиком; маркер в другом регистре; подстрока маркера от 6
  символов (та же длина окна `_WINDOW`, что у теста на утечку); маркер латиницей
  в трёх формах слага (имя файла, транслит, домен); маркер кириллицей;
* места: значением поля находки, ключом словаря, элементом списка, новым полем
  отчёта.

Плюс обратная сторона — `test_guard_still_lets_the_build_slug_through_where_it_belongs`:
слаг сборки проходит в своих трёх местах и НЕ проходит, будучи положенным в
`scope`. Без него «починка» могла бы свестись к запрету латиницы вообще.

**Красное состояние показано.** Возврат старого поведения (безусловное
`if _BUILD_RE.match(s): return True` в `_string_ok`) даёт:

```
13 failed, 16 passed
```

— падают все латинские случаи маркерного теста во всех четырёх местах и снятый
маркер T1-A. С починкой: `91 passed` (`test_u4_report.py` + `test_type_policy.py`).
