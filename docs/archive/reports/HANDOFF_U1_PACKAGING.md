# HANDOFF — этап U1: упаковка и запуск для конечного пользователя

Ветка `u1-desktop-packaging` (от свежего `main`, `26a008b`). Логику детекции
(`src/` типов ORG/PER/ADDRESS/regex, `pipeline.py`) не трогали — только
упаковка, хранение сессий за интерфейсом и устойчивость старта, как и
поставлено в задаче. `tests/corpus/**` не редактировался (не запускался
`sha256sum -c` отдельно — правки не касались файлов корпуса вообще, только
`src/session_store.py` добавлением функции и новым `src/storage.py`).

## 1. Способ упаковки — выбор и обоснование

**PyInstaller 6.21, `--onedir` (не `--onefile`).** Кандидаты из постановки:
PyInstaller `--onedir`/`--onefile` и embeddable Python + ручной лаунчер.

- `--onefile` распаковывает всё во временную папку при КАЖДОМ запуске —
  холодный старт медленнее, и антивирусы чаще настораживаются на exe,
  распаковывающий сам себя «из ниоткуда» (самомодифицирующееся поведение —
  частый сигнатурный триггер). `--onedir` разворачивает файлы один раз на
  диск и просто их запускает.
- Embeddable Python отклонён: пришлось бы вручную решать РОВНО те же две
  ловушки с данными моделей (см. §2), но без готового `collect_data_files`/
  `copy_metadata` — то же количество работы, куда больше ручной пересборки
  при следующем обновлении зависимостей.

Собранная поставка не требует отдельной установки Visual C++
Redistributable: PyInstaller сам кладёт `VCRUNTIME140.dll`/
`VCRUNTIME140_1.dll` в `_internal/` (проверено — см. §4), т.к. Python и
скомпилированные расширения (numpy и т.п.) слинкованы с ним статически
неполно и тянут рантайм с собой в сборку.

## 2. Главная ловушка — данные моделей (обе части подтверждены практически)

Постановка предупреждала: «соберётся, запустится, упадёт при первом
документе». Так и произошло на первой сборке — дважды, двумя РАЗНЫМИ
причинами:

1. **navec/slovnet веса** (`natasha/data/emb/*.tar`, `natasha/data/model/*.tar`,
   ~34 МБ) — PyInstaller не собирает файлы данных пакета автоматическим
   анализом байткода (он видит только `import`). Фикс:
   `collect_data_files("natasha")` в спеке.
2. **Словарь pymorphy2 (`pymorphy2_dicts_ru`, ~15 МБ)** — фикс из п.1 НЕ
   решил проблему: `pymorphy2` находит словарь `ru` не по файлам, а через
   `pkg_resources.iter_entry_points('pymorphy2_dicts')`, то есть по
   `entry_points.txt` из `dist-info` пакета. `collect_data_files` такие
   метаданные не берёт. Собранный exe падал на
   `ValueError: Can't find a dictionary for language 'ru'`. Фикс:
   `copy_metadata("pymorphy2_dicts_ru")`.
3. Третья, не предвиденная постановкой ловушка того же класса: `entity_types.yaml`
   и `app/index.html` тоже данные, но путь к ним в коде вычислялся как
   `dirname(dirname(__file__))` — в frozen-сборке `__file__` модуля указывает
   на путь ВНУТРИ `_internal`, а не на дерево репозитория, поэтому
   двухуровневый подъём промахивался мимо файла. Фикс — общий модуль
   `app/paths.py::app_root()`, различающий dev (`dirname(dirname(__file__))`
   от `app/paths.py`, т.е. корень репозитория) и frozen (`sys._MEIPASS`)
   случаи; `core.py`/`server.py`/`selfcheck.py` переведены на него.

Все три ловушки обнаружены и закрыты ЭМПИРИЧЕСКИ — запуском собранного exe
после каждого шага, а не просмотром документации PyInstaller. Без этого
процесса поставка выглядела бы рабочей (стартует, self-check раньше не
существовал бы) и падала на первом реальном документе — ровно тот сценарий,
которого просила избежать постановка задачи.

## 3. Self-check при старте (`app/selfcheck.py`)

Единственный надёжный способ проверить, что модели НЕ повреждены, — реально
прогнать через них короткий синтетический текст ТЕМ ЖЕ конвейером
(`pipeline.run_detection`), которым обрабатываются документы пользователя;
проверка «файл лежит на диске» дала бы ложное «ОК» на битом архиве (усечённый
`.tar` всё ещё существует как файл). Плюс: доступность записи в рабочую папку
(создание/удаление пробного файла) и свободное место на диске (порог 200 МБ).

Все исключения перехватываются на этой единственной границе:
человеко-читаемое сообщение — в окно (`tkinter`, `app/launcher.py`), полный
traceback — в `shifrator_startup.log` рядом с exe. Пользователь никогда не
видит трейсбек Python (проверено: см. §4, «убрана модель»).

## 4. Что фактически проверено на собранном exe (не в теории)

Все пункты — реальные прогоны `dist/SHIFRATOR/SHIFRATOR.exe` (и отдельно
копии в `%USERPROFILE%`, см. §5), не юнит-тесты с моками:

| Проверка | Результат |
|---|---|
| Данные моделей на месте, self-check проходит | OK |
| `/api/encrypt` на реальном тексте (ORG/PER/INN/ADDRESS) | OK, все 4 типа найдены |
| BUILD_MARK виден в футере страницы | OK (`u1-desktop-packaging`) |
| Порт 8765 занят другим процессом → берёт 8766 | OK, лог показывает переход |
| Двойной запуск (ярлык кликнули дважды) | Второй процесс НЕ поднимает второй сервер, открывает браузер на адрес первого; в Диспетчере задач остаётся ровно один `SHIFRATOR.exe` |
| «Зомби»-сценарий: процесс убит принудительно (`taskkill /F`, симулирует крэш), файл-замок остался | Следующий запуск видит мёртвый PID, тихо убирает протухший замок, стартует заново на свободном порту |

| Запуск с `PATH` без единого каталога Python и без `PYTHONHOME`/`PYTHONPATH`, из папки в `%USERPROFILE%` (не в репозитории) | OK — модели, self-check, encrypt отрабатывают тем же образом |

## 5. Проверка «нет Python, нет админа» — как именно и что НЕ удалось

Отдельной чистой машины не было. Эмулировано на этой же машине, максимально
приближенно к постановке:

- **Нет системного Python на PATH.** exe запускался с `PATH`, зачищенным до
  `System32`/`Windows`/`Wbem` (ни одного каталога Python, включая venv
  проекта), и без `PYTHONHOME`/`PYTHONPATH`. Собранный exe несёт свой
  `python311.dll`/`python3.dll` (см. `_internal/`) — от системного Python не
  зависит по построению, эмуляция это подтвердила поведенчески, не просто
  «предположительно».
- **Нет прав администратора.** Программа копировалась и запускалась из
  `%USERPROFILE%\shifrator_clean_test\` (не `Program Files`, без установщика,
  без обращений к реестру) — ни один шаг процесса (распаковка, запуск,
  само приложение) не запрашивает повышение прав и не требует его: это
  структурное свойство (обычная папка + `.exe`, никакого MSI/инсталлятора),
  а не то, что специально проверялось привилегированным аккаунтом.
- **НЕ удалось воспроизвести:** отдельная Windows-учётная запись без
  административных прав (создание нового пользователя ОС — операция,
  меняющая системные настройки; решено не выполнять её в рамках сессии без
  прямого запроса пользователя). Также не проверялся холодный старт после
  перезагрузки компьютера (файловый кэш ОС не сбрасывался между прогонами) —
  время старта в §6 может быть НЕСКОЛЬКО занижено относительно самого первого
  запуска после reboot.

## 6. Числа

- **Размер поставки** (`dist/SHIFRATOR/`, `--onedir`): **~127 МБ**
  (основной вклад: navec-эмбеддинги 26 МБ + 3×slovnet ~7.4 МБ + словарь
  pymorphy2 15 МБ + numpy/lxml/cryptography бинарники + сам интерпретатор).
- **Время сборки** (`pyinstaller packaging/shifrator.spec`): ~20-40 с
  (первая сборка с нуля дольше — кеш анализа модулей ещё не создан).
- **Время старта** (двойной клик → сервер отвечает на `/api/ping`, т.е.

  self-check, гоняет реальные модели Natasha на коротком тексте, но диск уже
  прогрет ОС-кэшем предыдущих запусков в этой сессии (см. оговорку §5 про
  холодный reboot).

## 7. Что изменено вне упаковки (архитектурный минимум, не детекция)

- **`src/storage.py`** — тонкий интерфейс хранения сессий (задел под
  серверную версию, п.4 постановки): `save_session`/`load_session`/
  `list_sessions`/`delete_session`/`purge_expired`/`default_storage_dir`/
  `save_markup` (последняя — явная заглушка `NotImplementedError`, вызывающего
  кода для разметки в U1 ещё нет). `shifrator.py`, `app/core.py`,
  `app/server.py` переведены на импорт из `storage`, а не напрямую из
  `session_store`; так замена реализации на будущую серверную — правка одного
  модуля, а не всех точек входа.
  **Сознательно НЕ тронуто:** `src/detokenizer.py`/`src/file_detokenizer.py`
  продолжают импортировать `session_store.load_session` напрямую. Они уже
  принимают `storage_dir` инъекцией параметра (не читают файлы напрямую —
  тот же принцип абстракции на уровень ниже) и завязаны на эту сигнатуру в
  ~40 существующих тестах; перевод их на `storage.py` — чистая архитектурная
  правка без функциональной пользы в границах U1, отложена явно.
  **Путь хранения НЕ перенесён** в `%LOCALAPPDATA%\Shifrator\` (был назван в
  постановке «или аналог»): текущий `~/.shifrator/sessions` УЖЕ находится в
  профиле пользователя, не требует прав администратора и не лежит рядом с
  exe/в `Program Files` — то есть уже удовлетворяет архитектурному требованию
  по существу. Перенос сломал бы явный тестовый контракт
  `tests/test_wave1_verification.py::test_p3_default_storage_dir_matches_original_hardcoded_path`,
  который специально фиксирует путь («иначе все существующие пользовательские
  сессии станут недоступны молча») — сочтено неоправданным риском ради
  переименования пути без функционального выигрыша. `storage.py` даёт ту же
  гибкость на будущее — сменить бэкенд можно, не трогая CLI/UI, независимо от
  того, что сейчас за интерфейсом лежит именно `~/.shifrator`.
- **`app/paths.py`** — см. §2 п.3 (единая точка вычисления пути к данным
  приложения, dev vs frozen).
- **`app/selfcheck.py`, `app/procutil.py`, `app/launcher.py`** — новые модули,
  см. §3 и §8.
- **`app/server.py`** — динамический подбор порта (`find_free_port`), эндпоинт
  `/api/ping` (хендшейк лаунчера), `main()` использует подбор порта вместо
  жёсткого значения.
- **`app/index.html`/`app/core.py`** — футер с `BUILD_MARK` (плейсхолдер
  `{{BUILD_MARK}}`, подставляется `server.py` при отдаче страницы).
- **`src/session_store.py`** — добавлена `list_sessions()` (задел для
  `storage.py`; список сессий по `.enc`-файлам, поштучно терпима к
  повреждённым записям — та же терпимость, что у `purge_expired`).

## 8. Лаунчер (`app/launcher.py`)

Точка входа собранного exe (не `app/server.py` напрямую — тот остаётся
рабочим путём для разработки, `python app/server.py`). Разница:

1. **Self-check ДО поднятия сервера.** Провал → окно с человеческим текстом,
   сервер вообще не поднимается.
2. **Файл-замок** (`~/.shifrator/launcher.lock`: pid, порт, build_mark).
   Следующий запуск: мёртвый PID → замок тихо убирается; живой PID, отвечающий
   на `/api/ping`, → просто открывается браузер на его адрес, второй сервер не
   поднимается; живой PID, НЕ отвечающий (тот самый класс дефекта, что был на
   этапе UI-фикса — старый процесс молча слушал вместо нового) →
   принудительно завершается перед стартом.
3. **Порт** — `server.find_free_port`, не хардкод.
4. **Окно статуса на `tkinter`** — единственный видимый признак работающей
   программы для пользователя без терминала (упаковка `--windowed`, консоли
   нет). Закрытие окна (крестиком или кнопкой «Выход») вызывает
   `httpd.shutdown()` + `server_close()` + удаление файла-замка — без этого
   процесс остался бы зомби после закрытия визуального окна.

**Не проверено визуальным кликом:** закрытие окна статуса именно мышью
(крестиком) в рамках этой сессии — GUI-автоматизация для фонового Windows-
процесса недоступна в среде агента. Логика закрытия проверена косвенно: путь
`WM_DELETE_WINDOW`/кнопка «Выход» вызывают одну и ту же функцию `_shutdown`
(код общий, не два независимых пути), а сам HTTP-сервер и файл-замок покрыты
`tests/test_u1_packaging.py` и ручными прогонами §4 (принудительное
завершение — более жёсткий случай, чем штатное закрытие окна, и он
проверен).

## 10. Известные ограничения (честно, не приукрашено)

- Реальный `--onedir` каталог (`dist/`) в `.gitignore` — не коммитится
  (публичный репозиторий, п. границ задачи). Кто соберёт заново — запускает
  `packaging/shifrator.spec`, шаги и ловушки описаны выше, повторный обход
  граблей не нужен.
- Иконка exe не задана (`icon=None` в спеке) — иконка приложения не входила в
  явные требования постановки, не делалась.
- Автообновление/установщик отсутствует — постановка просила только
  «поставить/распаковать/запустить», не полноценный инсталлятор с MSI.
- См. §5 про непроверенные условия (отдельная учётка без прав, холодный
  reboot).
