## 4. НАХОДКИ — то, что пряталось за «известным шумом»

### S2-1. E′/E″ не в HEAD — см. §1. Тяжесть: постановочная (блокирует пункт 5).

### S2-2. Обвал границ ADDRESS спрятался за РОСТОМ агрегата masking B ⚠ главная

Агрегат B вырос 79.59% → 86.79% и во всех отчётах читался как улучшение
(этап C прямо заявлял «masking B 79.6→86.1%»). Разбор ПО ТИПАМ МАСКИ:

| тип маски | масок 2b→HEAD | **B границы** | C тип |
|---|---:|---:|---:|
| **ADDRESS** | 5265 → 1337 | **75.33% → 51.39%** ⚠ | 83.40 → 99.25% |
| PER | 3761 → 2549 | 62.32% → 87.86% | 98.87 → 99.73% |
| ORG | 4002 → 1128 | 66.28% → 94.41% | 44.01 → 54.29% |
| PASSPORT | 635 → 635 | 98.58% → 97.64% | 100% |

**Агрегат вырос ПОТОМУ, что у ADDRESS упало ЧИСЛО масок** (5265→1337), то есть
упал его вес в общем знаменателе, а PER/ORG подтянулись. Границы ADDRESS при
этом обвалились: эталонный адрес теперь закрывается маской целиком лишь в
половине случаев. Ни один HANDOFF этого не сообщал — метрика по типам масок
для B/C никогда не печаталась.

**Независимое подтверждение:** 117 ADDRESS-сущностей имеют обрезанные границы
и потекли (§4/S2-3) — тот же класс, измеренный другим прибором.

**Что сделано:** гейт теперь проверяет линии «в»/«г» **по каждому типу маски**,
а не только по агрегату (§5.2); заведён регресс-тест, воспроизводящий ровно эту
конфигурацию (тип обваливается 100%→0%, агрегат при этом РАСТЁТ 54.55%→90.91%,
гейт обязан краснеть).

### S2-3. Утечка ADDRESS +241 объяснена лишь НАПОЛОВИНУ; 89 случаев — артефакт метрики

Из 210 ADDRESS, которые «детектируются, но потекли»:

* **117 — обрезанные границы** (`trim`). Реальная потеря, согласуется с S2-2.
* **89 — границы ТОЧНЫЕ** (`exact`). Маска покрывает эталон полностью, а метрика
  всё равно считает утечку. Разбор фрагментов: `ekatepиhбypг`, `bopoheж`,
  `cahkt`+`пetepбypг`, `kaзahь`, `xиmkи`, `cepгиeb`+`пocaд` — **названия городов
  и голые числа `2`/`3`/`4`**. При точных границах значение может «выжить»
  только ВНЕ размеченного спана — то есть топоним встречается в документе ещё
  раз (датолайн «г. Екатеринбург, 15 марта 2024»), и метрика засчитывает это
  как утечку адреса.

Это ровно та **ненадёжность `leak_v2_address` на повторе топонима**, что уже
записана в проектной памяти, но её ВКЛАД в цифру ADDRESS никогда не выделялся.
**Следствие: рост ADDRESS-утечки 141→382 нельзя целиком относить к этапу C —
до ~89 из 241 могут быть артефактом измерения, а не потерей защиты.**

> НЕ ЧИНИЛ И НЕ ПОДГОНЯЛ. Правка метрики — это правка знаменателя гейта в той
> же сессии, где гейт замораживается; делать это одновременно нельзя. Вынесено
> как задача отдельной сессии. Цифры в §3.1 приведены КАК ЕСТЬ.

## 5. УСТРОЙСТВО ГЕЙТА

### 5.1. Два гейта сведены в один

Было: `tests/corpus/gate.py` (leak/FP/masking, база `results_baseline.json`) +
`experiments/stage_d/gate_d.py` (precision/долг, база `baseline_d.json`).
Пересечение — только «креши». Полная картина существовала лишь у того, кто
запустил оба (аудит §4.7), а `gate_d` без аргумента читал ЗАКОММИЧЕННЫЙ
`results_d_head.json`, из-за чего «запустил, зелёный» было валидным описанием
измерения недельной давности (§5.8).

Стало: **`tests/corpus/gate.py` — единственный гейт, ОДНА база**
(`results_baseline.json` — полный дамп прогона, из него считаются ВСЕ метрики,
второй baseline не нужен), **ОДИН прогон корпуса**. `gate_d.py` оставлен с
баннером «УСТАРЕЛ» — он провенанс цифр этапа D; семантика `_missed_leak_ids`
перенесена БЕЗ изменений.

Устаревший дамп больше не даёт зелёного молча: гейт сам гоняет корпус, а чтение
готового файла — явный флаг `--results` с печатью оговорки о свежести.

### 5.2. Четыре линии

| линия | что охраняет | где считается | допуск |
|---|---|---|---|
| **(а)** precision ORG/PER/ADDRESS | «стали маскировать лишнее» | `precision_by_type` (ось D) | 0.00 пп |
| **(б)** leak_v2 ≥6 и ≥8 | «стали хуже прятать ПДн» | по 13 типам **и** агрегату BIK-excl | 0 сущностей |
| **(в)** masking A round-trip | «замаскировали, но испортили значение» | агрегат **и по типам** + абсолютное `A == 100%` | 0.00 пп |
| **(г)** masking B границы | «маска не закрывает значение целиком» | агрегат **и по типам** | 0.00 пп |

Плюс: креши (0), FP всего (`FP_TOLERANCE=0`), MANIFEST до и после, известный
долг + диагностика состава.

**Проверка по типам, а не только по агрегату** — прямое следствие S2-2. Правило
«рост одного типа не должен прятаться за падением другого» действовало для
leak_v2 с этапа 0d; S2 распространил его на masking.

**masking C оставлен МЯГКИМ.** Постановка просила охранять «B/C», но «C
печатается и не роняет» — стоящее решение владельца (STATE §6), а C структурно
слеп к over-маскированию (FINDINGS D-PRECISION-90). Поэтому падение C даёт
громкое ПРЕДУПРЕЖДЕНИЕ, а блокирующая роль по типу маски отдана precision
(линия «а»), которая over-mask видит. **Если владелец хочет C жёстким —
это одна строка в `gate_config.py`.**

### 5.3. Обоснование допусков — измерением, а не вкусом

Допуск компенсирует ШУМ ИЗМЕРЕНИЯ. Значит его величина обязана следовать из
измеренного разброса. **Корпус прогнан ТРИЖДЫ на одном HEAD** (два прогона
подряд отдельным скриптом + третий — самим `gate.py` в штатном режиме):

```
документов: 324 / 324
ПОБАЙТНО идентичны: True
документов с расхождением: 0
leak_v2>=6 TOTAL: 2321 / 2321      FP-негативы: 650 / 650
masking A/B/C:  100.0000/86.7913/95.0278  (оба прогона)
precision ORG/PER/ADDRESS: 99.77168949771689 / … — совпало до последнего знака
```

Третий прогон проверяется однострочником, без доверия к тексту этого отчёта:
`results_gate_current.json` (дамп, который `gate.py` пишет сам) **побайтно
равен** `results_baseline.json`.

**Разброс НУЛЕВОЙ** на трёх прогонах — при том, что E″ в HEAD НЕТ (S2-1).
Это согласуется с самим E″: корпус был детерминирован и до него, плавали
~2500-сегментные РЕАЛЬНЫЕ документы, которых в корпусе нет. Отсюда: любой ненулевой допуск не компенсировал бы шум, а
ПРОЩАЛ бы регресс — поэтому 0 везде. Стоимость ошибки названа в обе стороны:
слишком узкий → ложные срабатывания (здесь невозможно, шум = 0); слишком
широкий → регресс проходит молча (ровно сценарий пяти красных этапов).

Ужесточение против этапа D: `precision_pp` 0.5 → **0.0** (0.5 была уступкой
неизвестному тогда разбросу). Проверено — гейт от этого зелёный.

Мягким остался ОДИН порог: **известный долг** (решение владельца на этапе D).
Компенсатор — диагностика состава: тот же счёт при смене множества даёт
предупреждение, чтобы подмена «N на другой N» не растворялась в допуске.

## 6. САМО-ТЕСТ: четыре подложенных регресса → четыре красных

Гейт, который никогда не краснел, — непроверен. Метод: заведомо зелёная пара
(baseline == current), в КОПИЮ current подкладывается РОВНО ОДИН дефект.

**Контроль (без регресса) → ЗЕЛЁНЫЙ.** Без него четыре красных ничего не
доказывают.

```
(i) ЛИНИЯ «а» — ORG-маска на объявленном негативе          ВЕРДИКТ: КРАСНЫЙ
  - (а) precision[ORG]: 100.00% -> 50.00% — упал ниже baseline − 0.00пп
  - (3) FP по негативам: 0 -> 1 (+1), допуск FP_TOLERANCE=+0 превышен

(ii) ЛИНИЯ «б» — одна PHONE потекла (none -> full)          ВЕРДИКТ: КРАСНЫЙ
  - (б) PHONE[leak_v2>=6]: 0 -> 1 (+1 сущностей) — рост частичной утечки
  - (б) PHONE[leak_v2>=8]: 0 -> 1 (+1 сущностей) — рост частичной утечки
  - (б) TOTAL(BIK-excl)[leak_v2>=6]: 0 -> 1 (+1 сущностей)
  - (б) TOTAL(BIK-excl)[leak_v2>=8]: 0 -> 1 (+1 сущностей)

(iii) ЛИНИЯ «в» — одна маска не восстанавливается           ВЕРДИКТ: КРАСНЫЙ
  - (в) masking_correctness[A round-trip]: 100.00% -> 80.00% — УПАЛА (допуск 0.00пп)
  - (в) masking_correctness[A round-trip] = 80.00% < 100% — значение НЕ
        восстанавливается байт-в-байт (инвариант проекта)
  - (в) masking_correctness[A round-trip / ORG]: 100.00% -> 0.00% — на типе

(iv) ЛИНИЯ «г» — одна маска не закрывает эталон целиком      ВЕРДИКТ: КРАСНЫЙ
  - (г) masking_correctness[B границы]: 100.00% -> 80.00% — УПАЛА (допуск 0.00пп)
  - (г) masking_correctness[B границы / ADDRESS]: 100.00% -> 0.00% — на типе

(iv-bis) НАХОДКА S2-2 — обвал типа при РОСТЕ агрегата        ВЕРДИКТ: КРАСНЫЙ
  агрегат B: 54.55% -> 90.91% (ВЫРОС — проверка по агрегату была бы ЗЕЛЁНОЙ)
  - (г) masking_correctness[B границы / ADDRESS]: 100.00% -> 0.00%

(5) ДОЛГ — подмена «N на другой N» при том же счёте (1 -> 1) ВЕРДИКТ: ЗЕЛЁНЫЙ
  ⚠ состав утечки-долга сменился: −1 [ушли] +1 [пришли] (из пришедших НЕ в
    known_leaks: 1) — подмена «N на другой N», проверить вручную
```

Зеркала — `tests/corpus/test_gate_regression_detection.py`, **13 тестов**
(было 2). Плюс проверка «рост утечки ORG не прячется за падением PER» и
«мягкость C: предупреждает, но не роняет».
