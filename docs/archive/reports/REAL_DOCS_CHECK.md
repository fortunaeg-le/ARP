"Исправлен баг с пограничными данными"), доступен блоб `wert.docx` —
**реальный документ** (акционерное соглашение в отношении АО «Когнитив

пор физически присутствует в объектах репозитория. Это не подпадает под
известный контекст задачи (`real_docs/`, `dog.docx`, `shifrator_real`), но
является ровно тем классом утечки, для которого затевалась проверка.
Решение о его судьбе (rewrite истории?) — за владельцем, эта сессия ничего
не удаляла.

## 2. История git

```
git log --all --diff-filter=A --name-only -- 'real_docs/*' '*.docx' '*.doc' '*.pdf'
```

`real_docs/*` и `dog.docx` — **не найдены** ни разу как добавленные пути в
текущей истории. Причина видна отдельно: в репозитории есть каталог
`.git/filter-repo/` (запуск `git filter-repo`, датирован 20 июля 2026,
`already_ran` + `commit-map` на 58 записей), и `.gitignore` содержит прямое
указание:

```
# уже была утечка договора, чищено filter-repo. real_docs/ и любые дампы его текста
real_docs/
...
/dogovor.docx
```

Это подтверждает: **утечка `real_docs/`/`dogovor.docx` была и её чистили
`filter-repo`** — переписыванием истории с заменой хешей коммитов. Косвенное
доказательство — `.git/filter-repo/first-changed-commits` ссылается на
`f3e65c97351dd1a824fc0dd7e43bc47b12a4c83e`, которого в текущей истории уже
нет (`git show` → `fatal: bad object`) — то есть это старый хеш коммита,
переписанного filter-repo. Значит, чистка была реальной операцией над
историей, а не пожеланием на будущее.

`dogovor.docx` из `.gitignore` в рабочем дереве сейчас отсутствует (не
найден `find`), то есть не завёлся заново после чистки.

**Отдельная находка (не по паттернам запроса, но по духу проверки):**
`wert.docx` — добавлен в `daaef29e` (12.07.2026), удалён в `8ebb187a`
(тот же день, следующий коммит). Извлечён и прочитан текст блоба
(`git show daaef29e:wert.docx`): реальное акционерное соглашение в
отношении АО «Когнитив пилот», с реальными ФИО двух физлиц-подписантов и
названиями пяти юрлиц. Этот коммит **filter-repo не затронул** — блоб
по-прежнему извлекается из истории. Технически подпадает под тот же класс
риска, что и `real_docs/`, но остался незамеченным при прошлой чистке,
вероятно потому что не совпадает с игнорируемыми именами (`real_docs/`,
`dogovor.docx`).

## 5. Результаты прогонов

Просмотрены `docs/archive/reports/*` и `experiments/`. Упоминания «ИНН
7707083893», «ООО «Ромашка»», «Иванов И.И.» и подобные — это
**повторяющиеся синтетические примеры** в HANDOFF-документах (одни и те же
тестовые ИНН/ФИО кочуют по нескольким файлам как учебные иллюстрации
детектора), не выдержки из реального документа.

`experiments/stage_eprime_determinism/` — проверен особо (там гонялся
реальный документ владельца):
- `owner_repro.py` — по своему явному контракту печатает только числа масок
  по типам, sha256 анонимизированного текста и признак детерминизма по
  слоям (L1–L4); реальный текст в вывод не передаётся ни в одной ветке кода.
- `_corpus_sha_new.json` — только имена файлов корпуса и их sha256, без
  текста.
- `HANDOFF_STAGE_EPRIME_DETERMINISM.md` (раздел 10, обновление
  24.07.2026) — приводит только числовые счётчики масок владельца
  (`[237, 224, 226, 224, 233, 224]`) и какие типы сущностей плавают
  (ADDRESS/ORG/PERSON), текста документа нет.

Итог: файлы результатов содержат координаты/числа/хеши без текста — чисто,
как и ожидалось по п.5 задания.
