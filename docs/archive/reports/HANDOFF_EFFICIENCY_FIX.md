## 1. Убрано дублирование точки входа «полный прогон» (EFFICIENCY_AUDIT §2.1)

**Диагноз аудита**: условие 1 гейта (`gate.py` — 0 крешей на 324 документах)
строгое НАДМНОЖЕСТВО того, что проверяет `pytest -m slow`
(`test_full_corpus_encrypt_never_crashes` — тоже 0 крешей на тех же 324).
Сессия, гоняющая оба перед коммитом, прогоняет Natasha по всему корпусу
ДВАЖДЫ ради одной и той же проверки.

**Решение — документация, не код.** Оба теста остаются в кодовой базе:
`test_full_corpus_encrypt_never_crashes` нужен как самостоятельный контракт
для контекстов, где `gate.py` в сессии не запускается (например голый CI-джоб
на одном `pytest -m slow` без гейта). Убирать сам тест значило бы убрать
проверку, а не дублирование ЕЁ ЗАПУСКА — задание прямо это запрещает.
Вместо этого:

- в докстринг `gate.py` добавлено явное указание: если `gate.py` будет
  запущен в этой сессии, отдельный `pytest -m slow` не нужен;
- в докстринг `test_full_corpus_encrypt_never_crashes` — симметричное
  указание с той же формулировкой;
- в `docs/STATE.md` §0 — та же строка, там, где её прочитают первой (не в
  архиве).

Это не код-фикс, потому что дублирование было не багом харнесса, а
поведением ОПЕРАТОРА сессии (какие команды он решает запустить) — гейту
нечего чинить в себе, вопрос был «кто вообще будет знать, что оба запускать
не нужно».

**Доказательство, что креш-регресс всё ещё ловится.** Логика условия 1
(`gate.compare()`, сравнение множеств `crashed` до/после) раньше не имела
собственного юнит-теста — только проверялась косвенно, целым прогоном
корпуса. Написан быстрый тест
`tests/corpus/test_gate_regression_detection.py` (секунды, без Natasha,
`src/` не импортирует):

```
venv/Scripts/python.exe -m pytest tests/corpus/test_gate_regression_detection.py -q
2 passed in 2.02s
```

Метод: искусственно "ломаем" один документ — строим `results` ровно в форме,
в которой `run_measurement.run_all()` кладёт креш при необработанном
исключении (`outcome="crashed"`, см. `run_measurement.py`, `except
Exception`), и проверяем, что `gate.compare()` докладывает регресс со
строкой `"КРЕШИ"` и id документа. Второй тест — то же без поломки — гейт
остаётся зелёным по условию 1. Оба теста ЗЕЛЁНЫЕ на текущем коде, то есть
креш-детекция работает независимо от того, какой из двух путей
(`gate.py`/`pytest -m slow`) физически запускался в сессии.

**Экономия.** Один полный прогон корпуса на сессию, где раньше гонялись оба
пути — **~8-20 минут** (оценка из `HANDOFF_STAGE_1.md`/`HANDOFF_STAGE_0D.md`,
подтверждена в самом `EFFICIENCY_AUDIT.md` §1/§2.1). Риск устранения —
минимальный: убрана не проверка, а её повторный физический запуск; сама
проверка теперь ещё и покрыта отдельным быстрым юнит-тестом, которого раньше
не было вовсе.

## 2. `tests/corpus/subsample.py` — отладочная подвыборка (EFFICIENCY_AUDIT §2.2)

**Диагноз аудита**: правило «итерируйся на 30-50 документах, полный прогон
только в конце» существовало только как текст задания — в харнессе не было
НИКАКОЙ его поддержки. Сессии реально итерировались на ручных точечных
проверках ОДНОГО документа (`tokenize()` напрямую), и `HANDOFF_STAGE_4.md`
§3.1 прямо документирует случай, где такая проверка пропустила регрессию
(гомоглиф-мутация якорного слова), которую поймал только полный прогон.

**Реализация** — новый скрипт `tests/corpus/subsample.py`, гоняющий тот же
харнесс (`run_measurement.process_doc`/`run_all`), что `gate.py`, но на
подмножестве документов. Состав подвыборки — объединение:

- по 2 base-документа каждого из 9 `contract_type` (детерминированно, те же
  18, что в `tests/test_corpus_no_crash.py::_fast_doc_ids`);
- 4 граничных документа, явно названных в `docs/FINDINGS.md` как редкие
  вскрытые дефекты (Stage4-B: `loan_0006__m2718_homoglyph`,
  `services_0002__m1337_linebreak`; PER-B: `works_0009`, `sale_0006`) —
  всегда в подвыборке, независимо от фильтров, иначе сам мотив скрипта
  (точечная проверка одного документа пропускает именно такие классы)
  остаётся непокрытым подвыборкой;
- по флагам `--trick`/`--type`/`--feature` — все документы корпуса,
  несущие указанный приём/тип сущности/фичу (можно указывать несколько
  раз, каждый добавляет ещё документы).

Без фильтров подвыборка — **22 документа** (проверено:
`select_doc_ids(gold)` -> 22 id). С фильтром — до 30-50+, в зависимости от
того, сколько документов корпуса несёт эту фичу (`--type SNILS` -> 191,
`--trick homoglyph_cyrillic_in_digits` -> 35 — фильтры расширяют охват
осознанно, это ожидаемо шире типового диапазона «30-50», указанного в
задании как ориентир для дефолтного случая).

**Предупреждение "не заменяет полный прогон"** печатается ДВАЖДЫ (до и после
отчёта) при каждом запуске скрипта, текстом:

```
ПОДВЫБОРКА — ЧЕРНОВИК ДЛЯ ОТЛАДКИ.
НЕ заменяет финальный полный прогон tests/corpus/gate.py перед коммитом.
Регресс на редком типе, не попавшем в подвыборку, здесь может быть НЕ виден.
```

Тот же текст — в докстринге модуля целиком (первый блок, до описания
запуска). Скрипт НЕ пишет `results_baseline.json`, не сравнивает с baseline и
не участвует в гейте — чисто отладочный инструмент внутри сессии.

**Проверка работы** (выборка логики, без прогона Natasha — быстро):

## 3. Ложный таймаут `test_g_regression` — напоминание в STATE.md (EFFICIENCY_AUDIT §4)

**Диагноз аудита**: `test_g_regression` несколько раз падал по таймауту
из-за CPU-конкуренции с параллельным полным прогоном (`gate.py`/`pytest -m
slow` в другом терминале той же сессии) — причина по существу устранена
(фильтр `-m "not slow"` в дочернем subprocess, см. докстринг самого теста), но
факт живёт только в архивном `HANDOFF_STAGE_0D.md` §1.5, который сессии не
читают по умолчанию. Дважды это чуть не привело к попытке «починить»
несуществующий баг.

**Решение**: одна строка добавлена в `docs/STATE.md` §0 (там, где её
прочитают в начале сессии, а не в архиве):

> Ложный таймаут `test_g_regression` = конкуренция за CPU с параллельным
> полным прогоном (`gate.py`/`pytest -m slow` в другом терминале той же
> сессии), НЕ дефект — при таймауте сначала проверь нагрузку, не диф.

## 4. Что НЕ сделано в этой сессии — кеш Natasha (EFFICIENCY_AUDIT §2.3)

Самый крупный по абсолютной экономии пункт аудита — кеш сырых NER-спанов
детекции для сессий, меняющих ТОЛЬКО метрику (`measure_lib.py`), а не
детекторы. Дважды подтверждённый паттерн: `HANDOFF_METRIC_ADDRESS.md` и
`HANDOFF_METRIC_NUMERIC.md` обе гоняли полный Natasha-конвейер заново, хотя
`src/` в обеих сессиях не менялся вовсе.

**Сознательно не реализовано здесь** — задание явно выводит этот пункт за
границы сессии: он требует структурной правки `run_measurement.py::
process_doc` (разделения «прогон конвейера» / «скоринг»), инвалидации кеша по
хэшу `src/*.py`+`entity_types.yaml`, и приёмки той же строгости, что у любой
правки измерительного прибора (сверка старого/нового вывода метрик побайтово
на неизменном кеше) — не походя внутри процессной сессии. Остаётся
**следующим по величине выигрышем**, см. `EFFICIENCY_AUDIT.md` §2.3 для
полной оценки реализуемости и экономии.
