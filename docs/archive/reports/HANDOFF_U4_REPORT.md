## 1. Что сделано

| 1. Метрики по разметке | `app/report.py` `build_report` | precision/recall по просмотренному, доли правок границы и типа; разбивка по типам, механизмам, сборкам |
| 2. Отчёт без ПДн | `app/report.py` (белый список + часовой) | структурные коды вместо текста; строка вне закрытого словаря = отказ собрать отчёт |

`Blob`-ом на диск пользователя. Никаких исходящих вызовов не добавлено.

## 2. Схема отчёта — белый список полей

Версия схемы — `report_version: "1"`. Верхний уровень:

```
report_version   "1"
generated_at     ISO-время сборки отчёта
tool_build       слаг сборки инструмента (BUILD_MARK)
scope            "session" | "all"
schema_note      фраза-константа про белый список
period           {from, to}      — ISO-границы разметки в выборке
contents         {included[], excluded[]}  — что в отчёте есть и чего нет
limitations      []              — ограничения метрики (см. §4)
sample           {documents, documents_with_denominator,
                  documents_without_denominator, edits}
totals           {masks_total, missed, false_mask, boundary, type,
                  unknown, edits_total}
metrics          {precision_reviewed_pct, recall_reviewed_pct,
                  boundary_edit_rate_pct, type_error_rate_pct}
by_type          {ТИП:      {masks, <счётчики>, edits_total, <metrics>}}
by_detector      {МЕХАНИЗМ: {masks, <счётчики>, edits_total, <metrics>}}
by_build         {СБОРКА:   {<счётчики>, documents_touched, edits_total}}
findings         [ ... ]
```

Находка (`_FINDING_FIELDS` — **единственное** место, где решается, что вообще
может попасть в findings):

```
document         порядковый номер документа В ОТЧЁТЕ (не session_id!)
kind             missed | false_mask | boundary | type | unknown
entity_type      PERSON | ORG | ADDRESS | … | unknown
detector         regex | ner | manual | none | unknown
container        paragraph | table_cell | text_line | unknown
container_index  int | null      — номер абзаца / таблицы / строки txt
row, col         int | null      — для ячейки таблицы
length_chars     int             — длина фрагмента
tokens           int             — слов в фрагменте
has_digits / has_latin / has_cyrillic / has_punct / has_initials   bool
case_shape       upper | lower | title | mixed | no_letters
build            слаг сборки, на которой сделана правка
```

Это и есть «структурные коды вместо текста» из постановки: вместо
«пропущено ФИО "Иванов И.И."» отчёт говорит `PERSON, ячейка t2 r3 c1, длина 11,
2 слова, инициалы есть, кириллица, регистр title, ни один детектор не сработал`.
Разработчик видит КЛАСС проблемы; значения не видит никто.

**Чего в схеме нет намеренно:** `value`, `session_id`, имя файла, любые
координаты внутри сегмента (start/end), любой текст документа. `session_id`
убран сознательно — это не ПДн, но это ручка к хранилищу; порядкового номера
документа для группировки находок достаточно.

## 3. Почему утечка невозможна ПО ПОСТРОЕНИЮ (три рубежа)

«Не забыть не положить текст» — не механизм. Реализованы три, каждый ловит
промах предыдущего:

1. **Белый список.** Отчёт собирается с нуля, а не «запись разметки минус
   лишнее». Поля перечислены в `_FINDING_FIELDS`, собирают их функции,
   физически возвращающие только int/bool/код словаря (`_value_shape`,
   `_context`).
2. **Нормализация на входе.** Всё, что пришло строкой из хранилища
   (`entity_type`, `detector`, `kind`, `build_mark`, `created_at`), проходит
   `_norm_*`: неизвестное значение → `"unknown"`, дата → переразбирается
   `datetime` и печатается заново. В отчёт попадают строки, **порождённые
   кодом**, а не пронесённые из данных.
3. **Структурный часовой** `assert_structural`. Готовый отчёт обходится
   целиком; каждая строка — и ключи, и значения — обязана быть либо схемным
   ключом, либо кодом закрытого словаря, либо ISO-датой, либо ASCII-слагом
   сборки, либо **дословно** одной из констант модуля (`_FIXED_PROSE`). Иначе
   `ReportLeakError`, и `build_report` не возвращает отчёт вообще. Ключи
   проверяются наравне со значениями — иначе фрагмент текста мог бы приехать
   ключом словаря.

Часовой вызывается ВНУТРИ `build_report` (не «рядом»), сервер переводит
`ReportLeakError` в человеческую ошибку и файл не отдаёт.

## 4. Как считаются метрики и чем они ограничены

Обозначения: `M` — масок поставил движок (знаменатель), `FP` — снятых как
«не ПДн», `MISS` — помеченных как пропущенные, `BND`/`TYP` — правок границы/типа.

```
found      = M − FP
precision_reviewed = found / M
recall_reviewed    = found / (found + MISS)
boundary_edit_rate = BND / M
type_error_rate    = TYP / M
```

Правки границы и типа стоят на РЕАЛЬНЫХ ПДн, поэтому из `found` не вычитаются:
это качество границы/типа, а не ложное срабатывание.

Атрибуция по типу: `missed` → к типу, который назвал ПОЛЬЗОВАТЕЛЬ (движок не
назвал никакого); `false_mask`/`boundary`/`type` → к типу, который сказал
ДВИЖОК (`old_entity_type`). Иначе ошибка «ORG вместо PERSON» уехала бы в
статистику невиновного PERSON. Механизм для `missed` — отдельная категория
`none` («не сработал ни один детектор»), а не пропуск данных.

**Ограничения — они напечатаны в шапке самого отчёта, не только здесь:**

* precision — доля масок, которые проверяющий НЕ ОТКЛОНИЛ; маска, на которую он
  не посмотрел, считается верной. **Верхняя оценка.**
* recall — найдено / (найдено + ЗАМЕЧЕННЫЕ пропуски); незамеченный пропуск в
  знаменатель не входит. **Верхняя оценка.**
* выборка мала и смещена: в агрегате преобладают документы, где было что
  отмечать (документ с нулём правок попадает в знаменатель только пока жива его
  сессия и отчёт строится по нему).
* эти числа НЕ заменяют полный замер на корпусе (`tests/corpus/gate.py`) и не
  являются приёмочными.

### Знаменатель и 24 часа

Сколько масок всего — это состояние СЕССИИ, а сессия живёт 24 ч против 30 дней
у разметки (этап S1). Без ответа на это любая метрика по разметке старше суток
осталась бы без знаменателя. Решение: `app/core.py` кладёт в **каждую** запись
разметки компактный слепок `census` (`masks_total` + `by_type` + `by_detector`)
на момент правки; отчёт берёт слепок САМОЙ РАННЕЙ записи сессии — это состояние
до ручных правок, то есть чистый результат автоматики. Для разметки, сделанной
до U4, слепка нет: пробуем прочитать живую сессию, а если её уже нет — документ
честно считается «без знаменателя» и входит абсолютными числами
(`documents_without_denominator`). Проверено живьём:
`test_live_report_survives_session_deletion` удаляет сессию и требует, чтобы
знаменатель остался.

## 5. Экран «Аналитика» (задача 4)

Внутренний экран владельца. Плитки: масок поставлено, precision, recall,
пропущено, ложных, правок границы+типа. Ниже — три таблицы (по типам ПДн, по
механизмам детекции, по версиям сборки) и блок «Отчёт для разработчика»:
переключатель области (вся разметка / текущий документ), явный список «что
уйдёт / чего нет», предпросмотр в двух вкладках и две кнопки скачивания.

**Отчёт наружу и экран показывают ОДНИ И ТЕ ЖЕ числа.** Это решение, а не
недосмотр: в отчёте нет ПДн по построению, значит цензурировать внутренний
экран относительно внешнего файла нечего. Разница — упаковка: файл несёт шапку
с ограничениями и отдаётся одним куском.

## 6. Результат теста на утечку (приёмка 1)

Документ, где маркерные строки стоят в роли ФИО / организации / адреса /
e-mail, проверен на ЖИВОМ сервере всеми четырьмя видами правки; отдельно —
unit-тест, где маркер подставлен в **каждое** строковое поле записи разметки
(`kind`, `entity_type`, `segment_id`, `value`, `old_entity_type`,
`old_detector`, `build_mark`, `apply_error`, ключи и значения `census`).

Проверка жёстче постановки: ищется не только маркер целиком и не только в
другом регистре, но и **любая его подстрока длиной ≥6 символов**.

```
tests/test_u4_report.py ....................... 23 passed
```

Ключевые:

* `test_live_report_leaks_no_marker_anywhere` — json_text, md_text и сам объект
  отчёта, обе области (`session` и `all`); отчёт при этом непустой
  (3 пропуска + 1 ложная + 4 находки), иначе «утечки нет» ничего не доказывало бы.
* `test_marker_in_every_markup_field_does_not_reach_report` — маркеры не
  «потерялись», а нормализовались в коды: `kind=unknown`, `entity_type=unknown`,
  `detector=unknown`, `container=unknown`, `build=unknown`, а длина и число слов
  посчитаны верно.
* `test_markers_do_not_collide_with_report_prose` — **санитарная проверка самих
  маркеров**: в ПУСТОМ отчёте их быть не может. Понадобилась сразу: первый
  вариант маркера `МЕТКАОРГАНИЗАЦИИ456` содержал слово «ОРГАНИ», которое есть в
  собственной прозе отчёта («…ни организаций…»), и тест краснел на ЛОЖНОЙ
  тревоге. Без этой проверки «утечка» и «неудачно выбранный маркер»
  неразличимы.
* Само-тесты часового: `test_guard_rejects_free_text_value` (текст значением),
  `..._key` (текст ключом словаря), `..._prose_not_from_module_constants`
  (безобидная на вид фраза не из констант), `test_build_report_raises_when_guard_trips`
  (часовой стоит внутри сборки, отчёт с утечкой не возвращается вообще).

Живая проверка в браузере (реальный сервер, изолированный профиль, 2 документа,
все 4 вида правки): в DOM экрана и в объекте отчёта — 0 маркеров и 0 их
6-символьных окон; заодно проверено, что не утекли и реально задетектированные
значения («Меркурий», ИНН, e-mail).

## 7. Предпросмотр = выгрузка, побайтно (приёмка 3)

Совпадение сделано **структурным**, а не проверяемым: `downloadReport(fmt)`
сначала показывает нужную вкладку, затем берёт строку **из того же узла
`<pre>`**, который пользователь только что читал, и сохраняет её. Второй ручки
«а теперь скачай» нет намеренно — два ответа сервера были бы двумя местами, где
они могут разойтись.

Побайтная сверка в живом браузере (`TextEncoder`, сравнение по байтам):

```
md   : pre_equals_server=true, bytes_equal=true, bytes=6243
json : pre_equals_server=true, bytes_equal=true, bytes=8892
markers_found=[]   marker_windows_found=[]
```

Серверная половина закреплена тестом
`test_live_preview_text_is_exactly_the_downloadable_bytes`, детерминизм —
`test_report_is_deterministic_byte_for_byte` (два вызова с одним `now` дают
идентичные байты в обоих форматах).

### 9.1 ВАЖНО: рабочее дерево общее с сессией S3 — прогон смешанный

К моменту прогона в дереве лежали НЕ ТОЛЬКО мои правки. Сессия S3 параллельно

```

experiments/stage_s3/        S3 (новый)
```

Отсюда два следствия, которые нельзя замолчать:

1. **Числа полного `pytest -q` относятся к СМЕСИ** моих изменений и
   незавершённой работы S3 по адресу. Приписывать их себе — целиком или в

2. **«Детекция байт-в-байт» у меня держится по построению, а не по замеру**:

   активной правкой соседней сессии.

Во время прогона в системе крутились ДВА `pytest -q` (мой на `venv/`, S3 на
системном Python) — см. §9.3, там это оказалось НЕ причиной.

### 9.3 Полный прогон: 1 падение, и оно ПРЕД-существующее (находка U4-G-TIMEOUT)

→ 1 failed, 976 passed, 3 deselected, 10 xfailed in 879.78s (14:39)

   Доминируют два ПРЕД-существующих теста: `test_determinism.py::
   test_two_runs_byte_identical_fast` **184 c** и `test_corpus_no_crash.py::

3. **Решающая проверка:** отдельный `git worktree` на чистом `HEAD abf3ee8`
   (ноль правок рабочего дерева — ни моих, ни S3) → **то же падение, 300.71 c**.
   Worktree удалён, файлы S3 не тронуты (стащить их `git stash` было бы
   разрушительно для параллельной сессии — не делалось).

нагрузки» дополнено, потому что в текущем виде оно уводит разбор в сторону.

### 10.1 Побочная находка: спека PyInstaller не знала про новый модуль

`app/report.py` импортируется ЛЕНИВО (внутри функций `core`/`server`), а
`packaging/shifrator.spec` перечисляет плоские модули в `hiddenimports` явно —
`report` туда, разумеется, не попал. В собранном exe это дало бы не падение, а
**тихую деградацию**: экран «Аналитика» отвалился бы, а `core._markup_census`
(он ловит `Exception`) молча перестал бы писать слепок знаменателя — метрики
остались бы без денominatorа и никто бы не узнал почему. Прогон тестов из
исходников такого не видит в принципе.

Починено (+`"report"`), и поставлен общий страж:
`test_pyinstaller_spec_lists_every_app_module` требует, чтобы КАЖДЫЙ `app/*.py`
(кроме точки входа `launcher.py`) был перечислен в спеке. Страж
**фальсифицирован**: при удалении `"report"` из спеки падает с
`assert not ['report']`, при возврате — зелёный. Следующий новый модуль в `app/`
не проскочит молча.

## 11. Что осталось / на что смотреть следующему

* **`storage.list_markup_sessions()` не существует.** `report._markup_session_ids()`
  вынужденно перечисляет `*.markup.json` в `storage.default_markup_dir()`
  напрямую — единственное место во всём `app/`, идущее в ФС мимо функции
  хранилища. Это нарушает инвариант «в хранилище только через `storage.py`».
  Добавить `list_markup_sessions()` в `src/storage.py` и переключить отчёт на
  неё — первое, что стоит сделать, когда `src/` освободится от сессии S3.
* **`markup_summary().entries` считает записи разметки**, а `census` живёт
  ВНУТРИ записей и на это число не влияет — сводка на экране проверки осталась
  корректной. Проверять при любых будущих служебных записях в разметке.
* **Смещение выборки** (документ без правок не попадает в агрегат) — не дефект
  реализации, а свойство «метрика по разметке». Закрывается либо записью
  «документ проверен, правок нет» при завершении проверки, либо отдельным
  реестром проверенных документов. Требует правки модели разметки (U3) —
  сознательно НЕ сделано в этой сессии, названо ограничением в отчёте.
* Метрика ничего не знает о том, ДОСМОТРЕЛ ли пользователь документ до конца.
  Пока это покрыто формулировкой «по просмотренному, верхняя оценка».
