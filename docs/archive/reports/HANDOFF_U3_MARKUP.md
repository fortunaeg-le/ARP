# HANDOFF — этап U3: экран проверки и разметка

Ветка `u1-desktop-packaging`, поверх коммитов U1/U2. Правки — только `app/` и
`src/storage.py`, как и поставлено. `src/extractor.py` не тронут (параллельная
сессия чинит E″ там же); никакие другие файлы `src/` не тронуты; логика
детекции не менялась ни на строку — весь этап работает НАД уже готовым
результатом детекции (сессией), не внутри неё.

## 1. Что сделано (коротко)

- **Экран проверки интерактивен.** На обезличенной панели можно мышью выделить
  пропущенный фрагмент и выбрать тип (13 типов из постановки), а по щелчку на
  уже стоящей маске — снять её как ложную, изменить тип или исправить границу.
  Ни разу не требуется вводить координаты/спан/оффсет вручную.
- **Разметка сохраняется сразу**, независимо от решения о пересборке —
  `{session_id}.markup.json` через новые функции `storage.py`
  (`save_markup`/`list_markup`/`update_markup`/`delete_markup`). Читается,
  редактируется (тип у ещё не применённой записи), удаляется.
- **Пересборка — отдельная явная команда** («Применить правки и пересобрать»),
  задача 3 решена в пользу «да, документ должен пересобираться» — обоснование
  ниже (§3).
- **Round-trip с ручными масками работает** — см. §5, это была реализация с
  наибольшим риском.
- **Прогресс на большом документе** — не точный (граница сессии запрещает
  трогать детекцию), но честная оценка: число сегментов сразу после
  извлечения + процент по прошедшему времени (§6).

## 2. Экран проверки — что видит пользователь (сценарий приёмки №1)

1. Перетащил договор на экран 1 → статус-строка показывает «Читаю документ…»,
   затем «Ищу персональные данные… (N%)» с полосой прогресса и подписью
   «Документ: K фрагм.» — как только K становится известно (доли секунды после
   извлечения, задолго до готовности).
2. Экран 2 (Проверка): слева исходный текст, справа обезличенный с подсветкой.
   Под панелями — **новый блок «Что спрятано»** (без изменений с этапа U2) и
   **новый блок «Ваши правки»**.
3. Юрист замечает, что в обезличенном тексте осталось, например, ФИО открытым
   текстом. **Выделяет его мышью прямо в правой панели** (курсор — обычный
   текстовый, `cursor:text` на незамаскированных участках). Как только
   выделение снято (`mouseup`), рядом с курсором всплывает меню с 13 кнопками
   типов («ФИО», «Организация», «Адрес», …). Клик по «ФИО» — фрагмент
   ПОДСВЕЧИВАЕТСЯ пунктиром (визуальный маркер «в очереди на применение»), а
   в блоке «Ваши правки» появляется строка: «Пропущено · ФИО: «Иванов И.И.» ·
   ожидает применения» со счётчиком (бейдж «1» у заголовка блока).
4. Если выделение задевает уже существующую маску или выходит за пределы
   одного непрерывного куска текста — всплывает понятное сообщение
   («Нельзя выделить фрагмент, задевающий существующую маску…»), ничего не
   сохраняется, приложение не падает.
5. Юрист может отметить ещё несколько пропусков, затем нажимает
   **«Применить правки и пересобрать»**. Кнопка на время запроса показывает
   «Применяю…», затем документ в ОБЕИХ панелях (и список «Что спрятано»)
   обновляется — новые маски встают на место, счётчик «спрятано N знач.»
   растёт. Тост снизу экрана: «Применено правок: 2. Документ пересобран.»
6. «⬇ Скачать обезличенный текст» — скачивает уже ПЕРЕСОБРАННУЮ версию (кнопка
   не изменилась, но `CUR.anon_text` теперь актуален).
7. На экране 3 вставляет скачанный текст + ID сессии → «Восстановить
   оригинал» — получает исходный текст, включая то самое ФИО, которое юрист
   пометил вручную (см. §5 — доказано живым HTTP-прогоном и в реальном
   браузере, не только модульно).

Клик по УЖЕ стоящей маске (правая панель) открывает другое меню: «🚫 Это не
персональные данные», «✏️ Изменить тип», «↔️ Исправить границу». Первые два —
без повторного выделения текста. «Исправить границу» временно «раскрывает»
маску и её соседний текст в один выделяемый кусок (чисто визуально, документ
на сервере не меняется) — пользователь выделяет исправленный вариант ровно тем
же способом, что и «пометить пропущенное»; отмена возвращает исходный вид без
следа.

## 3. Задача 3 — пересборка при применении: решение и обоснование

**Решение: ДА, документ пересобирается**, но НЕ автоматически при каждой
пометке — отдельной явной командой «Применить правки и пересобрать»,
применяющей ВСЕ ещё не применённые правки пачкой.

Обоснование (совпадает с требованием постановки, добавлено к нему техническое
«почему именно так, а не иначе»):

- **Продуктовая часть** — как и написано в постановке: без пересборки
  разметка полезна только нам (будущий корпус), но не юристу здесь и сейчас —
  он не станет тратить время на разметку без немедленной пользы. Пересборка —
  то, ради чего он вообще откроет это меню.
- **Почему НЕ мгновенно при каждой пометке**, а отдельной кнопкой: пользователь
  обычно находит несколько пропусков за один проход глазами; пересборка после
  КАЖДОГО клика заново перерисовывала бы обе панели и сбрасывала прокрутку на
  каждом шаге — раздражающий UX на длинном договоре. Пачечное применение (как
  «Сохранить» в редакторе) — пользователь домечает всё, что видит, одним
  проходом, потом одним кликом получает готовый результат. Технически это же
  решение сильно снижает число перезаписей файла сессии (одна операция вместо
  N).
- Каждая правка тем не менее **сохраняется на диск сразу** (не только в
  памяти вкладки браузера) — так разметка не теряется при случайном закрытии
  вкладки/окна ДО нажатия «Применить», и корпус пополняется, даже если
  пользователь в итоге решит не пересобирать документ в этот раз.

## 4. Механика пересборки (для тех, кто продолжит этот код)

Все четыре вида правки построены из ДВУХ примитивов над сессией
(`app/core.py`):

- `_add_missed(doc, session, seg, start, end, entity_type, config_path)` —
  добавляет НОВОЕ вхождение маски (валидирует границы/пересечения,
  генерирует новый токен `[PREFIX_N]`, N — следующий свободный номер для
  этого префикса в сессии).
- `_remove_occurrence(session, token, seg, start, end)` — убирает ОДНО
  конкретное вхождение токена по точным координатам; если это было последнее
  вхождение — токен убирается целиком.

Соответствие видов правки этим примитивам:

| вид правки | что происходит |
|---|---|
| пропущено (`missed`) | `_add_missed` |
| ложная маска (`false_mask`) | `_remove_occurrence` |
| граница (`boundary`) | `_remove_occurrence` (старое) + `_add_missed` (новое, тот же тип) |
| тип (`type`) | `_remove_occurrence` (старое) + `_add_missed` (новое, другой тип) |

`apply_pending_markup` применяет пачку ПОСЛЕДОВАТЕЛЬНО к ОДНОЙ и той же
сессии в памяти; запись, ставшая невалидной К МОМЕНТУ применения (например,
пересеклась с другой правкой из той же пачки, применённой раньше), помечается
`applied=false` с текстом ошибки в `apply_error` — ОСТАЛЬНЫЕ правки это не
блокирует (частичный успех, а не всё-или-ничего). После пачки сессия
**перезаписывается** (`session_store.save_session` под тем же `session_id`,
через новую `storage.replace_session_entities`), сохраняя ИСХОДНЫЙ
`expires_at` — правка НЕ продлевает TTL хранения ПДн.

**Откуда берётся текст для пересборки.** Файл, из которого документ был
извлечён, к моменту правки уже удалён (временный, чистится сразу после
ответа `/api/encrypt`). Поэтому при шифрации теперь сохраняется НОВЫЙ sidecar
`{session_id}.doc.json` (`storage.save_doc_segments`/`load_doc_segments`) —
сегменты исходного документа (id/текст/тип/метаданные), тот же формат, что
`SourceDocument`/`TextSegment` из `models.py`. Экран проверки (и сразу после
шифрации, и после каждой правки) теперь ВСЕГДА рендерится из ПАРЫ
(`doc.json` + текущее содержимое сессии) через единую функцию
`core._render_state` — один путь рендера, а не два расходящихся (тот же
класс инцидента, который на этапе B закрыла консолидация
`pipeline.run_detection`, см. `HANDOFF_UI.md`).

## 5. Round-trip с ручными масками — главный риск, проверено трижды

1. **Модульно/HTTP** (`tests/test_u3_markup.py`, живой `app/server.py` в
   отдельном процессе, НЕ моки): 8 тестов, включая:
   - `test_mark_missed_apply_and_roundtrip` — пометить пропущенное → применить
     → `decrypt` возвращает исходное слово, `unresolved == []`.
   - `test_false_positive_unmask_roundtrip` — снять маску с EMAIL → применить
     → значение вернулось в анонимный текст ОТКРЫТЫМ (это и есть смысл
     действия — «это не ПДн»), `decrypt` не роняется отсутствующим токеном.
   - `test_boundary_and_type_fix_roundtrip` — исправление типа маски (PHONE →
     SUM) → применить → `replacements` показывает новый тип → `decrypt`
     восстанавливает исходное значение.
   - `test_manual_mask_does_not_disturb_other_automatic_masks` — ручная маска
     добавлена, ДВЕ автоматические (EMAIL/PHONE) в том же документе после
     пересборки и `decrypt` возвращают ТЕ ЖЕ значения, что и до правки.
   - `test_missed_overlapping_existing_mask_is_rejected` — см. ниже.
2. **Живой браузер** (не автоматизированный тест, интерактивная сессия):
   настоящий `app/server.py`, настоящая страница, симуляция выделения через
   `Range`/`Selection` API (клик по типовой кнопке — реальный DOM-клик) +
   реальные fetch-запросы к серверу. Прогон: загрузка синтетического .txt →
   прогресс-бар и счётчик сегментов отработали → пропущенное слово
   (`СЕКРЕТНОЕСЛОВОXYZ`) выделено и помечено «ФИО» → «Применить правки» →
   документ в панели обновился, слово исчезло из открытого текста, `[PERSON_1]`
   появился → клик по свежей маске открыл меню действий → восстановление
   через форму экрана 3 вернуло **побайтно исходный текст**, включая слово,
   ИНН/e-mail/телефон, `unresolved` пуст.
3. **pytest полный прогон** — не должен показать регресс: 912 passed / 2
   deselected / 10 xfailed ДО этой сессии (замер сначала, см. §8) → тот же
   счёт + 8 новых после (детекция не менялась, поэтому детекционные тесты
   побайтно те же).

### Пересечение (задача 2 приёмки, «поведение должно быть определённым»)

Ручная маска, ЧАСТИЧНО накрывающая автоматическую (или наоборот — новое
выделение задевает существующую маску) — **отклоняется явной ошибкой** ДО
сохранения записи разметки: `"Выделение пересекает уже существующую маску —
сначала снимите её или воспользуйтесь «Поправить границу»."`
(`test_missed_overlapping_existing_mask_is_rejected`). Ничего не сохраняется
и не портится молча — пользователь получает понятный путь (снять старую
маску или использовать «Исправить границу», который сам делает
remove+add атомарно в рамках одной пересборки). Выбор в пользу отказа, а не
«последний побеждает»/«игнорировать пересечение»: тихое перекрытие масок —
ровно тот класс дефекта («криво замаскировано, а не пропущено»), который
`docs/STATE.md` §6 называет асимметрично опаснее пропуска (пропуск человек
поймает при следующей проверке, испорченную маску — нет).

## 6. Задача 4 — счётчик прогресса

`/api/encrypt` стал асинхронным: `POST /api/encrypt/start` возвращает
`job_id` немедленно, обработка идёт в фоновом потоке; `GET
/api/encrypt/status?job_id=…` отдаёт `{status, segment_count, percent,
elapsed}`; фронт опрашивает каждые 400 мс и двигает полосу прогресса +
подпись «Документ: K фрагм. · N% (оценка по времени, не точный прогресс
стадий)».

**Почему не точный прогресс по стадиям.** Точный счётчик обработанных
сегментов потребовал бы callback-точек ВНУТРИ `pipeline.run_detection` и
детекторов (`regex_detector`/`ner_detector`/`anchor_registry`) — то есть
правки в `src/`, кроме `storage.py`, что этой сессии запрещено («логику
детекции не трогать вообще» — граница задачи, не моя интерпретация).
Реализовано МИНИМАЛЬНОЕ изменение в разрешённых границах: число сегментов
известно сразу после `extract()` (быстрый шаг, задолго до конца детекции —
`core.run_encrypt(on_extracted=...)`, колбэк добавлен только в `app/core.py`),
а процент — честная линейная оценка по прошедшему времени и числу сегментов
(калибровка `_SECONDS_PER_SEGMENT = 0.03`, грубая, из порядка величин
`docs/STATE.md`: единицы-десятки секунд на документах в тысячи сегментов),
которая асимптотически идёт к 95% и прыгает на 100% ТОЛЬКО по факту
готовности — не создаёт иллюзию точности, которой нет.

**Если позже понадобится точный прогресс** — минимальная точка входа: 4
callback-вызова в `src/pipeline.py::run_detection`, по одному после каждого
из шагов (`detect_regex` → `detect_structural` → `detect_ner` →
`merge_compound_entities`); каждый детектор уже возвращает список целиком
(не поточно), поэтому более гранулярный прогресс (по сегментам ВНУТРИ шага)
потребовал бы более глубокой правки самих детекторов — не рекомендуется без
отдельной постановки, стоимость несоразмерна пользе индикатора.

## 7. Где лежит разметка (задача 2/4 приёмки)

`~/.shifrator/sessions/{session_id}.markup.json` — тот же профиль
пользователя, что и `{session_id}.enc`/`.txt`/`.meta.json`, НЕ в проекте.
Плюс новый `{session_id}.doc.json` (сегменты исходного документа — тоже ПДн,
та же папка). Оба содержат фрагменты РЕАЛЬНОГО текста — это неизбежно и
явно показано в интерфейсе (блок «Ваши правки» на экране 2: «хранится только
на этом компьютере, в той же папке, что и сессии (путь), и никуда не
отправляется»). `.gitignore` уже покрывает всю директорию `.shifrator/`
целиком (не отдельными масками файлов) — новые sidecar-файлы автоматически
под тем же правилом, правка `.gitignore` не понадобилась. Живой тест
`test_markup_and_doc_sidecars_live_under_home_not_repo` подтверждает: путь
хранения лежит под изолированным `HOME`, не под корнем репозитория.

Удаление сессии (`storage.delete_session`, кнопка «Удалить» на экране 3)
теперь чистит ВСЕ sidecar-файлы (`.meta.json` + новые `.doc.json`/
`.markup.json`), не только `.enc`/`.txt`. `storage.purge_expired` (TTL-очистка)
тоже расширена: раньше `session_store.purge_expired` ничего не знал о
sidecar-ах этапов U2/U3 — они бы копились в хранилище БЕССРОЧНО после
истечения TTL самой сессии (существовавшая с этапа U2 дыра для
`.meta.json`, эта сессия заодно закрывает её и для новых файлов):
`storage.purge_expired` теперь дополнительно подчищает sidecar-ы, чей `.enc`
уже удалён.

## 10. Известные ограничения (честно)

- «Исправить границу»/выделение мышью работает **в пределах ОДНОГО
  сегмента** (абзаца/ячейки таблицы) — нельзя ручной маской захватить текст,
  разорванный переносом строки/ячейкой (тот же класс, что B3 закрывает для
  автоматической детекции; для ручной разметки не реализовано — вне границ
  этой сессии, задача явно про «экран проверки», не про повторение B3).
- Прогресс — оценка по времени, не точные стадии (см. §6) — намеренно, в
  рамках границ задачи.
- Фоновая job-очередь `/api/encrypt/start` — в памяти процесса (`_JOBS`),
  без верхнего ограничения на число одновременных задач: для однопользова-
  тельского локального инструмента это осознанный минимализм (как и весь
  остальной сервер), не рассчитано на нагрузку.
- Удаление СОХРАНЁННОЙ (уже применённой) записи разметки удаляет только
  запись из корпуса — документ, который уже пересобран, не откатывается
  автоматически (задокументировано в докстринге `delete_markup_entry`).
- Анализатор/отчёт (U4), склонение при восстановлении ручных ФИО-масок —
  сознательно не в этой сессии, как и указывала постановка.
