## 1. Вердикты по фиксам

### P1 (порча данных при восстановлении граничных пар) — **ПОДТВЕРЖДЁН**

Реализован Вариант А из предписания аудита: `tokenizer.py` больше не заводит `boundary_partner`/
`group_token` — каждая половина граничной пары получает токен по обычному правилу
`(entity_type, original_text)`, то есть свой собственный.

Доказательства (не со слов отчёта, а прогонами):
- `tests/test_boundary_entities.py::TestBoundaryPairRoundTrip` (изменённый набор, добавлен
  фиксом) — round-trip tokenize→save_session→detokenize для сценария 1 (телефон через `\n`) и
  сценария 2 (ложное срабатывание `23456789`/`1` на стыке ячеек) — оба посимвольно точны.
- Моя собственная проверка на уровень выше — **стык P1 и компонента 2, который не проверял
  никто**: `TestP1CrossesComponent2` в `test_wave1_verification.py`. Собран НАСТОЯЩИЙ `.docx`
  (через `python-docx`, реальные XML-раны), токенизирован через `tokenize()`, прогнан через
  `session_store.save_session` → `file_detokenizer.detokenize_file` (та же функция, что вызывает
  CLI `decrypt-file`). Результат: `table.cell(0,1).text == "23456789 экз."` — целое число, не
  `"1 экз."`, как было бы при старом общем токене. Для телефона — `"+7 (495)"` и `"123-45-67"`
  оба на месте.
- Другие типы сущностей на границе: `TestP1OtherEntityTypesAndDedup` — организация, разорванная
  переносом строки, ПЛЮС та же организация целиком в другом месте документа: дедупликация по
  `(entity_type, original_text)` не путает половину пары с независимым целым вхождением,
  round-trip точен в обоих местах. Тот же телефон, разорванный в ДВУХ разных местах документа —
  обе пары восстанавливаются независимо и точно.
- Существующие тесты уже покрывали ИНН и телефон на стыке ячеек таблицы (оба разделителя —
  `""` в окне детекции и `" | "` в сборке текста).

**Отдельно и громко — утечка B3 НЕ открылась заново.** Это проверено прямо:
`tests/test_breaking_leaks.py::TestEntitySplitAcrossSegmentBoundary` (репродукция самого
дефекта B3 из BREAKING_REPORT) — три теста, все ЗЕЛЁНЫЕ, не xfail. Единственный xfail во всём
прогоне — `TestPhoneHomoglyphLeak` (B4, кириллическая омоглиф-цифра), не связан с B3/P1.
`tests/test_boundary_entities.py` тоже сохранил все тесты "..._is_not_leaked" нетронутыми — в
diff изменены ТОЛЬКО тесты на общий токен (`test_both_halves_get_the_same_token` →
`test_both_halves_get_their_own_token`), как и предписывал P1 «Вариант А»; тесты на отсутствие
утечки не тронуты — ТЗ по этому пункту соблюдено.

### Тихий успех decrypt-file — **ПОДТВЕРЖДЁН**

`read_zip_parts` (block 8) теперь требует `[Content_Types].xml` в корне архива; три адаптера
дополнительно требуют свою опорную часть (`word/document.xml` для docx, хотя бы один
`ppt/slides/slide*.xml` для pptx, хотя бы один `xl/worksheets/sheet*.xml` для xlsx). Сигнатуры
всех трёх `rewrite()` + `replace_tokens_in_group` + `detokenize_file` синхронно поменялись на
`tuple[int, ...]` со счётчиком замен.

Доказательства:
- Прежде красный `tests/component2/test_e_malformed_input.py::test_valid_zip_without_any_target_part_raises_ooxml_error`
  теперь **зелёный** (прогнан отдельно: `8 passed`).
- Проверил обе стороны границы «ошибка / норма», как требует ТЗ:
  - Должно падать: переименованный `.txt`, пустой файл (0 байт), обрезанный архив, ZIP-бомба
    (по числу записей и по размеру) — все в `test_e_malformed_input.py`, все проходят.
  - Должно работать штатно: `.xlsx` без `sharedStrings.xml`, но с inline-строками в листе —
    `test_d_xlsx_specifics.py::test_inline_string_cell_resolved` (билдер явно не передаёт
    `shared_strings_xml`) — зелёный, замена прошла. `.docx` без единого токена —
    `test_file_without_any_token_produces_intact_copy` явно проверяет `replaced == 0` и
    `unresolved == []`.
  - **На уровне реального CLI-процесса (никто раньше не проверял; `tests/test_cli.py` вообще не
    вызывает `decrypt-file`)**: `TestCliDecryptFileZeroReplacements` в моём файле гоняет
    `shifrator.py decrypt-file` субпроцессом. `.docx` без токенов → код возврата **0**, файл
    создан, в stderr — предупреждение «в файле не найдено ни одного токена». `.docx` С токеном →
    код возврата 0, никакого предупреждения о нуле замен, stderr пуст, значение реально
    подставлено в текст абзаца.
- Согласованность счётчика между тремя адаптерами: сигнатуры идентичны по коду (проверено
  чтением diff всех трёх файлов рядом), семантика "replaced" одинаково описана в докстрингах.
  `test_unresolved_token_does_not_count_towards_replaced` — токен без резолва (`[ORG_99]`) не
  входит в счётчик, только реально применённые (`[ORG_1]`) — подтверждено на `docx_rewrite`
  напрямую.

Мелкое расхождение (не дефект поведения, см. раздел 2, F1).

### P2 (атомарная запись `.enc`) — **ПОДТВЕРЖДЁН**

`session_store.save_session` теперь пишет через `tempfile.mkstemp` в той же директории + запись
+ `_chmod_600` + `os.replace`, с `except BaseException: os.remove(tmp_path); raise` — тот же
паттерн, что уже был в `ooxml_core.rewrite_zip`.

Смоделировал прерывание записи (не kill/BSOD, но эквивалентно по эффекту): monkeypatch
`os.replace` бросает `OSError` ПОСЛЕ того, как tmp-файл с полным содержимым уже записан на диск.
Проверено: под финальным именем `{sid}.enc` НЕ появляется файл (`test_crash_mid_write_leaves_no_partial_enc_under_final_name`),
и временный `.tmp`-файл не остаётся мусором (`test_no_leftover_tmp_files_after_crash`) — оба
теста зелёные.

### P3 (путь хранилища из `session_store`, не хардкод в `shifrator.py`) — **ПОДТВЕРЖДЁН**

`shifrator.py:cmd_encrypt` больше не строит `Path.home() / ".shifrator" / "sessions"` сам, а
берёт `session_store.default_storage_dir()`. **Критичная проверка (путь не должен был
измениться) выполнена в первую очередь**: `default_storage_dir()` возвращает буквально
`_DEFAULT_STORAGE_DIR = Path.home() / ".shifrator" / "sessions"` — тот же самый литерал, что был
в `shifrator.py` до фикса. `test_p3_default_storage_dir_matches_original_hardcoded_path`
сравнивает оба независимо построенных пути напрямую. Путь сессий пользователя не сломан.

CLI-тесты (`test_cli.py`, не редактировался) по-прежнему зелёные без изменений — encrypt/decrypt/
delete ведут себя как раньше по выводу и кодам возврата; отдельно проверено, что `decrypt-file`
(который тоже читает сессию через `default_storage_dir` косвенно, через `load_session`) видит ту
же сессию, что создал `encrypt` — это прямо демонстрируют мои CLI round-trip тесты (encrypt →
decrypt-file с тем же `session_id` находит сессию и раскрывает токен).

### P4 (assert → raise в `ner_detector.detect_ner`) — **ПОДТВЕРЖДЁН**

Код теперь `if e.original_text != actual: raise AssertionError(...)` вместо голого `assert`
верхнего уровня. Проверено НЕ чтением кода, а поведенчески: извлёк реальный блок инвариантной
проверки прямо из `src/ner_detector.py` (тем же тестом, автоматически — не переписывал руками) и
прогнал его в отдельном скрипте под `python -O` с заведомо нарушающим инвариант объектом.
Результат: `AssertionError` долетает и под `-O` (`test_p4_invariant_violation_raises_under_python_dash_O`,
зелёный). Контрольный тест на голый `assert` в исходнике тоже зелёный
(`test_p4_source_uses_raise_not_bare_assert_for_invariant`).

## 3. Утечка B3 — отдельно и громко

**НЕ открылась.** Обе половины любой сущности, разорванной границей сегмента, по-прежнему
всегда токенизируются (проверено на телефоне через `\n`, ИНН и телефоне через стык ячеек

самого дефекта B3 (`TestEntitySplitAcrossSegmentBoundary`) зелёные.

## 4. Что проверено, проблем не найдено

  проверено в этой верификации, оба сценария (реальная сущность и ложное срабатывание) точны.
- Согласованность сигнатур трёх адаптеров (docx/pptx/xlsx) и `replace_tokens_in_group` —
  идентичны по коду и докстрингам.

  `decrypt-file` видят одну и ту же сессию.
- P4: инвариант `original_text == segment.text[start:end]` реально бросает `AssertionError` под

- Полный регресс: **283 passed, 1 xfailed (B4), 0 failed** — эталон «269+ passed, 1 xfailed,

- `~/.shifrator/` не читался и не писался ни разу за время верификации: все прогоны — во

  для unit-тестов, тем же паттерном, что уже используется в проекте.
