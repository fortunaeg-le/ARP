# BREAKING REPORT — этап 3 (попытка сломать SHIFRATOR перед сдачей)

Область: не «ещё один граничный случай», а способы заставить систему **соврать**
(сказать «успех», но потерять/исказить данные), **утечь ПДн мимо токенизации** и
**отказать** (подвесить пайплайн) на вводе, который реальный — в т.ч. неаккуратный —
пользователь способен подать на практике. Код **не чинился**: только находки,
документация и воспроизводящие тесты в `tests/test_breaking_*.py`.

Не дублирует FINDINGS.md этапа 2 (все FIXED-находки закрыты и повторно не проверялись),
кроме одного разрешённого случая: **B5** — НОВЫЙ путь к симптому закрытой находки #7
(тихая порча UTF-16 + утечка ПДн), которого фикс #7 не покрывает.

**Как читать статус** (тот же, что в FINDINGS.md):
- `XFAIL (bug)` — тест проверяет КОРРЕКТНОЕ поведение, которое сейчас нарушено;
  `@pytest.mark.xfail(strict=True)`. Воспроизводит дефект; когда его починят и метку
  снимут — тест позеленеет (XPASS→FAIL), и о нём не забудут.
- `PASS (pins)` — фиксирует фактическое (нежелательное/пограничное) поведение как есть.
- `PASS (спека OK)` — подтверждение, что защита/обещание реально работает (не дефект).

## 2. Не воспроизвелось (специально пробовал сломать — устойчиво)

Проверенная устойчивость, чтобы было видно, что это не пропуск:

- **ReDoS в детокенизаторе (сторона `decrypt`).** `_TOKEN_RE = \[[A-Z_]+_\d+\]` —
  несмотря на перекрытие `_` в классе `[A-Z_]` и литералом `_`, движок `re` не
  деградирует: `[` + 60 000 букв/подчёркиваний обрабатывается за **< 0.001 c**.
  DoS только на стороне `encrypt` (паттерн `SUM`, находка B1), не на `decrypt`.
- **DoS по объёму в `decrypt`.** Ответ LLM в **100 000 валидных токенов (800 КБ)** —
  0.04 c; ответ **3.9 МБ без токенов** — мгновенно; **50 000 неизвестных токенов** —
  0.03 c. Детокенизация линейна, ответ в 100× длиннее оригинала её не роняет.
- **Смещения при эмодзи / не-BMP символах.** `Клиент 😀 Ivan … ИНН 7707083893` и
  `📞😀🎉 … +7 (495) 123-45-67` — ИНН и телефон после эмодзи (U+1F600, вне BMP)
  токенизируются корректно: Python считает смещения по кодовым точкам, суррогатных
  сдвигов нет. `TestEmojiOffsetsRobust` (PASS).
- **«Грязный» ответ LLM — токеноподобный текст в коде/JSON.** `orgs = ["ORG_1", "ORG_2"]`
  **не** принимается за токены (после `[` идёт `"`); настоящий `[ORG_1]` восстановлен,
  неизвестный `[ORG_9]` ушёл в `unresolved`. `TestDirtyLlmResponseRobust` (PASS).
- **Последовательность `encrypt → delete → decrypt` старым id.** Пользователь
  скопировал `session_id` заранее и расшифровывает после удаления — чистое
  «сессия не найдена», код 1, без падения. `TestEncryptDeleteDecryptSequence` (PASS).
- **ФИО, разорванное переносом** (`Иван\nПетров`) — обе части находятся как два
  отдельных `PERSON`-токена; при детокенизации восстанавливаются посимвольно точно,
  **утечки нет** (в отличие от телефона/организации, B3).

### Ожидаемое поведение, не находка (зафиксировано в спеке — вне таблицы)

- **Колонтитулы, сноски, комментарии, надписи (`w:txbxContent`), вложенные таблицы
  в ячейках** — вне охвата MVP (спека, Блок 1: «Область охвата MVP — только тело
  документа»). При вложенной таблице extractor штатно печатает предупреждение с

  не дефект; но пользователь должен явно знать, что реквизиты в колонтитулах **не
  анонимизируются** (см. риск в разделе 3).
- **9-значный номер договора, ошибочно принятый за `KPP`** — известное ограничение
  MVP (у КПП нет контрольной суммы; спека, Блок 2, приёмка). Не проверялось повторно.

## 3. Итоговая оценка готовности к реальному использованию

**Давать эту версию людям для работы с настоящими договорами прямо сейчас — нельзя.**
Продукт устойчив в ядре (сессии, детокенизация, разрешение пересечений, оффсеты при
Юникоде — всё держит нагрузку и грязный ввод), но у него остаются два дефекта, каждый
из которых по отдельности бьёт по главному обещанию «анонимизировать и не потерять».

Блокируют выпуск:
1. **B1 (ReDoS в `SUM`)** — единственная длинная числовая строка в документе подвешивает
   `encrypt` на десятки секунд и более без каких-либо признаков ошибки. Это отказ
   инструмента на легко достижимом (и тривиально эксплуатируемом) вводе.
2. **B2 + B3 (утечки ПДн)** — банковский счёт с пробелами (типичный формат договоров)
   и любое чувствительное значение на стыке абзаца/ячейки уходят в LLM в открытом виде.
   Для продукта, чья единственная задача — не выпустить ПДн наружу, это прямое
   невыполнение назначения, причём **молча**: пользователь видит «успех» и токены и
   уверен, что документ чист.

Условно допустимо доработать до пилота: **B4** (омоглифы — ниша), **B5** (UTF-16 без
BOM — реже, но всё ещё тихая порча) и **B6** (`delete` рапортует ложный успех и `.txt`
копятся без границы — риск утечки остаточных данных и деградации при долгой работе).

**Минимальный набор для разблокировки реального использования:** переписать паттерн
`SUM` без перекрытия квантификаторов (B1); детектировать реквизиты с внутренними
разделителями и/или предупреждать о числовых блоках, не прошедших ни один детектор (B2);
предупреждать пользователя о непокрытых зонах — стыки сегментов, колонтитулы (B3 и
ограничение MVP); чистить `.txt`-сайдкары в `delete`/`purge_expired` (B6). До этого
версия годится для демонстрации на «чистых» тестовых документах, но не для реальных
договоров с настоящими ПДн.
