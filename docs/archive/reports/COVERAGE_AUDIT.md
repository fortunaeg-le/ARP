## 0. ВЕРДИКТ

**Цифрам замера можно верить — с одной оговоркой: главная метрика (residual leak) СИСТЕМАТИЧЕСКИ ЗАНИЖЕНА, то есть реальных утечек БОЛЬШЕ, чем в отчёте — но не меньше.**

Всё остальное — recall, precision, span coverage, число крешей, список пропусков — воспроизводится из сырого JSON **байт-в-байт** и не завышено. Попытка доказать «система на самом деле лучше, чем показано» провалилась: отчёт нигде не льстит системе. Наоборот — по утечкам он к системе слишком добр.

**Итог по направлению подгонки:** гипотеза «recall завышен» — **опровергнута** (recall честен и вдобавок объявлен верхней границей). Гипотеза «утечек больше, чем показал замер» — **подтверждена**: +68 доказанных числовых утечек, не посчитанных харнессом, плюс 1070 сущностей из 31 упавшего документа, исключённых из знаменателя таблицы §2.

## 2. НАЙДЕННАЯ ПОДГОНКА (места, где метрика мягче заявленного)

### 2.1. Residual leak числовых типов — ALL-OR-NOTHING, а докстринг обещает «части» [ГЛАВНОЕ]

`measure_lib.digit_cores()` берёт **максимальную** цифровую последовательность эталонного значения и проверяет, дожила ли она **целиком** (`if c in anon_glue`). Для счёта из 20 цифр, разорванного границей ячейки/переводом строки, детектор ловит ЧАСТЬ, а вторая часть (8–11 цифр) уходит в анонимный текст в открытом виде — но проверка ищет все 20 подряд, не находит и рапортует «не утекло». Это прямо противоречит докстрингу `leak_pieces`: «какие ЧАСТИ эталонного значения дожили».

**Доказательство (agency_0002, счёт `40802810445145901597`):**
анонимный текст содержит `…[kpp_1] 45145901597 pekb…` — **11 реальных цифр счёта открытым текстом**. Харнесс: `leaked=False`.

Независимым слепым сканом (`scratch/audit/blind_scan.py`, свой нормализатор) нашёл 283 таких расхождения; после строгой перепроверки уже нормализатором самого харнесса (окно ≥8 цифр) **подтверждено 68 реальных утечек**, которые харнесс не посчитал:

| тип | подтв. недосчитанных утечек |
|---|---:|
| ACCOUNT | 63 |
| OGRN | 3 |
| BIK | 1 |
| PHONE | 1 |
| **итого** | **68** |

(Остальные 215 расхождений — артефакты моего агрессивного сканера, ≥3-символьные токены; под строгим порогом харнесса не подтвердились, **честно отбрасываю**.) Почти все 68 — счета, разорванные `linebreak_inside_entity` / `cell_boundary_split` / `mut:linebreak`, где B3 склеил один фрагмент, а второй утёк. Для BIK «44525593» из 9-значного БИК = утечка почти целиком.

**Коррекция:** ACCOUNT leak 33.6 % → **43.4 %**; общий leak по 293 — 50.0 % → **≥50.7 %**. Это ПОЛ, а не потолок: искал только окна ≥8 цифр; частичные утечки 6–7 цифр не считал.

### 2.2. Табличный residual leak §2 считается БЕЗ 31 упавшего документа

Таблица §2 («по 293 обработанным») исключает 1070 эталонных сущностей 31 крешнутого документа. Эти документы не шифруются вовсе → утекают на 100 %. Отчёт это раскрывает в TL;DR (100 % док. «утекают или не шифруются»), но **сама таблица leak% занижена**: например, реальный leak с учётом крешей — **55.3 %**, а не табличные 50.0 %. Строку «leak по всем 324» отчёт в §2 не выводит — читатель, глядящий на таблицу, видит заниженное.

### 2.3. Recall засчитывается по пересечению ≥1 символа (мягко — но раскрыто)

Строка `run_measurement.py:140`: `found` = любое перекрытие ≥1 символа при совпадении типа. Значит, «г.» из «г. Москва, ул. Ленина, д. 5», закрытое системой, = успех recall. Пересчёт:

| тип | loose recall (отчёт) | full-cover (≥ эталон) | exact (симв-в-симв) |
|---|---:|---:|---:|
| ADDRESS | 89.2 % | 71.5 % | **33.6 %** |
| PER | 64.8 % | 49.0 % | 45.6 % |
| ORG | 73.9 % | 49.7 % | 44.9 % |

862 из 5767 «найденных» (14.9 %) НЕ покрыты целиком. **В защиту отчёта:** он это честно раскрывает (§2 про PASSPORT, §3/§7 про ADDRESS-иллюзию) и прямо пишет «главной метрикой следует считать residual leak, а не recall». Это не скрытая подгонка, а раскрытая мягкость. Но цифру 89.2 % для ADDRESS нельзя цитировать без exact 33.6 % рядом.

### 2.4. Headline recall 55.9 % — это blended-среднее

Base·canonical baseline = **87.2 %**, mutant·adversarial = **34.8 %** (5516 сущностей, 53 % корпуса тянут среднее вниз). Единая цифра 55.9 % смешивает «лёгкий» и «состязательный» слои. `GENERATION_NOTES` прямо предупреждает не давать единую цифру; отчёт §2 всё же выносит 55.9 % в заголовок (хотя ниже раскрывает по типам и приёмам). Не подгонка в пользу системы (скорее наоборот — среднее занижено мутантами), но методически цифру 55.9 % нельзя подавать как «полноту системы».

Сопоставление типа — **строгое** (ADDRESS, найденный как ORG, в recall НЕ засчитан). Здесь харнесс НЕ мягчит. Проверено по коду (`x["gtype"] == gt`).

## 3. Утечки, ПРОПУЩЕННЫЕ САМИМ ЗАМЕРОМ (слепой контр-замер, §2.4/§2.5)

Независимый прогон encrypt по всему корпусу + свой нормализатор (снятие Cf/NBSP/SHY, свод омоглифов, свод цифро-омоглифов) + поиск ЛЮБЫХ ПДн-подобных последовательностей вне gold:

1. **68 числовых частичных утечек** (см. §2.1) — не видны ни одной метрике этапа 2. Главная находка: харнесс, меряющий «утечку», сам её недосчитывает на разорванных реквизитах.
2. **KBK/20-значные коды утекают** (8 примеров, напр. `18210101010110001…`). Это НЕ ПДн (бюджетные коды — негативы), отчёт §5 их и относит к негативам/шуму. Реальной новой ПДн-утечки вне gold **не нашёл** — автор корпуса разметил свой текст полно.
3. **Ручной зонд 20 «неудобных» форм** (`scratch/audit/probe.py`) через живой конвейер — утекло 7/20. Все 7 попадают в УЖЕ раскрытые отчётом дыры:
   - СНИЛС `112-233-445 95`, дата рождения `5 марта 1990` → нет детектора (отчёт §3);
   - код подразделения паспорта `770-095` → нет детектора (отчёт §3);
   - адрес без города `Советская 12/1` → ugly-адрес/`glued_to_prev` (отчёт §4);
   - `А.С.Пирогова` (инициалы слитно) → PER-регистр/паттерн (отчёт §3 `no_pattern`);
   - 12-значный ИНН физлица `771234567890` → отброшен по **контрольной сумме** (я задал невалидный номер; детектор 12-значный есть — отчёт §3 «rejected_invalid_checksum», НЕ новая дыра).

   **Ни одного скрытого класса утечки зонд не вскрыл.** Это сильный довод В ПОЛЬЗУ честности отчёта: враждебная ручная проверка воспроизводит ровно заявленные им дыры, а не новые.

## 4. Дыры в корпусе (что добавить перед следующим замером)

- **Частично-разорванные числовые реквизиты как отдельный класс с эталоном частичной утечки.** Сейчас метрика их «не видит» (§2.1). Нужны кейсы «детектор берёт 9 цифр из 20» с явной разметкой утёкшего хвоста.
- **Короткие/иностранные ФИО, невидимые метрике leak.** 94 PER-сущности не имеют ни одного ≥4-символьного токена (Ким Ен Су, инициалы) → `leak_pieces` их частичную утечку не поймает (только целиком через fallback). Метрика слепа к ним по построению.
- **Реальные договоры.** Оговорка §8 («синтетика = верхняя граница, на реальных данных recall НИЖЕ, leak ВЫШЕ») присутствует ДОСЛОВНО и не смягчена — засчитано. Но пока цифры получены на форм-наборе, который автор признаёт «своим представлением о договорах»: узость набора завышает recall на «лёгких» типах (EMAIL/ORG/ADDRESS-recall).
- Автор кода корпуса, судя по `digit_grouping_dashes` (0 %) и 12-значному ИНН, **в код не подглядывал** — формы вскрывают реальные дыры, а не обходят их. Признаков «подгонки форм под регулярки» не нашёл.

## 6. Что теперь честно можно сказать о системе (без смягчений)

Замер честный и воспроизводимый; отчёт не преувеличивает качество системы ни в одной цифре — если и грешит, то в сторону **недооценки утечек**. По существу же: на состязательном синтетическом корпусе система выпускает в анонимный текст хотя бы часть эталонной ПДн из **каждого** обработанного документа, а с учётом 31 полного отказа (`encrypt` падает) — из всех 324; реальная доля утёкших сущностей — **~55 %, а не 50 %**. SNILS, дата рождения и код подразделения паспорта не ищутся вовсе; омоглифы/невидимые/разрывы валят числовые реквизиты; ADDRESS «находится» на 89 %, но по факту утекает компонентами на 77 %. Всё это — верхняя граница на выдуманных договорах; на реальных будет хуже. Пользоваться цифрой можно ТОЛЬКО для контроля регресса и приоритизации, и ни в коем случае — для заявлений о соответствии 152-ФЗ.
