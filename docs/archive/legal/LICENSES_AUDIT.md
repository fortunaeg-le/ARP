## 3. Отдельная проверка главных подозреваемых (модели и словари — не PyPI-пакеты)

### 3.1 pymorphy2 + словарь OpenCorpora — 🟡 ЖЁЛТАЯ, главная находка аудита

- **Код** `pymorphy2` и `pymorphy2-dicts-ru`: MIT (подтверждено по
  `dist-info/METADATA` обоих пакетов).
- **Данные** (сам словарь: `words.dawg`, `paradigms.array`, суффиксы и т.д.
  внутри `pymorphy2_dicts_ru/data/`, собраны из OpenCorpora rev. 417127):
  явно указаны в README пакета как
  **Creative Commons Attribution-Share Alike 3.0** (CC BY-SA 3.0,
  https://creativecommons.org/licenses/by-sa/3.0/).
- **Как используется в проекте**: `pymorphy2.MorphAnalyzer` / `MorphVocab`
  импортируются в `src/` (используется для морфологии, склонения при
  восстановлении, `MorphVocab.inflect` — этап E, зафиксирован в памяти
  сессии). Это прод-путь, не тесты — словарь-данные едут в
  составе поставки как часть установленного пакета.
- **Что это значит**: CC BY-SA — **не** non-commercial (коммерческое
  использование разрешено), но это **share-alike**: производные материалы
  («adaptations») от словаря должны распространяться на тех же условиях
  (CC BY-SA) + указание авторства. Ваш код, который просто *использует*
  словарь через API библиотеки (не модифицирует и не переупаковывает сами
  данные словаря), по общей практике open-source экосистемы (сотни
  коммерческих продуктов используют pymorphy2/OpenCorpora) не считается
  производным от словаря. Но это интерпретация, не факт закона.
- **Риск**: низкий на практике (де-факто стандарт индустрии для русской
  морфологии, широко используется коммерчески), но формально **требует
  проверки юристом**, если поставка on-premise предполагает передачу файлов
  словаря клиенту как есть (а не только доступ через API) — в этом случае
  условие атрибуции (упоминание OpenCorpora + CC BY-SA) точно применимо и
  должно попасть в NOTICE (см. черновик ниже).
- **Замена с зелёной лицензией**: нет прямого эквивалента с той же полнотой
  покрытия русской морфологии и лицензией более свободной, чем CC BY-SA —
  сам OpenCorpora — открытый краудсорс-корпус, альтернативы (pymystem,
  Yandex) обычно проприетарны или ограничены по объёму бесплатного
  использования.

### 3.2 Natasha-стек: natasha, slovnet, navec — код зелёный, веса требуют уточнения

- **Код** всех четырёх пакетов (`natasha`, `navec`, `slovnet`, `razdel`,
  `yargy`, `ipymarkup`): подтверждено MIT по бандл-файлам `LICENSE` внутри
  `dist-info` каждого пакета (не только по классификатору PyPI — прочитан
  текст файла).
- **Предобученные веса** (`NewsEmbedding`, `NewsNERTagger` в
  [ner_detector.py](../../../src/ner_detector.py), `NewsMorphTagger`,
  `NewsSyntaxParser` в [syntax_compound.py](../../../src/syntax_compound.py)):
  скачиваются отдельно (обычно с GitHub Releases проектов natasha/navec,
  natasha/slovnet) при первом обращении — в текущем окружении файлы весов
  на диске не найдены (значит либо ещё не скачивались, либо кэш вне
  проверенных путей). Сами файлы весов не проверялись напрямую (нет
  локальной копии), но:
  - проект natasha прямо позиционируется как готовый к продакшн/коммерческому
    использованию (README репозитория), а репозитории navec/slovnet
    распространяются под тем же MIT LICENSE, что покрывает и код, и релизные
    артефакты по стандартной практике GitHub-репозиториев.
  - Обучающий корпус (новостные тексты) для эмбеддингов/тегеров не имеет
    полностью прозрачного provenance (авторские права на исходные новостные
    статьи) — это типичная неопределённость для NLP-моделей, обученных на
    вебскрейпинге, и не специфична для natasha.
  - **Требует проверки юристом**, если критично на 100% — рекомендуется
    письменное подтверждение от мейнтейнеров natasha (issue/email) о статусе
    коммерческого использования весов, для документального следа при
    коммерческой поставке. Риск оцениваю как низкий (тот же паттерн, что у
    большинства открытых NLP-моделей, включая многие проприетарные продукты
    на рынке).
