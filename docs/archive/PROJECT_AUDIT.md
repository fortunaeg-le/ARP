## 1.3 Статус B3 — РЕАЛИЗОВАН ПОЛНОСТЬЮ (с доказательством)

B3 (сущность, разорванная границей сегмента) реализован в `src/tokenizer.py`:
- `_BOUNDARY_WINDOW = 60` (`tokenizer.py:26`);
- `_boundary_sep()` (`tokenizer.py:197`) — разделитель окна: `""` для соседних ячеек
  одной строки таблицы, `"\n"` для всех прочих границ (см. память проекта и спеку блока 4);
- `_detect_boundary_entities()` (`tokenizer.py:219`) — окно `хвост(≤60)+sep+голова(≤60)`
  по каждой паре соседних непустых сегментов, повторный прогон публичных
  `detect_regex`/`detect_ner`, фильтр «интервал пересекает точку стыка», деление на пару
  Entity_A/Entity_B с пересчётом оффсетов, реестр партнёров;
- в `tokenize()` пары получают **общий токен**, если обе половины пережили разрешение
  пересечений (`tokenizer.py:350–374`).
- Тесты: `tests/test_boundary_entities.py` (13 тестов, зелёные) — телефон через `\n`,
  ИНН через стык ячеек, дедупликация с обычной детекцией, общий токен пары.

Проверено вживую: телефон `+7 (495)\n123-45-67` в `.txt` токенизируется в
`[PHONE_1]\n[PHONE_1]`. Канал утечки B3 закрыт. **Но восстановление таких пар ломает
данные — это новая критическая находка P1 (раздел 3), внесённая самим B3-фиксом.**

# 3. Критические проблемы (новые, не дублируют FINDINGS #1–12 и B1–B6)

## P1. Восстановление сущности, разорванной границей сегмента, молча подменяет вторую половину первой — порча данных, внесённая B3-фиксом

- **Критичность: КРИТИЧНО** (посимвольная точность восстановления нарушена; программа
  отрабатывает «успешно», пользователь не узнаёт).
- **Где:** взаимодействие трёх мест: `src/tokenizer.py` (общий токен пары,
  `tokenize()`, строки ~350–374) → `src/session_store.py:save_session` (дедупликация
  записей **по token**: сохраняется только ПЕРВАЯ запись, т.е. original_text первой
  половины) → `src/detokenizer.py` / `src/file_detokenizer.py` (маппинг
  `token → один original_text`).
- **Механика.** Половины разорванной сущности получают один общий токен `[PHONE_1]`,
  но у них разные `original_text` («+7 (495)» и «123-45-67»). Сессия хранит одну запись
  на токен — выживает первая. При decrypt ОБА вхождения токена заменяются текстом
  первой половины.
- **Воспроизводимый сценарий 1 (реальная сущность).** `.txt`:
  `"Контактный телефон +7 (495)\n123-45-67 указан в договоре"` →
  анонимизировано `"… [PHONE_1]\n[PHONE_1] …"` → decrypt возвращает
  `"… +7 (495)\n+7 (495) …"`. Хвост номера `123-45-67` уничтожен. Проверено вживую.
- **Воспроизводимый сценарий 2 (ложное срабатывание портит невинные данные).**
  Соседние ячейки строки таблицы docx: `"Приложение 1"` и `"23456789 экз."`.
  В граничном окне ячейки склеиваются БЕЗ разделителя → `"123456789"` матчится как KPP →
  `"Приложение [KPP_1] | [KPP_1] экз."` → восстановление даст `"Приложение 1 | 1 экз."` —
  число `23456789`, вообще не являвшееся ПДн, молча заменено на `1`. Проверено вживую.
- **Что увидит пользователь:** корректно выглядящий восстановленный текст и код возврата 0.
  **Чего НЕ увидит:** что часть значения (или соседнее невинное значение) подменена.
  Ни предупреждения, ни unresolved — токен-то известен сессии.
- **Почему не поймали раньше:** `tests/test_boundary_entities.py` проверяет только
  сторону токенизации (общий токен, отсутствие утечки); round-trip через
  `save_session → detokenize` для граничных пар не тестировался.
- **Как чинить (предписание, требует решения пользователя по семантике):**
  - Вариант А (минимальный и точный, рекомендую): **отказаться от общего токена пары** —
    каждая половина получает СВОЙ токен со СВОИМ original_text (убрать реестр
    `boundary_partner`/`group_token` в `tokenize()`, половины идут по обычному правилу
    `(entity_type, original_text)`). Восстановление становится посимвольно точным в обоих
    сегментах автоматически. Цена: LLM видит два разных токена у одной сущности —
    ровно то, от чего спека блока 4 (раздел «Общий токен паре») хотела уйти; этот пункт
    спеки придётся переписать. Затронет: `tokenize()` (упрощение), спеку блока 4,
    тесты `test_boundary_entities.py` (те, что проверяют общий токен, — их придётся
    менять ОСОЗНАННО, с записью в отчёт, это изменение контракта, а не «подгонка»).
  - Вариант Б (сохранить общий токен): хранить в сессии для парного токена **полное**
    значение (хвост+разделитель+голова из окна) и при сборке анонимизированного текста
    заменять пару НА ОДНО вхождение токена (вторая половина — пустая строка). Точен для
    границ с `"\n"`, но НЕ для ячеек таблицы (в сборке между ячейками стоит `" | "`,
    а в окне — `""`); сложнее и трогает сборку текста. Не рекомендую без крайней нужды.
  - При любом варианте: добавить round-trip тест «encrypt→decrypt» для граничной пары.
- **Чем это НЕ является:** это не повод выключать B3-детекцию (она закрывает реальную
  утечку) и не дефект `detokenize` (он честно подставляет то, что лежит в сессии).
  Дедупликацию по token в `save_session` тоже не трогать — она корректна для обычных
  токенов; проблема в том, что пара кладёт под один токен два разных значения.

## P2. `save_session` пишет `.enc` неатомарно

- **Критичность: мелочь** (шумный отказ, не тихий): `session_path.write_bytes(encrypted)`
  без tmp+rename (`src/session_store.py:179-180`). Прерывание процесса на середине записи
  оставит битый `.enc`; следующий `load_session` даст `SessionNotFoundError`
  «не расшифровывается» — данные encrypt-прогона потеряны, но это видно сразу, и
  `purge_expired` такой файл не удаляет (пропускает с предупреждением).
- **Сценарий:** kill/BSOD во время `encrypt` большого документа.
- **Как чинить:** запись во временный файл в той же директории + `os.replace` — тот же
  приём, что уже используется в `ooxml_core.rewrite_zip`. Одно место, ничего смежного.
- **Чем это НЕ является:** не гонка (ключ уже атомарен), не канал утечки.

## P3. Дублирование дефолтного пути хранилища в `shifrator.py`

- **Критичность: мелочь** (мина под будущие правки, сейчас поведение корректно).
- **Где:** `shifrator.py:cmd_encrypt` строит `Path.home() / ".shifrator" / "sessions"`
  сам, вместо того чтобы взять `session_store._DEFAULT_STORAGE_DIR` (private) или
  получить путь из API. Если дефолт в `session_store` когда-нибудь изменится,
  `.enc` и `.txt` разъедутся по разным директориям молча.
- **Как чинить:** экспортировать из `session_store` функцию/константу дефолтного пути и
  использовать её в CLI. Не менять сам путь!
- **Чем это НЕ является:** не предложение менять расположение хранилища.

## P4. `detect_ner` защищает инвариант оффсетов оператором `assert`

- **Критичность: мелочь.** `src/ner_detector.py:178-183`: инвариант
  `original_text == segment.text[start:end]` проверяется `assert`, который отключается
  при `python -O`. Нарушение инварианта — прямой путь к тихой порче текста в блоке 4
  (это прописано в спеке). Пока CLI никто с `-O` не запускает.
- **Как чинить:** заменить на `if … raise AssertionError(…)` (или логирование + отказ).
- **Чем это НЕ является:** сам инвариант сейчас держится (тесты зелёные) — это защита
  от будущих правок, а не активный баг.

Прочее известное и НЕ дублируемое здесь: незакрытый дефект компонента 2 («валидный ZIP
без целевых частей копируется как успех», намеренно красный тест) — уже задокументирован

| **ИТОГО encrypt** | **~522 s (8.7 мин)** | недопустимо для инструмента «легче локальной LLM» |

## E1. B3-проход по граничным окнам стоит дороже всей основной детекции и почти всегда находит ноль

- **Замер:** 309.5 s из 522 s (59% пайплайна) на документе, где НИ ОДНА сущность не
  разорвана границей (типичный случай). 5999 окон × ~52 мс.
- **Где:** `src/tokenizer.py:_detect_boundary_entities` — на КАЖДУЮ пару соседних
  сегментов зовёт полные `detect_regex(win_doc, config_path)` и `detect_ner(win_doc,
  config_path)` для окна ≤121 символа.
- **Декомпозиция стоимости одного окна:** чтение+парс `entity_types.yaml` — 4.74 мс × 2
  вызова (детекторы перечитывают конфиг при каждом вызове; 11998 чтений за прогон ≈ 57 s);
  Natasha NER-тэггер ~3.6 мс; `AddrExtractor` (yargy) — 15–43 мс (доминирует).
- **Сколько стоит сейчас и потом:** сейчас ×2.5 к времени encrypt. Для веб-слоя
  (компонент 1) это разница между «запрос обрабатывается» и «запрос висит 9 минут»:
  синхронный HTTP-запрос отвалится по таймауту. Компонент 2 не затронут (не импортирует
  детекторы).
- **Как чинить (по убыванию отдачи, БЕЗ изменения семантики детекции):**
  1. **Кэшировать конфиг** — модульный кэш по `(abspath, mtime)` в
     `regex_detector._load_regex_types`, `ner_detector._load_ner_config`,
     `tokenizer._load_token_prefixes`. Публичные сигнатуры не меняются. Экономия ≈ 57 s
     на этом документе (и ~30 s в основной детекции — см. E3). Ничего не ломает:
     конфиг и так считается неизменным в течение прогона.
  2. **Фильтр окон до запуска детекторов.** Токен/сущность может пересекать стык только
     если по обе стороны стыка стоят «сшиваемые» символы. Минимальный безопасный фильтр:
     если `tail` пуст после rstrip или `head` пуст после lstrip — окно пропустить; если
     стык «неалфавитно-нецифровой с обеих сторон» (например, хвост кончается на `.`/`;`) —
     regex-паттернам и Natasha там нечего сшивать. Консервативный вариант: гонять
     `detect_regex` всегда (он дёшев: ~0.04 мс/окно), а **NER в окне** — только если
     `tail[-1]`/`head[0]` буквенно-цифровые. На замерном документе это убирает почти все
     NER-вызовы окон (строки кончаются точкой). Риск: ФИО «Иванов\nИ.И.» — хвост кончается
     буквой, голова буквой → окно останется. Задокументировать выбранное правило в спеке
     блока 4.
  3. Если и этого мало — батчить окна в один текст с картой оффсетов (сложно, хрупко,
     фаза 2; не начинать без замера после шагов 1–2).
- **Чем это НЕ является:** не предложение отключить B3 и не изменение
  `_BOUNDARY_WINDOW`/разделителей (см. память проекта: `""` для ячеек — намеренно).

## E2. `AddrExtractor` на каждом сегменте — доминирующая стоимость основной NER-детекции

- **Замер:** 15–43 мс на строку ~100 символов (yargy-парсер) → ~140–180 s из 206.7 s
  `detect_ner` на 6000 строк. Для сравнения: NER-тэггер Natasha — 3.6 мс/строка
  (22 s на документ), т.е. адресный экстрактор в 5–10 раз дороже нейросетевого тэггера.
- **Где:** `src/ner_detector.py:detect_ner` — `list(_addr_extractor(text))` для каждого
  сегмента безусловно.
- **Сколько стоит потом:** веб-слой — та же арифметика, что E1.
- **Как чинить (варианты, нужен выбор пользователя):**
  1. Пре-фильтр сегментов: гонять AddrExtractor только по сегментам, содержащим
     адресные маркеры (`г.`, `ул.`, `д.`, `обл.`, `пр-т`, `пер.`, индекс `\b\d{6}\b` и
     т.п. — список вынести в конфиг). Риск ложноотрицательных: адрес без маркеров
     («Москва, Ленина 5») — редок в договорах, но риск утечки задокументировать и
     принять осознанно.
  2. Оставить как есть и принять стоимость (если 200-страничные документы — не целевой
     сценарий MVP; на договоре в 10 страниц encrypt ≈ 25–30 s, терпимо).
  Замер обязателен после любого выбора.
- **Чем это НЕ является:** не предложение заменить Natasha/yargy другой библиотекой
  (запрет спеки на самовольную замену пакетов).

## E3. Перечитывание `entity_types.yaml` на каждый вызов каждого детектора

- **Замер:** 4.74 мс на чтение; в основной детекции — по 1 разу на вызов (мелочь), но
  вместе с B3-проходом — **11998–23999 чтений одного и того же файла за один encrypt**
  (57–114 s). Отдельно от E1, потому что чинится одним кэшем и ускоряет также
  многодокументные прогоны и будущий веб-слой (конфиг перечитывался бы на каждый запрос).
- **Где:** `regex_detector._load_regex_types` (+ компиляция паттернов заново),
  `ner_detector._load_ner_config`, `tokenizer._load_token_prefixes`.
- **Как чинить:** см. E1 шаг 1 — один общий кэш по `(abspath, mtime)`.
- **Чем это НЕ является:** не предложение изменить формат/расположение конфига.

**Не является неэффективностью (проверено замером):** компонент 2 — `.xlsx` на 10 000
ячеек переписывается за **0.26 s** (бюджет спеки < 3 s, запас 10×), пиковая
python-память ~6 МБ; `decrypt`/`delete` не тянут natasha (холодный старт 0.3 s);
детокенизация линейна (пины в BREAKING_REPORT: 100k токенов — 0.04 s).

# 5. Что я проверил и проблем НЕ нашёл

- **Все заявленные правки трёх раундов** (FINDINGS #1–7, #9, #10; B1, B2, B3, B5, B6) —
  реально в коде, тесты на них зелёные (раздел 1.2).
- **Изоляция реального хранилища в тестах:** CLI-тесты подменяют `USERPROFILE`/`HOME`,
  юнит-тесты используют `storage_dir=tmp_path`. `~/.shifrator/` аудитом не читался и не
  писался; все проверки — во временных директориях.
- **Атомарность `key.bin`** — код соответствует спеке (os.link + fallback O_EXCL), тесты
  гонки зелёные.
- **`_resolve_overlaps` на реальных данных не взрывается:** строка-перечень из 400
  девятизначных чисел через пробел → detect_regex 0.07 s, resolve 0.03 s (пересечений
  почти нет — finditer ест окна последовательно). Кубический худший случай существует
  теоретически, но реального входа, который его вызывает, я не нашёл.
- **Инвариант-проверка `detect_ner` (скан E×S)** — 0.5 s на 4800×6000, не узкое место.
- **ReDoS:** паттерн SUM после B1 полиномиален (пины в tests/test_breaking_redos.py);
  `_TOKEN_RE` детокенизатора устойчив (пин в BREAKING_REPORT).
- **Согласованность `TOKEN_RE`:** `ooxml_core.TOKEN_RE` посимвольно равен
  `detokenizer._TOKEN_RE` (требование спеки о дублировании соблюдено).
- **Компонент 2:** неизменённые части архива переносятся байт-в-байт, `count`/
  `uniqueCount` не трогаются, тип ячейки сохраняется, zip-бомба отсекается по оглавлению
  (тесты групп A–F зелёные); производительность и память — в бюджете (раздел 4).
- **Ленивая загрузка:** `decrypt`/`delete`/`decrypt-file` не импортируют natasha
  (проверено сабпроцессом и таймингом).
- **Кодировки CLI:** `sys.std*.reconfigure(utf-8)` на месте; smoke на кириллице прошёл.
- **Пограничный случай B3 «сущность через 3+ сегмента»** — окна строятся только по парам
  соседних сегментов; сущность, размазанная на три сегмента, реконструируется частично.
  Считаю это known limitation (крайне нишевый вход), НЕ находкой: зафиксировано здесь,
  чтобы будущая модель не открывала заново.

Границы проверенного: PDF-путь не существует (не проверялся); веб-слоя нет; ручная
проверка открытия перезаписанных файлов в реальном MS Office в этом окружении невозможна
(нет Office) — опора на тесты структуры XML/ZIP и на приёмку блоков 9–12, где открытие
проверялось вручную.

# 6. Порядок работы для будущих чатов

1. **Первым — решение по P1** (порча данных при восстановлении граничных пар). Это
   единственная активная тихая порча в системе. Требует выбора семантики пользователем
   (вариант А или Б в P1); после выбора — правка `tokenize()` + round-trip тест.
   Пока P1 не решён, пользователям стоит знать: если в анонимизированном тексте один и
   тот же токен стоит дважды ПОДРЯД (через перенос строки/`|`) — восстановление этого
   места будет неверным.
2. **Вторым — E1+E3 (кэш конфига + фильтр окон):** дёшево (одно-два места), даёт
   кратное ускорение encrypt, ничего не меняет в семантике. Можно делать параллельно с
   п.1 — файлы пересекаются только в `tokenizer.py` (E1-фильтр и P1-правка оба в
   `tokenize`/`_detect_boundary_entities`; если параллельно — сначала п.1).
3. **Третьим — решение по E2** (AddrExtractor): нужен выбор пользователя
   (пре-фильтр с задокументированным риском vs принять стоимость).
4. **Дефект компонента 2** (ZIP без целевых частей → тихая копия): предписание уже
   готово в `docs/reports/COMPONENT2_TEST_REPORT.md`; после починки красный тест
   `test_e_malformed_input.py::test_valid_zip_without_any_target_part_raises_ooxml_error`
   позеленеет сам — НЕ редактировать его.
5. P2–P4 — мелкие, в любой момент, по одному коммиту.
6. Компонент 1 (веб-слой): писать спеку с учётом раздела 4 — encrypt на больших
   документах занимает минуты (до фиксов E1–E3), веб-слой обязан быть асинхронным;
   `ner_detector` импортировать лениво по маршруту encrypt; блоки 8–12 использовать
   как есть.
7. **Не трогать ни при каких обстоятельствах:** `~/.shifrator/` (путь, `key.bin`,
   форматы имён), способ запуска `python shifrator.py …`, плоские импорты `src/`,
   существующие тесты (регресс чинится в коде), разделитель `""`/`"\n"` граничных окон
   без пересмотра B3-семантики целиком.
