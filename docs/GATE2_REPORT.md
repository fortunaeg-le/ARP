# Этап GATE-2 — гейт видит то, чего не видел (2026-07-29)

**ПУНКТ 1, ПЕРВОЙ СТРОКОЙ: линия «порча документа» внедрена и ЗЕЛЁНАЯ.** На
полном корпусе масок, не легших ни на эталонную сущность, ни на объявленный
негатив, — **330** (ORG 322, ADDRESS 7, PER 1, остальные 12 типов — 0). Линия
сравнивает это число с точкой отсчёта по каждому типу и по агрегату, допуск 0,
и она **блокирующая**: при внедрении красной не оказалась, подгонять допуск не
пришлось. Решение владельца требуется не по «превращать ли в блокирующую», а по
одному связанному вопросу — он назван в §1 ниже (класс «банки-контрагенты»,
322 из 330 масок).

Корпус гонялся **один раз**, последним действием, как предписано.

## 1. Порча документа не видна → линия «д»

**Что было.** Маска, не пересёкшая ни эталонную сущность, ни объявленный
негатив, попадала в диагностический счётчик `nothing` (этап D). Гейт его
**печатал, но ни с чем не сравнивал** ([gate.py:434-437](../tests/corpus/gate.py)
до этапа). Замаскировать номера пунктов договора, куски прозы, обрывки таблиц
можно было в любом объёме — прогон оставался зелёным.

**Что сделано.** [`gate.compare_overmask`](../tests/corpus/gate.py) — сравнение
по каждому типу и по агрегату, допуск
[`OVERMASK_NOTHING_TOLERANCE = 0`](../tests/corpus/gate_config.py). Своя
печатная секция «(д) OVER-MASK ПРОЗЫ» вместо строки-приписки к precision.

**Число: 330** (ORG 322, ADDRESS 7, PER 1). Линия зелёная (330 → 330).

**Что владелец должен знать про этот набор.** Он неоднозначен, и это разобрано
не мной, а этапом S3: из 330 масок **322 — банки-контрагенты в ORG**, которых
корпус не размечает ни сущностью, ни негативом. То есть линия охраняет и
законный класс тоже. Последствие: этап, который НАМЕРЕННО начнёт маскировать
неразмеченное (например банки как ORG), эту линию уронит и обязан будет
двигать точку отсчёта осознанно — ровно так, как двигают `known_leaks`.

Альтернатива, **замеренная этапом S3 и оставленная предложением**, — считать не
весь набор, а подмножество «маска, которую не обосновывает даже правило её
собственного типа»: 2660 → 3 → 94 → **7** на четырёх дампах
(`experiments/stage_s3/overmask_shape.py`). Она требует, чтобы харнесс замера
импортировал `src/` (сегодня `measure_lib` от `src/` не зависит вообще) — это
отдельное решение владельца, поэтому линия построена на **полном** наборе: он
строго шире, ловит и то, что ловило бы подмножество, и новой зависимости не
требует. Цена — названная выше ложная краснота на намеренном расширении
маскирования.

**Красное состояние показано.** На реальном дампе подложены 5 масок «п. 3.2»:

```
(д) over-mask прозы[ORG]: 322 -> 327 (+5 масок) — система закрыла маской текст,
    который не является ни эталонной сущностью, ни объявленным негативом (порча документа)
(д) over-mask прозы[ВСЕГО]: 330 -> 335 (+5 масок)
```

Плюс три само-теста: рост по типу, рост одного типа при падении другого (не
должен гаситься), падение = улучшение и гейт не роняет.

## 2. Направление ошибки границ не видно → линия «е»

**Что было.** Ни одна штатная метрика не отвечает, маска **короче** эталона или
**длиннее**: masking B видит только недобор (маска шире эталона по B —
**не нарушение вообще**, [measure_lib.mc_check_bc](../tests/corpus/measure_lib.py)),
`exact` — булево без направления, `left_trim`/`right_trim` молчат о случае «слева
внутрь, справа наружу». Перебор мог расти неограниченно при зелёном гейте.

**Что сделано.** Логика прибора ADDR-B перенесена из
`experiments/stage_addr_b/addr_probe.py` в
[`measure_lib.boundary_by_gold` / `boundaries_by_type`](../tests/corpus/measure_lib.py)
и считается **для всех 15 типов**; прогон кладёт результат в поле `bnd` каждой
эталонной записи. **Прибор теперь зовёт эти же функции** — две реализации одной
метрики разъехались бы, и постоянная линия перестала бы совпадать с прибором,
которым этап ADDR-B мерил.

Два числа раздельно, по каждому типу, каждое — и в сущностях, и в символах;
допуски [`BOUNDARY_UNDER_TOLERANCE`](../tests/corpus/gate_config.py) и
`BOUNDARY_OVER_TOLERANCE`, оба 0.

**Числа (точка отсчёта — тот самый единственный прогон):**

| | недобор (утечка) | перебор (порча) |
|---|---:|---:|
| **всего** | **660 сущн. / 4557 симв.** | **330 сущн. / 2709 симв.** |
| PER | 288 / 2075 | 19 / 177 |
| ADDRESS | 142 / 1546 | 30 / 281 |
| PASSPORT | 15 / 15 | **281 / 2251** |
| EMAIL | 60 / 323 | 0 |
| PHONE | 39 / 284 | 0 |
| INN_PER | 35 / 35 | 0 |
| ORG | 28 / 113 | 0 |
| SUM | 16 / 125 | 0 |
| INN | 11 / 11 | 0 |
| BIRTHDATE / OGRN / KPP / ACCOUNT / BIK / SNILS | 9 / 6 / 5 / 4 / 2 / 0 | 0 |

Сущностей с измеренной границей 12033; маска своего типа приписана 9906; ровно
по эталону 8929.

**Сходимость с прибором ADDR-B — проверка провенанса.** Отчёт ADDR-B по адресам:
«КОРОЧЕ 142», «ДЛИННЕЕ 30 (2.3%)», «лишних символов 281»
([ADDR_B_REPORT.md](ADDR_B_REPORT.md) §Приёмка). Постоянная линия даёт по
ADDRESS **142 / 30 / 281** — те же числа, то есть перенос логики ничего не
исказил.

**Что сразу видно нового:** крупнейший перебор не у адресов, а у **PASSPORT —
281 сущность и 2251 лишний символ** (известный over-capture, до этого этапа не
охранявшийся ничем).

**Что в линию НЕ входит и почему.** Сущности без маски своего типа (2127 штук,
27564 открытых символа) считаются отдельно и печатаются как контекст: у них
открыт весь эталон, и если записать это в недобор, линия начнёт двигаться от
любого изменения recall — то есть будет мерить не то, что обещает. Непойманное
значение охраняют линия «б» (leak_v2) и известный долг.

**Красное состояние показано** (на реальном дампе):

```
(е) границы[PASSPORT / недобор, сущностей]: 0 -> 3 (+3) — часть эталона осталась ОТКРЫТЫМ текстом (утечка)
(е) границы[ADDRESS  / перебор, сущностей]: 0 -> 2 (+2) — маска закрыла лишний текст (порча читаемости)
(е) границы[ADDRESS  / перебор, символов]:  0 -> 110 (+110) — …
```

Само-тесты: недобор; перебор (с проверкой, что линия «г» его **не видит** —
иначе тест не доказывал бы нужду в новой линии); **размен** «недобор упал,
перебор вырос» (одно общее число такой размен принимает молча); ненайденная
сущность в недобор не попадает; дамп без поля даёт регресс с причиной.

## 3. Реквизиты не охранялись по точности → линия «а» расширена

**Что было.** `NER_SPINE_TYPES = ("ORG", "PER", "ADDRESS")` — линия «а» держала
три типа. Оба ИНН, ОГРН, КПП, счета, БИК, телефон, e-mail, паспорт, СНИЛС, дата
рождения, суммы — **вне охраны по точности**: precision любого из них мог упасть
до нуля, и гейт остался бы зелёным. Общий счёт FP (условие 3) — агрегатный, в
нём падение одного типа тонет.

**Что сделано.** `compare_precision` идёт по всем `ALL_ENTITY_TYPES`; тип с
`precision is None` (нет масок-решений) пропускается, как и раньше — «нет
данных» не приравнивается ни к 100%, ни к регрессу. Допуск тот же
(`PRECISION_TOLERANCE_PP = 0.0`), отдельной константы намеренно нет.

**Красным при расширении не стал ни один тип.** Значения на точке отсчёта:
PER 99.96, ORG 100.00, ADDRESS 99.92, INN 99.29, INN_PER 100.00, OGRN 98.69,
KPP 97.00, ACCOUNT 100.00, BIK 100.00, PHONE 100.00, EMAIL 100.00,
PASSPORT 100.00, SNILS 100.00, BIRTHDATE 100.00, SUM 100.00. Ослаблять ничего не
потребовалось.

**Красное состояние показано:** 8 масок SUM на объявленном негативе →
`(а) precision[SUM]: 100.00% -> 98.76%`. Само-тест — на INN.

**Одно ожидание теста перевёрнуто намеренно.** `test_gate_regression_detection.
py::test_t2_mask_of_the_person_inn_on_a_negative_counts_as_fp` (этап T2-INN)
утверждал: «линия «а» держит только NER-хребет, реквизиты в неё не входят» — то
есть **закреплял слепое место как норму**. Теперь он требует обратного:
INN_PER обязан краснеть и по precision. Это не ослабление теста, а разворот
устаревшего ожидания; сам тест стал строже.

## 4. Порог ложных срабатываний — ФАКТ

**В живом гейте порог НЕ зашит.** [gate.py:195-201](../tests/corpus/gate.py):

```python
fp_b = baseline_agg["fp_on_neg_total"]   # ← из results_baseline.json
fp_c = current_agg["fp_on_neg_total"]
if fp_c - fp_b > fp_tolerance:           # fp_tolerance = gate_config.FP_TOLERANCE = 0
```

То есть сравнивается **дельта к точке отсчёта**, а единственная константа —
допуск 0. Текущее значение 16 → 16, и добавление одного ложного срабатывания
роняет гейт (проверено само-тестом и живой демонстрацией: 16 → 24 → красный).
Переставлять нечего.

**Откуда взялось «около 650» и где оно живёт.** Это порог **отставного** гейта
этапа D: `experiments/stage_d/baseline_d.json:8` (`"fp_neg_total": 650`) и
`:242` (`"fp_neg": 5` — допуск +5), читается
`experiments/stage_d/gate_d.py`, у которого в шапке стоит «УСТАРЕЛ (этап S2),
запускать надо tests/corpus/gate.py». Плюс те же числа в
`tests/test_gate_d.py:25-34` — это само-тест отставного гейта на **синтетических**
состояниях, корпусных данных он не читает.

**Ловушка, которую надо назвать.** Файл `gate_d.py` работоспособен, и его
запуск сегодня напечатает «зелёно» против точки отсчёта, где FP = 650, тогда как
фактически их 16: **выросли бы FP с 16 до 650 — отставной гейт этого не
заметил бы**. Живой путь к коммиту он не охраняет и не должен, но как артефакт
он выглядит рабочей охраной. Кода я не менял (числа `baseline_d.json` — провенанс
цифр этапа D, на них ссылается HANDOFF_STAGE_D_PRECISION). **Решение —
владельца:** удалить `gate_d.py` вместе с его baseline или оставить как
провенанс, добавив в него отказ запускаться.

## 5. Генератор и эталон разошлись → тест-охрана

**Факт расхождения подтверждён:** `tests/corpus/generate.py:595` и `:721`
по-прежнему размечают суммы как негатив `"сумма — не ПДн"`, а эталон с этапа
T-GOLD-A содержит **648 сущностей типа SUM и ноль негативов «сумма»**. Запуск
генератора молча вернул бы эталон назад.

**Что сделано.** [tests/test_gold_type_contract.py](../tests/test_gold_type_contract.py)
— три теста:

1. **ни одной суммы среди негативов**; в тексте падения сказано, что произошло
   (запущен генератор), чем это ломает метрику (каждое правильное срабатывание
   на сумме становится «ложным», FP с 16 до ~650) и что делать
   (`reclassify_sum.py`, он идемпотентен, затем `validate.py` и пересборка
   точки отсчёта);
2. **тип SUM на месте и в полном составе** (648) — первый тест молчал бы и на
   пустом эталоне: нет негативов — нет нарушения;
3. **тест-обоснование**: генератор всё ещё размечает суммы негативом. Если его
   однажды исправят в источнике, этот тест покраснеет и скажет, что охрану выше
   можно упрощать.

**Красное состояние показано:** во временной копии дерева 648 сумм возвращены в
негативы (сам `gold.json` не тронут) — два теста краснеют, текст падения:

> ЭТАЛОН ОТКАТИЛСЯ: в gold.json снова есть негативы «сумма — не ПДн» — 648 штук
> (например [('agency_0001', '893 033,00 руб.'), …]). Так размечает суммы
> ГЕНЕРАТОР tests/corpus/generate.py … FP по негативам вырастает с 16 до ~650.
> Что делать: … reclassify_sum.py …

## Приёмка

**1. Каждая новая линия показана в красном состоянии.** Живые демонстрации на
настоящем дампе корпуса (§1, §2, §3) + красная демонстрация линии 5 на копии
дерева (§5) + **12 новых само-тестов** в
`tests/corpus/test_gate_regression_detection.py` и
`tests/test_gold_type_contract.py`. Каждая красная строка называет причину
человеческим текстом, а не номером условия.

**2. Существующие линии не изменились.** Единственный полный прогон против
ПРЕЖНЕЙ точки отсчёта: все 15 типов `recall/leak_v2>=6/leak_v2>=8` — `X -> X`,
FP по негативам 16 → 16 (и по каждому типу), masking A 100.00 / B 91.59 /
C 95.20 — без движения, precision по каждому типу — без движения, известный долг
44 → 44, крешей 0. Допуски существующих линий не тронуты ни один
(`git diff` по `gate_config.py` — только добавления).

**3. Контрольные суммы: 658 до и после.** `MANIFEST.sha256` — 658 файлов, OK до
прогона и OK после (лог прогона, строки 3 и 40). После пересборки точки отсчёта
манифест перегенерирован (`update_manifest.py`, 658 файлов), и повторная оценка
показала OK. Заодно исправлено устаревшее утверждение в `BASELINES.md`, будто
точки отсчёта в манифест не входят: с этапа ADDR-B входят обе, поэтому их
пересборка ТРЕБУЕТ обновления манифеста.

**4. Полный набор тестов.** `1229 passed, 3 skipped, 3 deselected, 10 xfailed`
(676 с) — +12 тестов этапа, ни одного падения. Прогнан ДВАЖДЫ: до пересборки
точки отсчёта и на финальном состоянии (`1229 passed … 637 с`,
`experiments/stage_gate2/pytest_final.log`) — второй прогон корпус не гоняет
(полнокорпусный тест deselected меткой `slow`), так что правило прогонов не
нарушено.

**5. Полный гейт — один прогон, последним действием.** Да, один
(`experiments/stage_gate2/gate_full.log`).

## Сколько раз гонялся полный корпус

**Один раз.** Всё остальное — либо быстрый набор (33 документа `subset_iter.json`:
одна отладочная проверка нового поля + обязательная пересборка срезовой точки
отсчёта), либо оценка **уже снятого** дампа без прогона корпуса
(`gate.py --results`, живые красные демонстрации).

Порядок был такой:
1. правки и отладка — только быстрый набор;
2. полный набор тестов;
3. **единственный полный прогон корпуса** (`gate.py`): существующие линии
   подтверждены байт-в-байт, красной оказалась ровно одна строка — «в BASELINE
   нет поля `bnd`», то есть условие внедрения линии «е»;
4. точка отсчёта пересобрана из ЭТОГО прогона (старый дамп сохранён в
   `experiments/stage_gate2/results_baseline_before_gate2.json`), сверена со
   старой поимённо — совпала по всем существующим метрикам;
5. срезовая точка отсчёта (33 док.) и `MANIFEST` пересобраны следом;
6. **тот же дамп** переоценён против новой точки отсчёта без прогона корпуса —
   **гейт ЗЕЛЁНЫЙ по всем шести линиям**
   (`experiments/stage_gate2/gate_after_rebase.log`).

Второго полного прогона не потребовалось: пункт 6 — не прогон, а оценка готового
дампа, ровно тот режим, для которого у гейта есть флаг `--results`.

## Чего этап не делал

Корпус, эталон и детекторы не тронуты (`src/` — ноль правок). Списков
запрещённых слов не заводилось. Ни один существующий допуск не ослаблен, ни один
тест не ослаблен: единственное изменённое ожидание (§3) стало строже.
