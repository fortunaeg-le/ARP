## РАЗДЕЛ 1. ЧТО ДЕЛАЕТ ПРОГРАММА

### Назначение
SHIFRATOR — инструмент для защиты персональных данных (ПДн) при работе с большими языковыми моделями (LLM). Основной случай использования: юрист хочет отправить текст договора в ChatGPT для анализа, но в контракте есть реквизиты, персональные данные, адреса организаций. SHIFRATOR находит эти данные локально, на компьютере пользователя, заменяет их условными токенами (`[INN_1]`, `[PERSON_42]` и т.п.), и пользователь отправляет уже обезличенный текст. Позже, когда приходит ответ от LLM, SHIFRATOR восстанавливает исходные значения на месте токенов.

### Пользователь
Юрист, аналитик или специалист по проверке документов, который работает с конфиденциальной информацией и не хочет, чтобы исходные данные попадали в облачный сервис LLM.

### Жизненный цикл документа
1. **Загрузка.** Пользователь загружает файл договора (`.txt` или `.docx`).
2. **Сканирование.** SHIFRATOR извлекает текст из абзацев и таблиц верхнего уровня тела документа. Колонтитулы, сноски, примечания, надписи и вложенные таблицы не читаются — они объявляются непрочитанными зонами. Часть узлов не читается и зоной не объявляется (см. раздел 5).
3. **Обнаружение ПДн.** Система находит в тексте 13 типов данных: ФИО, организации, адреса, ИНН, ОГРН, КПП, номера счетов, БИК, паспортные номера, телефоны, email, СНИЛС, даты рождения.
4. **Анонимизация.** Каждое найденное значение заменяется токеном, исходное значение сохраняется в зашифрованном виде локально.
5. **Проверка пользователем.** Юрист видит рядом исходный и обезличенный текст с подсветкой замен, может проверить, что система ничего не пропустила.
6. **Отправка.** Пользователь отправляет обезличенный текст в LLM, получает ответ.
7. **Восстановление.** Пользователь вставляет ответ LLM (с токенами) обратно в SHIFRATOR, система восстанавливает исходные значения.

### Форматы

**Вход:** только `.txt` (UTF-8) и `.docx`. Любое другое расширение отвергается
(`extractor.extract` → `ValueError`; в интерфейсе список разрешённых расширений
— `.docx`, `.txt`). Обезличить `.xlsx` или `.pptx` система не может.

**Восстановление:**

| Путь восстановления | Форматы | Где доступно |
|---|---|---|
| Восстановление файлом (`decrypt-file`) | `.docx`, `.xlsx`, `.pptx` | только командная строка; в интерфейсе такой возможности нет |
| Восстановление текстом | текст выводится на экран (CLI) или возвращается в интерфейс | CLI и интерфейс |

* `.txt` файлом не восстанавливается: при попытке — `ValueError`; текст выводится на экран.
* `.xlsx` и `.pptx` не могут быть входом цикла. При восстановлении файлом программа
  перезаписывает токены в файле, который пользователь принёс сам; такой файл на этапе
  шифрации система не порождает.
* При шифрации на диск пишется `{session_id}.txt` — обезличенный текст.

### Сетевое взаимодействие

Сетевых обращений наружу нет ни при первом, ни при последующих запусках.

* В `src/` и `shifrator.py` сетевых вызовов нет вообще (совпадения на `http://` —
  строки XML-namespace OOXML, не адреса загрузки).
* Локальный сервер интерфейса слушает только `127.0.0.1`; лаунчер обращается к
  собственному серверу по петле (`http://127.0.0.1:<порт>/api/ping`).
* Веса моделей поставляются внутри пакета `natasha==1.6.0` — файлы
  `emb/navec_news_v1_1B_250K_300d_100q.tar` (26,6 МБ),
  `model/slovnet_ner_news_v1.tar`, `model/slovnet_morph_news_v1.tar`,
  `model/slovnet_syntax_news_v1.tar` лежат в каталоге `natasha/data` установленного
  пакета, и загрузчики берут эти пути по умолчанию. Ничего не скачивается.
  `pymorphy2` берёт словарь из пакета `pymorphy2-dicts-ru`.
* Установка самих Python-пакетов требует источника дистрибутивов (сеть либо
  локальное зеркало/wheelhouse). Это установка, а не работа программы.

### Хранение данных на диске пользователя

Программа создаёт директорию `~/.shifrator/` (Windows: `C:\Users\<имя>\.shifrator\`) со следующей структурой:

- **`sessions/key.bin`** — общий ключ шифрования для всех сессий. Создаётся один раз при первом запуске, ротации в коде нет; перечитывается с диска при каждой операции. Права на файл выставляются только на POSIX; **на Windows права не выставляются**.
- **`sessions/{session_id}.enc`** — зашифрованный файл токен-маппинга (исходные значения с их токенами).
- **`sessions/{session_id}.txt`** — обезличенный текст в виде обычного файла.
- **`sessions/{session_id}.unread.json`** — только если документ содержит непрочитанные зоны и пользователь явно согласился на режим `--allow-lossy`. Содержит открытый текст из непрочитанных зон.
- **`sessions/{session_id}.doc.json`** — открытый JSON. Содержит **полный исходный текст документа открытым текстом** в поле `segments[].text`, плюс вторую, нормализованную копию части сегментов в `metadata._addr_view_cache`. **Токенов и ссылок на сущности в файле нет.** Поля файла: `source_format` и `segments[]` с `id`, `text`, `source_type`, `metadata`.
- **`markup/`** — если пользователь исправляет результаты обезличивания в интерфейсе (отмечает пропущенные данные или неверные границы), исправления сохраняются здесь, отдельно от сессий. Поле `value` записи — фрагмент реального текста открытым текстом.

**Удаление.** Таймера, планировщика или фонового потока в коде нет. Очистка
просроченных сессий (`purge_expired`) вызывается ровно из одного места продукта —
начало CLI-команды `decrypt`. Интерфейс не удаляет просроченные сессии никогда:
при работе только через интерфейс файлы лежат бессрочно. При обращении к истёкшей
сессии выдаётся ошибка, файл при этом не удаляется. Явное удаление сессии
(`delete <session_id>`) снимает `.enc`, `.txt`, `.meta.json`, `.doc.json`
обычным `unlink` — содержимое не затирается. Файл `{sid}.unread.json` не
удаляется ни одним путём, включая явное удаление сессии. `key.bin` не трогается
никогда — ни при удалении сессии, ни при очистке.

### Где на диске лежат ПДн

- **`{session_id}.enc`** — зашифрован Fernet.
- **`{session_id}.doc.json`** — открытый текст всего документа (см. выше).
- **`{session_id}.unread.json`** — открытый текст непрочитанных зон, если пользователь разрешил режим lossy.
- **`markup/`** — фрагменты реального текста открытым текстом.
- **Веса моделей natasha** — внутри установленного пакета, персональных данных не содержат.

## РАЗДЕЛ 3. ЧТО В ПРОГРАММЕ СВОЁ

### 1. Структурный двухпроходный детектор ORG и PER (этапы A и B)

**Идея:** Вместо полагания на NER-тэггер (natasha NER часто классифицирует организации неправильно в жанре договоров), используется структурное правило:
- **Проход 1:** найти якорь (ключевые слова: «ООО», «АО», кавычки, введение «Общество…»; для людей: должность, предлоги «в лице», фамилия по pymorphy).
- **Проход 2:** расширить от якоря, проверить лемму ядра, построить реестр для разрешения конфликтов.

**Отличие от очевидного:** Нейросетевой NER обучается на примерах и ошибается на редких формах (склонение имён компаний, безъякорные люди). Структурный подход находит сущность, если выполнены формальные условия (есть якорь + соответствует шаблону).

**Измерено на корпусе (прогон 2026-07-25/28):** полнота организаций 97.19 % (462 эталонных), полнота людей 74.06 % (3420 эталонных).

### 2. Разрешение пересечений через обрезку, не выброс

**Идея:** Если две найденные сущности пересекаются (например, адресный детектор нашёл телефон внутри адреса, или regex-ИНН находится внутри адреса), не выбросить одну целиком, а обрезать до непересекающейся части.

**Отличие:** Простой подход — выбросить адрес, оставить ИНН. Но если в адресе была часть персональных данных ВНЕ зоны пересечения, она остаётся в открытом виде. Обрезка сохраняет эту часть под своим токеном.

### 3. Якорная модель ADDRESS (этап C)

**Идея:** Адреса в договорах встречаются разными формами: с маркерами («по адресу:»), без маркеров («ул. Ленина, д. 5»), в таблицах. NER-тэггер natasha ловит также неспециализированный текст (названия статей, ГОСТы, даты). Вместо этого: строгие правила для якоря (топоним + номер, или помещение + номер), обрезка по предложениям, барьеры от других сущностей (ИНН/реквизиты/люди).

**Результат:** ложных адресов на объявленных негативах — с 634 до 1; полнота на адверсариальных мутациях при этом снизилась.

### 4. Восстановление из токенов (этап E)

**Идея:** В договорах имена склоняются, организации встречаются в разных формах, поэтому подстановка первого найденного вхождения даёт неверный текст. Делается:
- Сохраняется каноническая форма каждого значения (для людей — именительный падеж, для реквизитов — стандартный формат).
- При восстановлении подставляется каноническая форма, а не первое сохранённое вхождение.
- Сохраняются все найденные формы каждого значения.

### 5. Сборка данных, разорванных форматированием (multispan)

**Идея:** Одно значение в `.docx` часто разложено на несколько кусков разметки: адрес разорван переносами строк и ячейками, номер договора разбит форматированием отдельных символов. Сущность хранит не один диапазон, а набор диапазонов, и собирается из кусков через нормализованное представление с картой смещений обратно в исходный текст.

**Отличие от очевидного:** прямолинейный детектор работает по видимому тексту одного фрагмента и такое значение либо не находит, либо находит его половину — и вторая половина остаётся в документе открытой. Здесь значение собирается целиком, а маскируется по всем своим кускам, не задевая текст между ними.

### 6. Обеспечение одинакового результата на одном документе (детерминизм)

**Идея:** Результат обезличивания одного и того же файла не должен меняться от запуска к запуску. Порядок обработки, разрешение пересечений и нумерация токенов сделаны не зависящими от порядка поступления кандидатов; проверка детерминизма входит в прогон корпуса.

**Отличие от очевидного:** при обычной сборке из нескольких детекторов результат зависит от порядка их срабатывания и от внутреннего состояния NER-модели, и один файл даёт разные наборы токенов. Подтверждено пятью прогонами на реальном документе владельца: расхождений в результате нет.

### 7. Обнаружение непрочитанных зон в .docx

**Идея:** Перед обработкой сканировать структуру документа и обнаружить части, которые система не читает (колонтитулы, сноски, примечания, надписи, вложенные таблицы). Если найдены — отказаться с сообщением (fail-closed) или предупредить (режим lossy).

**Отличие:** системы, которые молча пропускают эти части, не сообщают пользователю, что часть текста не обработана. SHIFRATOR это показывает. Полный перечень того, что читается и что объявляется зоной — в разделе 5.

## РАЗДЕЛ 4. ДАННЫЕ, НА КОТОРЫХ ПРОВЕРЯЕТСЯ ПРОГРАММА

### Корпус тестирования

Основной набор — `tests/corpus/`, содержит:
- **324 документа:** 162 файла `.txt` + 162 файла `.docx` (одинаковое содержимое в обоих форматах для каждого номера); 108 базовых и 216 мутированных (`combo`, `homoglyph`, `invisible`, `case`, `digit_spaces`, `linebreak`, `cell_split`).
- **10 932 эталонные сущности** по 13 типам. Категории: adversarial 6451, canonical 3013, ugly 1921.
- **Происхождение:** полностью синтетические. ФИО, названия организаций, адреса, номера реквизитов сгенерированы программно, совпадение с реальными людьми/организациями случайно.
- **Разметка (gold):** порождается тем же генератором, что и сами документы, — текст документа и разметка получаются из одного вызова над одной моделью, смещения каждой сущности пишутся в момент сборки текста. Категория сущности (canonical/ugly/adversarial) берётся из модели. Ручного шага аннотации в этом пути нет.
- **Контрольные суммы:** ИНН, ОГРН, расчётные счета содержат валидные контрольные суммы, вычисленные по настоящим алгоритмам. Где невалидность внесена умышленно, это отмечено в разметке.

### Вторичный корпус (Corpus V2)

`tests/corpus_v2/` — меньший набор (138 документов), используется для проверки специальных типов сущностей и вариативности форм.

### Синтетичность

Синтетический корпус даёт точно известный состав данных (что есть и что пропущено).
Синтетические договоры при этом не воспроизводят весь спектр реальной вариативности:
опечатки, нестандартные сокращения и форматы из боевых документов.

| **Ложные срабатывания на негативах** | 650 | На текстах, объявленных в корпусе не-ПДн, система выдала 650 замен. Пользователь видит лишние токены; данные при этом не раскрываются. |
| **Круговое восстановление (masking A)** | 100.00 % | Обезличивание + восстановление даёт исходный текст. |
| **Границы масок (masking B)** | 86.31 % | Границы маскируемых спанов совпадают с эталоном в 86 % случаев. Остальные ~14 % — маска короче или длиннее эталона (например, захвачено следующее слово). |
| **Тип маски (masking C)** | 95.07 % | В 95 % случаев подставлен токен правильного типа. |

Разрезы по типам: полнота организаций 97.19 %, полнота людей 74.06 %.

### Что означают эти числа при работе с договором
- **Полнота 81 %:** если в договоре 100 ПДн, около 19 не будут найдены. Пользователю нужно просмотреть текст и отметить пропущенное вручную.
- **Утечка 20 %:** часть значения может остаться видимой; это видно при проверке.
- **650 ложных срабатываний:** лишние токены видны в интерфейсе, пользователь может их снять.
- **Круговое восстановление 100 %:** восстановленный текст совпадает с исходным.

### Чтение .docx и непрочитанные зоны

Файл читает **python-docx** (плюс прямое чтение XML через lxml для наследования
регистра). Обход — только дочерние узлы тела документа: берутся `w:p` (абзацы) и
`w:tbl` (таблицы) верхнего уровня. **Natasha в чтении файла не участвует вообще** —
она работает по уже извлечённому тексту.

| Элемент .docx | Читается | Объявляется непрочитанной зоной |
|---|---|---|
| обычный абзац `w:p` | да | — |
| таблица верхнего уровня `w:tbl` | да | — |
| результат поля (`w:fldChar`/`w:t`) | да | — |
| колонтитул верхний (`word/header*.xml`) | нет | да (`header`) |
| колонтитул нижний (`word/footer*.xml`) | нет | да (`footer`) |
| сноска / концевая сноска | нет | да (`footnote` / `endnote`) |
| примечание `w:comment` | нет | да (`comment`) |
| надпись `w:txbxContent` | нет | да (`textbox`) |
| вложенная таблица `w:tbl` внутри `w:tc` | нет | да (`nested_table`) |
| **отслеживаемая вставка `w:ins`** | **нет** | **нет** |
| **простое поле `w:fldSimple`** | **нет** | **нет** |
| **умный тег `w:smartTag`** | **нет** | **нет** |
| **элемент формы `w:sdt` (блочный)** | **нет** | **нет** |
| **элемент формы `w:sdt` (внутристрочный)** | **нет** | **нет** |
| удалённый текст `w:delText` | нет | нет (решение задокументировано: невидимое содержимое) |
| код поля `w:instrText` | нет | нет (там же) |

Пять видов узлов — `w:ins`, `w:fldSimple`, `w:smartTag`, `w:sdt` блочный и
внутристрочный — не читаются И не объявляются зоной: их текст не обезличивается и
предупреждения о них пользователь не получает. В реальном договоре владельца
полей более тысячи.

### Прочие известные ограничения

| Что не работает | Причина | Следствие |
|---|---|---|
| **PASSPORT: границы спана** | Паттерн паспорта захватывает служебные слова. | Паспорт находится, границы маски неточны. |
| **ADDRESS: жадный захват номеров** | yargy-тэггер захватывает прозаические номера как индексы. | Больше ложных срабатываний. |
| **Регистровые вариации ФИО** | Natasha опирается на регистр как признак имени собственного. | ФИО в нижнем регистре без других маркеров не находятся. |
| **Документы объёмом >2500 сегментов** | Обнаружен недетерминизм NER на очень больших текстах. | Результат на таком документе может отличаться между прогонами. На корпусе и на реальном документе владельца (пять прогонов) расхождений не воспроизведено. |
| **Невидимые омоглифы** | Кириллица и латиница совпадают по начертанию (А/A, С/C). | После нормализации отдельные случаи могут остаться. |

### Числовые границы
- Полнота выше на базовых формах (категория canonical), ниже на ugly и ещё ниже на adversarial.
- Для ИНН/ОГРН валидность контрольной суммы используется как сигнал, а не как условие отбраковки: значение с опечаткой остаётся ПДн.

## РАЗДЕЛ 7. РАБОТА С ПЕРСОНАЛЬНЫМИ ДАННЫМИ

### Механизмы, реализованные в коде
1. **Локальность:** сетевых обращений наружу нет; сервер интерфейса слушает только `127.0.0.1`.
2. **Шифрование хранилища:** токен-маппинг (`.enc`) шифруется Fernet общим ключом `key.bin`. Один ключ на директорию хранилища, ротации нет.
3. **Срок жизни сессии:** значение TTL хранится в сессии и проверяется при обращении; удаление файлов выполняется только командой `decrypt` в командной строке (см. раздел 1). Через интерфейс просроченные сессии не удаляются никогда.
4. **Отчёты:** отчёты и статистика, которые отдаёт интерфейс, содержат типы и коды, не исходные значения.

### Где ПДн лежат на диске

| Файл | Содержимое | Защита |
|---|---|---|
| `~/.shifrator/sessions/key.bin` | Ключ шифрования | Файл на диске; права выставляются только на POSIX, на Windows — нет |
| `~/.shifrator/sessions/{sid}.enc` | Исходные значения | Зашифрован Fernet |
| `~/.shifrator/sessions/{sid}.txt` | Обезличенный текст | Открытый текст, ПДн не содержит |
| `~/.shifrator/sessions/{sid}.doc.json` | **Полный исходный текст документа** + нормализованная копия части сегментов | **Открытые ПДн** |
| `~/.shifrator/sessions/{sid}.unread.json` | **Текст непрочитанных зон** | **Открытые ПДн** |
| `~/.shifrator/markup/` | Правки пользователя; поле `value` — фрагмент реального текста | Открытый текст |

### Факты, существенные для оценки
1. **`{sid}.doc.json` и `{sid}.unread.json` содержат ПДн открытым текстом.** `.unread.json` создаётся только при согласии на режим `--allow-lossy`; `.doc.json` создаётся всегда.
2. **`{sid}.unread.json` не удаляется ни одним путём**, включая явное удаление сессии.
3. **Удаление сессии — это `unlink` файлов без затирания содержимого.** Ключ `key.bin` при этом не трогается: он общий и не уничтожается никогда.
4. **`key.bin` — единая точка отказа:** если ключ удалён или повреждён, все сессии становятся нерасшифровываемыми. Резервной копии ключа в коде нет.
5. **Автоматической очистки по расписанию нет.** При работе только через интерфейс файлы сессий лежат бессрочно.
6. **Ручная разметка сама не удаляется.** Порог 30 дней объявлен в коде (`_MARKUP_TTL_DAYS = 30`), функция очистки `purge_expired_markup()` существует, но ни один путь продукта её не вызывает. Разметка удаляется только явными действиями пользователя (удаление всей разметки или удаление сессии с флагом удаления разметки).
7. **Механизм замены обратим:** таблица соответствия «токен → исходное значение» сохраняется у пользователя на диске (`{sid}.enc`), восстановление исходного текста выполняется штатной командой.

### Что программа делает и чего не делает
Делает:
- Не передаёт исходные ПДн наружу; из программы наружу ничего не уходит.
- Наружу пользователь отправляет обезличенный текст с токенами.
- Восстановленные данные показываются только локально по явному запросу.

Не делает:
- Не защищает от локального доступа: файлы `~/.shifrator/sessions/` читаются любым, кто имеет доступ к учётной записи.
- Не затирает данные в оперативной памяти.
- Не восстанавливает данные после потери `key.bin`.
- Не обрабатывает колонтитулы, сноски, примечания, надписи, вложенные таблицы и пять видов узлов из раздела 5 — их содержимое не обезличивается.

### Восстановление файла и колонтитулы
При восстановлении файлом программа перезаписывает `.docx`/`.xlsx`/`.pptx`,
принесённый пользователем: ZIP пересобирается из исходных байтов, меняются только
затронутые части (`word/document.xml`, `word/header*.xml`, `word/footer*.xml`,
`word/footnotes.xml`, `word/endnotes.xml`). **Колонтитулы сохраняются из этого
файла, и токены внутри них раскрываются.** Исходный документ при восстановлении
не участвует и программе недоступен: на этапе шифрации `.docx` не сохраняется,
сохраняется только обезличенный `{sid}.txt`.
