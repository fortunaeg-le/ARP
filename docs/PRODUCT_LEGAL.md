## РАЗДЕЛ 1. ЧТО ДЕЛАЕТ ПРОГРАММА

### Назначение
SHIFRATOR — инструмент для защиты персональных данных (ПДн) при работе с большими языковыми моделями (LLM). Основной случай использования: юрист хочет отправить текст договора в ChatGPT для анализа, но в контракте есть реквизиты, персональные данные, адреса организаций. SHIFRATOR находит эти данные локально, на компьютере пользователя, заменяет их условными токенами (`[INN_1]`, `[PERSON_42]` и т.п.), и пользователь отправляет уже обезличенный текст. Позже, когда приходит ответ от LLM, SHIFRATOR восстанавливает исходные значения на месте токенов.

### Пользователь
Юрист, аналитик или специалист по проверке документов, который работает с конфиденциальной информацией и нуждается в гарантии, что исходные данные не попадут в облачный сервис LLM.

### Жизненный цикл документа
1. **Загрузка.** Пользователь загружает файл договора (`.txt` или `.docx`).
2. **Сканирование.** SHIFRATOR читает весь текст документа, извлекает текст из всех абзацев и таблиц, но НЕ читает колонтитулы, сноски, текстовые поля и вложенные таблицы — это ограничение системы.
3. **Обнаружение ПДн.** Система находит в тексте 13 типов данных: ФИО, организации, адреса, ИНН, ОГРН, КПП, номера счетов, БИК, паспортные номера, телефоны, email, СНИЛС, даты рождения.
4. **Анонимизация.** Каждое найденное значение заменяется токеном, исходное значение сохраняется в зашифрованном виде локально.
5. **Проверка пользователем.** Юрист видит рядом исходный и обезличенный текст с подсветкой замен, может проверить, что система ничего не пропустила.
6. **Отправка.** Пользователь отправляет обезличенный текст в LLM, получает ответ.
7. **Восстановление.** Пользователь вставляет ответ LLM (с токенами) обратно в SHIFRATOR, система восстанавливает исходные значения.

### Форматы
- **Входные:** `.txt` (текстовый файл UTF-8), `.docx` (Microsoft Word).
- **Выходные при восстановлении:** `.txt`, `.docx`, `.xlsx` (таблицы), `.pptx` (презентации) с сохранением исходного форматирования.
- Входной `.docx` читается полностью (абзацы, таблицы, форматирование), но без колонтитулов/сносок/надписей, как описано ниже.

### Сетевое взаимодействие
Нет. Программа работает полностью локально:
- Нет запросов в интернет при обработке документа.
- Никакие данные не отправляются наружу.
- Веб-интерфейс слушает только локальный адрес `127.0.0.1` (если используется).
- Сетевые запросы существуют только для загрузки предобученных моделей NLP при первом запуске (natasha, pymorphy2 скачивают веса с GitHub), но это разовая операция и может быть отключено кэшированием.

### Хранение данных на диске пользователя

Программа создаёт директорию `~/.shifrator/` (Windows: `C:\Users\<имя>\AppData\Roaming\.shifrator\`) со следующей структурой:

- **`sessions/key.bin`** — общий ключ шифрования для всех сессий, размер ~32 байта. Создаётся один раз при первом запуске, после этого не меняется.
- **`sessions/{session_id}.enc`** — зашифрованный файл токен-маппинга (исходные значения с их токенами). Размер зависит от количества ПДн в документе, обычно 1-100 КБ.
- **`sessions/{session_id}.txt`** — обезличенный текст в виде обычного файла, сохраняется для удобства скачивания.
- **`sessions/{session_id}.unread.json`** — только если документ содержит непрочитанные зоны (колонтитулы и т.п.) и пользователь явно согласился на режим `--allow-lossy`. Этот файл содержит открытый текст из непрочитанных зон (ПДн может быть видимым).
- **`sessions/{session_id}.doc.json`** — внутренний формат сессии (структурные данные о найденных сущностях). Содержит токены и ссылки на исходные значения, но сами исходные значения хранятся в `.enc` файле и в памяти. Эта папка не должна быть доступна конечному пользователю без расшифровки.
- **`markup/`** — опционально: если пользователь исправляет результаты обезличивания в интерфейсе (отмечает пропущенные данные или неверно определённые границы), исправления сохраняются отдельно. Сохраняются отдельно от основной сессии и хранятся 30 дней.

**Удаление.** Сессии автоматически удаляются через 24 часа. Пользователь может удалить сессию вручную через CLI командой `delete <session_id>`. После удаления восстановить исходные данные невозможно (ключи уничтожаются).

### Потенциальные источники ПДн на диске

- **`{session_id}.enc`** — зашифрован, безопасен.
- **`{session_id}.unread.json`** — содержит открытый текст, если пользователь разрешил режим lossy (по умолчанию такого файла нет).
- **`{session_id}.doc.json`** — содержит ссылки на исходные значения (их токены и метаданные), но сами значения хранятся в зашифрованном виде в `.enc`.
- **Кеш моделей natasha** — модели хранятся в кешс Python (обычно в `~/.natasha/` или `~/.cache/`), это предтренированные веса без персональных данных.

## РАЗДЕЛ 3. ЧТО В ПРОГРАММЕ СВОЁ

### 1. Структурный двухпроходный детектор ORG и PER (этапы A и B)

**Идея:** Вместо полагания на NER-тэггер (natasha NER часто классифицирует организации неправильно в жанре договоров), используется структурное правило:
- **Проход 1:** найти якорь (ключевые слова: «ООО», «АО», кавычки, введение «Общество…»; для людей: должность, предлоги «в лице», фамилия по pymorphy).
- **Проход 2:** расширить от якоря, проверить лемму ядра, построить реестр для разрешения конфликтов.

**Отличие от очевидного:** Нейросетевой NER обучается на примерах и ошибается на редких формах (склонение имён компаний, безъякорные люди). Структурный подход гарантирует нахождение, если выполнены формальные условия (есть якорь + соответствует шаблону).

**Результат:** ORG обнаруживается на 94%, PER на 72%, значительно лучше, чем чистая Natasha (которая ошибается, например, на ИП в названиях).

### 2. Разрешение пересечений через обрезку, не выброс

**Идея:** Если две найденные сущности пересекаются (например, address детектор нашёл телефон внутри адреса, или regex-INN находится внутри адреса), не выбросить одну целиком, а обрезать до непересекающейся части.

**Отличие:** Простой подход — выбросить адрес, оставить INN. Но если в адресе была часть персональных данных ВНЕ зоны пересечения, она утекает в открытом виде. Обрезка сохраняет эту часть под своим токеном.

**Применение:** Критично для предотвращения утечек при конфликтах детекторов.

### 3. Якорная модель ADDRESS (этап C)

**Идея:** Адреса в договорах встречаются разными формами: с маркерами («по адресу:»), без маркеров («ул. Ленина, д. 5»), в таблицах. Просто дать NER-тэггеру natasha — он ловит также непеспециализированный текст (названия статей, ГОСТы, даты). Вместо этого: строгие правила для якоря (топоним + номер, или помещение + номер), обрезка по предложениям, барьеры от других сущностей (ИНН/реквизиты/люди).

**Результат:** Ложных адресов на негативах упало с 634 до 1. Цена — чуть меньше recall на адверсариальных мутациях, но это ожидаемо.

### 4. Восстановление из токенов (этап E)

**Идея:** Просто подставить первый найденный вариант значения обратно неправильно (в договорах люди склоняются, организации в разных форматах). Делается:
- Сохраняется каноническая форма каждого значения (всегда в именительном падеже для людей, стандартный формат для ИНН).
- При восстановлении подставляется каноническая форма, а не первое сохранённое вхождение.
- Для совместимости с пользовательскими правками: сохраняются все найденные формы каждого значения.

**Отличие:** Примитивный подход теряет актуальность в контексте договора (восстановленный паспорт в именительном падеже, когда оригинал был в творительном).

### 5. Механизм шифрования сессий (Fernet)

**Идея:** Каждая анонимизированная сессия — это отдельный файл со своей парой (токены, исходные значения), зашифрованный симметричным ключом Fernet (из пакета `cryptography`).

**Отличие:** Не требует центрального сервера, работает полностью локально. Ключ хранится один раз в `key.bin`, все сессии используют один ключ (компромисс для простоты).

**Применение:** Защита от случайного доступа к файлам `.enc` на общем компьютере.

### 6. Обнаружение непрочитанных зон в .docx

**Идея:** Перед обработкой сканировать структуру документа и обнаружить части, которые система не умеет читать (колонтитулы, сноски, текстовые поля). Если найдены — отказаться с понятным сообщением (fail-closed) или предупредить (режим lossy).

**Отличие:** Много систем молча пропускают эти части, пользователь даже не знает, что часть текста потеряна. SHIFRATOR делает это видимым.

### 7. Нормализация текста перед детекцией (этап 2)

**Идея:** Текст договора содержит невидимые символы (NBSP, мягкие переносы, мягкие соединители, завуалированные омоглифы кириллицы/латиницы). Эти символы ломают простые regex-паттерны. Перед детекцией текст нормализуется, а координаты спанов сохраняют отсчёт на исходный текст.

**Отличие:** Детекторы работают на чистом тексте, но восстановление подставляет исходные значения без потери форматирования.

## РАЗДЕЛ 4. ДАННЫЕ, НА КОТОРЫХ ПРОВЕРЯЕТСЯ ПРОГРАММА

### Корпус тестирования

Основной набор — `tests/corpus/`, содержит:
- **324 документа:** 162 файла `.txt` + 162 файла `.docx` (одинаковое содержимое в обоих форматах для каждого номера).
- **Происхождение:** Полностью синтетические. ФИО, названия организаций, адреса, номера реквизитов — сгенерированы программно, совпадение с реальными людьми/организациями случайно.
- **Разметка (gold):** Ручная аннотация 13 типов сущностей, негативы, серые зоны. Каждой сущности указана категория: canonical (базовая форма), ugly (реальная форма из практики), adversarial (специально сконструирована для тестирования граничных случаев).
- **Контрольные суммы:** ИНН, ОГРН, расчётные счета содержат валидные контрольные суммы, вычисленные по настоящим алгоритмам. Где невалидность внесена умышленно (для проверки обработки ошибочных ПДн), отмечено в разметке.

### Вторичный корпус (Corpus V2)

`tests/corpus_v2/` — меньший набор (138 документов), используется для проверки специальных типов сущностей и вариативности форм.

### Синтетичность как преимущество и ограничение

**Преимущество:** Контролируемое тестирование. Ясно, какие данные есть и какие пропущены.

**Ограничение:** Синтетические договоры могут не отражать весь спектр реальной вариативности (опечатки, странные сокращения, нестандартные форматы, которые встречаются в боевых документах).

## РАЗДЕЛ 5. КАЧЕСТВО И ЕГО ГРАНИЦЫ

### Текущие измеренные показатели (на корпусе из 324 документов, этап 2b)

| Метрика | Значение | Что это значит |
|---|---|---|
| **Recall** (полнота) | 77.1% | Из 100 ПДн в документе система находит примерно 77. Потеря 23% — это данные, которые остаются открытыми. |
| **Leak_v2** (частичная утечка) | 23.1% | Среди найденных данных примерно 23% остаются видимыми в результате (например, одно слово из адреса, омоглифом скрытое, или часть номера счёта). Это не полная утечка, но риск. |
| **FP on negatives** (ложные срабатывания) | 1975 | На негативных текстах (не являющихся ПДн) система выдала 1975 ложных алармов. Цена: пользователь видит лишние токены, но данные не утекают. |
| **Masking Correctness A** | 100.0% | Round-trip: обезличенный текст + восстановление = исходный текст. 100% — восстановление работает идеально. |
| **Masking Correctness B** | 79.59% | Границы маскируемых спанов совпадают с эталоном в 80% случаев. Остальные 20% — пропуски или расширения (например, маскируется не только ФИО, но и следующее слово). |

### Известные ограничения

| Что НЕ работает | Причина | Риск |
|---|---|---|
| **Непрочитанные зоны .docx** (колонтитулы, сноски, надписи, вложенные таблицы) | Стек natasha не предоставляет API для их чтения. | Высокий: текст этих зон остаётся открытым. По умолчанию система отказывается обрабатывать такие документы. |
| **PASSPORT спан-контракт сломан** | Паттерн паспорта захватывает служебные слова. | Средний: паспорт ловится, но границы неточны. |
| **ADDRESS на adverb жадно ловит** | yargy-тэггер на праве захватывает прозаические номера как индексы. | Средний: больше ложных срабатываний, но утечка низкая. |
| **Регистровые вариации ФИО** | Natasha опирается на регистр как признак имени собственного. Строчные ФИО без других маркеров не ловятся. | Средний: ФИО в нижнем регистре пропускаются. |
| **Документы объёмом >2500 сегментов** | Недетерминизм NER на очень больших текстах (редко встречается, но было обнаружено). | Низкий: происходит редко, но результат может быть нестабилен. |
| **Невидимые омоглифы** | Кириллица и латиница выглядят одинаково в некоторых шрифтах (А/A, С/C). После нормализации могут остаться видимыми. | Низкий: требует специальных условий. |

### Числовые границы
- Recall гарантирует нахождение базовых форм ПДн (canonical категория).
- На ugly-формах recall ниже, на adversarial — еще ниже (это ожидаемо).
- Для ИНН/ОГРН: валидность контрольной суммы — сигнал, не шлагбаум (опечатка в реквизите всё равно ПДн, отбраковывать опасно).

### Для чего используются эти метрики в договорах
- **Recall 77%** означает: если в договоре 100 ПДн, примерно 23 не будут найдены. Пользователь должен проверить текст глазами и отметить пропущенное вручную.
- **Leak 23%** — частичная утечка (одно слово из адреса, скрытое омоглифом) — требует внимания пользователя при проверке.
- **FP 1975** — ложные токены в тексте (например, номер пункта контракта считался за PHONE) — видны в интерфейсе, пользователь может удалить.
- **Masking A 100%** — гарантия: если вернуть восстановленный текст, он совпадёт с оригиналом побайтно.

## РАЗДЕЛ 7. РАБОТА С ПЕРСОНАЛЬНЫМИ ДАННЫМИ

### Механизмы защиты ПДн
1. **Полная локальность:** Никакие данные не отправляются в интернет. Программа работает на компьютере пользователя, сервер (если используется веб-интерфейс) слушает только `127.0.0.1`.
2. **Шифрование в хранилище:** Исходные значения ПДн хранятся в зашифрованном виде (Fernet, симметричное шифрование). Файл `.enc` без ключа не расшифровывается.
3. **TTL сессий:** Сессии автоматически удаляются через 24 часа. Старый ключ больше не восстанавливает данные.
4. **Отчёты без содержимого:** Любые отчёты, которые интерфейс отдаёт пользователю (аналитика, статистика), не содержат исходные значения ПДн, только статистические коды и типы.

### Где ПДн хранится на диске
| Файл | Содержимое | Защита | Статус |
|---|---|---|---|
| `~/.shifrator/sessions/key.bin` | Ключ шифрования | Доступен файловой системе OS | ⚠️ Критичен |
| `~/.shifrator/sessions/{sid}.enc` | Исходные значения | Зашифрован Fernet | ✓ Защищён |
| `~/.shifrator/sessions/{sid}.txt` | Обезличенный текст | Открытый текст | ✓ Безопасен (не содержит ПДн) |
| `~/.shifrator/sessions/{sid}.doc.json` | Метаданные найденных сущностей | Открытый JSON | ⚠️ Содержит токены и ссылки |
| `~/.shifrator/sessions/{sid}.unread.json` | **Текст непрочитанных зон** | **Открытый текст** | 🔴 **Содержит ПДн** |

### Критические замечания
1. **`{sid}.unread.json` содержит открытый текст ПДн** — если пользователь согласился на режим `--allow-lossy`. Этот файл остаётся на диске, не шифруется. Пользователь должен быть об этом предупреждён.
2. **`key.bin` — единая точка отказа** — если ключ удалён или повреждён, все старые сессии становятся невосстановимыми. Нет резервной копии ключа в коде.
3. **TTL 24 часа** — условное, не абсолютное. Пока компьютер включён и процесс работает, сессия не удаляется. Удаление проверяется только при доступе к папке (`purge_expired`).

### Гарантии и ограничения
✓ **Гарантируется:**
- Исходные ПДн не передаются наружу в интернет.
- Анонимизированный текст (с токенами) — единственное, что уходит в LLM.
- Восстановленные данные видны только локально при явном запросе.

⚠️ **Не гарантируется:**
- Защита от локального доступа (если кто-то сидит за компьютером, может прочитать файлы `~/.shifrator/sessions/`).
- Стирание следов в памяти (если компьютер скомпрометирован, часть ПДн может быть в оперативной памяти).
- Восстановление после потери ключа (если `key.bin` удалён, сессии невосстановимы).
