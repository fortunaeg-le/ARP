## 2. Ускорение прогона (этап SPEED)

Две независимые правки, обе НЕ трогают решений детекции — проверено
побитным совпадением чисел на срезе (33 док.) и на полном корпусе:

1. **Кеш разбора `entity_types.yaml`.** Файл парсился заново 330 раз за
   прогон среза (10 мест на документ, 9,3 % времени — замер C+). Семь мест
   разбора переведены на `src/config_cache.py::load_yaml_cached(path)` — кеш
   по (путь, `mtime`), правка конфига на диске подхватывается следующим
   вызовом. Проверено счётчиком: 330 обращений к кешу → 1 реальный
   `yaml.safe_load`.
2. **Параллельный прогон по документам.** `run_measurement.run_all` получил
   параметр `workers`: `None` (умолчание) — разумное значение от числа ядер,
   урезанное доступной памятью (`_default_workers()`, Windows
   `GlobalMemoryStatusEx`, без новых зависимостей); `1` — прежний
   однопоточный `for` без `multiprocessing` вообще. Результат собирается
   `pool.imap` (не `unordered`) — порядок строго по `gold`, как раньше.
   Память: воркер с моделями `natasha` держит ~296 МБ сразу после импорта,
   ~409 МБ после 33 документов (замер `tasklist`, без `psutil`); бюджет
   700 МБ/процесс. `gate.py`/`subsample.py` получили флаг `--workers N`.

Разбор по числам, проверка эквивалентности (workers=1 vs авто, побитно) и
профилирование — [`JOURNAL.md`](JOURNAL.md), запись SPEED.
