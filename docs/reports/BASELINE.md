## 8. Разведение эффектов (0a починка креша · 0b новая метрика)

Два эффекта тянут утечку в РАЗНЫЕ стороны, их нельзя смешивать в одну цифру.
Числа BIK-**включены** для сопоставимости со старым отчётом (тогда BIK не выделяли).

| | старый отчёт<br>293 док · leak_v1 | этот замер<br>324 док · leak_v1 | этот замер<br>324 док · leak_v2 (≥6 / ≥8) |
|---|---:|---:|---:|
| документов обработано | 293 (31 креш) | 324 | 324 |
| recall_loose | 55.9% | 56.1% | 56.1% |
| **leak** | **50.0%** (по 293)<br>**55.3%** (по 324, креши=утечка) | **49.3%** | **45.8% / 40.7%** |

**Переход 1 — вклад починки креша (0a):** `55.3% → 49.3%` = **−6.0 пп**. 31 документ
(≈1070 сущностей) раньше крешил на encrypt и не защищался никак (100% утечка); теперь
все 324 обрабатываются, и защита ранее-крешивших документов тянет средневзвешенную
утечку вниз. Сравнивать надо именно с 55.3% (честная all-324 база), а не с 50.0%
(по выжившим 293) — иначе эффект прячется.

**Переход 2 — вклад новой метрики (0b):** `leak_v1 49.3% → leak_v2 45.8%` (мягкий).
**Знак нетто отрицательный, и это НЕ противоречит этапу 0b — это его уточнение.**
Метрика v2 работает в две стороны:

| направление | сущностей (BIK-excl) | из чего |
|---|---:|---|
| **v2 ЛОВИТ, v1 пропускал** (частичные утечки) | **+333** | PER +167, ACCOUNT +85, EMAIL +32, ORG +24, OGRN +11, INN +6, ADDRESS +5, PHONE +2 |
| **v2 СНИМАЕТ, v1 засчитывал** (ложные/неприменимые) | **−752** | ADDRESS одиночный компонент −447, BIRTHDATE −228 (v2 неприменима), PASSPORT −26, PER −21, PHONE −26, INN/KPP −4 |
| **нетто** | **−419** | |

«**+354**» из этапа 0b — это была величина ПЕРВОГО столбца (дополнения, которые v2
ловит сверх v1); мой прогон воспроизводит её как **+333** (расхождение — иной
доковой набор на момент 0b). Это НЕ нетто-изменение утечки. Нетто отрицательно,
потому что v2 одновременно и корректно ВЫЧИТАЕТ 752 сущности: 447 адресов-одиночек
(§5 ниже) и 228 дат рождения, к которым оконная метрика попросту неприменима.
**Вывод: v1 и v2 — не «хуже/лучше», а разные линзы. Тренд по числовым/буквенным
типам ведём по v2 (честнее ловит частичное), но помним, что для ADDRESS v2 строже,
а BIRTHDATE v2 не покрывает вовсе (утечка там 100% по v1).**

## 9. Диагностика ADDRESS (v1 засчитал, v2 — нет)

Единственное место, где v2 СНИЖАЕТ цифру относительно v1: одиночный выживший
компонент адреса. v1 считает адрес утёкшим, если выжил ЛЮБОЙ компонент (дом «25»,
кусок улицы); v2 требует **почтовый индекс (6 цифр)** ИЛИ **связку «улица+дом»** —
одинокий номер дома или город сам по себе деанонимизации не даёт.

| ADDRESS (всего 1308) | шт. |
|---|---:|
| v1 = leak И v2 = leak (реальная утечка адреса) | 544 |
| **v1 = leak И v2 = none (одиночный компонент)** | **447** |
| v1 = none И v2 = leak (v2 поймала, v1 нет) | 5 |

**447 адресов** переклассифицированы: v1 считал утечкой, v2 — нет. 10 примеров того,
